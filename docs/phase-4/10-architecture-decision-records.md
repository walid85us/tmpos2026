# 10 — Architecture Decision Records

Concise ADRs for the major structural choices in this package. Each: **Context → Decision → Consequences**. Status is **Proposed** (M1 is planning; decisions are ratified as their milestone executes).

---

## ADR-01 — Server-authoritative authorization; demote client role to render-only
**Context:** Live authorization is 100% client-side — `role` comes from a client-read Firestore field, entitlements/permissions from client `sessionStorage`; there is no server re-check ([01](./01-current-state-inventory-and-gap-matrix.md) GAP-01/12).
**Decision:** The server derives the effective authorization context from canonical Postgres on every request (deny-by-default). The client role/entitlement/status becomes render-only and is never an authorization input.
**Consequences:** Requires the deployed API (M3) + canonical IAM (M5). Closes G-CLIENTAUTH/G-IAM. The SPA can still be statically hosted but must call an authorized API rather than assume authority.

## ADR-02 — Separate Backend Control Plane login & session boundary
**Context:** No server session exists; the DEV Backend CP entry gate is a bare boolean ([01](./01-current-state-inventory-and-gap-matrix.md) GAP-02). The Backend CP governs the whole platform.
**Decision:** A distinct admin login exchange (Firebase ID token verified server-side once) issues a **separate** HttpOnly/Secure/SameSite admin session cookie with CSRF, MFA, and step-up; it never reuses the tenant session ([03](./03-backend-control-plane-login-session-blueprint.md)).
**Consequences:** Two auth boundaries and two cookies. **Production topology (mandatory, not a preference):** the Backend CP runs only on a dedicated administration host that is distinct from every tenant host — a same-site subdomain qualifies and a separate registrable domain is stronger ([03 §2 #1, §2a](./03-backend-control-plane-login-session-blueprint.md), [09 M4](./09-roadmap-m0-m9.md)). A same-host or same-origin production deployment is not supported: the production composition root refuses host-sharing session origins, and the admin console refuses to run on any address other than a configured administration origin (`VITE_ADMIN_CONSOLE_ORIGINS`). **Local development only:** a Vite dev server serves the console on the development host under `/admin`; production builds compile that exception out. Closes G-CPLOGIN when its pass rule is met (M4).

## ADR-03 — Postgres canonical; Firebase for authentication only; Supabase dormant
**Context:** Firebase is the authoritative auth provider; Postgres holds identity/authz/audit; Supabase is dormant with an unwired `identity_link`.
**Decision:** Postgres is the canonical source of truth for identity, authorization, entitlements, audit, and (via M7) business data. Firebase is used for **authentication only**, verified at the server login exchange. **Supabase stays dormant; no cutover in Phase 4.**
**Consequences:** No provider migration risk in this phase. `identity_link` remains unwired until a separately-authorized future decision.

## ADR-04 — Unify the permission-level ordering into one catalog (SUPERSEDED — see ADR-19)
**Context:** Tenant code orders `manage < approve`; platform code orders `approve < manage` and says *"Do not unify them"* ([04](./04-canonical-iam-and-four-user-migration.md) §3, GAP-11).
**Decision:** Adopt one canonical ordering `none → view → create → edit → approve → manage → full` (approve below manage) in a single shared catalog; migrate the tenant comparator.
**Consequences:** Eliminates a correctness hazard where the same level names sort differently — but the flip is **not** grant-neutral: under the new order every tenant `manage`-holder now satisfies `approve` thresholds it previously did not (e.g. `manager` gains `refunds:approve` / `returns:approve_return`). Therefore the migration **requires** re-pinning affected `approve`-gated money actions to `≥ manage`/explicit grant, a before/after grant-diff report, explicit owner approval, deny-by-default on unknowns, dual-read shadow evaluation, and per-action regression tests ([04 §3](./04-canonical-iam-and-four-user-migration.md)). Delivered in M5 (phase i).
**Owner decision D2 (recorded M5-GAP11-P2):** of the two re-pins 04 §3 allows, the explicit per-role grant. Every documented approval-gated money action is allowed only by an explicit per-role `true`, never by a level alone; the grant is necessary, not sufficient; the initial values equal today's answers. It is carried in the non-authoritative candidate only — production is not re-pinned — and any cutover remains open ([09](./09-roadmap-m0-m9.md)).
**Owner decision D3 (recorded M5-GAP11-P3):** the owner rejected all thirteen changes the unified ordering still makes after D2 — twelve widenings and one narrowing — and each keeps today's answer through a closed table of thirteen ordering-compatibility pins, which are not money-action classifications and not a rule. With them the candidate answers exactly as the shipped authority on every tuple, and the owner approved the resulting zero-diff artifact conditionally: the approval holds only while the final diff is empty. It is carried in the candidate only; production is unchanged and the cutover remains a separate, unauthorized decision ([09](./09-roadmap-m0-m9.md)).
**Superseded (M5-GAP11-P5, [ADR-19](#adr-19--family-aware-permission-semantics-money-actions-as-explicit-editable-grants-decided)):** M5-GAP11-P4 showed that one ordering plus D2 and D3 cannot preserve owner-edited and custom tenant roles in the deployed client, so the global cutover was rejected. The store and platform families each keep their own ordering; money approval is an explicit editable grant. The D2 table is reclassified as the built-in money-grant defaults (same values); the thirteen D3 pins are retired from active evaluation; the P2 and P3 records and the evidence artifact (`docs/phase-4/evidence/gap11-ordering-flip-grant-diff.md`, frozen at 84fa74e9) are kept as history. No global ordering cutover occurs.

## ADR-05 — Move entitlements & permissions off `sessionStorage` into server storage
**Context:** Plan/feature entitlements and platform permissions are client `sessionStorage` and forgeable; the System Owner can reshape entitlements with no server write ([01](./01-current-state-inventory-and-gap-matrix.md) §C, GAP-12).
**Decision:** Materialize entitlements into `tenant_feature_entitlement` (source ∈ plan/default/manual) and move platform permission overrides to server-owned storage; the client keeps only a read-only projection.
**Consequences:** Closes G-ENTITLE. Delivered M5 (with M7f for the plan/feature catalog).

## ADR-06 — Durable append-only audit as the single audit source
**Context:** `auditEventWriter` is built but unwired; the owner "audit log" is forgeable `sessionStorage`; the system produces zero durable audit ([01](./01-current-state-inventory-and-gap-matrix.md) GAP-07).
**Decision:** Wire the append-only `audit_event` writer into every authorization/mutation path; the immutability trigger (rejects UPDATE/DELETE for all roles) is the integrity guarantee. The forgeable client "audit log" is replaced by reads over `audit_event`.
**Consequences:** Closes G-AUDIT. Until wired (M6) the platform has no compliance trail — a hard gate before authoritative authorization goes live. A command's audit row is written inside that command's own transaction (ADR-17).

## ADR-07 — Single provider egress boundary (SSRF elimination, secret encryption, webhook verification)
**Context:** `GET /api/shipping/label-proxy?url=` fetches arbitrary URLs; the Shipping API is unauthenticated and holds live keys in process memory; webhooks are unverified ([01](./01-current-state-inventory-and-gap-matrix.md) §E, GAP-03/04/06/14).
**Decision:** All external provider egress goes through one boundary with **host allowlists** (no request-controlled URL), **encrypted stored credentials**, and **webhook signature verification**; provider calls run via the outbox/workers.
**Consequences:** Closes G-SSRF/G-SECRETS/G-WEBHOOK/G-PROVIDER. Delivered M7e/M8 (design M3).

## ADR-08 — Deployable backend runtime, migration runner, scoped app role + RLS
**Context:** Production is a static SPA with no backend; migrations are applied manually; the DB connection is the owner role bypassing RLS ([01](./01-current-state-inventory-and-gap-matrix.md) GAP-16/17).
**Decision:** Stand up a deployed server runtime with environments (local/test/staging/prod), a migration runner, a secrets store, and **connection-role separation** — a scoped app role (RLS-bound) for tenant paths, a separate privileged role for migrations/admin, with tenant/store RLS policies.
**Consequences:** Closes G-MIGRATE/G-DBROLE and enables every server-authoritative gate. Delivered M3.

## ADR-09 — M7 vertical-slice migration order (Customers/Employees first, governance last)
**Context:** All business domains are in-memory mock; they have reference dependencies (sales→customers, repairs→inventory, shipping→orders, governance→everything).
**Decision:** Migrate in dependency order — **M7a** Customers/Employees first; **M7b** POS/Sales/Invoices/Payments; **M7c** Inventory/Supply Chain; **M7d** Repairs/Services/Warranty/Returns; **M7e** Shipping; **M7f** Billing/Plans/Entitlements; **M7g** Settings/Domains/Integrations; **M7h** Command Center/Support/Audit read-models **last** ([06](./06-module-migration-map-m7.md)). The owner-fixed labels put POS (M7b) before Inventory (M7c), yet POS decrements stock; this is resolved by **shipping M7b POS with authoritative stock-decrement deferred until M7c** rather than relabelling.
**Consequences:** Respects FK dependencies; each sub-slice is **independently releasable with its own rollback gate** and a data backfill/cutover + "no mock path remains" check ([06 §1](./06-module-migration-map-m7.md)); ships with its own tests, scoping, transactions, idempotency, and audit. Closes G-PERSIST incrementally.

## ADR-10 — Firestore emulator semantic evidence is a mandatory pre-deploy gate
**Context:** M0 shipped a **static** rules guard only (21/21); the emulator semantic suite is unexecuted because Java was unavailable (GAP-18, G-EMU).
**Decision:** Stand up a Java-enabled environment in M2; the emulator semantic suite becomes a **repeatable CI gate** that must pass before any Firestore-rules deployment or go-live. The static guard is retained as a fast pre-check.
**Consequences:** Closes G-EMU as a gate (not a one-off). No rules deploy without a green emulator run.

## ADR-11 — Integrated payment capability is in scope (DECIDED)
**Context:** This is a POS with `order`/`payment`/`refund`; the owner has decided the payment model ([01](./01-current-state-inventory-and-gap-matrix.md) GAP-26, gate G-PCI).
**Decision:** TM POS2026 supports **cash + external-terminal/manual-reference + integrated card-present via a PCI-certified semi-integrated terminal/provider + hosted/tokenized CNP**. Card data is collected only by provider-hosted/certified components; TM POS2026 stores only **opaque payment-method tokens** and **never** receives/stores/logs/exposes PAN/CVV/track/PIN/unencrypted CHD or processor credentials in browser storage. The payment contract ([05 §5](./05-canonical-data-ownership-and-api-db-contracts.md)) covers auth/capture/settlement/void/refund/dispute/reconciliation, verified webhooks, idempotency + duplicate-charge prevention, credential encryption/rotation, provider-outage behavior, and terminal/device→tenant/store scope. The specific provider is selected **in M7b** by documented criteria (not a hidden future milestone).
**Consequences:** G-PCI remains a production BLOCKER until provider selection + integration + evidence + PCI-category validation pass; but the architectural direction is DECIDED. **No SAQ category (SAQ A / P2PE / other) is claimed until the final integration architecture establishes eligibility** — confirmed with the provider/acquirer/QSA.

## ADR-13 — Privacy & DSAR foundation is in scope (DECIDED — implement, not exclude)
**Context:** A multi-tenant SaaS holding customer/employee PII needs a data-rights foundation; the owner has decided to implement it (gate G-PRIVACY).
**Decision:** Build a production privacy/DSAR foundation ([05 §6](./05-canonical-data-ownership-and-api-db-contracts.md)) — data inventory/classification, tenant-controller/platform-processor split, identity verification, tenant approval + platform escalation, cross-domain discovery, export/correction/deletion-anonymization (where legally permitted), retention/legal-hold/restriction/portability, provider propagation, immutable audit, deadline/status, failure/partial handling, backup limitations — distributed across **M1 (contracts) → M5 (authz) → M6 (audit/workflow/retention) → M7a–h (domain behavior) → M8 (ops) → M9 (evidence + legal sign-off)**, with **no new milestone**.
**Consequences:** G-PRIVACY remains a production gate until implementation + evidence + legal-owner sign-off pass. **No universal-compliance claim is made**; final policy and jurisdictional obligations require owner/legal review.

## ADR-14 — M7b→M7c inventory obligation (outbox) prevents silent divergence
**Context:** The owner-fixed order runs POS (M7b) before Inventory (M7c), yet POS decrements stock; a "deferred decrement" must not let a sale silently diverge from inventory (gate G-INVENTORY-CONSISTENCY).
**Decision:** At sale completion, **M7b writes a durable, transactional, idempotent `inventory_obligation` (outbox)** rather than claiming a decrement; inventory-tracked production sale completion is **feature-disabled / non-inventory mode** until **M7c consumes the obligation and reconciliation passes**, at which point the block lifts. Invariant: **no production sale may claim inventory was decremented unless a durable, transactional, idempotent inventory mutation OR obligation exists and reconciliation passes.**
**Consequences:** Resolves the inventory→POS dependency without reordering the owner-fixed M7b/M7c labels and without silent divergence; adds a blocking M7b→M7c dependency gate. The `inventory_obligation` is an ADR-17 outbox event.

## ADR-15 — G-HIST is a historical evidence limitation with an M8 investigation + M9 acceptance path
**Context:** M0 could not disprove pre-fix Firestore exploitation; leaving it an undefined blocker risks an unprovable gate.
**Decision:** Reframe G-HIST as a **historical evidence limitation, not a waivable active vulnerability**. **M8** performs a bounded **read-only** attempt to retrieve existing authorized historical evidence **without enabling new retroactive collection**; if present, classify it. **M9** — if no reconstructing evidence exists — records an explicit **owner risk acknowledgement** (exposure window existed; current state showed no privileged mismatch; Firestore `auditEvents` empty; historical non-exploitation unprovable; fail-closed rules active; compensating controls + monitoring established).
**Consequences:** Gives an unprovable historical question a defined, bounded, honest disposition instead of an open-ended blocker; the current fail-closed posture and compensating controls carry the risk forward transparently.

## ADR-12 — Two server sessions in M4; minimal audit before M5; M5 runs in internal phases
**Context:** The tenant app also needs server-side identity/session (not only the Backend CP), M5 performs audited provisioning while durable audit was scheduled for M6, and M5 bundles the entire IAM system as the hard dependency for all of M7.
**Decision:** M4 delivers **two separate server session boundaries** (tenant + admin) sharing one canonical catalog/status model ([03 §1a](./03-backend-control-plane-login-session-blueprint.md)); a **minimal durable audit writer** lands in M3/M4 so M5's provisioning/grant changes are audited before the full audit machinery in M6; and M5 executes in **three ordered internal phases: (i) authz service + ordering unification → (ii) entitlement/permission storage move → (iii) status/parity + four-user migration + isolation** — execution phasing within M5, not new milestones. *(Update, M5-GAP11-P5: phase (i)'s ordering unification is superseded by family-aware permission semantics, [ADR-19](#adr-19--family-aware-permission-semantics-money-actions-as-explicit-editable-grants-decided).)*
**Consequences:** Removes the "Firebase-auth-only re-trusts the client" hole, the M5↔M6 audit-ordering contradiction, and the single-giant-M5 blast radius, without adding milestones outside M0–M9.

## ADR-16 — Store-owned payment gateway connections with a platform-governed connector catalog (DECIDED)
**Context:** The existing Shipping provider pattern configures provider credentials in an **unauthenticated, global, in-memory credential store keyed by provider id only** (no tenant/store scope) — a pattern that must not be repeated for payments. The owner has directed that payment-gateway connections are configured at the **store** level, not by the System Owner.
**Decision:** Payment-gateway connections are **owned and configured by the store** (Store Owner, or another store user with an explicit canonical `manage_payment_gateway_connections` permission, [04 §2.1](./04-canonical-iam-and-four-user-migration.md)), under **Store Settings → Payments** — never supplied, retrieved, or normally viewed by the System Owner. The **System Owner Backend CP governs only the connector catalog + security policy** (available providers, env/region availability, minimum versions, bounded health, global incident disablement, plan eligibility, audited break-glass) — [03 §8](./03-backend-control-plane-login-session-blueprint.md). Every connection is scoped to `(tenant_id, store_id, provider_key, environment)`; OAuth/provider-hosted onboarding is preferred (no browser secret); any unavoidable secret is envelope-encrypted server-side with only a reference stored ([05 §5.1](./05-canonical-data-ownership-and-api-db-contracts.md)). The initial connector catalog targets **Stripe / Square / Adyen** (M7b-verified for launch market/hardware/PCI). Two model invariants are pinned ([05 §5.1](./05-canonical-data-ownership-and-api-db-contracts.md)): **OAuth callback binding** (`state`/PKCE/exact-redirect-URI-allowlist/account→initiating-session) and **connector-catalog endpoint integrity** (endpoints/OAuth-URLs/webhook-hosts are code-shipped/reviewed/egress-allowlisted, not admin-free-form; catalog mutation is a step-up + reason + durable-audit action) — closing connection-CSRF/auth-code-injection and the compromised-catalog route back to platform-scale credential theft.
**Consequences:** Reuses the Shipping *interaction model* (UX pattern only — credential routes, webhook handling, audit, and permission checks use the M6 standard, **not** the Shipping code path; the Shipping M7e remediation is parallel cleanup, not a prerequisite for payment security) (Settings tab, active-provider summary, provider cards, expandable connection panel, test/prod choice, **server-proxied Test Connection**) while explicitly rejecting its unsafe traits (unauth routes, global RAM secret store, no store scope, SSRF, env-gated webhook-verification bypass, generic role gating, no audit). Shipping is upgraded to the same credential/security standard in **M7e** — no new milestone. G-PCI's acceptance criteria now include store-owned config + canonical permission + credential/multi-store isolation.

## ADR-17 — PostgreSQL is the authoritative transaction boundary; transactional outbox with at-least-once delivery (DECIDED)
**Context:** A retried write must not double-apply (G-IDEMPOT), a mutation must not commit without its audit record (G-AUDIT, ADR-06), and provider effects run through the outbox (ADR-07, ADR-14). M6-IDEMPOT-P2's `perform` path leaves a crash window, because its business write is outside the idempotency store's transaction ([08](./08-production-gate-and-risk-register.md) G-IDEMPOT). [02 §8](./02-target-production-architecture.md) had also named a shared cache (e.g. Redis) for idempotency keys.
**Decision (owner, M6-OUTBOX-P3):** PostgreSQL is the future authoritative transaction boundary. One transaction commits the authorized business mutation, the lease-checked idempotency completion, the durable audit record and zero or more outbox events — or none of them (`server/runtime/commandTransaction.ts`). The idempotency record, the command's audit row and the outbox are PostgreSQL state, served by one adapter over one database. Redis or another distributed cache may later serve rate limiting; it is never the sole authority for transaction-coupled idempotency or outbox state. Events are created atomically and delivered at least once until dead-lettered (`server/runtime/outbox.ts`): a lost acknowledgement redelivers the same immutable envelope under the same event ID, so every consumer deduplicates by `eventId`. Neither exactly-once processing or delivery nor global ordering is claimed: each envelope carries its aggregate's version, and `occurredAt` (the transaction's start time) is never a cursor. Event contracts come from a closed registry that stays append-only while any event of a version can still be claimed; by release policy, which no code enforces across releases, a type keeps one aggregate type in every release, the record limits only tighten, and a new type@version reaches every worker before any command emits it. A conflict is a 409 `write_conflict`. **Amended (M5-GIAM-D1-P2-R1):** it is recorded for replay — it and an update's `invalid_state` are the two deterministic post-authorization rejections, each sealed as the idempotency record's completion inside the transaction that fenced the lease, revalidated the authority and determined it, and each writing no mutation, no audit record and no event. A refused intent is therefore answered once and answered the same way for as long as its record is retained, and for that whole window the same key cannot mutate; past the retention the key is no longer the same key in contract terms. A sealing failure rolls that transaction back and leaves the earlier lease-expiry behaviour untouched.
**Consequences:** The crash window is closed by contract for `command` routes; `perform` keeps it and is never approved for a production route. Nothing is live, and no hosted provider is selected. M6-PG-P4 delivers the PostgreSQL adapter (`server/persistence/postgresTransactionalStore.ts`: one transaction kernel, three separate ports) and its schema (migration 006: `idempotency_record`, `outbox_event` and the store clock `m6_store_clock()`, RLS-enabled and granted to `tmpos_app` alone; the audit row goes to the existing `audit_event` through the existing writer on the same transaction). M6-PG-P5 moves those objects, before 006 was ever applied to a managed database, into the internal schema `tmpos_internal` (owned by the migration principal, USAGE to `tmpos_app` alone), adds a trigger that enforces the outbox delivery transitions for every writer, caps claims at the delivery policy's 20 attempts in the adapter, contains the pinned driver's connection-loss defects in the store's own code except in the window DA-19 records — nothing more is handed to a lost connection once the store has seen the loss, and `createSupervisedPgClient` replaces a pool after a failure its transaction body did not raise, with no retry — and drops server notices in both principals' client options. M6-PG-P6, still before any managed apply, takes every table and clock privilege away from `tmpos_app`: the runtime role reaches the store only through nine fixed `SECURITY DEFINER` lifecycle routines owned by the migration principal, which decide on the store's clock and change a record or an event only under the lease or claim token presented (DA-18). It also replaces the driver's `begin()` with the application's own transaction kernel (`createSupervisedPgClient`): pools of one connection, one guarded dispatcher for BEGIN, the settings, the body, COMMIT and ROLLBACK, a gate the driver's close callback shuts synchronously, no savepoint or transaction control reachable from a mutator, and no retry (DA-19, DA-20). Since M6-PG-P7 the kernel also resets each connection — `DISCARD ALL`, with the driver's `prepare` forced off — before another transaction can use it, and retires any connection it cannot reset (DA-21). An adapter is approved only after it passes `assertIdempotencyStoreContract`, `assertCommandTransactionContract` and `assertOutboxDeliveryContract` over two instances against real PostgreSQL, fault injection and interleaved statements included. The M6-PG-P4 adapter passes them over two independent instances against disposable PostgreSQL, with fault injection, lock waits, cancellation, a lost COMMIT acknowledgement, and commands and claims interleaved across both instances (`tests/db/transactionalStore.integration.test.mjs`). A kind's business mutation is a source-defined mutator the adapter is constructed with; only values cross the port. Since M6-PG-P7-R1 the adapter is composition-ready: the transaction root (`server/composition/productionTransactions.ts`) composes it through `createSupervisedPgClient` (DA-15), only for a route that requires idempotency and only over an `APP_DATABASE_URL` classified before any contact as a direct or session-mode endpoint — a transaction pooler is refused, since the kernel resets each connection before reuse (DA-21). No production route requires it, so it is composed nowhere today, and migration 006 is applied to no managed database: binding it needs the runtime LOGIN role and its endpoint (G-DBROLE), the managed apply of 005 and 006 (G-MIGRATE — while 006 is pending the managed 005 apply refuses at its exact-[005] plan gate, and whether to plan to a target version or authorize both together is undecided) and a real business route (G-IDEMPOT). No worker or publisher exists. Before M5 a command's audit record and events carry no actor (null, like tenant and store). Retention and purge of delivered, dead and expired rows, dead-letter observability and an audited redrive are later work (M8).
**Update (M6-RATE-P2, ADR-26):** rate limiting is served by PostgreSQL first (migration 014). A cache remains a possible later replacement for the rate-limit store only, never for transaction-coupled idempotency or outbox state.

## ADR-18 — trusted identity is resolved by owner-privileged routines, and re-read inside the committing transaction (DECIDED)
**Context:** Migration 005 gives the runtime role `tmpos_app` no privilege on `platform_identity`, `app_user` or `identity_link`, so it cannot turn a provider-verified reference into the app-owned `internal_user_id`. Every existing reader does it through the OWNER connection instead (`authorizationRepository.ts` `getIdentityByProviderUid` / `getAppUser`), which bypasses Row-Level Security — the open identity-read half of [08](./08-production-gate-and-risk-register.md) G-DBROLE. Meanwhile a command is planned from a context resolved earlier, on another connection, before its idempotency lease was granted; G-CPLOGIN requires a sensitive handler to re-verify the principal's security version **inside its own write transaction**, and 002 requires the audit actor to be the app-owned id, never the raw provider uid. M6-PG-P8 stopped for exactly these reasons: no roadmap-defined business route could obtain an actor, a scope, a permission or that revalidation.
**Decision (M5-ID-P1, M5 phase (i)):** neither the runtime role nor a second credential gains table access. Migration 007 adds **three routines and no table, column or role**, in its own schema `tmpos_identity` (corrected in M5-GAP11-P1-R1: an earlier revision said 006's `tmpos_internal`). `m5_resolve_principal(provider, uid)` takes only a reference the authentication boundary has ALREADY verified and answers exactly one bounded row — the actor, its durable status, a read-only limitation, a security version and its **usable** membership grants (a grant appears only when it is active and its scope is whole). `m5_revalidate_principal_context(actor, version, scope, tenant, store)` re-reads that authority and answers the role still granted there. Both are `SECURITY DEFINER`, pinned to `pg_catalog, pg_temp`, revoked from PUBLIC and granted EXECUTE to `tmpos_app` alone; the private version helper is granted to nobody, so the runtime cannot compute a version for an actor it has not resolved. **Every refusal is one identical value**, so no caller learns whether a provider UID, user, tenant or store exists, and no return column, message or hint carries a provider reference. **The security version** is a digest of the account status and identity-link lifecycle — deliberately NOT of membership grants, so withdrawing one grant invalidates a command without revoking every session that person holds elsewhere. **The permission is never decided in SQL:** the routine returns a role id and the catalog in trusted source decides, so there is one catalog rather than two. **Ordering is binding:** the store calls the revalidator **after** the idempotency fence and **before** any business state, so a stale lease still refuses first and learns nothing about the identity, and a revoked actor never reaches a mutator. Every row the decision rests on is read `FOR SHARE` in one fixed order (app_user, tenant, store, user_membership), which makes a racing revocation deterministic in both directions under READ COMMITTED.
**Consequences:** The path a production route will take never needs the owner connection: `tmpos_app` still holds no privilege on any identity relation, and a containment test refuses a direct read of one from `server/runtime`, `server/persistence` or `server/composition`. **No existing caller was converted** — `authorizationRepository.ts` still reads through the owner connection, is untouched here, is reachable from no deployable entry, and replacing it is later M5 work. The audit writer's fallback to the unclassified `getRuntimeDb()` client is removed — an audit record now rides its own write's executor or is not written. A command that carries a trusted context names the app-owned actor in its AUDIT row; without one it stays null, exactly as before. An outbox event names no actor, tenant or store in either case — migration 006 types those columns as keyed digests, not identifiers, and this stage keys none. A read-only context (a `read_only` or `overdue` account, tenant or store) may not commit a command at all. A request's tenant or store id is a **selector only**: it can narrow to a grant the database already recorded, never create one, and an ambiguous or absent selection is refused because no authoritative document defines a default. **Tenant- and store-scope permissions are undecidable** until GAP-11's ordering unification and its six mandatory safeguards land ([04 §3](./04-canonical-iam-and-four-user-migration.md)) — re-pinning the approve-gated money actions and owner-approving the grant diff are not this stage's to decide — so composition refuses a deployed route declaring one rather than guessing; only platform scope, whose ordering 04 §3 already calls canonical, is evaluated. Nothing is composed into a deployable entry, **no business route exists and none is live**, and 007 is applied to disposable PostgreSQL only (`tests/db/principalResolution.integration.test.mjs`), never to a managed database. Still open: the runtime LOGIN role and endpoint (G-DBROLE), the managed apply (G-MIGRATE), a first business route and its product rules (G-IDEMPOT), a production admission adapter, step-up, and GAP-11. *(Update, M5-GAP11-P5: GAP-11 is closed at repository level by [ADR-19](#adr-19--family-aware-permission-semantics-money-actions-as-explicit-editable-grants-decided); tenant and store scope stay undecidable in the route catalogue until owner decision D1 defines a specific route and its authoritative product rules.)*

## ADR-19 — Family-aware permission semantics; money actions as explicit editable grants (DECIDED)
**Context:** ADR-04 chose one global ordering to close GAP-11 (tenant/store `manage < approve`, platform `approve < manage`). The flip is not grant-neutral, so owner decisions D2 (explicit per-role money-action grants) and D3 (thirteen compatibility pins keeping every changed answer) made the candidate equal the shipped authority — but only where each role holds its catalog default. M5-GAP11-P4 showed the deployed client also decides over owner-edited levels and custom roles, where no pin applies: an edited `inventory: approve` would stop satisfying `inventory: manage`, and a manager edited to `returns: approve` would lose `approve_return` and `complete_return_disposition`. A single ordering cannot preserve those answers.
**Decision (M5-GAP11-P5):** replace the global ordering with **family-aware permission semantics**. The store family orders `none, view, create, edit, manage, approve, full`; the platform family orders `none, view, create, edit, approve, manage, full`. Both live once in `src/authorization/permissionFamilies.ts`; every comparison names its family (`meetsFamilyLevel`, `meetsPermissionRequirement`, `permissionLevelRank`; the public `meetsPermissionLevel` and `platformPermissionMeets` delegate with their family fixed); an unknown or malformed family or level denies and a comparison across families is refused. The family is never inferred from a role, a default level, or an edited or custom state. Money actions (`approve_refunds`, `approve_return`, `approve_billing_actions`) are explicit editable boolean grants (`src/authorization/moneyCapabilities.ts`): built-in defaults allow refund and return approval for `manager` and `store_owner` and billing approval for `billing_admin` and `system_owner`; the owner's `true` grants and `false` revokes; custom roles start without one; a missing, malformed or unknown grant denies; no level or ordering grants one; plan, entitlement, parent-module minimum, read-only, identity, tenant, store and scope gates still deny. The two refund-approval forms converge on one capability (Refunds at View or above plus the grant); the platform System Owner, holding no store role, is denied store refund and return approval. The DEV-only path stays unrouted and follows the same contract; the M5 route catalogue keeps refusing tenant and store scope until D1.
**Consequences:** GAP-11 and G-IAMUNIFY close at repository level (M5-GAP11-P5). Every non-money store answer is unchanged in every production-reachable role state (259 built-in-default, 1,517 single-area-edit, 2,598 sub-permission-toggle and 504 custom-role decisions, regenerated from code). Six money answers change, each an owner decision: the converged refund check now allows a manager edited below Refunds Approve who keeps the grant, and custom roles no longer get refund or return approval from a level. The D2 table becomes the built-in money-grant defaults (same values); the D3 pins are retired from active evaluation; the P2/P3 records, the shadow comparator and the evidence artifact (frozen at 84fa74e9) stay as history. Still open: G-IAM (server-side enforcement), durable role-editor persistence (store edits are in memory, platform edits in `sessionStorage`), AZ-1 to AZ-8, and owner decisions D1 (the first platform-scoped command and its product rules) and D4 (the managed migration target). Supersedes ADR-04.
**Update (M5-GAP11-P5-R1):** a money capability is consumed where the money action runs, not only where it is offered. The POS decides a refund again from current state when it executes it (the operator's own authority is Process Refunds plus the explicit `approve_refunds` grant). A supervisor approval covers one refund request and is bound to the user, the operator and that operator's role, the tenant and plan, and the supervisor role configuration it was decided on, so a change to any of them voids it, even one later changed back. Read-only mode (the write block, or a `read_only` or `suspended` tenant) denies the approval and the refund. Return approval and rejection re-decide `approve_return` in the handler. Every existing billing refund and credit entry point (billing page: transaction refund, issue and apply credit, the refund form; tenant page: "Revoke + Refund", apply and void credit from the credit detail and the credits list) is offered only while `approve_billing_actions` is held and decides it again before acting; the System Owner acts only through its locked grant. A test-owned inventory (`src/authorization/moneyActionInventory.test.ts`) lists each entry point with its capability, family, parent minimum and kind, checks on the syntax tree that each handler's guard precedes its state change and that nothing ahead of the guard changes state, and fails when a POS refund record, a billing credit-note change or a tenant credit apply or void is not a declared entry's sink. All of this is client-side only: no server command route exists, so G-IAM stays open, and durable role and approval storage stay open.

## ADR-20 — The first server-authorized business command: a tenant's display name (DECIDED — owner decision D1)

**Context:** Every M5/M6 foundation existed — the session boundaries, the canonical catalogue, trusted principal resolution and transaction revalidation (ADR-18), the durable idempotency store and command transaction (ADR-17) — but no business route used them, so G-IAM had no server-enforced command and M6-PG-P8 had stopped for want of a route with product rules. The owner's D1 names the route and its rules (M5-GIAM-D1-P1): update a tenant's display name, platform-scoped, requiring the canonical platform Tenants domain at Edit or above; the target tenant is the resource, never authorization evidence; no role-name shortcut, System Owner only through its canonical decision, and a custom platform role with sufficient authority may succeed; only `displayName` changes; the name is trimmed to 1–120 Unicode scalar values with no control character; an `expectedVersion` is required; a name already in place is a no-op that moves no version and writes no audit record or event; a real change moves the name and the version once, with a trusted audit record and one `tenant.display_name_changed` v1 event, atomically.

**Decision:** `PATCH /admin/v1/tenants/display-name`, body `{ tenantId, displayName, expectedVersion }`, response `{ tenantId, displayName, version }` — the brief's `/api/platform/tenants/:tenantId/display-name` in the form the route conventions call for: a platform command belongs to the administrative session boundary (`/api` is the tenant boundary's namespace), and a route path is literal with no parameter, so the tenant travels in the body, where the idempotency fingerprint covers it. The route requires `edit_tenant_profile`, the existing canonical sub-permission for `tenant_management` at Edit (non-sensitive, no prerequisite, no money grant). The admin boundary's authorizer is the **canonical platform authorizer** (`server/composition/platformAuthorization.ts`): it resolves the session's verified principal to its app-owned actor through migration 007, selects the actor's one active platform grant, and decides the permission with `evaluateCanonicalPermission`, which now reads a role through its **definition** — its levels and money grants as data — so no role id is a shortcut and a custom definition is decided like a built-in one; the built-in definitions are the catalogue's defaults, so every built-in answer is unchanged (proven for every role, permission and limitation). A granted decision hands the chain the trusted scope it was made on, and the command carries that scope into its transaction: the lease fence, the actor's revalidation (007), **migration 008**'s fixed `SECURITY DEFINER` operation `tmpos_command.m5_tenant_display_name_update` (a `FOR UPDATE` row lock; the version is compared before the name), the audit record naming the actor, the event and the idempotency completion commit together or not at all. Migration 008 adds `public.tenant.row_version`, moved only by a trigger (+1 when the row changes, whatever a writer names), and grants `tmpos_app` EXECUTE on the one operation and nothing on the column; its rollback refuses once any version has moved. The command's body is validated once its idempotency record is acquired: a refused body is a 400 `invalid_request` that commits and records nothing, like a conflict, and a reused key with any other body — malformed or not — is the existing 422 key-reuse conflict; a missing tenant is a 404 and a stale version a 409 `write_conflict`, each committing nothing; nothing about a tenant is disclosed before authentication and authorization succeed. Owner decision **D4** is recorded as policy only: a future managed apply targets the complete contiguous chain through the newest committed migration, never 005 alone.

**Consequences:** G-IAM has its first server-enforced command and stays `OPEN`: tenant/store-scope authorization, durable custom platform roles (migration 003 admits the five built-in ids and no role store exists, so a deployment holds built-in roles only), an audited editor for them, and every other command remain. The command transaction port gains two update outcomes, `not_found` and `unchanged`; the runtime answers the first 404 and records the second's 200 through the idempotency store, since nothing moved. A planner may now answer `COMMAND_REQUEST_INVALID` (a 400 decided after acquisition, recording nothing), and a replay still never plans. The platform-scope audit row reaches the changed tenant only through its correlation with the event (DA-22). Nothing is deployed or live: the admin boundary's production session store and admission do not exist, and 008 is applied to disposable PostgreSQL only. No client editor exists, so binding the admin console's Tenant Management page — with a tenant read route that returns the version — is the next product stage; tenant suspension and reactivation is the next command; billing refunds and credits come later, behind server authorization and their provider transaction boundary.
**Update (M5-GIAM-D1-P4, ADR-25):** the resolution this ADR placed in the authorizer now happens once per request, in the administrative boundary's admission (migration 013's read, which calls 007's resolution). The authorizer (`createAdmittedPlatformAuthorizer`) decides the same canonical permission on the scope that admission selected, and `createPlatformRouteAuthorizer` is removed. The transaction-time revalidation (ADR-21) is unchanged.


## ADR-21 — The first command is decided, and recorded, exactly: one transaction for the no-op, one grant for the authority (DECIDED — M5-GIAM-D1-P1-R1)

**Context.** Review of the first server-authorized command (ADR-20) found four gaps: a name already in place was answered after the command's transaction had ended, so a concurrent change could make the recorded 200 stale; transaction-time revalidation (007) took the first active grant at the scope, so a grant added, duplicated or re-issued after authorization still passed, where initial authorization refuses two platform grants; 005's tenant-scope column grant let any runtime login rename a tenant outside the command, since the policy trusts settings a session sets itself; and the audit record reached its tenant only through the outbox event's correlation ID. Names could also carry bidirectional controls that render other than they read.

**Decision.** (1) A command that finds its changes already in place commits exactly one thing — its sealed unchanged response as the idempotency completion — in the same transaction that fenced the lease, revalidated the actor and locked the aggregate row; the runtime makes no completion of its own. (2) The trusted scope carries the selected grant (`membershipId`), and the transaction re-reads exactly it: migration 009's `m5_revalidate_platform_authority` requires that grant with that role, exactly one active platform grant, an account neither denied nor read-only, and the security version — locking the account `FOR UPDATE` (so a grant insert waits on its foreign key) and every grant of the actor `FOR SHARE` — and the composition re-decides the route's permission on the role's current definition over the same role definitions the authorizer used. 007 stays frozen; its routine is superseded, not edited. (3) 009 revokes `UPDATE(display_name)` from `tmpos_app`; `legal_name` is kept until proven obsolete. (4) `audit_event.subject_tenant_id` (nullable uuid, indexed, no FK) carries the command's own validated target. (5) Every Bidi_Control character is refused by the runtime validator and by 009's `m5_tenant_display_name_update_v2`, which supersedes 008's operation for the runtime role; stored names are not rewritten.

**Consequences.** 009 is code-only (disposable PostgreSQL); its rollback refuses while any audit record names a subject, and 008's rollback refuses while 009 is applied, so the chain rolls back newest first — D4's future managed apply names the contiguous chain through 009. Commands of one actor serialize on the account row. 007's first-match routine keeps its grant with no production caller (doc 08 DA-27); legacy bidi names need rendering isolation (DA-28); 005's policies still trust session-set settings for the remaining column grants (DA-29, G-DBROLE). G-IAM, G-AUDIT and G-CPLOGIN stay open. The next command is tenant suspension and reactivation.
## ADR-22 — A tenant's lifecycle is one transition, one witness, and one recent authentication (DECIDED — M5-GIAM-D1-P2)

**Context.** The second server-authorized command had to suspend and reactivate a tenant. Three things made it unlike the first. A lifecycle change is not a field edit: asking for the state a tenant already holds is a mistake to refuse, not a no-op to replay, so the display-name command's `unchanged` contract is exactly wrong here. Suspension must take access away *now* — the tenant boundary re-asked admission only every five minutes, and nothing a tenant/store session carried would have moved when its tenant was suspended, because 007's security version deliberately excludes memberships and knows nothing of tenant status. And suspending a tenant is sensitive in a way renaming one is not, while no step-up mechanism existed: the provider's verified authentication time was read once at login and discarded. A review of the first command had also left DA-31 open: a command route on the *authenticated* boundary could still have committed with no resolved actor.

**Decision.** (1) **Two transitions, and a closed answer set.** `PATCH /admin/v1/tenants/status` moves `active -> suspended` or `suspended -> active`. The request names only its target; the status it must start from is derived in trusted source, so no request can propose a third transition. A target equal to the current status, or a row in any of 002's other four states, is `invalid_state` — a new bounded outcome (409) the store and the runtime carry end to end — and writes nothing. The command carries no unchanged response, so there is none to record. (2) **A dedicated access version, not `row_version`.** Migration 010 adds `public.tenant.access_version`, moved by exactly one in the same statement as the status and never returned to a value it has held, so a session admitted before a transition is stale after it — including after a reactivation, which is why reactivating cannot revive what suspension ended. `row_version` moves on every field edit and must not end anyone's session, so the two are separate. No role holds a privilege on either column: 010 revokes nothing because nothing ever reached them, and its verify proves that for direct, inherited and SET-only paths rather than asserting it. (3) **No window.** The tenant boundary re-asks admission on every protected request (`ADMISSION_REVALIDATE_MS.tenant = 0`); an interval of any length is the grace period the product rules forbid. The administrative boundary keeps its own interval, because the administrator who reactivates a tenant must not be logged out by suspending it. (4) **One tenant-state decision.** `tenantState.ts` decides every status once — active continue, read-only deny writes, suspended deny, anything unrecognised deny — and scope selection applies it, so a suspended or unknown-status tenant selects no scope at all instead of being selected and checked later. (5) **Step-up on trusted evidence only.** The provider's verified authentication time is bound to the session record at login, beside the principal's digest and the admitted security version; a route may declare `recentAuth: 'required'`, and the chain refuses past ten minutes with a bounded `step_up_required`. The same deadline travels into the transaction and is re-judged on the DATABASE's clock, so evidence that expires in flight commits nothing. Nothing a request carries can set or extend it, and there is no shared PIN. (6) **DA-31 closes by declaration.** Every route that requires idempotency must declare `trustedContext: 'required'`; startup refuses one that does not, and the chain enforces it on both boundaries before the body is read, the key acquired or the operation entered. (7) **The reason is audit evidence, not aggregate state.** A bounded 10-500 scalar reason travels on the plan's audit annex — never the tenant row, never an event payload — and is written to the audit row's existing reason pair: a closed `reason_code` naming both statuses, and the operator's own words.

**Consequences.** 010 is code-only (disposable PostgreSQL); its rollback refuses while any tenant is suspended, because rolling back removes the only operation that could reactivate one, and warns — rather than refusing — when an access version has moved, since reactivating raises that version and no refusal on it could ever be cleared. D4's future managed apply names the contiguous chain through 010. **Decision (2)'s version is maintained but not yet read:** the link is the tenant boundary's `SessionAdmission` adapter, which must report a version incorporating it, and none exists — `productionSessions.ts` composes no tenant admission, store or authorizer — so today a suspension's effect on a tenant session rests on the status denial alone, and the reactivation guarantee is specified and enforced by nobody (doc 08 DA-32). Re-asking admission per request costs an admission call per tenant request — two, once the route authorizer re-reads as well (M5-GIAM-D1-P2-R1, doc 08 DA-38); the `validatedAt` stamp is not written on a boundary with no window, so it is no cost and no availability dependency (DA-33). Neither command is bound to a client, and the Tenant Management UI binding is the immediate next stage (DA-34). The reason's character rule is enforced by the runtime contract and the store, not by a column CHECK (DA-35). G-IAM, G-AUDIT, G-CPLOGIN and GAP-13 stay open.
**Update (M5-GIAM-D1-P4, ADR-25):** the administrative boundary no longer keeps an interval; it re-asks on every protected request too. Decision (3)'s reason is kept by the witness instead: a tenant's state is not part of the platform witness, so suspending a tenant still logs out no administrator.


## ADR-23 — A tenant session is bound to a witness of the actor's whole standing (DECIDED — M5-GIAM-D1-P2-R1)

**Context.** ADR-22 left `tenant.access_version` maintained and read by nobody: the tenant boundary composed no session store, no admission and no authorizer, so a suspension's effect on a tenant session rested on the status denial alone (doc 08 DA-32). Two things had to exist before that could be proved rather than asserted. The session boundary has always declared a **durable, shared** store as its contract ([03](./03-backend-control-plane-login-session-blueprint.md) §2 #18) and had only the in-memory test kit, which the deployable artifact excludes. And the admission port answers ONE opaque version per principal, while a tenant actor's standing is many grants across many tenants — so the version had to be derived, not read. Suspension alone would not have needed the access version at all: migration 007's resolver already hides a suspended tenant's grants, so the answer moves on suspension by itself. What it cannot express is REACTIVATION — the grant returns and the answer would go back to byte-identical, reviving an idle session the suspension ended.

**Decision.** (1) **Migration 011 owns its own schema, `tmpos_session`** — as 007 and 008 own theirs — holding one table, five fixed session operations and one admission read. `tmpos_app` gets schema USAGE and EXECUTE on the six routines, **none of it grantable, and no privilege at all on the table**. Section 6 proves that rather than asserting it, on three independent surfaces: no non-owner entry in `pg_class.relacl` or `pg_attribute.attacl` (a column grant is the easy miss), no EFFECTIVE privilege by `has_table_privilege` for any of those four roles (which sees a direct grant, one to PUBLIC, an inherited one and a predefined role such as `pg_read_all_data` alike), with every object ACL read through `acldefault` when it is NULL, and no MEMBERSHIP of the owning role by any of the four roles these migrations own — membership is invisible to an ACL and hands a role everything the owner has, including an RLS bypass, so migration 010's check is made here for this schema too. The integration suite then observes the runtime role itself refused (`42501`) on every DML statement it issues against the table. (2) **The admission read is `STABLE`, and that is load-bearing:** it calls 007's resolver and joins each tenant's access version, and a `STABLE` plpgsql function uses the calling query's snapshot for every statement it runs, so the grants and the versions are read as of one instant. A `VOLATILE` one would take a new snapshot per statement and could answer from two. (3) **The witness is a digest of the whole standing** — actor, account status, limitation, 007's security version, and every grant's id, scope, tenant, store, role, tenant status, store status and tenant access version — over a newline join that is injective because the digest is length-prefixed with the grant count, each grant contributes a fixed eight lines, and every field is printable and newline-free by a constraint checked before the digest is taken (`isTrustedPrincipal`). It is ordered by membership id **as a uuid**, in SQL, so no collation change can move it — nothing in TypeScript re-sorts or would notice an out-of-order array. A tenant-scoped grant with no access version is an OUTAGE, never a refusal and never an admission: the routine RAISES, because 007 resolved that grant against a tenant row in the same snapshot, so the only way the version is missing is that 011's routine sees less of `public.tenant` than 007's does — a privilege fault, not a verdict about the actor. Answering "refused" there would tell the boundary the principal may hold no session, and the boundary acts on that by deleting every session it holds, so a privilege drift would sign the whole estate out at once (M5A-13 proves the raise). A drift that hides the rows from 007 TOO — FORCEd row security on `public.tenant` — never reaches that check: 007 drops the grant, and the answer is a refusal. 011 refuses to apply over that state; a FORCE added afterwards is recorded under DA-40. A grant no version could revoke is the one thing this mechanism cannot protect, so it declines to pretend otherwise. (4) **The store may answer "no such session" only when the database said so.** Every other doubt — an unrecognised row shape, a stamp it cannot parse, an unreadable clock, an outcome the routine does not define, a driver fault — THROWS, because the boundary reads a throw as an outage and refuses the request, while "no such session" would silently sign a live user out. (5) **A wrong audience is a wiring fault, not a request:** the tenant admission adapter THROWS when asked about the admin boundary, because a denial there would 401 every administrator *and* destroy their live sessions on every device.

**Consequences.** DA-32 is closed, and proved end to end over real local sockets and disposable PostgreSQL: a suspension refuses the very next protected request and revokes the session; a login while suspended is refused; after reactivation the witness differs from the pre-suspension one while the principal version the composed path reports does not move — which is precisely why the access version exists; a session IDLE across the whole episode is refused on its next request with `session_version_mismatch`, which is the revival case the version was written for and the one a session that transacted during the suspension cannot show; a store session is denied by its parent tenant, which it never names; a display-name edit moves `row_version` only and ends nothing; and and a tenant suspension reaches no admin session in this composition — where the admin boundary still runs a stub admission over the in-memory store, so what the real path proves there is the narrower fact that a platform grant is still not a tenant session. 011 is code-only (disposable PostgreSQL); D4's future managed apply names the contiguous chain through 011, and its rollback refuses while the table holds ANY row — it takes `ACCESS EXCLUSIVE` before counting, so a login committing between the count and the drop cannot be destroyed unseen, and it judges no expiry because the only clock available to it is the DATABASE's while every `expires_at` was computed from the RUNTIME's. Five things are recorded rather than removed: both boundaries share one table and one runtime role (DA-37); a protected request makes two admission reads (DA-38); 007's *fault* refusals — a duplicate identity anchor, two active links, a 201st membership — now end every session the principal holds rather than denying one request, because 011 passes its one `refused` value straight through and 007 is frozen (DA-40); a MEMBERSHIP or STORE lifecycle has no monotonic witness of its own, so a session idle across a store's suspend-and-reactivate would be revived exactly as a tenant's would have been without the access version — unreachable today, since no shipped command changes either, and asserted as a characterization test so the day one is written its author is told what to add (DA-41); and **the tenant boundary still has no shipped route** — the whole proof runs against a witness route defined inside the integration harness and injected into a real runtime instance there, never exported and refused in production source and in the artifact by containment tests (DA-39). The role-to-permission half of the tenant authorizer is deliberately not decided, and it is worth being exact about what enforces that. The authorizer checks only that a route's permission NAMES a canonical tenant key; it never compares that key against the actor's role, because the canonical decision answers `undecidable` for the whole tenant plane until owner decision D1 (G-IAM/D1, the first tenant-plane production route; retagged M5-GIAM-D1-P3 — GAP-11 is closed at repository level). What keeps such a route out of production is the transaction root: `uncataloguedRoutePermissions` answers `route_permission_undecidable` for any tenant- or store-scope requirement, and composition throws on any blocker, so the process refuses to start. G-IAM, G-CPLOGIN, G-DBROLE, G-AUDIT, G-MIGRATE and GAP-13 stay open.

**Amended (M5-TENANT-SESSION-P1, [ADR-31](#adr-31--tenant-session-ordering-a-tenant-login-holds-its-actors-standing-until-it-commits-decided--m5-tenant-session-p1)).** DA-41 is closed in code by migration 016. Stores carry a trigger-owned access version. Every UPDATE that changes a tenant's or a store's status, or a store's tenant, moves its version, a raw owner write and a replica's included; a tenant's or a store's key never changes (23514); and a store INSERT starts at 1 whatever it names. Each actor's tenant- and store-scope grant writes, and every delete of a tenant or store such a grant names, move a per-actor counter. The adapter reads `m5_admit_tenant_session_v2`, and the witness is now `t2:` over nine fields per grant plus 013's authority version and 016's grant version. The residuals are recorded under DA-41.

## ADR-24 — The platform lists tenants through one definer read that re-confirms its grant, and the console binds both commands to it (DECIDED — M5-GIAM-D1-P3)

**Context.** Two platform commands existed (ADR-20 to ADR-22) and no client could reach either: the admin console's Tenant Management was a placeholder (doc 08 DA-34). A page that edits tenants needs a list of them, with the row version each command takes as `expectedVersion`. But the runtime role cannot produce that list. `tmpos_app` reads `public.tenant` only under migration 005's row policy, which opens exactly one tenant's row to a tenant- or store-scoped context and nothing to a platform one, and that policy is deliberate. The stage brief said a schema migration was not expected; the owner was asked and replied "continue", so the migration below is recorded as a deviation from that expectation.

**Decision.** (1) **One read route.** `GET /admin/v1/tenants` (`server/runtime/tenantDirectory.ts`) is an admin-session route under `view_tenants` (tenant_management at View or above). It declares `trustedContext: 'required'` and acts only on the trusted scope the canonical platform authorizer resolved. It takes no body and no idempotency key. The query allows only `limit` (1–50, default 25) and an opaque cursor, 23 canonical base64url characters naming the last tenant of the previous page; any other key, a repeat or an encoding is a 400 before any read. The response is `{ tenants: [{ tenantId, displayName | null, status, version }], nextCursor, actions: { editDisplayName, changeStatus } }` and nothing else. The port's answer is validated before any of it is copied into the response. A lost grant is the generic 403, an unknown continuation a 400, and any outage or malformed answer a bounded 503. (2) **`actions` are presentation, not authority.** They are computed by the same canonical rule the authorizer applies (`createPlatformPermits`, `server/composition/platformAuthorization.ts`), so the page shows only controls the server would allow; each command is still authorized from the beginning by its own chain. (3) **Migration 012 owns its own schema, `tmpos_directory`**, as 007, 008 and 011 own theirs, because a routine added to an existing schema would make an older rollback or inventory assertion false. The schema holds one `STABLE SECURITY DEFINER` routine, `m5_tenant_directory_page(uuid, text, uuid, text, uuid, integer)`, with its search path pinned and EXECUTE granted to `tmpos_app` as the only non-owner grantee. In the snapshot it reads the page in, the routine re-confirms the caller's live platform grant: the account is neither suspended nor pending activation, its security version is equal, and it holds exactly one active platform grant, the named membership and role. The page is a keyset page ordered by `(created_at, tenant_id)`, an order no rename or status change moves. The routine decides no permission and answers `denied`, `cursor_unknown` or `invalid` as a single row. Fail-closed postconditions check the routine count, the definer, stability and search-path attributes, the ACLs, and that no runtime role is a member of the owner. It creates no table, performs no write and creates no role, and the down file removes exactly the routine and the schema. (4) **Composition.** The PostgreSQL adapter (`server/persistence/postgresTenantDirectory.ts`) is built by the transaction root over the client it already owns, through `PRODUCTION_INVENTORY.reads`, and the route is declared in `productionRouteDeclarations()`. (5) **The console binding.** `TenantManagementPage.tsx` lists, shows, renames, suspends and reactivates tenants through the read and the two commands alone. Every change names the server's version and holds one idempotency key per intent: the same key on a retry after an uncertain answer, a new key after a definitive one. There is no optimistic state, and the directory is read again after every definitive answer, a conflict included. Lifecycle changes sit behind confirmation dialogs.

**Consequences.** DA-34 is delivered except the step-up experience. No re-authentication flow exists, so a `step_up_required` refusal asks the person to sign in again *(until M5-ADMIN-STEPUP-P1: ADR-28)*. The page exposes no store lifecycle control, because a store has no monotonic witness (DA-41, still open). Tenant Management is the one open workspace, and the other nine stay placeholders. 012 is code-only, proved on disposable PostgreSQL only (`tests/db/tenantDirectory.integration.test.mjs`) and applied to no managed database. D4's future managed apply names the contiguous chain through 012, and 005–011 are byte-identical. Four things are recorded rather than fixed. First, a stored legacy display name longer than 4,096 UTF-16 code units makes any page that includes it a bounded 503, and `actions` stay presentation only; the page query has no supporting index, so its cost grows with the tenant count (DA-44). Second, the routine's grant re-check refuses stale authority but is not a boundary against the runtime role, which can build a valid tuple through 007's resolver (DA-45). Third, the S2-DB-1 suite-order dependency is recorded as DA-42. Fourth, local build memory sensitivity is recorded as DA-43. Nothing is deployed or composed into a deployable entry, and no route is live. The tenant plane still has no production route: its role-to-permission decision waits on owner decision D1 (G-IAM/D1). G-IAM, G-CPLOGIN, G-DBROLE, G-AUDIT and G-MIGRATE stay open.

## ADR-25 — An administrative session is bound to a monotonic witness of its platform standing, and authorized on the scope its own admission selected (DECIDED — M5-GIAM-D1-P4)

**Context.** The administrative boundary had no durable admission: the production composition always named `admin_admission_unavailable`, and the runtime re-asked admission only once a minute, so a withdrawn platform grant would have kept acting for up to that window. The canonical authorizer (ADR-20) resolved the actor again on every request through 007, a second read that could disagree with anything admission had seen. A witness was needed that moves on EVERY change to an administrator's standing and never returns to a value it has held, and nothing in 001–012 gives that. 007's security version deliberately excludes memberships, so it never moves for a platform grant. What it does cover — account status and identity links — it digests from row timestamps, which come back when an exported row is re-inserted with them, or when a row is changed and changed back by a session running as a replica (002's `updated_at` triggers do not fire there). It does not cover the identity anchor at all. A witness built from the grant row would not do either: the membership id and role return unchanged when a grant is disabled and re-enabled, and its timestamps are reproduced by the same re-insert.

**Decision.** (1) **Migration 013 owns its own schema, `tmpos_admission`**, as 007, 008, 011 and 012 own theirs. It holds one table, `platform_authority_version` (one row per actor, a bigint from 1 to 2^53-1, and no foreign key, so the counter outlives the account), one `SECURITY DEFINER` trigger function granted to nobody, and one admission read. (2) **The database moves the version, whoever writes.** Four `AFTER INSERT OR UPDATE OR DELETE FOR EACH ROW` triggers, one per table and each `ENABLE ALWAYS` so that replica mode fires them too, add one to the actor's version. Any insert or delete of its `platform_identity`, `app_user` or `identity_link` row, or of a platform-scope `user_membership` row, moves it. So does any update of `app_user`, `identity_link` or a grant at platform scope before or after the write that changes a column other than `updated_at`. On `platform_identity` only an anchor change counts (`internal_user_id`, `auth_provider`, `auth_provider_uid`): email and display name mirror the provider's profile and decide nothing. A tenant- or store-scope grant never moves it. A write that moves a row between actors moves both, each once; otherwise each write moves its actor exactly once. Cascading deletes fire each table's trigger, so only "increased" is meaningful. (3) **One read, one snapshot, no decision.** `m5_admit_platform_session(provider, uid)` is `STABLE SECURITY DEFINER`. It calls 007's resolution, keeps the platform-scope grants and adds the version as decimal text (0 when the actor has no row), and every refusal is one identical row. `tmpos_app` holds USAGE on the schema and EXECUTE on the read only. The precondition refuses unless the applier owns the four tables. Section 6 refuses to finish unless exactly the declared routines, grants and owners are in place and exactly the four declared triggers call the function (`tgtype` 29, enabled `A`, no column list, no `WHEN`). (4) **Admission decides in trusted source.** `createPlatformSessionAdmission` (`server/composition/platformAuthorization.ts`) admits only an `active` or `trialing` account with no read-only cap, holding exactly one active platform grant — none is unauthorized, two are ambiguous, and there is no first match — whose role the canonical catalog defines. Its witness is `p1:` plus a SHA-256 digest over the actor, account status, cap, 007's security version, grant, role and authority version. A malformed answer is an outage, never a denial, and being asked about the tenant audience is a wiring fault that throws. (5) **No window.** `ADMISSION_REVALIDATE_MS.admin = 0`: every protected request re-admits, the current-session read included, and logout never asks. A denial revokes every administrative session of the principal; a witness change revokes the session presented; an outage revokes nothing. The authority version only increases, so no restoration of the standing the witness covers revives a session; a code-defined role definition is outside the witness (doc 08 DA-47). A tenant's state is not in the witness, so ADR-22's reason for the old interval — the administrator who reactivates a tenant must not be logged out by suspending it — still holds. (6) **Authorize on what admission read.** Admission hands the scope it selected to the same request's authorizer (`ActiveSession.admitted`), and `createAdmittedPlatformAuthorizer` decides the route's canonical permission on that scope alone; a request with no admitted scope is an outage. `createPlatformRouteAuthorizer` is removed. The command transaction keeps migration 009's revalidation. (7) **Composed together or not at all.** The transaction root builds the PostgreSQL platform admission (`server/persistence/postgresPlatformAdmission.ts`) over its one kernel, and the sessions root's `durableSessionAdapters` builds the admission and the authorizer from it together, never one alone. Readiness asks the administrative admission's probe.

**Consequences.** Handed the durable bundle, the production composition no longer names `admin_admission_unavailable` or `admin_authorizer_unavailable`. `rate_limit_store_unavailable` remains, so it still refuses *(until M6-RATE-P2: ADR-26)*, no production entry composes either root, and nothing is deployable. The tenant admission offers no probe, so it is still not part of readiness. 013 is code-only, exercised on disposable PostgreSQL only (`tests/db/platformAdmission.integration.test.mjs`, `tests/db/adminBoundary.integration.test.mjs`), and applied to no managed database. D4's future managed apply names the contiguous chain through 013, and 005–012 are byte-identical. 013's rollback and a re-application each refuse while any administrative session exists: session rows are the only place a witness lives, a recreated table would restart every counter at zero, and a login racing the rollback can commit its session after it. Six things are recorded rather than fixed (doc 08). The read is an oracle for the runtime role, as 007's resolver already is (DA-46). Role definitions are code, so a changed definition applies on the next request but ends no session (DA-47). The table owner can disable the triggers or delete version rows outside the contract (DA-48). Opposite-order writes to the same actors' rows can deadlock, a command's committing re-check does not read the authority version, and each protected request costs one admission read (DA-49). A tenant-plane grant flood past 007's 200-grant bound denies admin admission (DA-50). A profile edit moves the version (DA-51). G-IAM (the step-up experience, DA-34, among the rest), G-CPLOGIN, G-DBROLE and G-MIGRATE stay open, and GAP-11 stays closed at repository level.

## ADR-26 — PostgreSQL is the initial distributed rate-limit store, behind the unchanged port, and it fails closed (DECIDED — M6-RATE-P2)

**Context.** M6-RATE-P1 delivered the `DistributedRateLimiter` port, its conformance suite and the runtime's limits, but no shared store, so every production composition named `rate_limit_store_unavailable`, and the runtime refuses to serve any route but the probes without a limiter (`rate_limit_required`). [02 §8](./02-target-production-architecture.md) and ADR-17 named a shared cache (e.g. Redis) as a possible rate-limit store and chose none. By M5-GIAM-D1-P4 every other adapter a protected request needs — the session store, both admissions, the idempotency store and the command transaction — was PostgreSQL state behind the transaction root's one kernel. A shared limiter must also detect what no per-instance counter can: an instance keyed with a different `RATE_LIMIT_KEY`, under which one client becomes a second bucket and every limit multiplies.

**Decision.** (1) **PostgreSQL is the initial store.** Migration 014 owns its own schema, `tmpos_rate_limit`, as 007 and 011–013 own theirs. It holds two tables — `bucket`, one row per (namespace, dimension, pseudonymous limiter key, limit, window), and `key_fingerprint`, at most one row — and four routines: the consume, the probe and the reclaim (`SECURITY DEFINER`), and the key check the consume and the probe share (`SECURITY INVOKER`, granted to nobody), each pinned to `pg_catalog, pg_temp`. It creates no role. `tmpos_app` holds USAGE on the schema and EXECUTE on the consume, the probe and the reclaim only, and no privilege on either table; both tables are RLS-enabled with no policy. Section 6 refuses to finish unless exactly those routines, owners, attributes, grants and effective privileges hold, and also refuses when `tmpos_audit_writer`, `anon` or `authenticated` can execute any rate-limit routine, by a grant or by membership in `tmpos_app`, or is a member of `tmpos_app` at all, however the membership is granted (a `NOINHERIT` member, which `has_function_privilege` does not report, may still be able to `SET ROLE tmpos_app`, so membership is refused outright rather than judged by its options): a role that could call the consume or the probe first could register a fingerprint of its choosing. (2) **The adapter stays behind the port.** `server/persistence/postgresRateLimiter.ts` implements `DistributedRateLimiter` as it stands; the runtime imports no adapter, and the conformance suite runs against the store unchanged. Replacing the store means a new adapter and a new composition binding, not a runtime change. (3) **Semantics.** The policy is part of the bucket's key, so a changed limit or window starts fresh buckets, and namespaces never share one. A window opens at the first successful consume of an absent or expired bucket and lasts exactly the window; no consume extends it, and an expired bucket is reopened in place. A consume of `cost` is allowed iff the count plus the cost stays within the limit. A refused consume changes neither the count nor the expiry, and answers the time left on the DATABASE's clock (`clock_timestamp()`, read after the row lock, or after the unlocked read that decides a refusal), in whole milliseconds, 1..window, so instances whose clocks disagree share one window. A consume the committed state already refuses — a live window, at the clock read after that read, whose count plus the cost exceeds the limit — is answered `limited` from an unlocked read and writes nothing: inside a window the count only grows and nothing can replace the window before it expires, so that refusal stands on a database clock that does not step backwards (if it does, the rare error is a refusal where an allowance was due, never the reverse); a refusal that races the consume spending the last allowance can still take the locked path. Every other consume locks its bucket (`FOR NO KEY UPDATE`) before it reads the count, and an absent bucket is created by an `INSERT … ON CONFLICT DO NOTHING` that loses cleanly to a concurrent one; so consumes of one bucket serialize across every instance, and two first consumes cannot both open a window. A bucket that cannot be locked in three rounds raises a serialization failure, which the adapter answers as unavailable. This relies on READ COMMITTED, the kernel's isolation. (4) **Bounds.** Each consume and each probe is one transaction on the runtime kernel under `lock_timeout` 200 ms, `statement_timeout` 300 ms and `idle_in_transaction_session_timeout` 400 ms, all below `LIMITER_DEADLINE_MS` (500 ms). The adapter bounds every call by its caller's signal and by its own 500 ms timer, whichever ends first, and sends nothing for a call already aborted, which joins no line. It answers the moment that bound ends, even with the transaction's COMMIT in flight, whose outcome the kernel still supervises: an allowance committed after the bound is answered unavailable — its cost spent, never an allowance unrecorded. The adapter also serializes consumes per bucket per instance ("lanes"): a consume of a bucket this instance already has in flight waits in the adapter, holding no connection, under its own deadline, and an abort while it waits sends nothing. So one client holds at most one kernel connection per bucket it reaches, and a flood from a single source holds no more of the kernel's connections than the buckets it reaches, rather than one per request; a source reaching several buckets, or many sources, can still exhaust them (Consequences). A line holds at most `RATE_LIMIT_LANE_DEPTH` (64) consumes of one bucket per instance, the one in flight included; past it a consume of that bucket is unavailable at once and joins nothing. A waiter that gave up still counts until the line reaches it, so a line whose head cannot end (a COMMIT the network never answers) holds a bounded number of links. (5) **Fail closed; no local fallback.** An outage, a timeout, an abort, a driver error, a serialization failure, an answer that is not exactly one in-contract row, and a key mismatch all answer `unavailable`, and the runtime refuses the request with a bounded 503 (`service_unavailable`, logged as `rate_limit_unavailable` or `rate_limit_timeout`). The probe answers true only for exactly one `ready` row, so an unreachable store, a read-only session or a standby (`store_read_only`) or a mismatched key makes `/readiness` 503; `/health` never touches the limiter. There is no retry, no queue, no cache of allowances and no per-process limiter: while PostgreSQL cannot answer, protected requests are refused, never allowed. (6) **What is stored.** The pseudonymous limiter key (43 base64url characters, HMAC-SHA256 under `RATE_LIMIT_KEY`), the namespace, dimension, limit and window, the count, the window's start and end, and the key's fingerprint. Never a client address, a provider UID or account identifier, a token, a cookie, a header or any other part of a request, and never `RATE_LIMIT_KEY` itself. (7) **Key skew is detected in the store.** The fingerprint is HMAC-SHA256 keyed with the bytes `RATE_LIMIT_KEY` decodes to (not its text) over the ASCII string `tmpos-rate-limit-key-fingerprint:v1`, a constant used for nothing else. The first consume or probe on a store without one registers its own, atomically; every later call must present the same fingerprint, and a different one is answered `key_mismatch` before any bucket is read, so every consume of that instance is unavailable and its readiness fails. No routine writes the fingerprint again and the runtime holds no privilege on its table, so it is never erased or replaced automatically; only 014's rollback, or the owner in the manual procedure below, removes it. Because the FIRST caller registers, a wrongly keyed instance that calls first after 014 is applied locks every correctly keyed instance out (every protected request 503, readiness 503). A holder of the runtime database credential can do the same on purpose without the key, by calling first with a fingerprint of its choosing, so right after 014 is applied (or re-applied after its rollback) a correctly keyed instance must call before anything else holds that credential, or the owner must confirm the registered fingerprint (doc 08 DA-53). Recovery is an operator procedure, not a routine: stop the wrongly keyed instances, confirm the intended key's fingerprint, delete the one `key_fingerprint` row as the owner in a maintenance window, and let a correctly keyed instance register. Nothing does this automatically. Rotating `RATE_LIMIT_KEY` likewise needs an explicitly designed, coordinated procedure. None is provided, and deliberately no reset (doc 08 DA-53). (8) **Cleanup is out of band and bounded.** The consume reclaims nothing. A fourth routine, `m6_rate_limit_reclaim()`, deletes at most four buckets that expired before its own clock reading, oldest first, through the expiry index `bucket_expires_at_idx`, skipping every row another transaction holds (`FOR UPDATE SKIP LOCKED`) and deleting each by its primary key. The adapter calls it in a transaction of its own under 50 ms lock, statement and idle-in-transaction bounds, in the background. Each allowed consume that opened a window (the only kind that can add a row) and was answered to its caller owes one call — one whose window opened only after its caller was answered unavailable owes none; owed calls run one at a time per instance, the next only after one deleted a full four, and one that deletes fewer, or fails, clears what is owed. No consume waits for a reclaim, and a reclaim that fails or times out changes no consume's answer. Its lock hold is bounded far below a consume's 200 ms lock wait, so a consume of an expired bucket that a reclaim holds at that moment still gets its answer. The probe never reclaims, and there is no timer, sweep or worker. (9) **Composition.** The transaction root builds the adapter over its one kernel and hands over a binding that awaits the key (`ProductionTransactions.rateLimiter`). The sessions root parses `RATE_LIMIT_KEY` once and binds the limiter with those bytes, so the keyring the runtime keys pseudonyms with and the fingerprint the store checks come from one key. With that binding and a valid key, `rate_limit_store_unavailable` no longer arises. Without the binding it stays a blocker, and with the key missing or malformed it stays beside `rate_limit_key_missing` or `rate_limit_key_invalid`.

**Why not Redis now.** A second stateful service would add a provider, a credential, a network path, a backup and a failure mode of its own, for a counter that needs only a row lock and one clock. The database every protected request already depends on provides both. No measured traffic exists to size a cache against, and ADR-17 allowed a cache for rate limiting without requiring one. Redis, or another store, stays a possible later replacement if measured traffic or latency justifies it: behind the same port, passing the same conformance suite, and never as a fallback for PostgreSQL or the reverse. No Redis or other provider is added.

**Consequences.** The limiter adds write load to the primary database. Every protected request (every route but `/health` and `/readiness`) is at least one short transaction on the runtime kernel, which writes whenever the consume is allowed, and a login is up to three: the request limit, the login client limit and, after verification, the account limit. A consume the committed state already refuses takes no row lock and, once the key fingerprint is registered, is assigned no transaction ID and writes no WAL (measured on a disposable cluster: `pg_current_xact_id_if_assigned()` is null after it); a refusal that races the consume spending the last allowance can still take the locked path. Those transactions share the runtime kernel's ten one-connection pools (`RUNTIME_POOL_MAX` = 10 in server/platform-identity/db.ts, at the supervised client's `MAX_POOLS` ceiling) with sessions, admission and commands, and consumes of one hot bucket that take the locked path serialize on its row, each allowance holding it through its commit's WAL flush. The lanes keep a single source to one connection per bucket, but many sources can still exhaust the kernel's ten connections, which is an edge or WAF concern. That is judged sufficient for the current scale, which has no production traffic; its cost under real traffic is unmeasured (doc 08 DA-52, and the measured local limits there). After a burst each window opened is matched by up to four reclaimed while a backlog remains and reclaims succeed; during a burst of new clients windows can open faster than one reclaim at a time clears them, and with no traffic the backlog stays. Every window reopen is a non-HOT update and reclaims leave dead entries at the low end of the expiry index; under a long-held database snapshot (a long transaction, a replication slot, `pg_dump`) vacuum cannot clear them, and with about 100,000 of them (a one-off check on a throwaway local PostgreSQL 16 cluster, not part of the committed tests) both reclaims tried hit the 50 ms statement bound and failed with SQLSTATE 57014 until the snapshot ended, while consumes, which use the primary key, were unaffected; storage grows meanwhile (DA-52). A consume aborted before its COMMIT is answered at once and releases its bucket's line when the kernel answers; the kernel cancels its statement and retires that connection, and the server rolls the abandoned transaction back only when it sees the session end, so the next consume of that bucket, from any instance, can wait on that row lock — bounded by the server-side bounds — and is a 503 if it outwaits its 200 ms lock bound. That fails closed and is recorded, not fixed (DA-52). A PostgreSQL outage refuses every protected request rather than serving it unlimited. 014 is code-only, exercised on disposable PostgreSQL only, and applied to no managed database. Its rollback refuses first (`object_not_in_prerequisite_state`) unless its transaction is READ COMMITTED, and takes its `ACCESS EXCLUSIVE` locks as a statement of their own before its check, so the check's fresh snapshot sees every window opened while the lock was awaited (at a stricter level an earlier statement's snapshot could hide one); it refuses (`object_in_use`) while any bucket is still inside its window, and otherwise drops every bucket and the registered fingerprint. After a rollback every protected request is a bounded 503 and readiness fails until 014 is applied again, and the next application registers whichever key reaches it first. D4's future managed apply names the contiguous chain through 014, and 001–013 are unchanged. Section 6 checks four named roles; the real runtime LOGIN role (a member of `tmpos_app`, which cannot log in) is not among them, as in 010–013, so that role's memberships remain a deployment check (G-DBROLE). No production entry composes either root: the deployable entry is the next composition task, and `server/runtime/server.ts` still serves the probes only (until M6-ENTRY-P1, below). The deployment half of the trusted-proxy contract is unchanged and open (G-UNAUTH). G-CPLOGIN, G-IDEMPOT, G-IAM, G-DBROLE and G-MIGRATE stay open, and G-UNAUTH stays partial.

## ADR-27 — Deployable production entry and fail-closed startup preflight (DECIDED — M6-ENTRY-P1)

**Context.** M4–M6 delivered the composition roots (sessions, transactions/idempotency/audit/outbox) as code-only: no production entry assembled the composition roots; the former entry (`server/runtime/server.ts`, deleted in M6-ENTRY-P1) bound a listener that served only the two probes. G-CPLOGIN, G-DBROLE and G-IDEMPOT each listed a deployable entry among its open items. The entry must prove every precondition — configuration, TLS, database connectivity, runtime login standing (no superuser, exact privilege roles, the new direct ledger-read privilege), migration ledger state — read-only before binding a listener, the one write being step 8's registration of the rate-limit key's fingerprint when none exists (doc 08 DA-53, DA-57). Startup must be fail-closed on every category and never automatic-repair. Graceful shutdown must respect signals during startup itself and drain in-flight requests within a known deadline. The entry is narrowly scoped: the administrative boundary only, every route but the two probes answering on the admin host alone.

**Decision.** (1) **The deployable entry (`server/entry/productionEntry.ts`) composes the administrative boundary only**, bound by `SESSION_ADMIN_ORIGINS` (exactly one `https://` origin), and SESSION_TENANT_ORIGINS is neither read nor required. It serves the 8 routes in SHIPPING_ROUTES: two probes (`/health`, `/readiness`), the admin login/current/logout, the tenant directory read and the two tenant-update commands — then a bounded 404 for any other path or host. (2) **Startup is 10 bounded steps, each with a 15 s deadline**, never restarted or repaired:
  - 1. Configuration validation (validateEntryConfig): each required env var is bounds-checked; no value is logged; refusals name each field and bounded code.
  - 2. Database client creation with verified TLS (classified APP_DATABASE_URL, verified DATABASE_CA_CERT).
  - 3. Database connectivity: one SELECT 1 on the runtime login.
  - 4. Runtime login validation (postgresStartupPreflight.ts): no superuser, BYPASSRLS, CREATEROLE, CREATEDB, replication; exactly tmpos_app and tmpos_audit_writer memberships (inherited, no ADMIN OPTION); no owned objects; **one direct privilege required here: SELECT on public.schema_migrations** — this privilege is new and must be provisioned by the G-DBROLE operator; no migration grants it.
  - 5. Migration ledger validation (postgresStartupPreflight.ts): exactly 001–014 in order, all finished, no dirty rows, checksums pinned (REQUIRED_MIGRATIONS hardcoded); nothing is applied, rolled back or repaired.
  - 6. Sessions and transactions composition: only the administrative boundary; SHIPPING_ROUTES must match exactly; any missing or extra route refuses.
  - 7. Dependency probes: the idempotency store and the command-transaction port answer their read-only probes.
  - 8. Rate-limit key fingerprint registration and validation: atomic; a mismatch or store unavailability refuses.
  - 9. Readiness checks: the session store (a read of a random key that names no session — its only probe; `/readiness` does not ask it), the admin admission, the rate limiter.
  - 10. Listener binding: only then is readiness ready and the startup logged `startup_ready`.
(3) **Startup refusals.** Every refusal logs one or more `startup_refused` lines, each carrying the category (with its bounded codes, split across lines at the log's field cap; no configuration content, driver message or address), ends the kernel and exits 1; no listener is left open (a socket that binds after step 10's deadline, `listen_timeout`, is closed at once). Categories: config_invalid (field:code), database_tls_invalid, database_unavailable, database_login_unsafe, migration_state_invalid, composition_refused, route_inventory_mismatch, dependency_unready (step 7 or 9 only; codes idempotency_store, command_transactions, session_store, admin_admission, rate_limiter), rate_limit_key_mismatch, rate_limit_store_read_only, rate_limit_store_unavailable, rate_limit_probe_malformed, listen_failed, startup_failed. (4) **No automatic migration policy.** The entry verifies the ledger; it never applies, rolls back or repairs. Management is a separate operator action. (5) **Graceful shutdown.** The lifecycle is installed first (before step 1). On SIGTERM/SIGINT during startup, the step in flight is abandoned and no listener remains open — a socket that binds after the signal is closed at once; a signal after step 2 ends the database client the kernel was built on; and the process exits 0. After a listener is bound, the signal turns readiness unavailable first, before anything drains; in-flight requests drain under their own deadlines; the kernel ends within RETIRED_POOL_GRACE_S (5 s fixed); the process exits 0. SHUTDOWN_FORCE_TIMEOUT_MS (10 s) after the signal the process exits 1 and logs `shutdown_forced` if anything still hangs. Repeated signals are coalesced into one shutdown sequence. (6) **Construction boundary.** The configuration is the process environment. The construction passed is PRODUCTION_CONSTRUCTION: verified-TLS database client from classified APP_DATABASE_URL, Firebase Admin SDK behind the Firebase adapter, and PORT on every interface. A disposable-database harness substitutes the database (ephemeral Postgres), token verifier (synthetic) and listen port (loopback). No testkit or fake is reachable from productionEntry.ts; testing uses separate test files with harnesses. (7) **Host boundary enforcement.** Every request but /health and /readiness must carry a Host header exactly matching the allowlist (derived from SESSION_ADMIN_ORIGINS; case-insensitive; X-Forwarded-Host never read). A mismatch is a bounded 404 before the rate limiter is consulted. This requires the real edge to route only the admin hostname to this entry and pass Host unaltered or reject any other — not proven here (G-UNAUTH dependency). (8) **Health and readiness.** /health: always 200, untimed, does not gate shutdown; like every response, probes included, it gets one bounded info `request` log line. /readiness: 200 when the rate limiter, the idempotency store, the command-transaction port and the administrative admission answer their probes; 503 otherwise; the session store is read once at startup (step 9) and is not probed by /readiness; used by orchestrators to remove the instance from rotation. A 503 readiness never stops the process — a dependency outage leaves it running; the causality runs only the other way, a shutdown signal turning readiness unavailable first and then draining.

**Consequences.** The entry is composed only through the production constructor (main.ts when executed directly); harnesses substitute construction parameters. The preflight proves the runtime login's standing (new credential for G-DBROLE; SELECT on public.schema_migrations must be provisioned separately by the operator). The entry is code-only and not deployed; startup preflight is proven against disposable PostgreSQL only. The tenant boundary is not in scope for M6-ENTRY-P1; tenant routes remain undeployed. G-CPLOGIN is narrowed only in its deployable-entry part (admin boundary composed, every non-probe route on the admin host only, startup preflight) and stays OPEN (admin-host deployment, step-up DA-34, login/logout audit); G-DBROLE is narrowed only in its enforced-startup-preflight part (ledger-read privilege required) and stays OPEN; G-AUDIT stays OPEN; G-UNAUTH stays PARTIAL, and real-edge proof is one of its open items. Deferred: real-edge deployment, step-up experience (DA-34), login/logout audit, concurrent-revocation race (pre-operation requirement still blocks production session activation), tenant boundary composition. Residuals: DA-46–DA-51 (M5), carried unchanged; DA-52–DA-53 (M6-RATE-P2); new DA-54–DA-58 (M6-ENTRY-P1, doc 08). The deployment half of the trusted-proxy contract remains open (G-UNAUTH). G-IDEMPOT, G-IAM, G-DBROLE and G-MIGRATE stay open, and deployment of G-CPLOGIN awaits real-edge proof.

**Amended (M7A-CUSTOMERS-P2, ADR-33 decision 8).** A second executable serves the tenant boundary on its own host: `server/entry/tenantMain.ts` running `server/entry/tenantEntry.ts`, compiled by `tsconfig.server.tenant.json` to `dist-server-tenant` and run by `npm run start:tenant`. It reuses this entry's shared configuration judgments, construction boundary, step deadline and helpers, now moved to `server/entry/entryStartup.ts` (`validateCommonEntryConfig`, `PRODUCTION_CONSTRUCTION`), and the same `createApp`/`createBoundedServer` chain and lifecycle; the runtime database's configuration and kernel are built by `server/composition/transactionKernel.ts`, which both transaction roots share. The administrative entry is otherwise unchanged: `audiences: ['admin']`, the 8 routes of `SHIPPING_ROUTES` and its 10 steps. Its configuration step also refuses `TENANT_SESSION_ISSUER_KEY` when present (`tenant_issuer_key_present`), and its compiled artifact grows from 52 to 54 files (`transactionKernel.js`, `entryStartup.js`); it gains no tenant-entry module (`tenantEntry.js`, `tenantMain.js`, `tenantTransactions.js`) and no customer module. Injected readiness checks are now shared per `PROBE_REUSE_MS`, as the stores' probes are; the administrative entry injects none.

## ADR-28 — Step-up by same-principal reauthentication on the existing login route (DECIDED — M5-ADMIN-STEPUP-P1)

**Context.** The tenant status command requires a provider-verified authentication at most 10 minutes old, bound to the session at login and judged again inside the committing transaction (ADR-22), and refuses with 403 `step_up_required` otherwise. The only way to get a newer one was a full sign-out and sign-in, which lost the tenant the administrator was working on (DA-34). A login already verifies the token, requires the TOTP second factor and an authentication at most 5 minutes old, re-asks admission, and rotates the session — but it rotates to WHATEVER principal signed in, so nothing tied a fresh sign-in to the administrator who started the action. The provider flow is in-page (an in-memory instance, a password or Google popup, then TOTP), and the server takes the authentication time only from the verified token's `auth_time`, which a token refresh does not move.

**Decision.** (1) **One opt-in mode of the existing route.** `POST /admin/v1/session/login` sent with `X-TMPOS-Reauthenticate: 1` runs every step of an ordinary login first, then requires the presented cookie to authenticate as a valid session under the ordinary session rules that session's principal to equal the newly verified one, and its security version to equal this login's admission version. (2) **The reauthentication checks create and revoke nothing.** They run after the ordinary login steps, whose admission denial still ends every session of the principal, unchanged. No valid presented session, a different principal, or a stale security version (`login_reauth_stale_version`; the next ordinary session request revokes that session through the existing version-mismatch path) is the generic 401 of any failed login; any other header value, or a repeated header, is the same 401 and never an ordinary login; a store outage is the bounded 503. (3) **A match rotates exactly as a login does.** The presented session is revoked, never updated; the new one binds the new provider-verified authentication time once; the old cookie then answers 401. (4) **The console resumes nothing by itself.** On a definitive `step_up_required` it discards the reason and key, runs the provider's in-page sign-in inside a dialog, and after a renewed session re-reads the directory and asks for a new confirmation — a new reason, the re-read version and a new idempotency key — only if the action still applies. No redirect, storage or address state is used. (5) **Unchanged:** the route inventory, migrations 001–014 (005–014 byte-identical to the stage's entry commit), `RECENT_AUTH_MAX_AGE_MS`, the 5-minute login age, the transaction-time check, and the cookie, Origin, CSRF, host, trusted-proxy and rate-limit rules.

**Alternatives rejected.** (a) *A subject marker in the session read* — returning an identity hint from `GET /admin/v1/session` so the browser could compare it: it would put identity in an answer that carries only `{ status, csrfToken }`, and the comparison would still be the browser's. (b) *A new step-up route* (`POST /admin/v1/session/step-up`, [03 §3](./03-backend-control-plane-login-session-blueprint.md)): it would change the shipping route inventory and duplicate the login's verification, factor, age, admission and limit steps, where one header reuses them in the same order. (c) *Client-side identity comparison* — the console comparing the provider's user before and after: browser claims confer no authority, and the server would still rotate to whoever signed in. (d) *Token refresh*: a refreshed ID token keeps the old `auth_time`, so it is not a new authentication; the 5-minute login age refuses it (`login_auth_stale`).

**Consequences.** DA-34 is closed, and G-CPLOGIN is narrowed in its step-up part only; it stays OPEN (admin-host deployment and the real edge, DA-9; the login/logout audit record, G-AUDIT; the tenant boundary composition; the pre-operation security requirement). The reauthentication needs the prior session to be still valid: if it ended, the administrator signs in fully and nothing is resumed (DA-61). Recency rests on the provider's `auth_time` and the 5-minute login policy (DA-62). A reauthentication attempt spends the login client and account budgets like any login. As at an ordinary login, a store failure between revoking the presented session and creating the new one answers 503 and leaves no session, and two concurrent reauthentications presenting one cookie can both create a session (DA-61; accepted, not changed here). The tenant boundary shares the code, and no client or entry uses it there. Code-only; nothing is deployed.

**Amended (M6-ADMIN-AUDIT-P1, [ADR-29](#adr-29--administrative-session-lifecycle-audit-in-the-session-transaction-decided--m6-admin-audit-p1)).** Two statements above are stale for the administrative boundary.
- **Store failure during rotation.** Ending the presented session, creating the new one and writing the audit record are now one transaction (`establish`). A store failure before its commit answers 503, issues no cookie and keeps the presented session. Only a commit whose answer was lost can leave the browser with no usable session (DA-61(a)).
- **The old record's stamp.** Before ending the old record, the transaction rewrites its `validatedAt` with the value it just read. This takes the row lock and changes nothing, so the old record still never carries new evidence, and the old cookie answers 401 once the transaction commits.

The tenant boundary keeps revoke-then-create. The login/logout audit record is delivered for the administrative boundary only, and G-AUDIT stays OPEN.

**Amended (M5-ADMIN-REVOKE-P1, [ADR-30](#adr-30--administrative-changes-take-effect-at-commit-except-da-76-and-logins-recent-sign-ins-and-commands-are-ordered-against-them-in-their-own-transactions-decided--m5-admin-revoke-p1)).** On the administrative boundary, two concurrent reauthentications presenting one cookie no longer both create a session. `establish` must end the presented session in its own transaction, so at most one succeeds and the other answers 401 `login_reauth_no_session` (DA-61(b)). The same check now also runs at commit: a presented session that a logout or a revocation ended first refuses the reauthentication, even after it passed the checks above.

**Amended (M5-TENANT-SESSION-P1, [ADR-31](#adr-31--tenant-session-ordering-a-tenant-login-holds-its-actors-standing-until-it-commits-decided--m5-tenant-session-p1)).** The tenant boundary no longer keeps revoke-then-create. Its logins and recent sign-ins go through `establish` and its logouts through `end`, with their audit records. A tenant recent sign-in must end the tenant session it presents, so at most one of several concurrent ones succeeds (DA-61(b)). No client or entry uses the tenant reauthentication mode.

## ADR-29 — Administrative session lifecycle audit in the session transaction (DECIDED — M6-ADMIN-AUDIT-P1)

**Context.** G-AUDIT and G-CPLOGIN both left the login/logout audit record open. The administrative boundary issued sessions with two separate store transactions (revoke, then create), ended them with a third, and recorded none of it. The runtime login already holds INSERT on `public.audit_event` through `tmpos_audit_writer` (migration 005). The supervised kernel runs any number of fixed statements in one transaction, and the command store already writes its audit row on its own transaction through the existing writer (ADR-17).

**Decision.**
1. **One transaction per audited operation, with the record last.** The session store gains two operations, which the administrative boundary alone uses and requires (`session_store_audit_required` at startup otherwise).
   - `establish` (login and reauthentication) ends the live presented session, creates the new one and inserts the `audit_event` row.
   - `end` (logout) ends the live session and inserts its row.
   - The insert goes through the existing writer, and its result must be exactly one INSERTed row, or everything rolls back.
2. **Frozen vocabulary.** The three actions are `platform.admin.session.login`, `.reauthenticate` and `.logout`. Their decisions are `allow`, `allow` and `not_applicable`, and their reason codes `admin_session_created`, `admin_session_reauthenticated` and `admin_session_ended`. The server picks the action from the path it took, never from a header alone ([03 §2b](./03-backend-control-plane-login-session-blueprint.md)). The writer owns each event's entire fixed row (`ADMIN_SESSION_AUDIT_EVENTS`, `buildAdminSessionAuditEvent`), and `validateAuditEventInput` refuses any row under these three ids that differs from it in any column.
3. **Attribution.** A login row carries the actor its own admission selected. On this boundary, an admission that names no scope is a 503. A logout row carries no actor, because logout re-asks no admission, and carries the `sessionRef` the login row gave that session. The store derives both references; no database link enforces the match. Its entry type (`SessionEndAudit`) fixes the actor as null, and the store and the writer each refuse a logout entry that names one. A refusal before a trusted actor exists writes nothing.
4. **Correlation and references.** `request_id` is a server-generated operation id, which the request's log line shares. The exception is a client that disconnected before the audited step, whose request line is written at the close without the id. A login then creates nothing. A logout still runs: a session still live is ended with its row, and an info-level `session_logout_after_close` line joins the two. `trace_id` is null. Sessions are named by a one-way, domain-separated digest of the store key, never the key or the id. The writer keeps those metadata keys for these three actions only, and those actions keep no other key (a logout row may carry `sessionRef` alone).
5. **"Ended" means ended by this transaction.** A presented or ended session counts as ended here only after this transaction read it live and took its row lock. Otherwise it is not named, and a logout writes nothing and answers 204. A logout that reads nothing live still deletes any expired row under the key in the same transaction, so an instance whose clock runs behind cannot keep accepting it. Among rows written through this audited store path, at most one can claim to have ended or replaced a given session. A row inserted any other way is not covered (the runtime role holds INSERT).
6. **At logout, revocation takes priority over the record.** If `end` fails for any reason, a warning is written and then the plain revocation runs, and the answer is 204 with the record unconfirmed and logged (DA-64). If both fail, the cookie is cleared and the answer is 503, and the warning written first is kept.
7. **No migration, grant, routine or route.** Preflight's migration set and approved grants are unchanged. The PostgreSQL adapter's `create` refuses an administrative record, so `establish` is the only application path to one.

**Alternatives rejected.**
- (a) *An audit row in a separate transaction after the session commit.* A session could exist with no record, and a record could exist with no session.
- (b) *A new audited definer routine (migration 015).* It would couple session and record in the database (DA-66), but it adds a migration and a managed-apply dependency (G-MIGRATE). This is deferred, not refused.
- (c) *The client's `X-Request-Id` as `trace_id`.* A client value would be persisted forever in an append-only table ([05 §3](./05-canonical-data-ownership-and-api-db-contracts.md) requires server-generated correlation).
- (d) *The store key as the session reference.* The key is the argument the session routines accept, so an audit reader holding the runtime role could read, extend or end a live session with it.
- (e) *Failing the logout when its record cannot be written.* This would leave a session live because of an audit outage.

**Consequences.** The administrative boundary's successful login, reauthentication and logout are recorded atomically with the session change. A failure before commit keeps the presented session, and a lost commit answer is an outcome unknown (DA-61(a)). G-CPLOGIN is narrowed in its audit part and G-AUDIT for these three events. Both stay OPEN. Still open:
- the tenant boundary;
- refused attempts and revocations no user asked for (DA-65);
- the logout fallback (DA-64);
- the absence of a database-level coupling (DA-66);
- a possible lock-order deadlock (DA-67);
- the shared deadline (DA-68).

DA-35's CHECK is not triggered: the store writes only fixed sentences. The evidence is in-process plus disposable PostgreSQL (`tests/db/productionEntry.integration.test.mjs` M6AA-01–14 check the persisted rows together with the session results). Code-only; nothing is deployed, and no managed database was touched.

**Amended (M5-TENANT-SESSION-P1, [ADR-31](#adr-31--tenant-session-ordering-a-tenant-login-holds-its-actors-standing-until-it-commits-decided--m5-tenant-session-p1)).** The first item under "Still open" is delivered in code. Both boundaries now require and use `establish` and `end`, and the tenant family is `tenant.session.login`, `.reauthenticate` and `.logout` at scope `none` (`TENANT_SESSION_AUDIT_EVENTS`, built by `buildSessionAuditEvent`). The PostgreSQL adapter's `create` still refuses only an administrative record; it still writes a tenant record with no row, and no boundary calls it (DA-66).

## ADR-30 — Administrative changes take effect at COMMIT (except DA-76), and logins, recent sign-ins and commands are ordered against them in their own transactions (DECIDED — M5-ADMIN-REVOKE-P1)

**Context.** G-CPLOGIN's pre-operation security requirement left the concurrent-revocation race open. The stage reproduced it at `1e14207` against disposable PostgreSQL, through the production composition, with each competing write scheduled behind a confirmed row lock. Seven defects:
- R1a: a recent sign-in committed after the revocation of the session it presented.
- R1b: a recent sign-in committed after that session's logout (5 of 10 rounds).
- R2: a login established on an admission read taken before a grant removal.
- R3a and R3b: a tenant command committed after the logout of its own session.
- R4: a tenant command committed after a grant removal and restoration, which 009 cannot see.
- R6: a tenant command committed after an identity-anchor repoint, which nothing locked.

A plain grant removal (R5) and a refresh after logout (R7) were already safe. Each defect was contained, because the next request was refused. But a session or a mutation committed after the change that should have refused it.

**Decision.**
1. **The ordering rule.** Every administrative change — a logout, a revocation, a grant removal or restoration, an account-status change, an identity-link insert or change, or an identity-anchor change — takes effect when its transaction commits. DA-76 is the one input to the standing that is not ordered: a tenant or store status change that moves the actor across 007's 200-grant bound, which the next request refuses.
   - **R-READ.** A protected request's session is decided by its session read, and its authority by its admission read. A change committed before the read refuses the request (401).
     - A read request may complete with 200 when its session read came before a logout or revocation and its admission read came before a standing change. That includes a logout committing between its session read and its admission read, because the admission read never reads the session row: this is permitted, not a defect.
     - Nothing undoes a request that completed first. Its refresh is an UPDATE of an existing row, so it never recreates an ended session.
     - On the tenant plane, the authorizer's second read may answer 403 (DA-63).
   - **R-COMMAND.** A tenant-management command takes effect at its commit. Until then its committing transaction holds:
     - the actor's account FOR UPDATE, and its identity links and grants FOR SHARE (009, unchanged);
     - the row of the session that presented the command (a touch that changes nothing).

     Under those locks it re-reads 013's admission for that session's provider reference. It requires the recomputed witness to equal the session's, and the selected scope to equal the command's. A change committed first refuses the command: nothing is committed, and the answer is 503 `transaction_unavailable`, the store's existing non-disclosure answer (DA-70). The next request is 401. A change not yet committed waits for the command's COMMIT.
   - **R-LOGIN.** A login or recent sign-in takes effect when `establish` commits. Its transaction reads admission, takes 009's locks for the scope that read selected, reads admission again, and requires the witness to equal the new record's. Otherwise the answer is 401 `login_standing_changed`, and nothing is created, recorded or revoked.
     - A recent sign-in also requires the presented session to be, in this order, live, administrative, the same principal's, and ended by this transaction. Otherwise the answer is 401 `login_reauth_no_session`, and nothing is created, ended or recorded.
     - An ordinary login still ends whatever live session it presents, and still establishes when the presented key names none.
   - **Outage.** An outage (store, admission, lock timeout, driver fault, malformed answer) is a bounded 503. Before COMMIT it writes and revokes nothing; a COMMIT whose answer was lost stays an outcome unknown (DA-61(a)). The establish check and 009's lock throw on a fault; neither folds a fault into a changed standing.
   - **No revival.** A revoked cookie never becomes valid again: revocation is a DELETE, nothing inserts under an existing key, and the witness carries 013's authority version, which only increases.
2. **Migration 015 serializes the changer.** Some changes to an administrator's standing took no lock that 009 conflicts with:
   - an anchor repoint (the provider reference changed; no key of the account moves);
   - an identity link inserted for the actor or re-pointed to it (its foreign keys lock anchor rows, not the account);
   - in replica mode, where no foreign-key check or cascade runs, a grant inserted or re-pointed and an anchor deleted.

   The runtime cannot lock the anchor: migration 005 grants it nothing on that table. An anchor lock taken after the account would also deadlock with an anchor DELETE, whose cascade reaches the account from the other end. So 015 makes the changer wait instead:
   - One trigger function, `tmpos_admission.m5_platform_standing_serialize`: plpgsql, VOLATILE, SECURITY DEFINER, search_path pinned, granted to nobody.
   - Three BEFORE ROW triggers, enabled ALWAYS and with no WHEN condition, fire it: on `platform_identity` UPDATE and DELETE (an UPDATE locks only when the anchor or its key moves); on `identity_link` INSERT and UPDATE; on `user_membership` INSERT and UPDATE (every scope).
   - Each takes FOR KEY SHARE on the account row of every actor the write moves, in uuid order: for an anchor change, the actors before and after it; for an anchor delete, the actor it removes; for a link or grant insert, the actor it names. For a link or grant re-point it is the new actor only, because 009 already holds the row itself whenever a command holds the old actor, and locking the old actor's account after it would reverse 009's order.
   - FOR KEY SHARE conflicts only with FOR UPDATE: 009's hold, and a DELETE or key change of the account, an anchor delete's cascade included (DA-74(b)). It does not conflict with an ordinary account write (status, display name) or with another changer's FOR KEY SHARE.
   - 015 adds no table, grant, role or data change, and the runtime never calls the function. It must be applied by the owner of schema `tmpos_admission`, and its postcondition refuses when `public.app_user` forces row security (DA-72).
3. **Lock order.**
   - Runtime command: [idempotency fence] → account (FOR UPDATE) → identity links (FOR SHARE) → grants (FOR SHARE) → session row (touch) → tenant → inserts.
   - `establish`: account → links → grants → presented session → (expired-row prune) → new session → audit record.
   - Session-only transactions take session rows only.
   - Changers: their own row → the account (015, FOR KEY SHARE) → the version row (013).
   - No runtime path takes an anchor row or a version row.
4. **Required dependencies, failing closed.** `establish` throws `standing_check_missing` when the store has no standing check. The command revalidator refuses construction without the session hold and the admission read, and refuses a command that carries no session key. The session key is a SQL parameter only: it is never audited, logged, evented or returned.

**Alternatives rejected.**
- (a) *A runtime lock on the identity anchor, after the account.* It needs a new grant. It does not block a link insert, whose foreign-key lock is compatible with FOR SHARE. It stalls profile syncs. And it deadlocks against an anchor DELETE (shown by a probe in the design review).
- (b) *An in-process mutex.* It does not hold across instances.
- (c) *Keeping 009's stated carve-out* ("a link inserted concurrently may land in between"). The next request would refuse, but a command or login would still commit after a change committed before it.

**Consequences.**
- For the administrative boundary, G-CPLOGIN's pre-operation create condition and the in-transaction re-verification of sensitive commands are implemented, in code only. The clause requiring stamp updates to be conditional on the principal's current security version is not implemented: updates are conditional on liveness only. No revival or authority path was found through it (an update never recreates a deleted row, and every administrative request re-reads admission and compares the witness). Amending that clause, or implementing a version-conditional update, is an open owner decision (DA-77). G-CPLOGIN stays OPEN. It stays unmet for the tenant boundary, whose login revokes and then creates with no standing re-read, and which no entry composes.
- DA-61(b) is closed for the administrative boundary: at most one of several concurrent reauthentications presenting one cookie succeeds (ADR-28, amended above).
- DA-63 is resolved as a classification: a fail-closed 403 that the test now proves rather than tolerates. The stage's M5A-09/09b runs predate the final runtime and 015; the final verification and CI re-run them. DA-49's last sentence is superseded.
- The startup preflight's ledger step (ADR-27, step 5) now requires exactly 001–015; the approved runtime grants are unchanged. D4's future managed apply names the contiguous chain through 015, and 005–014 are byte-identical to the stage's entry commit.
- Residuals: DA-70 to DA-77, among them 015's operator waits and row-security reliance, replica mode, the operator-vs-operator deadlocks, a pre-existing tenant-delete deadlock, the 200-grant bound and the stamp-update clause (DA-77). DA-67 is unchanged: `establish` still touches the presented session before its prune, and a principal-wide revocation takes no account lock.
- The evidence is disposable PostgreSQL only. `tests/db/adminRevocation.integration.test.mjs` runs two production roots on two kernels; it failed 13 of 27 at the base, and passed 27 of 27 in three runs on this stage's code with 015 at `0ed1a314…`, before the final change to 015, which only adds the refusal unless the applier owns schema `tmpos_admission`. The stage's final verification and CI re-run it on the committed bytes. `tests/db/platformAdmission.integration.test.mjs` M5P-09–11 cover 015. Code-only; nothing is deployed, and no managed database was touched.

**Amended (M5-TENANT-SESSION-P1, [ADR-31](#adr-31--tenant-session-ordering-a-tenant-login-holds-its-actors-standing-until-it-commits-decided--m5-tenant-session-p1)).** The first consequence's last sentence is stale. The tenant login no longer revokes and then creates: it is one `establish` transaction that holds its actor's standing and re-reads it (ADR-31). The tenant boundary is still composed by no entry.

## ADR-31 — Tenant session ordering: a tenant login holds its actor's standing until it commits (DECIDED — M5-TENANT-SESSION-P1)

**Context.** ADR-30 ordered the administrative boundary only. The tenant login read admission in its own transaction (011's read, which takes no lock), then revoked the presented session and created the new one in two more transactions. It re-read no standing where it wrote, and it wrote no audit record (DA-65). The stage's race suite (`tests/db/tenantSessionOrdering.integration.test.mjs`, then 42 tests, two production roots on two kernels over one disposable database) reproduced this on the base `a4328974`: 16 passed, 25 failed and 1 was skipped (M5T-I2: no hold exists to fault before 016). The failures:
- A login committed after a suspension, a grant removal, a role change, an account-status change or an anchor repoint that committed between its admission read and its write (M5T-C1, M5T-E1a–E1d). None of those changes waited for a login in flight (M5T-C2, M5T-E2a–E2d).
- A recent sign-in committed after the logout of the session it presented, and three concurrent recent sign-ins presenting one cookie all succeeded (M5T-F1, M5T-F3, M5T-K3). A logout after a recent sign-in could not report that it ended nothing (M5T-F2, M5T-K4).
- A session idle across a grant suspended and restored, a grant deleted and re-inserted under its id, a raw owner tenant status round trip, or a store suspended and reactivated was served again on its old witness (M5T-D2–D4, M5T-H2; DA-41).
- No login, recent sign-in or logout wrote a record (M5T-A2, M5T-J1, M5T-J2, M5T-J4, M5T-J5, M5T-I4).

A review of the first draft of 016, which moved access versions on status changes only, found three more revivals of an idle store session, each reproduced against that draft before it was fixed: its store moved to another tenant and back, and its store or its tenant row deleted and inserted again as a replica (M5T-H3–H5). The review found a fourth path, closed by the final 016: a tenant's or a store's key changed as a replica, then a row inserted under the old key, which starts its version again (a store at 1, a tenant at whatever its INSERT names) and so can answer a grant still naming that key with the version it was admitted at (for a store, a session admitted at 1) (`tests/db/tenantAdmission.integration.test.mjs` M5A-16b).

**Decision.**
1. **The ordering rule.** Every tenant-plane standing change takes effect when its transaction commits (for every writer but the owner acting outside 016's rules, DA-41's residuals): a change to the account (its status or any other column), an identity link or anchor change, a grant of any scope inserted, changed, removed, restored or re-pointed, a tenant or store status change, a store moved to another tenant, and a tenant or store deleted (a tenant's or a store's key never changes: 016 refuses the UPDATE). A tenant login or recent sign-in is ONE store transaction (`establish`), and it is ordered against those changes there.
   - **R-LOGIN.** The transaction's first step is `tmpos_session.m5_hold_tenant_standing` (016). It resolves the provider reference's one anchor and locks, until COMMIT and in this order: the account (`app_user`) FOR UPDATE; its identity links FOR SHARE, in `link_id` order; every grant of any scope and status (`user_membership`) FOR SHARE, in `membership_id` order; every tenant any grant names FOR SHARE, in `tenant_id` order; and every store any grant names FOR SHARE, in `store_id` order. It answers `absent` (no anchor, or no account) or `held`, and returns nothing it read. The next statement re-reads `m5_admit_tenant_session_v2` on a new snapshot, taken after every lock was granted. The recomputed `t2:` witness must equal the one the new record carries, which the login's own admission read produced before the transaction began. Otherwise (a changed witness, a refusal, or `absent`) `establish` answers `standing_changed`, the login is 401 `login_standing_changed`, and nothing is ended, created or recorded.
   - **Who waits on the hold.** An account UPDATE or DELETE (its row). An UPDATE or DELETE of the actor's links or grants (their rows). A grant inserted for, or re-pointed to, the actor (its foreign key's KEY SHARE on the account; 015's trigger in replica mode). An identity link inserted for, or re-pointed to, the actor, and an anchor changed or deleted (015's triggers, or their foreign keys). An UPDATE of a tenant or store that a grant names, 010's status command included (FOR SHARE against the row lock). A DELETE of such a tenant or store (its row, and the cascade). Each waits for the login's COMMIT, and the next protected request re-reads admission and refuses when the standing moved. A change committed before the re-read refuses the login.
   - **R-RECENT-SIGN-IN.** A recent sign-in also requires the presented session to be, in this order, live, of the tenant audience, the same principal's, and ended by this transaction. Otherwise `establish` answers `session_ended` with nothing written (401 `login_reauth_no_session`). So at most one of several concurrent recent sign-ins presenting one cookie succeeds, and one whose session a logout ended first is refused. An ordinary login still ends whatever live session it presents, and still establishes when the presented key names none. Only a presented tenant session that this transaction ended is named as replaced.
   - **R-READ.** Unchanged from ADR-30. A protected tenant request's session is decided by its session read, and its authority by its admission read (and the authorizer's own read, which may answer 403, DA-63).
   - **Outage.** A fault in the hold or the re-read, a malformed answer, or a lock or statement timeout throws. The login is a bounded 503 that ends, creates and records nothing. A COMMIT whose answer was lost is a 503 with the outcome unknown: the session and its record may exist, but its id was never delivered. Neither the hold nor the check folds a fault into a changed standing.
   - **No revival.** The `t2:` witness is a digest over the actor, the account status and its cap, 007's security version, 013's platform authority version, 016's tenant grant version, and for each grant its id, scope, tenant, store, role, tenant and store status, and tenant and store access version. Every input that could return to an earlier value now sits beside a counter that only increases (DA-41, closed in code).
2. **Migration 016 (`016_m5_tenant_session_ordering`).** One column, one table, two trigger functions, five triggers, two routines and two grants; no role. Every trigger is a row trigger enabled ALWAYS, so a replica's write fires it too.
   - `public.store.access_version` (bigint, default 1, CHECK 1..2^53−1). `tmpos_session.m5_access_version_moved` (SECURITY INVOKER, granted to nobody) fires BEFORE UPDATE on `public.tenant` (`trg_tenant_access_version`) and BEFORE INSERT OR UPDATE on `public.store` (`trg_store_access_version`). An UPDATE that changes the row's status, or a store's `tenant_id`, moves its access version by exactly one, whatever value the UPDATE named, and raises 22003 at the bound; any other change to the version is refused (23514). An UPDATE that would change a tenant's `tenant_id` or a store's `store_id` is refused outright (23514), whoever makes it, as a replica too: a version cannot follow its key, and a key is retired by deleting its row, which moves the grant version of every actor whose grant names it (below). A store INSERT is set to 1, whatever it names. 010's command still moves the tenant version exactly once.
   - `tmpos_session.tenant_grant_version`: one counter per actor, no foreign key, row security on with no policy, and no runtime privilege. `tmpos_session.m5_tenant_grant_moved` (SECURITY DEFINER, granted to nobody) fires AFTER INSERT, UPDATE and DELETE on `public.user_membership` (`trg_user_membership_tenant_grant_version`): it adds one for each actor whose tenant- or store-scope grant a write creates, removes or changes, cascaded deletes included. A change to `updated_at` alone moves nothing, and platform-scope grants stay on 013's version. It also fires AFTER DELETE on `public.tenant` and on `public.store` (`trg_tenant_tenant_grant_version`, `trg_store_tenant_grant_version`): it adds one, once per actor, for each actor holding a tenant- or store-scope grant of any status that names the deleted key. As a replica no cascade removes those grants, so a row inserted again under that key would otherwise return them with their old witness; in an ordinary session the cascade has already removed them, each moving its actor, and this move finds none.
   - `m5_admit_tenant_session_v2` (STABLE SECURITY DEFINER) answers 011's read plus each grant's store access version and the actor's two counters, in one snapshot. `m5_hold_tenant_standing` is VOLATILE SECURITY DEFINER. `tmpos_app` gets EXECUTE on these two and nothing else. 011's `m5_admit_tenant_session` stays and stays granted, but the adapter no longer calls it.
   - Up and down each refuse while any tenant session row exists, under SHARE ROW EXCLUSIVE on the session table (013's rule), because a rollback and re-application restart every store version at 1 and every grant version at 0.
3. **Lock order.**
   - Tenant `establish`: account (FOR UPDATE) → links → grants → tenants → stores (FOR SHARE) → presented session → new session (whose create prunes the principal's long-expired rows) → audit record.
   - Administrative `establish` and commands: unchanged (ADR-30). Both orders begin account → links → grants, so an actor holding both kinds of grant serializes at the account.
   - Changers: their own row first. The grant trigger then upserts the grant version, after 013's version row when a write moves both.
   - 016's apply and rollback: the session table first, then `public.tenant`, `public.store` and `public.user_membership`, the opposite of a login's order (DA-79).
   - A writer that updates a tenant or store row and then a grant of the same actor in one transaction, or any multi-row write in the opposite order to the hold's (a normal-mode tenant or store delete cascading through grants in its own order included), takes the rows in the opposite order to a login. PostgreSQL aborts one side of such a deadlock, which commits nothing: the login answers 503, or the writer's change is rolled back while the login's standing was current (DA-78). No other such pair was found among the writes of 009, 010, 013 and 015.
4. **Required dependencies, failing closed.** The transaction root builds one standing check for its one session store and dispatches on the record's audience: `createPlatformEstablishCheck` for an administrative record, `createTenantEstablishCheck({ hold: holdTenantStanding, read: readTenantAdmission })` for a tenant one, and a throw for anything else. `establish` without a check still throws `standing_check_missing`. The runtime now requires `establish` and `end` from both boundaries' stores (`session_store_audit_required` at startup otherwise). The tenant admission answers `{ admitted, securityVersion, actor }`, and a login whose admission names no actor (or an actor that is not a lowercase UUID) is a 503 before anything is written. On both boundaries only `false` (what both composed admissions answer) or `{ admitted: false }` is a denial, which refuses and then ends every session of the principal (a failed revocation is logged `*_admission_denied_unrevoked`); any other malformed answer (another non-object, an `admitted` that is not a boolean, an admission without a valid version) is `admission_unavailable`, a 503 that revokes nothing, where the base read it as a denial. `postgresTenantAdmission.ts` treats as an outage a refusal row carrying any value, and any version that is not canonical decimal text in range (access versions 1..2^53−1, the two counters 0..2^53−1); `holdTenantStanding` refuses a malformed reference as `false` before any statement (M5T-TA3b). On the administrative plane, `postgresPlatformAdmission.ts` and `platformStandingOf` likewise accept 013's authority version only as canonical decimal text in 0..2^53−1, and anything else is an outage (M5PA-08b, M5PS-05b).
5. **Audit.** Each tenant `establish` and `end` writes one `audit_event` row in the same transaction as its session change, from the tenant family `TENANT_SESSION_AUDIT_EVENTS` (`auditEventWriter.ts`): `tenant.session.login` and `tenant.session.reauthenticate` (`allow`), and `tenant.session.logout` (`not_applicable`). The store takes the family from the new record's audience at `establish` and from the ended session's at `end`. Every column is fixed as its administrative counterpart's, except that `scope_type` is `none` and `tenant_id` and `store_id` are null: a tenant session selects no scope at login. The actor is the internal user the tenant admission resolved, and null at logout. The metadata keys are the same three (`sessionRef`, `replacedSessionRef`, `authenticatedAt`). The logout fallback is ADR-29's (DA-64).

**Alternatives not taken.**
- (a) *009's locks alone, as the administrative check takes them.* They hold the account, links and grants but no tenant or store row, so a tenant or store status change would not be ordered against a login (DA-76's class).
- (b) *A per-actor advisory lock.* An advisory lock binds only the transactions that take it. A raw owner write, 010's command or a cascade would pass it unless every writer were changed to take it too, and the row locks and triggers already make them wait.
- (c) *SERIALIZABLE for `establish`.* PostgreSQL's serializable guarantee holds only among transactions that all run SERIALIZABLE, and nothing requires the writers it would have to be ordered against (010's command, operator writes, cascades) to run at that level. It would also turn contention into serialization failures that must be retried.
- (d) *An in-process mutex.* It does not hold across instances (ADR-30).

**Consequences.**
- G-CPLOGIN's pre-operation create condition is implemented for the tenant boundary too, in code only. The stamp-update clause is not implemented here either: tenant stamps are conditional on liveness only, and every protected tenant request re-reads admission (DA-77). No tenant business route exists, so there is no sensitive tenant command to re-verify (DA-39). G-CPLOGIN stays OPEN, and no entry composes the tenant boundary.
- DA-41 is closed in code; its residuals are owner writes outside every runtime role (the grant version table written directly, 016's triggers disabled or dropped, a tenant row inserted at any access version). DA-65 is delivered for the tenant audience: tenant logins, recent sign-ins and logouts are recorded, and the same unaudited classes remain. DA-61(b) is closed for the tenant boundary. DA-61(a), DA-64, DA-66, DA-67, DA-68 and DA-71 now describe the tenant boundary too. DA-76 does not reach the tenant login, whose hold covers every tenant and store its actor's grants name. New: DA-78 to DA-82, among them the waits and deadlocks the hold adds (DA-78, DA-79), the runtime role's store INSERT, closed in code by the trigger (DA-80), out-of-order rollbacks beneath 016 (DA-81) and the hold as a lock any runtime caller can take (DA-82).
- The startup preflight's ledger step requires exactly 001–016, and `APPROVED_ROLE_GRANTS` adds the two EXECUTE grants. D4's future managed apply names the contiguous chain through 016. 005–015 are byte-identical to the stage's entry commit.
- **Stores.** Store access versions are closed in code, and the race suite's M5T-H2–H5 assert the idle store session refused after a suspension and reactivation, a move to another tenant and back, and its store or its tenant row deleted and re-inserted as a replica (M5T-H6 is the control: a store no grant names moving changes nothing). A store login is ordered as a tenant one is: a store suspension committed after its admission read refuses it with 401 `login_standing_changed`, nothing created or recorded (M5T-H7), and one issued while the login holds the store waits for its COMMIT, after which the next request is 401 (M5T-H8). M5A-16b asserts a store's key, like a tenant's, never changes. A tenant-scope grant carries no store version by design, so a store of its tenant changing leaves a tenant-scope session's witness as it was. No store route and no store permission is in production: every tenant and store permission is undecidable, and startup refuses any tenant- or store-scope requirement (`route_permission_undecidable`). The deployable entry still composes `audiences: ['admin']` only. G-IAM and G-AUDIT stay OPEN.
- The evidence is disposable PostgreSQL only. The race suite failed 25 of its then 42 tests on the base, and now has 48; the stage's final verification and CI run it on the committed bytes. `tests/db/tenantAdmission.integration.test.mjs` M5A-14–M5A-20 cover 016 (its objects and grants, the session refusals, both trigger functions and all five triggers, v2, the hold's lock modes and six of its waiters, and the widenings its postcondition refuses), and M5A-05b now asserts the store case closed. Code-only; nothing is deployed, and no managed database was touched.

## ADR-32 — The first tenant route lists one tenant's customers through a definer read that re-confirms its grant (DECIDED — M7A-CUSTOMERS-P1)

**Context.** No durable customer model existed: the shop app keeps its customers in browser memory (`StoreLocalState.customers`, [05 §2](./05-canonical-data-ownership-and-api-db-contracts.md)). The tenant boundary had a durable session store, an admission and an authorizer (ADR-23, ADR-31) and no business route. Every tenant- and store-scope permission was undecidable until owner decision D1 named a route and its rule, and startup refused any route requiring one (`route_permission_undecidable`; doc 08 DA-39). M5-TENANT-SESSION-P1 proposed a read-only customer list as that route: Option A at tenant scope, Option B at store scope. This stage builds Option A with the minimal customer identity only, an id and a name.

**Decision.**
1. **The contract.** `GET /api/v1/customers` (`server/runtime/customerDirectory.ts`) is a session route of the tenant boundary under `view_customers` at tenant scope. It declares `trustedContext: 'required'`, no body, no idempotency and no recent sign-in.
   - It is a read. A composition that serves it must list it in the tenant authorizer's read classification (`reads`); then a read-only actor may use it, because the materializer's read-only cap holds every domain at View at most, and View meets the threshold. The module refuses to load if any tenant route permission is not a non-sensitive View read. Without that entry a read-limited actor is refused 403 (DA-87).
   - The query allows only `limit` (1–100, default 50, canonical decimal) and `cursor`, each at most once. Any other key, a repeat, an empty pair, an encoding, a non-canonical spelling or a query over 128 characters is 400 `invalid_request`, before any port is asked.
   - The answer is `200 { customers: [{ id, name }], nextCursor }` and nothing else: no tenant, store, role or grant, and no email, phone, group, tier, total spent or other money value.
   - Refusals keep the chain's generic bodies. Session refusals are the chain's 401s. A lost grant is 403 `forbidden`. An outage, a timeout or an answer out of shape (a row naming another tenant, or entries out of page order, included) is a bounded 503 `service_unavailable`, never a cached, partial or synthetic page.
2. **The tenant comes from the trusted scope alone.** The tenant authorizer selects the actor's one active tenant-scope grant (none or several deny) and hands that scope to the route. The tenant is never read from the path, the query, a header, the cursor or a body.
3. **The permission (owner decision D1 for this route).** `view_customers` is a new canonical tenant ROUTE permission (`TENANT_ROUTE_PERMISSIONS`, `server/platform-identity/m5CanonicalPermissions.ts`): the Customers domain at View or above.
   - `evaluateCanonicalPermission` decides it with the catalog's existing materializer: `materializeTenantPermissions(role, {}, read-only)`, then `meetsTenantPermissionLevel(level, 'view')` on the tenant family ordering. There is no second evaluator and no role-name branch. Customers is a core domain, so the empty entitlement set changes nothing. A role the materializer does not know, a platform role included, is denied.
   - `isDecidablePermission` answers true for it at tenant scope only. Every other tenant or store key stays `undecidable`, and `uncataloguedRoutePermissions` (`server/composition/productionTransactions.ts`) still refuses a deployment that requires one (`route_permission_undecidable`). At store scope `view_customers` names no permission (`route_permission_uncatalogued` at startup, denied at run time).
   - All four durable tenant roles, the only ones migration 003 admits, hold Customers at View or above by default: `store_owner` Full (the catalog's owner definition), `manager` Full, `technician` View and `sales_staff` Create. A platform grant or a store grant never satisfies it, because the authorizer counts only tenant-scope grants for a tenant route.
   - `createTenantRouteAuthorizer` (`server/composition/tenantAuthorization.ts`) now decides the selected grant's role wherever the catalog decides the key. For an undecidable key it behaves as before, and production refuses such a route at startup.
4. **Persistence: migration 017 (`017_m7a_customer_directory`).** It owns its own schema, `tmpos_customer`, as 011, 012 and 013 own theirs.
   - One table, `tmpos_customer.customer`: `customer_id` uuid primary key, `tenant_id` uuid NOT NULL referencing `public.tenant` (NO ACTION, so a tenant holding customers cannot be deleted), and `name` text COLLATE "C" under migration 009's character rules for a tenant display name, with a 200-character limit where 009 allows 120: 1–200 characters; no C0 control, DEL, C1 control, U+2028 or U+2029; no Bidi_Control character; and no leading or trailing whitespace (so a name of whitespace alone is refused too). Names made only of invisible characters still pass (DA-92). One index, `(tenant_id, name, customer_id)`. Row security is enabled with no policy, and no runtime role holds any privilege on the table.
   - One routine, `tmpos_customer.m7a_customer_page`, `STABLE SECURITY DEFINER`, with its search path pinned to `pg_catalog, pg_temp` and `row_security = off`. Its owner is not subject to the table's row security, so the setting changes nothing today; but were row security ever FORCED on the table, the routine would fail (a 503) rather than answer empty pages. It takes the trusted scope's actor, security version, membership, role and tenant, and re-confirms, in the same snapshot as the page:
     - the account exists and its status is on the allow-list `active`, `trialing`, `overdue` or `read_only`;
     - 007's security version is equal;
     - the actor holds exactly one active tenant-scope grant, counting only grants on a tenant that is not `suspended` or `pending_activation`, which is the set 007's resolver answers, so the routine and the authorizer count the same grants;
     - that grant is the named membership with the named role on the named tenant;
     - and the tenant's status is on the same allow-list.
     It decides no permission. It answers `invalid`, `denied` or `cursor_unknown` as a single row, or up to 101 customer rows, each carrying its tenant id beside the customer id and name.
   - It refuses to apply unless 016, 007 and 005's `tmpos_app` are in place, the applier can execute 007's security version, and the applier holds the owner's privileges on `public.tenant`, `public.app_user`, `public.user_membership` and `public.identity_link` (which 007's security version reads), none of them under forced row security.
   - `tmpos_app` holds USAGE on the schema and EXECUTE on the routine, and nothing else from 017. The file's postcondition requires three things. The routine carries its two settings. The table has row security enabled and not forced, with no policy. And `tmpos_app` does hold that EXECUTE and USAGE. It refuses any wider grant and any column grant. It refuses any runtime role (`tmpos_app`, `tmpos_audit_writer`, `anon`, `authenticated`) that is a member of an owner of the schema, the table or the routine, or that holds an effective privilege on the table by any path, a predefined role such as `pg_read_all_data` included (011's check).
   - The down file refuses (55000) unless it runs under READ COMMITTED, so that its check sees every committed row. It sets `row_security = off` before that check: otherwise, were row security forced on the table for an applier without BYPASSRLS, the check would see no row and the rollback would drop customer records. With the setting, PostgreSQL refuses the query (42501) and nothing is dropped. It takes ACCESS EXCLUSIVE on `public.tenant` and then on the customer table (the table's DROP takes the first lock anyway, through its foreign key). That order avoids a deadlock with page reads only. A customer INSERT (only tests write one today) takes the opposite order and can deadlock with the rollback; PostgreSQL detects it and aborts one side, and nothing is lost. While the rollback runs no login, admission or command can use `public.tenant`, so it belongs in a maintenance window. It refuses (55000) while any customer row exists, so a rollback never deletes business records, and otherwise drops exactly the routine, the table and the schema. While any customer row exists the chain cannot roll back past 017 at all, because 005's rollback (which drops `tmpos_app`) and 002's (which drops `public.tenant`) fail while 017's grants and foreign key remain.
   - The PostgreSQL adapter (`server/persistence/postgresCustomerDirectory.ts`) asks for `limit` + 1 rows to learn whether another page follows. It throws, which the route turns into a 503, on any answer out of shape. That covers any row that does not name the admitted tenant, a second tenant check independent of the routine's filter. It also covers any row out of strictly increasing (name bytes, id) order, the look-ahead row included, which the route never sees. The runtime validates the answer again before any of it reaches a response and refuses (503) a page out of that order, or with a name that is not 1–200 characters (code points) of well-formed UTF-16.
5. **The cursor.** It is opaque: 23 unpadded base64url characters encoding a tag byte (0x02, distinct from the tenant directory's) and the last customer's id, accepted only in its one canonical spelling. It carries no authority and no tenant. The routine looks its position up only among the admitted tenant's customers, so a cursor naming another tenant's customer, a deleted one or an unknown id is the same 400 and discloses nothing. The page is a keyset over `(name, customer_id)` under "C", a total order, so while no name changes (no rename path exists, DA-84) no customer appears on two pages.
6. **Availability.** The route factory and the adapter are repository code, composed and proved only in a tenant composition over local sockets (`tests/db/customerDirectory.integration.test.mjs`). The deployable entry (`server/entry/productionEntry.ts`) still composes `audiences: ['admin']` only, `SHIPPING_ROUTES` is unchanged, and the route is not in `PRODUCTION_INVENTORY`. No deployment serves it until a tenant host is composed. That needs a tenant hostname and origin, the tenant session composition, and a shipping inventory that includes the route. It also needs the tenant authorizer's read classification to include `GET /api/v1/customers`, and a customer port among the read ports the transaction root (`productionTransactions.ts`) builds, which today hold only the tenant directory's (DA-87).
7. **Audit.** The read writes no audit event (owner decision). The request log names the route's path, never its query, with the status and a bounded reason, and never carries customer data. Whether reads of personal-data lists are audited is recorded open (doc 08 G-AUDIT, DA-88).

**Alternatives not taken.**
- (a) *Row security keyed on migration 005's session variables.* The runtime sets `app.tenant_id` and `app.scope_type` itself, so they prove nothing about which tenant a request was admitted to (DA-29).
- (b) *A direct SELECT grant to `tmpos_app`.* Row security with no policy shows a grant no row, so a grant would need a row policy to confine it, and the only one available is (a)'s.
- (c) *A cursor carrying the name.* It would put personal data in URLs, browser history and proxy logs.
- (d) *A signed or encrypted cursor.* It needs a key this stage may not introduce. The tenant-scoped lookup already confines a forged cursor to the admitted tenant's own customers.
- (e) *A store-scope route (Option B).* Not decided. Staff holding only store grants are refused (DA-87).

**Consequences.**
- G-IAM stays OPEN. The first tenant-plane permission is decided in code, but no deployment serves the route (DA-87), and the server decides it from the four built-in roles' catalog defaults, so a role an owner edited in the client is not honoured server-side and no durable custom-role store exists (DA-85).
- G-PERSIST stays OPEN. 017 holds the minimal customer identity only: no write path, PII classification, retention, DSAR behaviour or data cutover exists, and the shop app still keeps customers in browser memory.
- G-AUDIT stays OPEN: the read-audit decision is open (DA-88). G-CPLOGIN is unchanged and stays OPEN.
- G-DBROLE stays OPEN. The routine's re-check refuses stale authority but is not a boundary against the runtime credential (DA-83, the class of DA-45).
- G-MIGRATE stays OPEN. The startup preflight's ledger step requires exactly 001–017, so this code refuses to start until 017 is applied (DA-87), and `APPROVED_ROLE_GRANTS` names the two new grants. D4's future managed apply names the contiguous chain through 017. 005–016 are byte-identical to the stage's entry commit.
- A continuation's position is its customer's current name (DA-84), and the order is byte order under "C", not locale-aware (DA-86). Also recorded: the canonical permission maps are frozen Maps whose contents stay mutable (DA-89); 014's rollback has the forced-row-security blind spot 017's now closes (DA-90); the DEV bootstrap rollback example fails while its tenant has customers (DA-91); and names of invisible characters alone pass 017's rule (DA-92).
- The evidence is disposable PostgreSQL only. Code-only; nothing is deployed, and no managed database was touched.

**Amended (M7A-CUSTOMERS-P2, ADR-33).** Decision 4's grant is revoked: `tmpos_app` no longer executes `m7a_customer_page`. The route reads through migration 018's `m7a_customer_page_v2`, bound to the presenting minted session, which calls 017's page as its owner for the authority it derives. The contract in decisions 1, 2 and 5 is unchanged, and so is the adapter's check of every row against the authorizer's tenant. The fourth consequence is superseded: DA-83 is contained against the runtime credential alone, not closed. In the fifth, the ledger step now requires exactly 001–018, and D4 names the chain through 018. Decision 6 (Availability) is superseded by ADR-33 decision 8: the compiled tenant entry serves the route in code, lists it in the tenant authorizer's read classification and builds its customer port over the shared kernel; it is not deployed (DA-87).

**Amended (M7A-CUSTOMERS-P3, 2026-09-28, ADR-34).** Decision 3 now has a second decided key. `create_customers` (the Customers domain at Create or above, tenant scope only) authorizes `POST /api/v1/customers`, decided by the same materializer and ordering, with no role default changed. Every other tenant or store key stays `undecidable`. The module's load-time guard (decision 1) now admits a non-sensitive route permission at View or Create, not only a View read, and states the read-only rule where it is enforced: under a `read_only` limitation only a View route permission is granted, so `create_customers` is denied. The G-PERSIST consequence's "no write path" is superseded: customer creation exists in code, not deployed. PII classification, retention, DSAR behaviour and the data cutover still do not exist. DA-92 is dispositioned for new writes (ADR-34 decision 9). The GET's contract, tenant source and cursor (decisions 1, 2 and 5) are unchanged. In the fifth consequence, the ledger step now requires exactly 001–019.

The authorizer reads the owner's stored Customers level for that grant's tenant and role (migration 020's `tmpos_role.m7a_role_levels`) on every decided request and hands it to the materializer, which applies it before the entitlement gate and the read-only cap; the levels are required, and a missing or malformed answer denies. The first consequence's "a role an owner edited in the client is not honoured server-side" is narrowed, not superseded: an owner's edit through `PUT /api/v1/roles/levels` is honoured, and an edit in the shop app still is not (doc 08 DA-85, DA-124). In the fifth consequence, the ledger step now requires exactly 001–020.

## ADR-33 — A tenant session exists only when the issuer-key holder mints it, and the customer read is bound in the database to that session (DECIDED — M7A-CUSTOMERS-P2)

**Context.** Doc 08 DA-83: `tmpos_app` could execute migration 007's resolver, which answers any provider UID's actor, security version, membership and role, and 017's `m7a_customer_page`, which takes exactly that tuple as its authority. SQL running as the runtime role alone (a leaked `APP_DATABASE_URL`, an injection) could therefore list any tenant's customers. The same role could execute 011's `m5_session_create` and create a session for any principal. The test for this stage is possession of the runtime database role alone, so nothing that role can produce proves anything: a session variable, a request identifier, an obscured identifier or an application-only assertion. The database cannot verify an identity provider's token without an extension this stage may not add. The proof chosen is therefore a key the role can neither read nor write. This is the first of the stage's two commits, the database boundary; the tenant entry that composes the key is the second.

**Decision.**
1. **Migration 018 (`018_m7a_tenant_session_mint`) owns its own schema, `tmpos_mint`.** 016's rollback refuses unless `tmpos_session` holds exactly six routines, and older rollbacks drop their schemas without CASCADE (017's reason). 018 creates:
   - `tmpos_mint.issuer_key`: at most one row (`singleton`), with `key` bytea of 32–64 bytes. Only the owner writes it.
   - `tmpos_mint.tenant_session`, the mint ledger: `session_key` (011's key shape), `standing_digest` and `issuer_digest` (32 bytes each) and `expires_at`, with `tenant_session_expiry_idx (expires_at)`. It has **no foreign key**. A row outlives its session until a day after its expiry, so while it is kept a captured mint cannot re-create a session that ended; a replay after that yields an already expired session, which reads nothing.
   - Two helpers granted to nobody: `hmac_sha256` (RFC 2104 from core `pg_catalog` functions only; a key over 64 bytes is refused) and `mint_message`.
   - Three routines `tmpos_app` may execute: `m7a_session_create` (`VOLATILE SECURITY DEFINER`), `m7a_customer_page_v2` (`STABLE SECURITY DEFINER`, `row_security = off`) and `m7a_issuer_key_check` (`STABLE SECURITY DEFINER`). Each pins its search path to `pg_catalog, pg_temp`.
   - It revokes `tmpos_app`'s EXECUTE on 011's `m5_session_create` and on 017's `m7a_customer_page`. Those two ACL changes are its only effect on earlier objects, and 001–017 are byte-identical.
   - Both tables have row security enabled, not forced, with no policy, and no runtime role holds a privilege on either. The apply-time postcondition proves the inventory; each routine's security, volatility and settings; every table, column, routine and schema ACL; that `tmpos_app` can execute the three and cannot execute 011's create, 017's page or a helper; that no runtime role (`tmpos_app`, `tmpos_audit_writer`, `anon`, `authenticated`) is a MEMBER of an owner, a `NOINHERIT` membership included; and that none holds an effective privilege on either table by any path (MAINTAIN too, on PostgreSQL 17 and later).
2. **Every session the runtime creates goes through `m7a_session_create`.** It first checks every argument of either audience against 011's table CHECKs. A mismatch answers `invalid` and writes nothing, so no caller value can reach a constraint violation's DETAIL in the server log.
   - *Administrative audience.* The proof must be NULL. The call is then 011's create, unchanged, so administrative minting stays unproven (doc 08 DA-95, DA-37).
   - *Tenant audience, in this order.* (i) A 32-byte proof, a lifetime of at most eight hours (`SESSION_TTL.tenant`) and a creation at most 60 s ahead of the database clock, or `invalid`. (ii) The proof, before any session or principal state is read: `refused` when no key is installed or the proof is not `HMAC-SHA256(key, message)`, compared as SHA-256 digests with `is distinct from`. (iii) The standing: the SHA-256 of the text of 016's `m5_admit_tenant_session_v2` row for the principal, as the database computes it. (iv) `conflict` when a session row of either audience already has the key. (v) Ledger rows a day past their expiry are pruned. (vi) The ledger row, or `conflict` if one exists. (vii) 011's create; anything but `created` raises (a same-key race) and takes the ledger row back with the transaction.
   - The message is the UTF-8 prefix `tmpos-tenant-session-mint:v1` followed by the row's eleven values as netstrings in a fixed order; a missing `authenticated_at` is the empty string. The runtime builds the same bytes (`tenantMintProof`, `server/persistence/postgresSessionStore.ts`).
   - The session store takes the key as `issuerKey`. It refuses anything but 32–64 bytes at construction and keeps a private copy. A store without it writes administrative sessions only: a tenant write throws `issuer_key_missing` before any statement. Any outcome but `created` is `not_created`, a 503 that issues nothing.
   - The mint does not require an admission of `resolved`, a creation near now or an expiry still ahead, so the port's conformance records mint and read nothing.
3. **The customer read takes one authority argument: the session's store key.** `m7a_customer_page_v2(p_session_key, p_after_customer_id, p_limit)` answers `invalid` for a key not of 011's shape. It answers `denied` unless all of these hold:
   - the session row has a ledger row, is of audience `tenant`, carries the ledger's own `expires_at`, and is live on `statement_timestamp()`;
   - its ledger issuer digest equals the SHA-256 of the key installed now (no key denies every read);
   - 016's answer for its principal is `resolved` with the minted standing digest;
   - that answer holds exactly one tenant-scope grant.

   It then calls 017's page as its owner with the actor, security version, membership, role and tenant it derived. 017's re-check, keyset, cursor rule and answers run unchanged, so the P1 pagination and error contract is unchanged (M7M-08). The store key is the SHA-256 of the cookie's identifier (`digestOf`): no routine returns it, and `tmpos_app` cannot select it.
   - A route may now declare `sessionBinding: 'required'` (`server/runtime/routes.ts`). Startup accepts it only on a session route with a declared authorization, `trustedContext: 'required'` and `idempotency: 'none'`, and refuses anything else (`route_session_binding_invalid`). Such a route's handler receives `ctx.sessionKey`, which is null on every other route. This is the one declared exception to the rule that the key reaches no handler (`server/runtime/app.ts`). In the runtime the key is a SQL parameter only, never logged, echoed or stored, and the request log never includes the context; a database log that captures bind parameters is doc 08 DA-102.
   - `GET /api/v1/customers` declares it. Its handler refuses a null key with 403 (`authz_context_missing`). The adapter (`server/persistence/postgresCustomerDirectory.ts`) refuses a key not of the store-key shape before any statement, and still refuses (503) any row not naming the authorizer's tenant.
4. **The database clock, in exactly the two 018 routines that judge time.** 011 takes every instant as a parameter ("NO CLOCK OF ITS OWN", `011_m5_tenant_admission.up.sql:45-48`). Here the caller holding the runtime role would choose that instant. So `m7a_session_create` bounds `created_at` and prunes the ledger by `statement_timestamp()`, and `m7a_customer_page_v2` judges expiry by it, with no grace and no `p_now`. The status command's recent authentication, re-judged on the database clock, is the precedent (ADR-22). A skew fails closed: a read is refused up to the skew before expiry, or every tenant mint is `invalid` (503) while the runtime's clock runs more than 60 s ahead of the database's (doc 08 DA-104).
5. **Issuer-key custody.**
   - The tenant-serving process holds the runtime login and `TENANT_SESSION_ISSUER_KEY` (32–64 bytes). The administrative process must never hold the key. In code since the tenant-entry commit (Decision 8), each entry refuses to start while the OTHER's named variable is present: the administrative entry refuses `TENANT_SESSION_ISSUER_KEY` (`tenant_issuer_key_present`), and the tenant entry refuses `IDEMPOTENCY_KEY` (`idempotency_key_present`) — which enforces only that neither process holds the other's variable under its own name; the database-boundary commit enforced neither. That the administrative process holds no issuer-equivalent bytes under another name is not code-enforced and stays an owner custody item (doc 08 DA-101).
   - The **database owner** installs the same bytes out of band: `insert into tmpos_mint.issuer_key (singleton, key) values (true, $1) on conflict (singleton) do update set key = excluded.key`. `$1` is a bound parameter taken from the secrets store, sent from a session whose statement and parameter logging does not capture it. The key never appears in a migration, a repository file, a literal or a dashboard.
   - The key comes from a CSPRNG and is at least 32 bytes, never derived from a passphrase: the mint and the key check verify a guessed key without throttling (doc 08 DA-101).
   - `m7a_issuer_key_check(p_fingerprint)` lets the runtime show that it holds the installed key. It sends `HMAC-SHA256(key, 'tmpos-tenant-issuer-key-fingerprint:v1')`, 014's construction, and learns only `match`, `mismatch`, `absent` or `invalid` (`probeIssuerKey`).
   - **Rotation is replacement.** The ledger's issuer digest binds each session to the key it was minted under. Replacing the key ends every older session's reads, and deleting it ends all of them, with no purge step (M7M-10). After a rollback of 018, a fresh key is installed, never the old one.
6. **Binding rules, for every later stage.**
   - Every new tenant business-data read is bound to a ledger-minted session, and its tenant is derived in the database. No new routine that accepts an authority tuple over tenant data is granted to `tmpos_app`. The existing exceptions are recorded, not closed: 012's directory page still takes an authority tuple the role can build (DA-45); 007's resolver, the admission reads and 005's self-set row-security context still disclose identity and membership data to it (DA-97); and that context lets `tmpos_app` alone read any tenant's tenant, store and entitlement rows, which are tenant business data, and still allows the store INSERT and the two column UPDATEs (DA-29, DA-97).
   - Nothing reachable by the runtime role alone may write `public.app_user`, `public.platform_identity`, `public.identity_link` or `public.user_membership`. The evidence is narrower than the rule. M7M-02 proves the login's own table privileges, by a grant, `PUBLIC`, an inherited role or a predefined role: INSERT on `audit_event` and `store`, UPDATE on the `store.store_name` and `tenant.legal_name` columns, and no other table or column write. It does not cover what the `SECURITY DEFINER` routines the login may execute write on its behalf, and they still write: 009's and 010's commands write `public.tenant` (010's status change checks no authority), and others write the sessions, idempotency records, the outbox, the rate-limit buckets and 018's mint ledger. M7M-02c is a source tripwire over those routines, not a proof: no routine the login can execute, no trigger function, and no routine named in the source of one in that set has a plain-text INSERT, UPDATE, DELETE, MERGE or TRUNCATE on one of the four tables in its source, which includes a SQL-standard (`BEGIN ATOMIC`) body, and no TRUNCATE names one of them anywhere in its target list. It cannot see dynamic SQL, COPY, C code, a foreign-key cascade (internal RI triggers are excluded) or a comment between two keywords.
   - While administrative minting is unproven (DA-95), no administrative route may write those four tables.

## ADR-34 — A tenant user creates a customer through one idempotent command whose authority the database re-derives from the presenting session (DECIDED — M7A-CUSTOMERS-P3)

**Context.** ADR-32 gave the tenant boundary its first route, a customer read. ADR-33 bound that read in the database to a minted tenant session, and left customer creation open. The owner brief for M7A-CUSTOMERS-P3 asks for `POST /api/v1/customers` on the tenant entry: an authorized tenant user creates a customer with a server-generated id and a name. The write must:
- use the existing tenant session boundary;
- enforce current authority at commit;
- isolate tenants;
- append its audit record;
- complete idempotency atomically.

At entry `9a25cb7`, only the administrative side had those pieces:
- `routes.ts` admitted `idempotency: 'required'` only under a platform-scope requirement.
- The idempotency fingerprint's tenant and store slots were reserved and always null.
- The PostgreSQL transactional store committed platform contexts only.
- The tenant entry refused any `IDEMPOTENCY_KEY` (`idempotency_key_present`).
- `view_customers` was the one decidable tenant key, and the module refused to load a tenant route permission above View.
- `tmpos_app` held no privilege on `tmpos_customer.customer`, and it still holds none.

**Decision.**
1. **The contract.** `POST /api/v1/customers` (`server/runtime/customerCreate.ts`, `CUSTOMER_CREATE_ROUTE`) is a session route of the tenant boundary under `create_customers` at tenant scope, on the GET's path. It declares:
   - a required JSON body of at most 4,096 bytes;
   - `idempotency: 'required'` and `trustedContext: 'required'`;
   - no recent sign-in and no `sessionBinding`;
   - a `command`: contract `tenant.customer.create`, mode `create`, aggregate type `customer`, one change field `name`, no event.

   Its rules:
   - **Body.** Exactly `{ name }`. Any other shape, a missing or extra field, or a name decision 9 refuses is 400 `invalid_request`. That is decided once the idempotency record is acquired. It writes no customer, audit record or completion, the key stays bound to that request's fingerprint, and the attempt's lease waits out its 60 s (doc 08 DA-117).
   - **Answer.** `201 { customer: { id, name } }`: the runtime's new version-4 id and the name as stored. There is no `Location` header, because no customer-detail route exists. The same name under two keys is two customers, because no repository rule makes customer names unique.
   - **Refusals** keep the chain's generic bodies:
     - 401 for a session refusal;
     - 403 `forbidden` for any denial;
     - 400 `invalid_request` for a missing, repeated or malformed `Idempotency-Key`;
     - 409 `request_in_progress` while another attempt under the key holds its lease and no command transaction holds the record;
     - 422 `idempotency_key_reused` for a different request under the key;
     - 429 from the limiter;
     - the bounded 404 on any host but the tenant host;
     - 503 `service_unavailable` for an outage, for every refusal inside the committing transaction (lost authority, a duplicate id, a store fault), and for a commit whose acknowledgement was lost, an unknown outcome (decision 5);
     - 503 `service_unavailable` (reason `idempotency_unavailable`), retryable, for a same-key request, typically on another instance, while the winner's command transaction holds the record: that transaction holds the record row as its fence, so the request's acquire waits on it until its lock bound. It is not a 409.
   - **Unchanged.** Host, Origin, CSRF, security headers, body limits and rate limits are the chain's, unchanged.
2. **The permission (owner decision for this route).** The owner brief names "the canonical Customers Create authority". ADR-32 recorded M7A-CUSTOMERS-P1's D1 for the GET the same way, from that stage's brief. `create_customers` is a new canonical tenant ROUTE permission (`TENANT_ROUTE_PERMISSIONS`, `server/platform-identity/m5CanonicalPermissions.ts`): the Customers domain at Create or above, at tenant scope only, non-sensitive.
   - It is decided exactly as `view_customers` is: `materializeTenantPermissions(role, {}, false)`, then `meetsTenantPermissionLevel(level, 'create')`. There is no second evaluator and no role-name branch, and no role default is changed. `store_owner` (Full), `manager` (Full) and `sales_staff` (Create) hold it. `technician` (View) is refused.
   - The read-only rule is stated where it is enforced (`TENANT_ROUTE_THRESHOLDS`). A `read_only` limitation grants a tenant route permission at View only, so `create_customers` is denied under it. The limitation comes from an account or tenant status of `read_only` or `overdue`. The load-time guard now admits a non-sensitive View or Create threshold, and still refuses a key that collides with a sub-permission.
   - `isDecidablePermission` answers true for both route permissions at tenant scope only. Every other tenant or store key stays undecidable.
   - A store or platform grant never satisfies it. The authorizer counts tenant-scope grants alone: none or several deny.
   - The POST is not in the tenant authorizer's read classification.
3. **Tenant-scope idempotency, for tenant session commands only.**
   - **Where it is admitted.** `parseIdempotency` (`server/runtime/routes.ts`) admits `required` at platform scope, as before, or at tenant scope on a route that is a `command` with `access: 'session'` and `audience: 'tenant'`. These stay refused (`route_idempotency_policy_invalid`): a tenant `perform`, which runs outside the store transaction; a Bearer tenant route; an administrative-audience tenant requirement; and every store-scope route.
   - **What binds the operation.** The chain binds it to the authorizer's trusted scope (`server/runtime/app.ts`): tenant, store and the app-owned actor come from the context the authorizer handed out, never from the request. A missing context is refused 403 (`authz_context_missing`) rather than bound as nulls.
   - **The fingerprint.** It gains the actor (`OperationBinding.actor`), and `operationOf` throws on a slot that is neither a string nor null (`idempotency_binding_invalid`). The record's scope is per principal. So the same principal, key and body under another tenant or actor is a 422, never a replay of the other context's response.
   - **The contract version.** `IDEMPOTENCY_CONTRACT_VERSION` moves from 1 to 2. The version is in every tag, so every record starts afresh, the administrative commands' included. Nothing is deployed, so no drain is needed now. A deployment that carries version-1 records needs a drain of one retention period (24 h), as a key rotation does.
   - **Unchanged.** Lease, fingerprint, seal, replay and conflict policies. A replay still runs after the session, CSRF, authorizer and trusted-context checks, so a revoked session or grant gets its refusal, never the recorded 201.
4. **The tenant revalidator** (`createTenantContextRevalidator`, `server/composition/tenantAuthorization.ts`). The tenant store's `ContextRevalidator` answers true only when all of these hold:
   - the scope is tenant, the limitation `none`, no recent-authentication deadline is set, and a session key is present;
   - the presenting tenant session is still live and now held by the committing transaction;
   - 016's v2 admission, re-read under the held standing, admits the principal at the session's own security version;
   - the same one-grant selection the authorizer makes (`scopeOf`) equals the authorized scope field by field: actor, security version, membership, role, limitation, tenant and store;
   - the route's permission, decided again on that role, is granted.

   A refusal is `false`. A hold, read or session fault throws. Either way the kernel rolls back and nothing commits.
5. **The transaction and its lock order.** The tenant root composes the M6 PostgreSQL store (`createPostgresTransactionalStore`) over the same kernel with `contextScope: 'tenant'`.
   - **What the store admits.** It requires a revalidator. It refuses a contextless command, and a context not of tenant scope or not of limitation `none`. It audits each command at exactly its context's scope: tenant scope, the context's tenant and no store. The administrative store's platform behaviour is unchanged, apart from step 7's audit-row check, which now applies to every command.
   - **One transaction, in this order:**
     1. the idempotency fence;
     2. the presenting session read without a lock (`readTenantSession`), for its provider reference alone;
     3. 016's hold of that actor's standing (`m5_hold_tenant_standing`: the account FOR UPDATE, then its links, grants, tenants and stores FOR SHARE);
     4. the session row read again and held by its touch (`holdTenantSession`);
     5. the v2 re-read, the witness and exact-scope compare, and `create_customers` decided again (decision 4);
     6. the mutator (`server/persistence/postgresCustomerCreate.ts`) calls 019's routine. It first runs an unlocked pre-check, taking no row lock, that refuses a key whose session is not live on the database clock now or was minted under an issuer key other than the one installed now; a key that passes is judged again under the locks that follow, so the pre-check adds no race (it only refuses, and each refusal is decided on rows committed when it read them). It then takes 016's hold again (already held, so it does not wait), takes the session row and its mint-ledger row FOR SHARE together, then the issuer-key row FOR SHARE, reads the database clock only after those lock waits, derives the authority afresh, and inserts. The mint-ledger row's own FOR SHARE and the pre-check were both added in P3 review fixes after the routine's first draft: without the lock, a delete of the ledger row raced the create instead of waiting on it (proved by `tests/db/customerCreateRoutine.integration.test.mjs` M7CR-10, red without the lock); without the pre-check, an expired or wrongly-minted key was still refused only after taking 016's hold and the session, ledger and issuer-key locks, so an owner probe on any of those rows waited on the doomed transaction (55P03) instead of running free (M7CR-11, red without the pre-check);
     7. the audit record, where exactly one row INSERTed is required or the transaction rolls back;
     8. the sealed completion;
     9. COMMIT.
   - **Races.** A revocation, logout, suspension, grant change or key rotation committed before the lock that decides it refuses the command. One attempted after it waits for the command's COMMIT. A tenant logout takes the session row only: the mint ledger has no foreign key and never cascades. This is ADR-31's establish order (standing, then session), so no lock cycle with a login or a logout was found.
   - **The mutator's answers.** It answers `applied` only for exactly one row whose `o_tenant_id`, `o_actor_id` and `o_membership_id` equal the context's tenant, actor and `membershipId`. No row is `refused`, and anything else is `mismatch`; both roll back. It never answers `conflict`, whose sealed 409 would commit.
   - **Raises.** A duplicate id (23505), a name 017's CHECK refuses (23514), an INSERT that wrote no row (`no_data_found`, decision 6), a malformed argument (22023) and an isolation other than READ COMMITTED (55000) raise and roll back. The kernel refuses savepoints, so the transaction cannot record a completion after a raise.
   - **Refusals.** Every refusal inside the transaction writes no customer, audit record, outbox event or completion, and answers 503 (DA-70's rule). The lease was acquired in its own earlier transaction, and it stays until it expires; it is not reported as rolled back.
   - **A lost commit acknowledgement** is an unknown outcome, also a 503, and never reported as a rollback. The app's command-port deadline answers first (reason `transaction_timeout`), before the store's outcome-unknown rejection. The lease is not released. A retry under the same key resolves through the retained idempotency record: it replays the sealed 201 if the commit landed. If it did not, the retry gets 409 until the lease expires, then reclaims the record and plans a fresh id.
   - **Success.** The 201 goes out only after COMMIT is acknowledged.
6. **Migration 019 (`019_m7a_customer_create`).** Its own schema, `tmpos_customer_write`, holds one routine: `m7a_customer_create(p_session_key text, p_customer_id uuid, p_name text)`. It is `VOLATILE SECURITY DEFINER`, with its search path pinned to `pg_catalog, pg_temp` and `row_security = off`. It returns one row `(o_tenant_id, o_actor_id, o_membership_id)` or no row. 019 creates no table, role, trigger or type, and changes nothing 001–018 created, their ACLs included.
   - **Authority.** The session key is the only authority argument. The routine derives everything as 018's read does:
     - a tenant session with a mint-ledger row, live on the database clock with the ledger's own expiry, minted under the issuer key installed now;
     - 016's answer `resolved`, with the minted standing digest;
     - exactly one tenant-scope grant.
   - **Write allow-list.** The account status and the grant's tenant status must be `active` or `trialing`. That is narrower than the read, which also admits `overdue` and `read_only`.
   - **Role set.** The role must be `store_owner`, `manager` or `sales_staff`. This is the catalog's Customers ≥ Create restated in SQL for the four durable roles migration 003 admits. A parity test pins it for every `TENANT_ROLE_IDS` entry, from the installed source and by behaviour (`tests/db/customerCreateRoutine.integration.test.mjs` M7CR-06). When a custom role becomes durable (doc 08 DA-85), the set must be replaced, not extended by hand.
   - **A written row.** After its INSERT the routine refuses when no row was written: it raises `no_data_found` (fixed text), so the transaction rolls back and the client gets 503. Without it, an owner-installed BEFORE INSERT trigger on `tmpos_customer.customer` that returns NULL would let the command commit its audit record and completion, and answer 201, with no customer. Only the table's owner can install such a trigger; `tmpos_app` cannot.
   - **Bounded inputs.** The key has 011's shape, the id is a version-4 UUID, and the name is 1–200 characters. The character rules are 017's CHECK, judged at the INSERT. Constraint errors are raised again with fixed text, so no name or id reaches a DETAIL line.
   - **Privileges.** EXECUTE is revoked from `PUBLIC`, `anon` and `authenticated` and granted to `tmpos_app` alone, with USAGE on the schema. `tmpos_app` still holds no privilege on the customer table.
   - **Preconditions.** 018 and `tmpos_app` exist and the schema does not. The applier can execute 016's hold and v2 read. The applier owns, or inherits the owner of, the session table, the mint ledger, the issuer key and the customer table, none with forced row security, and holds each privilege the routine uses on them.
   - **Postconditions (a)–(j)**, in 017's and 018's form:
     - the schema holds exactly the routine, with the attributes above;
     - no grant exists beyond the owner's and a non-grantable EXECUTE and USAGE to `tmpos_app`;
     - `tmpos_audit_writer`, `anon` and `authenticated` cannot execute the routine by any path (`PUBLIC`, an inherited role, or `SET ROLE`);
     - no runtime role is a member of an owner of the schema, the routine or those four tables;
     - no runtime role, nor any role it is a member of, holds a privilege on those four tables; no column grant exists on them; each still has row security enabled and not forced;
     - 017's and 018's surfaces hold, by count and exact signature;
     - membership closure: `tmpos_app` and `tmpos_audit_writer` are members of nothing, and `anon` and `authenticated` reach neither.
   - **Rollback.** The down file drops only the routine and the schema. It does not refuse while customers exist, because they are 017's rows and stay readable. It has two costs:
     - every POST then answers 503;
     - both entries refuse to restart (`role_privilege_missing`) until the code rolls back too.

     Roll 019 back before 016–018. The database does not enforce that order: a PL/pgSQL body records no dependency.
7. **Audit.** The store appends one `audit_event` row in the same transaction, through the existing writer, under 005's context-independent append policy (`tmpos_audit_writer_append`):
   - action `tenant.customer.create`;
   - required permission `create_customers`;
   - scope `tenant`, `tenant_id` the context's tenant, no store;
   - actor the context's app-owned actor;
   - `request_id` the command's server-generated correlation id;
   - reason `command_committed`;
   - metadata `{}`.

   It records neither the name nor the customer id, and `subject_tenant_id` stays null (it names tenant aggregates only). The row therefore does not name the created customer (doc 08 DA-111). Its tenant and actor are proven equal to the revalidated context in TypeScript and to 019's derived identity by the mutator. No database rule ties the row to the session (DA-114). The request log never carries the name.
8. **No outbox event.** No approved customer event contract exists, and none is invented: `events: []`. The tenant root composes no delivery port.
9. **The name rule for new writes.** `normalizeCustomerName` applies these steps in order:
   - It trims the edges. ES `trim` strips exactly the 25 edge code points 017's CHECK refuses at an edge, which a sweep of every code point pins.
   - It refuses C0 controls (NUL included), DEL, C1 controls, U+2028, U+2029, lone surrogates and Bidi_Control, written as `\u` escapes and never as raw characters.
   - It refuses a length outside 1–200 scalars.
   - It refuses a name with no scalar outside White_Space, Default_Ignorable_Code_Point, Cf, M and U+2800. Private-use and unassigned scalars count as visible, a recorded product choice.

   So the runtime is at least as strict as the column's CHECK, and the database never refuses a name the runtime admits. Internal whitespace is kept, with no case folding or normalization.

   DA-92 is thereby dispositioned for new customer writes. Existing customer names are never rewritten, 017's CHECK stays the database's floor, and 009's display-name rule is unchanged.

   The name travels in the command's change set. Command change schemas alone get a 400-UTF-16-unit string cap (`MAX_CHANGE_STRING_FIELD_LENGTH`), so a 200-scalar astral name fits. Event payloads and envelopes keep `MAX_STRING_FIELD_LENGTH` (256), and every record keeps its 4,096-byte bound.
10. **Startup and readiness of the tenant entry** (ADR-33 decision 8, amended above).
    - **Keys and mutators.** `IDEMPOTENCY_KEY` is required, and its refusal codes are in the ADR-33 amendment. The write slot requires every command route to commit through exactly one mutator of its contract's kind, mode and aggregate type (`command_mutator_unavailable`).
    - **What `createApp` is handed.** The tenant store's `idempotency` and `transactions`, and no `events`.
    - **Readiness.** It adds exactly the two probes `createApp` adds: `idempotency_store` and `command_transactions`, both 006's `m6_store_probe`. There is no 019 readiness probe. The login's EXECUTE on the routine is proven at every start by `APPROVED_ROLE_GRANTS` (`role_privilege_missing`). `/health` is unchanged.
    - **The administrative entry** is unchanged: its inventory, audience, configuration and artifact.

**Alternatives not taken.**
- (a) *A sealed 409 for a duplicate id.* The routine's raise aborts the transaction, and the kernel refuses a savepoint, so no completion can be written after it. A duplicate id is a 503, and a retry plans a fresh id.
- (b) *A tenant-scope `perform`.* It runs outside the store transaction, so nothing re-proves the tenant where the write commits, and it keeps the crash window.
- (c) *A routine taking tenant, actor or membership arguments.* ADR-33 decision 6 forbids granting `tmpos_app` a routine over an authority tuple the role can build.
- (d) *A direct INSERT grant to `tmpos_app`, confined by 005's row policies.* Their context is self-set (DA-29).
- (e) *A readiness probe that calls 019.* It would need a key, and the grant is already proven at startup.
- (f) *An id chosen by the database.* The 201, id included, is sealed into the completion before COMMIT, so the id must exist when the plan is made. The runtime generates it, and a `tmpos_app` holder can choose one (DA-115).
- (g) *The customer id or name in the audit metadata.* The writer's metadata allow-list has no such key. Widening the shared audit shape is later work (DA-111).

## ADR-35 — An owner's stored Customers level for each editable built-in role decides every customer request, in the runtime and again in the database (DECIDED — M7A-CUSTOMERS-P3-R1)

**Context.** P3's final report found an unmet acceptance requirement: an owner can narrow a role in the shop app while the server still lets a holder of that role create a customer. The owner brief for M7A-CUSTOMERS-P3-R1 asks for that to be corrected before P3 is called fully accepted or the customer-detail route is added. The Customers Create policy itself (`create_customers`, Customers at Create or above) is decided and is not reopened. Checkpoint 1 traced an owner edit and found no server-authoritative role configuration at all:
- The shop app's role editor changes client memory only. `updateTenantRole` (`src/context/AccessContext.tsx`) changes the React state of the provider it runs in, sends no request, and writes nothing durable. Another tab, a reload and a fresh provider keep the catalog default (`src/context/AccessContext.roleEditLocal.test.tsx` RLE-1). The SPA also holds no tenant-server session.
- The server decided both customer routes from the catalog defaults: the authorizer and the revalidator by `materializeTenantPermissions(role, {}, …)`, 019's routine by its fixed role set, and 018's `m7a_customer_page_v2` by no level at all.
- 001–019 held no role-definition table, and migration 003 admits the four built-in tenant role ids alone.

So a role narrowed to View still created, and a role narrowed to None still read. At entry `8c0a4a8` the regression case observed `{"put":404,"post":201,"customers":1,"audits":1,"completions":1}` (`tests/db/roleLevels.integration.test.mjs` M7RLH-01, red).

**Decision.**
1. **The disposition: the smallest durable owner edit.**
   - What is stored is, per tenant, the Customers level of each of the three built-in roles an owner may edit: `manager`, `technician` and `sales_staff`. No row, or a NULL level, is the catalog default: `manager` Full, `technician` View, `sales_staff` Create. `store_owner` is Full, and is never stored or edited (the catalog's owner short-circuit, now named `TENANT_OWNER_ROLE_ID` in `server/platform-identity/permissionCatalog.ts`).
   - Only the Customers domain is stored, because it is the only domain the server decides; a stored level the server did not enforce would read as enforced.
   - Only the store owner edits (decision 3). This is an interpretation **flagged for owner confirmation**. The client lets a manager holding `manage_role_permissions` edit other roles, but that grant is itself owner-editable only in client memory and has no server-side parity rule, so the server does not honour it. Independent review contested the owner-only reading and argued for STOP instead; it is recorded, not resolved (doc 08 DA-124).
   - Custom roles, other domains, deletion and the shop app's editor stay client-only. The editor is unchanged and calls no route, and the SPA has no tenant-server session, so **an owner who narrows a role in the shop app still does not reach the server**. Wiring it is a named dependency of a later slice (DA-124).
   - There is no owner-visible read route. The authoritative read is the one every customer decision makes, and the PUT answers the level it stored.
2. **The contract.** `PUT /api/v1/roles/levels` (`server/runtime/roleLevelUpdate.ts`, `ROLE_LEVEL_UPDATE_ROUTE`) is a session route of the tenant boundary under `edit_role_levels` at tenant scope. It declares:
   - a required JSON body of at most 8,192 bytes;
   - `idempotency: 'required'`, `trustedContext: 'required'` and `recentAuth: 'required'`;
   - a `command`: contract `tenant.role.level.update`, mode `create`, aggregate type `tenant_role_level` (never `tenant`, so the audit row names no subject tenant beyond its scope), change fields `roleId`, `domain` and `level`, no event.

   Its rules:
   - **Body.** Exactly `{ roleId, domain, level, reason }`. `roleId` is one of the three editable roles, `domain` is exactly `customers`, and `level` is one of the seven canonical levels. `reason` is trimmed and must then hold 10–500 Unicode scalar values with no C0 control, DEL, C1 control, U+2028, U+2029, lone surrogate or Bidi_Control character (the tenant status command's rule, restated because that module never ships in the tenant artifact). Anything else, the owner role as a target and any extra field included, is 400 `invalid_request` (reason `command_request_invalid`), decided once the idempotency record is acquired, as for the create (doc 08 DA-117). Nothing in the body is authority: `roleId` is the target of the edit, never the caller's role, and the tenant is never named.
   - **Answer.** `200 { roleLevel: { roleId, domain, level } }`, the level as stored. An identical retry under the same key replays it; the same key with another body is 422 `idempotency_key_reused`.
   - **Refusals** keep the chain's generic bodies, as the create's do (ADR-34 decision 1), and add 403 `step_up_required` (reason `recent_auth_required`) for a sign-in older than `RECENT_AUTH_MAX_AGE_MS` (10 minutes). Only the chain's outer check answers it, and it touches no key. A deadline that passes at the revalidator, or after 020's set routine's lock wait (decision 4), rolls the transaction back: 503 `service_unavailable`, the lease kept. The same key from the stale session is then 403 `step_up_required` (no key touched); from a fresh sign-in within the lease it is 409 `request_in_progress`; after the lease it is decided afresh (M7RLH-09 witnesses the 503, the kept lease, the 403 and the 409; the after-lease case is witnessed for the create, M7RLH-04, not for the edit).
3. **The permission: the owner rule.** `edit_role_levels` is a canonical tenant route permission (`server/platform-identity/m5CanonicalPermissions.ts`), sensitive, recorded under the Employees domain at Full. Neither is compared. It is granted exactly when the selected tenant grant's role is `TENANT_OWNER_ROLE_ID` and the limitation is `none`, and the role's stored levels were readable. It is deliberately not "Employees at some level": Employees is plan-gated and the server holds no entitlement set, so that rule would deny everyone. The load-time guard admits this one sensitive, Full-threshold owner-only key and nothing else. A store or platform grant never satisfies it, and none or several tenant grants deny, as for every tenant route permission.
4. **Step-up.** A role change is a sensitive action (doc 03: status change, entitlement grant, role change and provisioning require recent-login/step-up re-authentication). The chain refuses the route unless the session carries provider-verified authentication no older than 10 minutes. The tenant revalidator (`server/composition/tenantAuthorization.ts`) now requires a deadline exactly for a sensitive permission and refuses one on any other, and judges it on the database clock (`authenticationFresh`, `server/persistence/postgresSessionStore.ts`, the administrative path's `clock_timestamp()` rule). The edit's mutator judges the same deadline again, on the database clock, after 020's set routine answers, which is after that routine's own lock waits, because the routine's FOR UPDATE can wait on a create holding the role row (`server/persistence/postgresRoleLevels.ts`; added after review; `tests/db/roleLevels.integration.test.mjs` M7RLH-09 (the step-up re-judged after the lock wait) and M7RLH-09b (the fresh-sign-in control: create 201, then edit 200); `server/composition/productionTransactions.test.ts` M7TK-09). The audit record, the completion and COMMIT then follow with no further freshness check, so they may complete after the sign-in deadline (within the command's own transaction deadline).
5. **Every customer decision reads the stored level.**
   - *The catalog.* `materializeTenantPermissions(role, entitlements, readOnly, levels?)` applies a stored level in place of a non-owner built-in role's default for the domain it names, before the entitlement gate and the read-only cap; the owner ignores it. Malformed levels (not a plain object, an unknown domain, a non-canonical level) materialize `{}`. Existing callers that pass no levels are unchanged.
   - *The decision.* On the tenant route-permission branch of `evaluateCanonicalPermission`, `levels` are required: missing or malformed, the permission is denied, never decided on the defaults.
   - *The authorizer* reads the levels for the scope's tenant and role, which come from the admission answer, on every decided request, through 020's `m7a_role_levels` over the kernel's client (`createPostgresRoleLevels`). A read fault throws: a bounded 503, never a decision. An answer that is not an object of the stored domains at canonical levels is a fault too.
   - *The revalidator* reads them again on the committing transaction (`readRoleLevels`) after the standing is held and the admission re-read, and decides again with them.
   - *The database* decides again in 020's routines (decision 6).

   So `GET /api/v1/customers` requires the effective Customers level at View or above, and `POST /api/v1/customers` at Create or above. An edit denies that role's next request, an already-issued session included, with no re-login (M7RLH-03).
6. **Migration 020 (`020_m7a_tenant_role_levels`).** Its own schema, `tmpos_role`, for 017's, 018's and 019's reason: older rollbacks drop their schemas without CASCADE, and older files and suites pin exact inventories.
   - **The table** `tmpos_role.tenant_role_level`: `tenant_id` uuid NOT NULL referencing `public.tenant` (NO ACTION), `role_id` CHECK in the three editable roles, `domain` CHECK `customers`, `level` NULL or one of the seven, `updated_at` timestamptz NOT NULL, primary key `(tenant_id, role_id, domain)`. Row security is enabled with no policy and not forced. No runtime role (`tmpos_app`, `tmpos_audit_writer`, `anon`, `authenticated`) holds a privilege on it.
   - **Four routines**, each plpgsql `SECURITY DEFINER`, search path `pg_catalog, pg_temp`, `row_security = off`, EXECUTE to `tmpos_app` alone:
     - `m7a_role_levels(p_tenant_id, p_role_id)`, `STABLE`: the non-null stored levels as a jsonb object, or `{}` (nothing stored, `store_owner` and an unknown role alike). A NULL argument raises 22023.
     - `m7a_role_level_set(p_session_key, p_role_id, p_domain, p_level)`, `VOLATILE`: the target is validated first (22023, fixed text). It derives the editor exactly as 019's create derives its caller (unlocked live and issuer pre-check; 016's hold; the session and mint-ledger rows FOR SHARE; the issuer-key row FOR SHARE; the database clock after those waits; the standing digest; account and tenant status `active` or `trialing`; exactly one tenant-scope grant) and edits only when that grant's role is `store_owner`. It then inserts the row if absent (NULL level), takes it FOR UPDATE, refuses if it is gone, reads the clock again, and updates it. It answers `(o_tenant_id, o_actor_id, o_membership_id, o_level)` or no row.
     - `m7a_customer_create(p_session_key, p_customer_id, p_name)`, `VOLATILE`: 019's derivation and insert, with 019's role set replaced by the effective Customers level: `store_owner` Full; an editable role's stored level, else its default; any other role refuses. In order: an unlocked pre-read that refuses, writing nothing and locking no role row, a key whose effective level is already below Create; the row inserted if absent (NULL); `SELECT … FOR SHARE`, refusing if the row is gone; the decision on the locked value; the clock read again after that wait; the insert.
     - `m7a_customer_page_v3(p_session_key, p_after_customer_id, p_limit)`, `STABLE`: 018's `m7a_customer_page_v2` exactly, plus the effective level at View or above, read without a lock.
   - **Revokes** from `tmpos_app`: EXECUTE on 019's `tmpos_customer_write.m7a_customer_create`, USAGE on `tmpos_customer_write`, and EXECUTE on 018's `tmpos_mint.m7a_customer_page_v2`. Both decide from the role name, so a narrowed role would still create and read through them. These three ACL changes are 020's only effect on earlier objects; 001–019 are byte-identical.
   - **Every locking routine** requires READ COMMITTED and raises 55000 otherwise (019's reason, DA-113). A refusal decided after the insert-if-absent can leave the NULL lock row, which is the default and changes no decision; the runtime rolls every refusal back.
   - **The restated defaults**, the owner literal, the editable set and the ordering are pinned against the catalog, from the installed routines' source and from both files (`tests/db/tenantRoleLevelRoutine.integration.test.mjs` M7RL-08).
   - **Postconditions (a)–(k)** carry 019's, including effective privilege through membership for the tables the routines rest on, and add that no runtime role can reach 019's create, 018's `m7a_customer_page_v2` or `tmpos_customer_write` by any path.
   - **Hashes:** up `0a289ad4dcefdb4a5a260aed7a2121d93e23c5efe4f3550eb9fdc39094d9acfe`, down `182718aaf001567531ed9b3737e1cd723e040c4d9305f76a60e9c1c99f8185fc`.
7. **Races and their order (the brief's requirement 6).** A create and an edit each take their own 016 hold, session, ledger and issuer rows first, then the one role row `(tenant, role, 'customers')`. There is no cycle: distinct principals share only FOR SHARE locks in 016's hold, one principal serializes on its account row, and each then takes the one role row.
   - *An edit that holds the row first* makes the create wait, on the row or on the edit's uncommitted insert. Once the edit commits, the create's next statement reads the new level under READ COMMITTED, and a narrowed role refuses. That refusal happens inside the committing transaction: a 503 that commits nothing and keeps the lease (M7RL-09, M7RLH-04).
   - *A create that holds the row first* makes the edit wait until it commits (M7RL-10, M7RLH-05).
   - *An edit committed before the authorizer decides* denies with 403, which reserves nothing.
   - *The key of a refused create:* a same-key retry while the role is still narrowed is 403 at the authorizer, before any key is touched; after a restore, within the lease it is 409 `request_in_progress`; once the lease expires the key is decided afresh on the current level. A key refused 403 at the authorizer holds no record, so sending it again after a restore is a new command (201) (M7RLH-02, M7RLH-04).
   - *A session that expires while waiting* on the role row is refused, because each routine reads the clock again after that wait (M7RL-17).
   - The edit touches no session, grant or standing.
8. **Audit, idempotency and no event.** The edit commits in one transaction with its idempotency completion and one `audit_event` row: action `tenant.role.level.update`, permission `edit_role_levels`, scope `tenant` with the tenant and no store, the app-owned actor, reason code `role_<role>_customers_to_<level>` (the new level only), the owner's trimmed reason, `subject_tenant_id` null and metadata `{}`. The level before an edit is reconstructable from the audit history, the first being the catalog default, only for edits made through this route (DA-119). No outbox event: no approved contract exists, and none is invented. The mutator answers `applied` only for one row naming the revalidated tenant, actor and grant and the level asked for; anything else rolls back (503).
9. **Deploy and rollback move with the runtime.** 020 is deliberately not expand-contract: a window granting the old routines and the new would keep the name-based decision reachable. The startup preflight, shared by both entries, requires exactly 001–020 and 020's grants, so the P3 build refuses a 020 database and a P3-R1 build refuses a 019 one. The rollback order is:
   1. first, while the 020 runtime still serves, the owner sets every edited role back to its default through `PUT /api/v1/roles/levels`, and the operator confirms that the down file's own check finds no non-default level;
   2. then the runtime goes back to the P3 build;
   3. then 020's down, which refuses (under ACCESS EXCLUSIVE and READ COMMITTED) while any stored level differs from its role's default, and otherwise drops what 020 created and gives `tmpos_app` back the three grants.

   No runtime serves between the last two steps, since the P3 build refuses a 020 database. The database does not enforce the order (DA-122). No order lets the rollback silently re-widen a narrowed role, because 020's down refuses until every stored level equals its default (the owner's reset widens it deliberately, through the audited route). Running 020's down before the runtime switch, once the levels are reset, also converges: the 020 runtime then fails closed (503) until it is replaced. Switching the runtime to the P3 build before the owner's reset leaves no runtime able to start until the 020 runtime is rolled forward again; the owner then resets the levels through it, and the order above is followed.

**Alternatives not taken.**
- (a) *Copying the client's role state into the request.* A client-supplied role, level, tenant, header, cookie claim or self-set setting is not authority (the brief's requirement 5).
- (b) *Delegated editing by `manage_role_permissions`.* The grant is owner-editable only in client memory, and no server-side parity or cap rule exists (doc 04 requires one). Recorded for owner decision (DA-124).
- (c) *Levels for every domain.* The server decides only Customers; stored levels it did not enforce would read as enforced.
- (d) *Custom roles.* 003 admits four role ids and no server path assigns another; their storage, identity, assignment and deletion are undefined. An unknown role fails closed.
- (e) *Expand-contract for 020.* It would keep 019's and 018's role-name decisions reachable during the window.
- (f) *`edit_role_levels` as Employees at Full.* Employees is plan-gated and the server holds no entitlements, so it would deny every owner.
- (g) *An owner-visible read route.* Not needed for enforcement; the PUT answers the stored level.
- (h) *A down that ignores stored levels.* It would silently re-widen every narrowed role through 019's and 018's name-based answers.

**Consequences.**
- **Nothing closes.** G-IAM, G-PERSIST, G-AUDIT, G-IDEMPOT, G-DBROLE, G-MIGRATE, G-CPLOGIN, G-STATUS and G-ISOLATION stay OPEN.
  - An owner's edit made through the server route is enforced by both customer routes, in the runtime and in the committing database transaction. The shop app does not use that route, so a narrowing made in the shop app is still not enforced.
  - Everything is repository code served only by the compiled tenant entry, which is not deployed.
- **Register.** DA-85 is narrowed, not closed. DA-97 gains 020's two routines. DA-115 points to DA-118. DA-118 to DA-124 are new:
  - the direct create under the owner's level (DA-118);
  - a new unaudited IAM-change path, a pre-deployment blocker and a G-AUDIT exception (DA-119);
  - lock holding and starvation (DA-120);
  - the levels read's disclosure (DA-121);
  - the rollback order (DA-122);
  - the two reads (DA-123);
  - owner-only editing and the unwired shop-app editor (DA-124).
- **Role edits and customer creates are audited only through their HTTP routes.** A holder of `tmpos_app` plus a live minted key can call 020's create or set routine directly, with no audit, reason, step-up, idempotency or outbox record (M7RLH-08).
- **Evidence.** It is disposable PostgreSQL and local sockets only:
  - `tests/db/tenantRoleLevelRoutine.integration.test.mjs` (M7RL-01 to M7RL-17): apply and postcondition, inventory and ACLs, the login's effective privileges and 42501 on 019's create and 018's `m7a_customer_page_v2`, refused edits, the edit, every level against the catalog for the create (06) and the read (07), parity (08), both race orders (09, 10), the pre-read (11), a deleted row (12), the direct calls (13), lock holding (14), mutations each red then green (15), the down refusing, succeeding and restoring 019's grants, and re-apply (16), and expiry during the wait (17);
  - `tests/db/roleLevels.integration.test.mjs` (M7RLH-01 to M7RLH-08 and M7RLH-C1), over real loopback HTTP through the production tenant entry, from source and compiled: the regression (01), narrowing, restoring and the refused key (02), an already-issued session and the read at None (03), both race orders across two instances sharing one database (04, 05), non-owner editors, bounded refusals, step-up and replay (06), failure atomicity and lost COMMIT answers (07), the direct-call witnesses (08), the compiled entry's eight routes (C1), M7RLH-09 (the step-up re-judged after the lock wait) and M7RLH-09b (the fresh-sign-in control race: create 201, then edit 200);

## ADR-36 — The shop edits built-in Customers levels through a tenant session, and "Saved" means server-confirmed (DECIDED — M7A-CUSTOMERS-P3-R2)

**Context.** After R1 the server stored and enforced an owner's Customers level for each editable built-in role, but the shop app's role editor still changed only the tab it ran in: it made no server call, and the SPA held no tenant-server session. So the shop showed a local change the server never received: an owner could narrow a role on screen while the tenant server went on deciding customer requests on the stored level (ADR-35; doc 08 DA-124 (2)). The owner brief for M7A-CUSTOMERS-P3-R2 asks for that browser-to-server path to be made real for the built-in roles' Customers level, without describing the rest of the role matrix as server-enforced.

**Decision.**
1. **The session.** The shop app signs in to the tenant boundary through the M5 tenant-session contract (ADR-31): `POST /api/v1/session/login` with the signed-in user's Firebase ID token as `Authorization: Bearer` and `X-TMPOS-CSRF: 1`; the server verifies the token and mints the session (ADR-33), and `GET /api/v1/session` confirms it (`src/tenant/tenantSessionClient.ts`).
   - The session is the browser-managed HttpOnly `__Host-tmpos_tenant_session` cookie. The page holds only the session CSRF token, in memory, beside the UID it was issued for, and sends it as `X-TMPOS-Session-CSRF` on the PUT and on `POST /api/v1/session/logout`. The browser never receives or builds an issuer key, a mint proof or a database session key.
   - A session is reused only for the UID that established it. On a Firebase user switch the previous user's session is logged out before the next user's session is read or established (`ensure()` awaits any in-flight logout before it reads or establishes the next user's session), and every signed-out auth state, the first callback of a page load included, attempts a logout (`src/context/AccessContext.tsx`).
2. **The read-back route.** `GET /api/v1/roles/levels` (`server/runtime/roleLevelDirectory.ts`) sits on the edit's path, under the edit's owner rule `edit_role_levels`, with `trustedContext: 'required'`, `recentAuth: 'none'`, no body and no idempotency. Its tenant is the authorizer-selected trusted scope from the session's admission, passed as a parameter to 020's definer read `tmpos_role.m7a_role_levels(uuid, text)`, the three roles in one statement; unlike the customer read, it is not bound to the session key in the database (doc 08 DA-121). It answers the four built-in roles in the fixed order `store_owner`, `manager`, `technician`, `sales_staff`, each with `level`, `defaultLevel`, `source` (`fixed`; `stored`; `default` for no row or a NULL lock row) and `editable` (true for the three non-owner roles, whatever the source). The runtime handler (`roleLevelDirectoryOf`) validates the port's answer, and anything out of shape is a bounded 503. It writes no audit record and is `Cache-Control: no-store`. `TENANT_SHIPPING_ROUTES` adds it (session, no body, no idempotency): nine routes, beside ADR-34 decision 8's eight as ADR-35 amended it. Doc 05 §2 holds the contract.
3. **The panel.** The Employees permissions screen gains "Server-enforced Customers access" (`src/tenant/ServerCustomerLevels.tsx`), the only part of the screen that reaches the server: `store_owner` as "Full — fixed", and a level, a reason and "Save to server" for `manager`, `technician` and `sales_staff`. It reads on load, on a focus or visibility refresh (one at a time, skipped while a save or a sign-in confirmation is under way) and once per save's read-back. Grid changes to custom roles and other domains make no server call; the grid carries the banner "Changes in this table apply to this browser tab only. They are not saved to the server and are not enforced by it."
4. **"Saved" means server-confirmed.** A row says "Saved" only after an exact PUT 200 (a fresh execution or an idempotent replay of the same key) followed by a same-tenant read-back equal to the requested level. The key rules:
   - one `Idempotency-Key` per payload (role, level and reason);
   - no response: one automatic retry under the same key;
   - 409: the key is held and the level read back; when it already equals the draft, "The server now has X, but this save is not confirmed yet. Press Save again to confirm.", and that retry replays the key;
   - a 5xx or a body out of contract: the key is settled and the level read back: "Not saved by this attempt. The server has X." (with " — it may have been set elsewhere" when X is the requested level, and "Not saved by this attempt, and the level could not be read back. Try again." when the read-back fails);
   - a 401, a step-up 403, any other 403, a 400 and a 422 each have their own text; the 403 is "Not saved: the server refused this change. Only the store owner can change these levels."

   A later read that moves a Saved level replaces it with "Changed elsewhere — the server now has X." Every asynchronous result applies only under the user and tenant that started it; a read-back naming another tenant restarts the panel and keeps "Your last change may have been applied to a different store. Review the levels below." until the next user change.
5. **Authority is unchanged.** The owner rule stays as R1 made it, and owner-only editing stays **flagged for owner confirmation**, contested and unresolved (DA-124). The brief lets a manager edit only with a durable, server-verifiable `manage_role_permissions` grant, and none exists. So a manager's read is refused 403 and the panel shows no levels, with the note "Server-enforced Customers access can only be viewed and changed by the store owner. Changes in the table below affect this browser only."; the PUT refuses a manager at the authorizer (403), whatever the body.

**Alternatives not taken.**
- (a) *Manager editing without a durable grant.* A role name or a client-side flag is not authority, and doc 04's server-side parity and cap rules are undefined (DA-124).
- (b) *A tenant or version precondition on the PUT.* R1's contract is unchanged in this stage; a precondition is a later contract decision (DA-125). Until then the last writer wins, and each tab shows its own read-back.
- (c) *One global Save for the whole matrix.* Sending custom roles or other domains with the Customers PUT, or calling them saved, would imply enforcement the server does not do.
- (d) *A client-built session.* An issuer key, a proof or a database key in the browser, or a session made from client claims, is refused.
- (e) *A sign-out control in the shop.* Not added; a logout follows a Firebase sign-out or a user switch only (DA-127).

**Consequences.**
- **Nothing closes.** G-IAM, G-PERSIST, G-AUDIT, G-IDEMPOT, G-DBROLE, G-MIGRATE, G-CPLOGIN, G-STATUS and G-ISOLATION stay OPEN, and DA-118 and DA-119 remain pre-deployment blockers and G-AUDIT exceptions.
  - The existing customer list and create, `GET` and `POST /api/v1/customers`, decide on the stored level (ADR-35); the shop app does not call them, and `GET /api/v1/customers/{id}` does not exist yet.
  - The tenant entry is not deployed, and the shop build and `/api/v1/*` must be served on one origin, the tenant host (DA-107).
- **Supersedes.** ADR-35's and doc 09's R1 statements that the shop editor is unchanged and calls no route are superseded for built-in Customers levels (ADR-35 amendment above).
- **Register.** DA-85 is narrowed again, not closed. DA-43, DA-107, DA-121 and DA-124 are amended. DA-125 to DA-127 are new:
  - R1's PUT has no tenant or version precondition (DA-125);
  - shop users need a PostgreSQL identity and one tenant grant, and no production provisioning exists (DA-126);
  - the shop has no sign-out control (DA-127).
- **Evidence.** Disposable PostgreSQL and local sockets only:
  - the unit suites at the network boundary: `src/tenant/tenantSessionClient.test.ts`, `src/tenant/roleLevelsClient.test.ts`, `src/tenant/ServerCustomerLevels.test.tsx`, `src/context/AccessContext.tenantSession.test.tsx` and `server/runtime/roleLevelDirectory.test.ts`;
  - `tests/db/roleLevels.integration.test.mjs` (M7RL-G01 to M7RL-G04 and M7RLH-C1, the compiled entry's nine routes) over the tenant entry;
  - `tests/browser/shopRoleLevels.browser.test.mjs`: the production shop build in a real browser on `https://shop.tmpos.test` through CDP interception, with a synthetic identity provider faked at the browser boundary plus the Firestore emulator, and the real tenant entry over disposable PostgreSQL. In CI it is the step "Shop role levels in a real browser against the tenant entry and disposable PostgreSQL (M7A-CUSTOMERS-P3-R2)", in the runner's Chrome; local runs use Chromium.

  The customer and role-level route contracts are preserved; evidence counts belong in the stage report. 001–020 and the four frozen operator paths are byte-identical, with no new migration. Code-only: nothing is deployed, and no managed database was touched.
