**Scope:** the single authoritative register of gates that must clear before production go-live. Every gate has an owner (role), milestone, required evidence, a pass/fail rule, current state, and blocking severity. **Go-live is authorized separately by the owner after M9**, only when every blocking gate is `PASS`.

**Current state:** `OPEN` (not started/in progress), `PARTIAL`, `PASS`.

- It completes the provider's MFA challenge.

**M4-ADMIN-UI-P2 (committed in `dd89ff9`) adds:**
- A read-only Command Center read model (`server/runtime/commandCenter.ts`): `GET /admin/v1/command-center` behind the admin session and `{ scope: 'platform', permission: 'view_command_center' }`, with no state-changing operation. **Pre-operation security requirement.** This blocks production session activation, operational data access (the Command Center's included) and every sensitive admin action, and nothing in M4-ADMIN-UI-P2 bypasses it; it does not block the read-only shell.

The problem is that concurrent requests on one session can interleave admission revalidation with revocation:
- A request authenticated just before a concurrent denial can still run its handler.
- The store contract does not refuse a `validatedAt` or `lastSeenAt` update, or a login's session create, issued after a concurrent `revokePrincipal`.

What is required:
- The durable store must make those updates and creates conditional on the record still being live and on the principal's current security version.
- Sensitive handlers must re-verify that version inside their own write transaction.

**M6-IDEMPOT-P2 delivers the durable idempotency contract, in code only:**
- **Route policy.** Every route declares `idempotency` (`none` or `required`), and startup refuses a missing or unknown value. `required` registers only on a state-changing route with a verified principal and a declared platform-scope authorization; a tenant- or store-scoped route may not require it until M5 supplies server-derived tenant and store context to bind. Its operation is a `perform` handed only its IdempotentContext. Every current route is `none`, and `required` exists only on synthetic test routes.
- **The step.** It runs after the client limit, CSRF and origin, authentication, authorization and the bounded body read, and just before the operation. A missing, repeated or malformed `Idempotency-Key` (one UUID version 4) is a 400. Another request under the key is a 422 `idempotency_key_reused`, identical whatever differs. One still in progress is a 409 `request_in_progress`. A store timeout, outage or malformed answer, an operation overrun, or a completion the store cannot confirm is a 503; a malformed outcome is a 500.
- **Identity.** A dedicated `IDEMPOTENCY_KEY` keys domain-separated HMACs; the composition root refuses one equal to `RATE_LIMIT_KEY`, however padded. The record is bound to the client key and the principal, so each principal has its own key namespace; the request is bound to its method, route, session boundary, reserved tenant and store slots, and body.
- **Port and replay.** `DurableIdempotencyStore` (`server/runtime/idempotency.ts`) offers acquire, a lease-checked complete and a readiness probe, and every answer is strictly validated. A recorded response is sealed (AES-256-GCM, bound to its scope and fingerprint): 200/201 or the approved 409/422 rejections, JSON only, `Location` only, at most 16 KiB. Set-Cookie, Authorization, WWW-Authenticate, CSRF and tracing material are never recorded, and each replay carries its own request ID. Crashes, timeouts and malformed outcomes are never recorded.
- **Conformance.** `assertIdempotencyStoreContract` runs over two instances sharing synthetic state, with 22 positive controls. Static containment keeps the in-process store out of the production graph.

**M6-OUTBOX-P3 delivers the atomic command transaction and the transactional outbox, in code only ([ADR-17](./10-architecture-decision-records.md)):**
- **Command routes.** A `required` route may declare a `command`: its contract (kind, create or update, one aggregate type, a change schema, the events it may enqueue), validated at startup against a closed event registry, and a synchronous planner handed only the session boundary, the parsed body and a runtime-generated aggregate ID. The runtime enforces only that the planner returns a plan and no thenable; that it returns nothing it captured or imported, and makes no effect, are source-review rules, so atomicity covers what its plan hands the store, never an effect beside it. `perform` keeps the crash window and is never approved for a production route.
- **The transaction port.** `CommandTransactionPort` (`server/runtime/commandTransaction.ts`) commits, in one transaction, the lease check (the fencing token, checked first), the mutation at its expected version, the sealed completion, the audit record and the events — or nothing — answering `committed`, `lease_lost`, `conflict` or `unavailable`, strictly validated. The response is sent only after `committed`; a conflict is a 409 `write_conflict` that records nothing; every other outcome is a bounded 503 that assumes no rollback and releases no lease, so a retry replays a committed record or waits on the lease, and a stale attempt's late commit is fenced out.
- **The outbox.** An immutable envelope — event ID, type and version from a closed registry, aggregate type, ID and version, tenant/store/actor slots (null until M5), a server-generated correlation ID, a bounded flat payload (at most 4 KiB, explicit schema) and the store's transaction timestamp — with delivery metadata kept outside it. `OutboxDeliveryStore` (`server/runtime/outbox.ts`) claims atomically under fencing tokens with store-clock expiry, in batches of at most 32; only the holder acknowledges, retries or dead-letters; retries back off from 1 s to 15 min over at most 20 attempts. `deliverOutboxBatch` is one bounded pass; no worker runs. Delivery is at least once until dead-lettered: consumers deduplicate by event ID, and neither ordering nor exactly-once delivery is claimed.
- **Conformance.** `assertCommandTransactionContract` and `assertOutboxDeliveryContract` (`server/runtime/transactionalOutbox.testkit.ts`) run over two instances sharing synthetic state, with 17 positive controls each. Static containment keeps the in-process adapters, any delivery loop, SQL and database or network clients out of the production graph, and the approved-adapter table stays closed.

### G-DBROLE — the live role-topology check for the transactional store (recorded in M6-PG-P5; not run)

Migration 006 proves only the direct object grants on its own objects, and only when it runs. Before the adapter is bound, the owner-authorized G-DBROLE step must show — read-only, against the real database and the real runtime LOGIN (`<login>` below) — that effective reach still matches those grants. Run every query in a session that first executes `set search_path = pg_catalog, pg_temp`, so no operator or function planted in another schema answers in place of pg_catalog's. 1. **The login.** `select rolsuper, rolinherit, rolcreaterole, rolcreatedb, rolreplication, rolbypassrls, rolcanlogin from pg_catalog.pg_roles where rolname = '<login>'` → `f, t, f, f, f, f, t`.

3. **No path to an owner or a superuser.** `select count(*) from pg_catalog.pg_roles r where (r.rolsuper or r.rolbypassrls or r.oid in (select nspowner from pg_catalog.pg_namespace where nspname in ('tmpos_internal', 'public') union select relowner from pg_catalog.pg_class where relnamespace = 'tmpos_internal'::regnamespace or oid = 'public.audit_event'::regclass union select proowner from pg_catalog.pg_proc where pronamespace = 'tmpos_internal'::regnamespace or (pronamespace = 'public'::regnamespace and proname in ('reject_audit_event_mutation', 'audit_metadata_is_flat')))) and pg_catalog.pg_has_role('<login>', r.oid, 'MEMBER')` → `0`.
