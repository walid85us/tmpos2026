# 08 — Production Gate & Risk Register

**Scope:** the single authoritative register of gates that must clear before production go-live. Every gate has an owner (role), milestone, required evidence, a pass/fail rule, current state, and blocking severity. **Go-live is authorized separately by the owner after M9**, only when every blocking gate is `PASS`.

**Severity:** `BLOCKER` (go-live cannot proceed), `HIGH` (must be resolved or explicitly owner-waived), `MED` (resolve or accept with documented risk).
**Current state:** `OPEN` (not started/in progress), `PARTIAL`, `PASS`.

**M4-ADMIN-UI-P1 (committed in `dd89ff9`) adds the browser half:**
- The admin console signs in through the existing Firebase client SDK, using an in-memory instance.
- It completes the provider's MFA challenge.
- It exchanges the one ID token at `POST /admin/v1/session/login`.
- It keeps the session CSRF token in memory only.
- It renders the read-only shell only after `GET /admin/v1/session` confirms the session.
- In production it runs only on a configured administration origin and refuses everywhere else.

It is not live either: with no composed boundary, the console reports sign-in as unavailable.

**M4-ADMIN-UI-P2 (committed in `dd89ff9`) adds:**
- A read-only Command Center read model (`server/runtime/commandCenter.ts`): `GET /admin/v1/command-center` behind the admin session and `{ scope: 'platform', permission: 'view_command_center' }`, with no state-changing operation. It maps an injected reader port into a bounded view (posture counts, per-area attention counts, governance signals, service health; each section available, unavailable or not configured, with `asOf` and `stale`), and no reader string reaches the output. The route is uncomposed — neither the composition root nor the deployable entry imports it — and no authoritative source exists (M7h), so its data is synthetic: test adapters and hermetic browser interception only. The console dashboard (`/admin`) refreshes manually only, and an unavailable section never shows a number, including a reading that ages past 24 hours while the page is open (counted from the server's generation instant).
- The admin second factor is TOTP only, in the console and the server login policy: phone needs reCAPTCHA hosts the admin CSP refuses ([03](./03-backend-control-plane-login-session-blueprint.md) §2a).

**Pre-operation security requirement.** This blocks production session activation, operational data access (the Command Center's included) and every sensitive admin action, and nothing in M4-ADMIN-UI-P2 bypasses it; it does not block the read-only shell.

The problem is that concurrent requests on one session can interleave admission revalidation with revocation:
- A request authenticated just before a concurrent denial can still run its handler.
- The store contract does not refuse a `validatedAt` or `lastSeenAt` update, or a login's session create, issued after a concurrent `revokePrincipal`.

What is required:
- The durable store must make those updates and creates conditional on the record still being live and on the principal's current security version.
- Sensitive handlers must re-verify that version inside their own write transaction.

**Deployment invariants (M4-ADMIN-UI-P2).** Before any admin host serves the console:
- The Firebase project must not enforce reCAPTCHA (Enterprise) for email/password sign-in while the admin CSP excludes reCAPTCHA; otherwise every admin password sign-in fails closed as "unavailable".
- HSTS `includeSubDomains` requires every subdomain of the admin host — and of the runtime host, where the production entry (`server/entry/productionEntry.ts`) sends HSTS on every response (`hsts: true`) — to serve HTTPS.
- The Firebase web API key the console uses must not rely on an HTTP-referrer restriction: the Auth SDK sends its identity-toolkit requests with `referrerPolicy: 'no-referrer'` (and the admin document's `Referrer-Policy` is `no-referrer`), so a referrer-restricted key refuses every admin sign-in.
- The admin host must serve the console through `createAdminWebListener`, with `/admin/v1/*` routed to the runtime — never a static host with SPA fallback. No admin-host deployment exists yet.

**M5-GIAM-D1-P4 makes the administrative boundary's admission and authorization durable, in code only ([ADR-25](./10-architecture-decision-records.md)):**
- **Admission.** Migration 013's one `STABLE SECURITY DEFINER` read, `tmpos_admission.m5_admit_platform_session`, answers in one snapshot migration 007's resolution narrowed to the actor's PLATFORM grants, plus the actor's platform authority version. The adapter (`server/persistence/postgresPlatformAdmission.ts`) reports that answer and decides nothing. `createPlatformSessionAdmission` (`server/composition/platformAuthorization.ts`) admits only an `active` or `trialing` account with no read-only cap, holding exactly one active platform grant (none is unauthorized, two are ambiguous, and there is no first match) whose role the canonical catalog defines. A tenant or store grant never confers platform authority, whatever role id it carries.
- **Witness.** The session is bound to `p1:` plus a SHA-256 digest over the actor, the account status, its cap, 007's security version, the grant, its role and the platform authority version. The boundary re-asks on EVERY protected request, the current-session read included (`ADMISSION_REVALIDATE_MS.admin = 0`; it was 1 min); logout never asks. A denial revokes every administrative session of the principal and no tenant session; a changed witness revokes the session presented; an outage is a bounded 503 that revokes nothing. The authority version only increases, so a restoration — a grant re-enabled or re-inserted, a role changed back, an account restored — revives no session. A tenant's state is not in the witness, so suspending a tenant logs out no administrator.
- **Authorization.** The canonical authorizer (`createAdmittedPlatformAuthorizer`) decides on the scope that same request's admission selected, never on a second read; `createPlatformRouteAuthorizer` is removed. A command still re-reads its authority inside the committing transaction (migration 009, unchanged).
- **Composition.** The transaction root builds the PostgreSQL platform admission over its one kernel, and the sessions root binds the admission and the authorizer together from it (`durableSessionAdapters`), never one alone. Handed that bundle, `admin_admission_unavailable` and `admin_authorizer_unavailable` no longer arise; `rate_limit_store_unavailable` remains, so production composition still refuses *(until M6-RATE-P2, below)*, and no production entry composes either root. Readiness now includes the administrative admission's probe. The tenant admission offers no probe, so it is still not part of readiness.
- **Evidence**, against disposable PostgreSQL only: `tests/db/platformAdmission.integration.test.mjs` (migration 013) and `tests/db/adminBoundary.integration.test.mjs` (the composed administrative boundary over real local sockets).

**M6-IDEMPOT-P2 delivers the durable idempotency contract, in code only:**
- **Route policy.** Every route declares `idempotency` (`none` or `required`), and startup refuses a missing or unknown value. `required` registers only on a state-changing route with a verified principal and a declared platform-scope authorization; a tenant- or store-scoped route may not require it until M5 supplies server-derived tenant and store context to bind. Its operation is a `perform` handed only its IdempotentContext. Every current route is `none`, and `required` exists only on synthetic test routes.
- **The step.** It runs after the client limit, CSRF and origin, authentication, authorization and the bounded body read, and just before the operation. A missing, repeated or malformed `Idempotency-Key` (one UUID version 4) is a 400. Another request under the key is a 422 `idempotency_key_reused`, identical whatever differs. One still in progress is a 409 `request_in_progress`. A store timeout, outage or malformed answer, an operation overrun, or a completion the store cannot confirm is a 503; a malformed outcome is a 500.
- **Identity.** A dedicated `IDEMPOTENCY_KEY` keys domain-separated HMACs; the transaction composition root (and the runtime at startup) refuses one equal to `RATE_LIMIT_KEY`, however padded. The record is bound to the client key and the principal, so each principal has its own key namespace; the request is bound to its method, route, session boundary, reserved tenant and store slots, and body.
- **Port and replay.** `DurableIdempotencyStore` (`server/runtime/idempotency.ts`) offers acquire, a lease-checked complete and a readiness probe, and every answer is strictly validated. A recorded response is sealed (AES-256-GCM, bound to its scope and fingerprint): 200/201 or the approved 409/422 rejections, JSON only, `Location` only, at most 16 KiB. Set-Cookie, Authorization, WWW-Authenticate, CSRF and tracing material are never recorded, and each replay carries its own request ID. Crashes, timeouts and malformed outcomes are never recorded.
- **Conformance.** `assertIdempotencyStoreContract` runs over two instances sharing synthetic state, with 22 positive controls. Static containment keeps the in-process store out of the production graph.

**M6-OUTBOX-P3 delivers the atomic command transaction and the transactional outbox, in code only ([ADR-17](./10-architecture-decision-records.md)):**
- **Command routes.** A `required` route may declare a `command`: its contract (kind, create or update, one aggregate type, a change schema, the events it may enqueue), validated at startup against a closed event registry, and a synchronous planner handed only the session boundary, the parsed body and a runtime-generated aggregate ID. The runtime enforces only that the planner returns a plan and no thenable; that it returns nothing it captured or imported, and makes no effect, are source-review rules, so atomicity covers what its plan hands the store, never an effect beside it. `perform` keeps the crash window and is never approved for a production route.
- **The transaction port.** `CommandTransactionPort` (`server/runtime/commandTransaction.ts`) commits, in one transaction, the lease check (the fencing token, checked first), the mutation at its expected version, the sealed completion, the audit record and the events — or nothing. Since **M5-GIAM-D1-P2-R1** there is one further committed shape: a completion ALONE, carrying a deterministic rejection and no business state — answering `committed`, `lease_lost`, `conflict` or `unavailable`, strictly validated. The response is sent only after `committed`. Since **M5-GIAM-D1-P2-R1** the two deterministic post-authorization rejections are *sealed*: a `conflict` (the aggregate is not at the version named) and, for an update, an `invalid_state` (its state does not admit the change) each record their own bounded 409 as the completion, in the very transaction that fenced the lease, revalidated the authority and locked the row — writing no mutation, no audit record and no event. The intent is therefore decided once: an identical retry replays that 409 instead of being replanned (with the one pre-existing ambiguity every commit has — a COMMIT whose acknowledgement is lost answers the first caller 503, and the retry then replays the sealed 409), the same key with any other request is the 422 key reuse, and a key that was refused can never later become a mutation while its record is retained. If the completion does not hold, the whole transaction rolls back to `unavailable` and the lease is left to expire exactly as before. The remaining outcomes are not all 503s: an update's missing aggregate is a bounded 404 and an update whose changes already hold is its recorded 200; only a lost lease, an unavailable or timed-out store and an answer that does not conform map to a bounded 503, which assumes no rollback and releases no lease, so a retry replays a committed record or waits on the lease, and a stale attempt's late commit is fenced out.
- **The outbox.** An immutable envelope — event ID, type and version from a closed registry, aggregate type, ID and version, tenant/store/actor slots (null until M5), a server-generated correlation ID, a bounded flat payload (at most 4 KiB, explicit schema) and the store's transaction timestamp — with delivery metadata kept outside it. `OutboxDeliveryStore` (`server/runtime/outbox.ts`) claims atomically under fencing tokens with store-clock expiry, in batches of at most 32; only the holder acknowledges, retries or dead-letters; retries back off from 1 s to 15 min over at most 20 attempts. `deliverOutboxBatch` is one bounded pass; no worker runs. Delivery is at least once until dead-lettered: consumers deduplicate by event ID, and neither ordering nor exactly-once delivery is claimed.
- **Conformance.** `assertCommandTransactionContract` and `assertOutboxDeliveryContract` (`server/runtime/transactionalOutbox.testkit.ts`) run over two instances sharing synthetic state, with 17 positive controls each. Static containment keeps the in-process adapters, any delivery loop, SQL and database or network clients out of the production graph, and the approved-adapter table stays closed.

**M6-RATE-P2 delivers the distributed rate-limit store and composes it in code, proven against disposable PostgreSQL only ([ADR-26](./10-architecture-decision-records.md)):**
- **Migration 014** (`server/platform-identity/migrations/014_m6_distributed_rate_limit.*`): schema `tmpos_rate_limit` with the bucket table (one row per namespace, dimension, pseudonymous key, limit and window, with database-enforced bounds and an expiry index), a one-row key-fingerprint table, and four routines — the consume, the probe and the reclaim, `SECURITY DEFINER`, and the key check the consume and the probe share, granted to nobody. `tmpos_app` holds USAGE and EXECUTE on the consume, the probe and the reclaim, and no table privilege; section 6 also refuses when `tmpos_audit_writer`, `anon` or `authenticated` can execute any of them, by a grant or by membership in `tmpos_app`. - **The store's contract.** A fixed window from the first successful consume, never extended; a consume atomic across instances through its bucket's row lock, except one the committed state already refuses, which is answered from an unlocked read; a refused consume that changes nothing; a retry-after on the database's clock; policy and namespace isolation through the bucket key. There is no retry, queue, cache or local fallback.
- **Key skew.** The store registers the fingerprint of the first `RATE_LIMIT_KEY` it sees, atomically, and refuses every other. Nothing erases or replaces it; recovering from a wrong first registration is a manual operator procedure, and rotation needs a coordinated procedure that does not exist (DA-53).
- **Cleanup.** A separate reclaim routine, called by the adapter in its own short transaction: one call owed per consume that opened a window, run one at a time per instance; its failure changes no consume.
- **Composition.** The transaction root builds the adapter (`server/persistence/postgresRateLimiter.ts`) over its one kernel, and the sessions root binds it with the key it parsed itself. Readiness includes the limiter's probe.

### Runtime database-endpoint classification (recorded M6-PG-P7-R1; persisted M5-ID-P1)

Four clarifications about `classifyRuntimeDatabaseUrl` (`server/platform-identity/databaseEndpoint.ts`), the gate that decides whether an `APP_DATABASE_URL` may be used at all. They record behaviour that already exists; none changes it.

1. **Precedence, in order.** A missing value; a space or control character; an unparseable URL, then a wrong protocol; the host, then the port; a routing (`host`, `hostaddr`, `port`) or pooling (`pgbouncer`, `pool_mode`) query parameter, which is `app_database_endpoint_unsupported`; any *other* `?` or `#`, which is `app_database_url_invalid`; the authority's spelling; the credentials and database name; a pooler username missing its project reference; and last, a username and host naming different projects. So an endpoint refused as unsupported is never also reported as invalid, and the pooling refusal is reached before the generic query-parameter one.
2. **Identical to the migration executor's managed-DSN validator:** the postgres scheme; the direct and pooler host patterns, and the refusal of any other `db.` host; port 5432 only; the `pgbouncer` and `pool_mode` rules; the role pattern; the refusal of a username/host project mismatch; and a required password.
3. **Stricter at runtime than the executor:** the value is judged as written, so any whitespace or control character is refused; `hostaddr` and `port` are refused as well as `host`; *every* occurrence of a pooling parameter is checked, not just the first; any other query parameter or fragment is refused outright; the authority must be spelled exactly (`:05432`, an empty `:`, or two `@` are refused); the database name must have a valid shape; and a NUL in the password is refused. The executor alone additionally checks agreement with the project URL and the expected database name — a managed-target concern the runtime has no equivalent of.
4. **Composition is route-ready; the deployable entry is routeless (until M6-ENTRY-P1).** `server/composition/productionTransactions.ts` classifies the endpoint before anything is built, but its production inventory holds no route, so nothing is read, classified or connected today; the deployable entry (`server/runtime/server.ts`) serves the probes and the bounded fallback only. *Since M6-ENTRY-P1, `server/runtime/server.ts` is deleted and the deployable entry (`server/entry/productionEntry.ts`) serves exactly the approved inventory — the two probes and the six administrative routes, then the bounded 404 — and the transaction root classifies `APP_DATABASE_URL` for those routes before anything is built; in code only, not deployed.* Separately, the unclassified `getRuntimeDb()` client — which skips this classifier — has exactly three callers, all DEV-only and none reachable from a deployable entry: `db.ts` (defines it), `authorizationRepository.ts` (the DEV control plane) and `platform-identity/server.ts` (the DEV sidecar's readiness probe, which binds a listener only under `npm run identity:api`). ### The distributed rate-limit store — operating limits (recorded M6-RATE-P2; [ADR-26](./10-architecture-decision-records.md))

What migration 014 and `server/persistence/postgresRateLimiter.ts` do in operation, and what a deployment must still provide. None of it is live: no deployable entry composes the store *(until M6-ENTRY-P1; since then the deployable entry, `server/entry/productionEntry.ts`, composes it through the transaction root in code only, not deployed)*.

1. **Failure.** Any outage, timeout (lock 200 ms, statement 300 ms, idle-in-transaction 400 ms, and the 500 ms limiter cap), abort, malformed answer or key mismatch refuses the request with a bounded 503, logged as `rate_limit_unavailable` or `rate_limit_timeout`, and never allows it. The adapter answers at its 500 ms bound even with COMMIT in flight; an allowance committed after it is answered unavailable, so its cost is spent and no allowance goes unrecorded. The same conditions make the probe false, and so does a read-only session or a standby (`store_read_only`), so `/readiness` answers 503; `/health` never touches the limiter. There is no local fallback while PostgreSQL is down.
2. **Load.** Every protected request is at least one short transaction on the primary database, which writes whenever the consume is allowed; a login is up to three. A consume the committed state already refuses (a live window whose count plus the cost exceeds the limit) is answered from an unlocked read: no row lock and, once the key fingerprint is registered, no transaction ID and no WAL; a refusal racing the consume that spends the last allowance can still take the locked path. These transactions share the runtime kernel's ten one-connection pools (`RUNTIME_POOL_MAX` in server/platform-identity/db.ts, at the supervised client's `MAX_POOLS` ceiling) with sessions, admission and commands. The adapter serializes consumes per bucket per instance, so one source holds at most one connection per bucket it reaches, however many requests it sends — a source that reaches several buckets can still hold several connections, and many sources can exhaust the pool (DA-52); at most 64 consumes of one bucket wait per instance, the one in flight included (`RATE_LIMIT_LANE_DEPTH`), and past that a consume of that bucket is a 503 at once. A consume aborted before its COMMIT leaves its transaction open on the server until the server sees the retired session end, so the next consume of that bucket can wait on the row and is a 503 past its 200 ms lock bound (DA-52). Many sources can still exhaust the ten connections, which the edge must absorb (DA-52).
3. **Cleanup.** Never inside a consume. After an allowed consume that opened a window, the adapter calls `m6_rate_limit_reclaim()` in the background, in its own transaction under 50 ms lock, statement and idle bounds. Each such consume the adapter answers owes one call (one whose window opened only after its caller was answered unavailable owes none); owed calls run one at a time per instance, the next only after one deleted a full four, and one that deletes fewer, or fails, clears what is owed. Each call deletes at most four expired buckets, oldest first, through the expiry index, skipping locked rows, each by its primary key; its failure changes no consume. Its lock hold is bounded far below a consume's 200 ms lock wait, so a consume of an expired bucket being reclaimed still succeeds. The probe never cleans, and there is no timer or worker. So after a burst each window opened is matched by up to four reclaimed while a backlog remains and reclaims succeed; during a burst of new clients windows can open faster than one reclaim at a time clears them, and with no traffic the backlog stays. Under a long-held database snapshot (a long transaction, a replication slot, `pg_dump`), vacuum cannot clear the dead entries that window reopens (non-HOT updates) and reclaims leave at the low end of the expiry index; with about 100,000 of them (a one-off check on a throwaway local PostgreSQL 16 cluster, not part of the committed tests) both reclaims tried failed at the 50 ms statement bound (SQLSTATE 57014) until the snapshot ended. Storage grows meanwhile; consumes, which use the primary key, are unaffected. Monitor reclaim failures with SQLSTATE 57014, long transactions and the xmin horizon's age, and the table's bloat (DA-52).
4. **The key.** `RATE_LIMIT_KEY` must be identical on every instance. The first consume or probe registers its fingerprint in the database; an instance with any other key answers every protected request 503 and fails readiness. If a wrongly keyed instance calls first after 014 is applied, every correctly keyed instance is locked out that way. A holder of the runtime database credential can do the same on purpose without the key, by calling the consume or the probe first with a fingerprint of its choosing between 014's apply (or a re-apply after rollback) and the first correctly keyed call; that locks every instance out, fails closed and grants no allowance (DA-53). Runbook step: right after applying 014, have a correctly keyed instance call (its readiness probe registers the key) before anything else holds the `tmpos_app` credential, or have the owner confirm that the registered fingerprint equals HMAC-SHA256 keyed with the bytes `RATE_LIMIT_KEY` decodes to (not its text) over the ASCII string `tmpos-rate-limit-key-fingerprint:v1`, as `rateLimitKeyFingerprint` computes it. Recovery is an operator procedure: stop the wrongly keyed instances, confirm the intended key's fingerprint, delete the one `key_fingerprint` row as the owner in a maintenance window, and let a correctly keyed instance register. No routine does it, and nothing does it automatically. Rotation needs a coordinated procedure that does not exist (DA-53). 014's rollback also removes the fingerprint, drops every bucket with it, refuses first unless its transaction is READ COMMITTED (at a stricter level an earlier statement's snapshot could hide a window opened while its lock was awaited), takes its locks before its check, and refuses while any window is live.
5. **Trusted proxies (deployment work, unchanged by this stage).** `TRUSTED_PROXY_CIDRS` must list exactly the real edge's egress ranges, covering every hop and nothing wider. The edge must append to or overwrite `X-Forwarded-For` and be the runtime's only way in, and must present IPv4 clients as IPv4 or IPv4-mapped addresses (see G-IDEMPOT on NAT64). No real edge or proxy has been exercised, so that contract is unproved (G-UNAUTH, DA-9).
6. **Measured local limits.** A bounded concurrency check on a local disposable PostgreSQL 16.10 cluster over a Unix socket, run twice: with durable commits (`fsync` and `synchronous_commit` on, as CI's stock server) and with `fsync` off. It is not a production throughput claim: it says nothing about a managed database, network latency, pool contention with real sessions and commands, or failover.
   - Concurrency: 2 limiter instances on 2 kernels of 6 connections each, so 12 transactions in flight (32 concurrent callers).
   - Consumes: 2,000 — 600 on one hot bucket (limit 500) and 1,400 over 400 cold keys (limit 3).
   - Duration: durable commits 2,536 ms (789 consumes/s), latency p50 6.96 / p95 159.48 / p99 171.64 / max 193.59 ms; `fsync` off 1,352 ms (1,480/s), p50 4.81 / p95 75.82 / p99 89.45 / max 101.34 ms.
   - Errors and timeouts: in both runs 1,340 allowed, 660 limited, 0 unavailable, 0 database errors, 0 faults; background reclaims 162 (durable) and 95 started, at most 1 in flight per instance, 0 failed.
   - Exact accounting: held in both runs — 0 buckets over-allowed, 0 under-counted. One bucket, 120 concurrent consumes over 4 instances with limit 40 under durable commits: exactly 40 allowed, 80 limited, 0 unavailable, in 211–277 ms across runs.
   - One hot bucket's ceiling: an earlier durable run of 200 concurrent consumes of one bucket (limit 100, before refusals became lock-free) lost 76 to the 500 ms deadline. With durable commits one bucket grants on the order of a hundred allowances per 500 ms, since each allowance holds the row through its WAL flush.

- **Go-live rule:** every `BLOCKER` must be `PASS` and every `HIGH` must be `PASS` or explicitly owner-waived (with documented risk) before G-GOLIVE can be requested.
- **Security-HIGH waiver rule:** waiving any **security** HIGH gate (e.g. G-APPSEC, G-WEBHARDEN, G-PROVIDER) requires, in addition to owner sign-off, (a) **Security sign-off**, (b) a **documented compensating control**, and (c) a **time-boxed remediation date**. This is why the previously-waivable security-integrity gates (webhook signature verification, the hardcoded PIN, the RLS-bypassing DB role, money-path idempotency) were **elevated to BLOCKER** rather than left owner-waivable.
- **Non-waivable carve-out — G-APPSEC's lockfile-portability subcriterion.** A G-APPSEC waiver may cover SAST/DAST/SCA **findings** (e.g. an open transitive High). It may **never** waive the pre-install lockfile-portability checker, which is **non-waivable and blocks merge independently of G-APPSEC's disposition**. Without this carve-out a subcriterion silently inherits its parent's waivability, and a waiver granted over an unrelated advisory would dissolve supply-chain lock integrity along with it — which nobody granting such a waiver intends. The carve-out is required because the usual "it would fail anyway" reasoning is **false here**: an unportable lockfile does **not** reliably break the build — npm *skips* an unfetchable `optional`/`devOptional` package and `npm ci` still exits 0. That silent path is the realised failure this gate exists to prevent (a green install that omitted `@types/react`), so the control cannot rest on the build failing loudly. Per the precedent above, a security-integrity control that must not be waivable is treated as blocking regardless of its host gate's severity.
- **Legal-HIGH waiver rule:** **G-PRIVACY is a statutory gate** (GDPR Arts 15–22 DSAR, CCPA/CPRA) — its absence at go-live is a legal violation, not a discretionary risk. Waiving G-PRIVACY (or its core export/deletion sub-scope) requires, beyond owner sign-off, (a) **legal-owner sign-off**, (b) a **documented lawful basis**, and (c) a **time-boxed remediation date** — an owner alone may not waive it. The core DSAR-fulfilment sub-scope is treated as effectively blocking for any deployment processing EU/CA-resident PII.
- **Severity semantics:** a gate's blocking severity may **exceed** the defect severity of its source gap (defect severity ≠ go-live-blocking severity). Examples: GAP-18 (defect High) → G-EMU (BLOCKER); GAP-24 (defect Medium) → G-HIST (HIGH). This is intentional, not an error.
