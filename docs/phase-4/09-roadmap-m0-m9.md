# 09 — Authoritative Roadmap M0–M9 & Deferred-Work Reconciliation

**Scope:** the single authoritative Phase 4 milestone spine. No milestone exists outside M0–M9 (with M7 subdivided into M7a–M7h). There is no M10, M11, Phase 4.1, or "post-Phase-4" milestone in this roadmap. Any activity not assigned to M0–M9 is explicitly classified as out-of-product-scope, post-production enhancement, owner-declined, or superseded.

**Deployment / go-live is not a milestone.** It is a separate explicit owner authorization that may only be requested after M9 completes.

## 2. Milestone detail

### M2 — Quality baseline, test architecture, build integrity, emulator/CI foundation
Establish the mandatory test pyramid ([07](./07-quality-and-test-strategy.md)); stand up a **Java-enabled environment** so the Firestore emulator semantic suite runs (clears M0 G-EMU as a repeatable gate, not a one-off); wire CI to run unit/authz/contract/emulator suites and block merges on red; stand up **application-security scanning — dependency-audit/SCA + SAST on every PR, DAST against staging (G-APPSEC)** — restoring the static-analysis control the disabled Semgrep hook dropped; formalize the typecheck baseline as a ratchet (never regress; drive toward zero). No production runtime yet.

### M3 — Deployable backend runtime & infrastructure foundation
Choose and stand up the server runtime and environments (local/test/staging/production) per [02](./02-target-production-architecture.md); deliver a **migration runner** (today migrations are file-only, applied manually — see §3); a **secrets store** (no secrets in memory, no unauthenticated credential endpoints); connection-role separation (an app role that does **not** own tables / does not bypass RLS for tenant paths). M3 also performs **early remediation that must not wait for M8**: **eliminate or firewall the DEV Express sidecars** so no unauthenticated route (Shipping API, the open `label-proxy` SSRF, the unauthenticated `/identity/resolve` Postgres write) is reachable in any deployed environment; establish **shared enforced middleware** (auth/CSRF/rate-limit/security-headers) so protection is uniform, not per-route. It lays the **tenant-isolation foundation** — tenant context, server-side membership resolution, the RLS policy shape, and cross-tenant/cross-store test fixtures — and wires a **minimal durable `audit_event` writer** so audited operations in M4/M5 are covered before full audit lands in M6.

### M4 — Separate Backend Control Plane login, session & admin shell

Both share one canonical IAM catalog and one status model. The admin shell is wired to server endpoints; between M4 and M5 admin endpoints enforce only the **narrow pilot guard** (`system_owner` exact-eq) until M5 generalizes authorization. Absorbs the read-only Backend Control Plane already drafted in DEV (see §3 reconciliation). **Progress (committed in `dd89ff9`, not live):** the runtime carries both session boundaries (`/api/v1/session/*`, `/admin/v1/session/*`) with session-bound CSRF, login limits, bounded port calls with cancellation signals, admission revalidation (a denial revokes every session of the principal), admin MFA and recent authentication, and host-distinct origins; a provider-aware production composition root (`server/composition/productionSessions.ts`) refuses to compose until a durable session store and the admission and authorizer adapters exist (G-DBROLE, migration 005, M5). Step-up for sensitive actions and the login/logout audit record remain. *(Update, M5-GIAM-D1-P4: the durable session store and both boundaries' admissions and authorizers now exist in code, over migrations 011 and 013; the root still refuses on `rate_limit_store_unavailable`, and no production entry composes it.)* *(Update, M6-RATE-P2: that blocker no longer arises for a composition handed the transaction root's bundle and a valid `RATE_LIMIT_KEY` — the PostgreSQL rate-limit store, migration 014, [ADR-26](./10-architecture-decision-records.md); no production entry composes the root yet.)* *(Update, M6-ADMIN-AUDIT-P1: the administrative boundary's login/logout audit record is delivered in code, [ADR-29](./10-architecture-decision-records.md); the tenant boundary's is not.)*

**Admin UI (M4-ADMIN-UI-P1, committed in `dd89ff9`, not live):**

### M5 — Canonical IAM, tenant, store, permission & entitlement governance
Make **server-derived authorization the source of truth** ([04](./04-canonical-iam-and-four-user-migration.md)). M5 is large and is the hard dependency for all of M7, so it executes in **three ordered internal phases (execution phasing within M5 — not new milestones):** **(i)** authorization service + family-aware permission semantics (tenant/store and platform orderings recognized by family) + money actions as explicit editable capabilities + server-derived context (resolves the always-null authorization field); **(ii)** move plan/feature entitlements and platform permissions off client `sessionStorage` into server-owned storage; **(iii)** enforce suspended/inactive/parity/cap fail-closed + execute the four-user migration contract + tenant/store isolation enforcement. **M5 depends on M3, M4, and the minimal audit writer (M3/M4)** so that its provisioning/grant changes are durably audited. M5 also delivers the **DSAR requester/tenant/platform authorization** boundary (identity verification, tenant approval + platform escalation) per the [05 §6](./05-canonical-data-ownership-and-api-db-contracts.md) privacy contract, and the **store-scoped payment-gateway permissions** + platform delegated-support elevation model ([04 §2.1](./04-canonical-iam-and-four-user-migration.md), [03 §8](./03-backend-control-plane-login-session-blueprint.md)).

**Progress — M5 phase (i), stage M5-ID-P1 (code only, no business route, nothing live).** The trusted identity boundary phase (i) needs is delivered:
- **Migration 007 (`007_m5_trusted_principal_resolution`)** creates its own schema, `tmpos_identity`, holding three routines, and **no table, no column and no role** (corrected in M5-GAP11-P1-R1: an earlier revision said it adds them to 006's `tmpos_internal`; 007 keeps them apart because 006's rollback drops `tmpos_internal` without CASCADE). `m5_resolve_principal(provider, uid)` turns a reference the authentication boundary has ALREADY verified into the app-owned `internal_user_id`, the account status, a security version and the actor's usable membership grants; `m5_revalidate_principal_context(...)` re-reads that authority inside a committing transaction; a private helper computes the version. Both entry routines are SECURITY DEFINER with a pinned `search_path`, revoked from PUBLIC, and granted EXECUTE to `tmpos_app` alone.
- **The runtime role still holds no privilege on any identity relation.** Migration 005 grants `tmpos_app` nothing on `platform_identity`, `app_user` or `identity_link`, and 007 grants it nothing either — so the runtime reaches trusted identity only through those two routines. So the path a production route will take never needs the OWNER connection that `authorizationRepository.ts` uses today — but **no existing caller was converted**: that file is untouched, it is the DEV control plane reachable from no deployable entry, and replacing it is later M5 work. The **G-DBROLE** identity-read half is closed for new production code (a containment test refuses a direct identity read from `server/runtime`, `server/persistence` or `server/composition`); the credential half (a runtime LOGIN role) remains.
- **The security version** is a digest of the account status and identity-link lifecycle — the state that decides whether a person may hold a session at all. Membership grants are deliberately excluded, so withdrawing one grant invalidates a command without revoking every session that person holds elsewhere.
- **Transaction-local revalidation (the pre-operation half of G-CPLOGIN).** A command that carries a trusted context is re-read on its own transaction, **after** the idempotency fence and **before** any business state: account status, security version, tenant/store status and the active membership at exactly that scope, each row `FOR SHARE` in one fixed order so a racing revocation is deterministic. A failure commits no mutation, no idempotency completion, no audit record and no event, and answers the same bounded outcome an outage gives.
- **Actor attribution (part of G-AUDIT).** The command AUDIT record now carries the app-owned actor **from that trusted context** — never a caller-supplied value; with no context it stays null, exactly as before. An outbox event names no actor, tenant or store in either case: migration 006 types those columns as keyed digests rather than identifiers, and this stage keys none. A read-only context (a `read_only` or `overdue` account, tenant or store) may not commit a command at all.
- **Server-derived scope** is a pure selection over the resolved grants: a request's tenant or store id is a SELECTOR only, an ambiguous or unmatched selection is refused, and **no default scope is invented** because no authoritative document defines one.
- **Canonical permissions** are the existing catalog exposed once, matched exactly and case-sensitively, fail-closed on unknowns. **Tenant- and store-scope permissions remain UNDECIDABLE** until GAP-11's ordering unification and its six mandatory safeguards land ([04 §3](./04-canonical-iam-and-four-user-migration.md)) — only one of those, #3 (explicit approval of the grant diff), is assigned to the owner by 04 §3 — since decided as D3, which rejected every change the unified ordering makes and approved, conditionally, the resulting zero-diff artifact (M5-GAP11-P3, candidate only, not a cutover); #1 (the per-action re-pin) is an open policy choice 04 §3 leaves unmade (corrected in M5-GAP11-P1), since decided by the owner as D2 — an explicit per-role grant, carried in the candidate only (M5-GAP11-P2) — so a deployed route declaring one is refused at startup rather than guessed at. *(Update, M5-GAP11-P5: GAP-11 is closed at repository level by family-aware semantics, [ADR-19](./10-architecture-decision-records.md); tenant and store scope stay undecidable in the route catalogue until owner decision D1 defines a specific route and its authoritative product rules.)*

### M6 — Shared durability foundation
Expand the durable audit writer (seeded minimally in M3/M4) to **every** authorization/mutation path, and deliver durable idempotency, event/outbox, credential encryption + rotation, and transaction standards ([05](./05-canonical-data-ownership-and-api-db-contracts.md)). The **minimal** audit writer lands in M3/M4 (so M5's provisioning is audited); M6 completes coverage and adds the outbox/idempotency/rotation machinery. M6 depends only on M3, so it may run before or alongside M5. M6 also lays the **DSAR audit, request workflow, event, and retention/legal-hold foundations** ([05 §6](./05-canonical-data-ownership-and-api-db-contracts.md)).

**M6-RATE-P1 (committed in `dd89ff9`; accepted as a code-only foundation, not live) — trusted-proxy identity and the distributed rate-limit foundation:**
- **Client address.** One resolver (`server/runtime/clientAddress.ts`) decides who the client is:
  - The socket peer is the client, unless the peer is inside an explicitly configured trusted-proxy CIDR.
  - Only then is `X-Forwarded-For` read, walked right to left to the first untrusted hop. At most 8 entries are examined; the header may be at most 512 characters, on one line. `Forwarded` and `X-Real-IP` are never read.
  - IPv4 clients are limited per address and IPv6 clients per /64. Only IPv4-mapped IPv6 (`::ffff:0:0/96`) counts as its IPv4 address. NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`) addresses are IPv6 clients grouped by their /64: the IPv4 bits they embed are never an identity (corrected in M6-IDEMPOT-P2).
  - `TRUSTED_PROXY_CIDRS=none` (clients connect directly) is a development and test setting only: the production composition refuses it.
- **Limits.** Limits run through one provider-independent port, `DistributedRateLimiter` (`server/runtime/rateLimit.ts`):
  - Keys are HMAC pseudonyms under a secret supplied through composition.
  - Consumes are atomic, over a fixed window, with explicit allowed, limited and unavailable outcomes.
  - An executable conformance suite (`rateLimiter.testkit.ts`) comes with positive controls.
- **Failure handling.** There is no per-process limiter in the production graph and no fallback:
  - A store that cannot answer is a bounded 503.
  - The probes never touch the limiter, and readiness reports the store.
  - A missing or invalid proxy contract, key or adapter makes the production composition refuse.
- **What remains.** No distributed adapter is approved or composed, so **M6 is not complete**. The rate-limit half still needs an approved shared store, its adapter, and the deployment half of the proxy contract (details in [08](./08-production-gate-and-risk-register.md) G-IDEMPOT and G-UNAUTH). M4's production blockers (the admission race, G-DBROLE, migration 005) are separate and unchanged. *(Update, M6-RATE-P2: the store and its adapter exist and are composed in code — below; the deployment half of the proxy contract remains.)*

**M6-IDEMPOT-P2 (committed in `a6469f23`; accepted as a code-only foundation, not live) — the durable idempotency contract foundation:**
- **Route policy.** Every route declares `idempotency: 'none' | 'required'`, and startup refuses a missing or unknown value. `required` registers only on a state-changing route with a verified principal and a declared platform-scope authorization (a tenant- or store-scoped route may not require it until M5 supplies server-derived tenant and store context to bind; *since M7A-CUSTOMERS-P3 a tenant-scoped `command` route of the tenant session audience may, bound to the authorizer's trusted tenant, store and actor (contract version 2), and a store-scoped one still may not*); such a route's operation is a `perform` that receives only its principal, session boundary, parsed body, attempt and abort signal, and returns its outcome. Every current route (health, readiness, login, logout, current session, the Command Center read) is `none`; `required` exists only on synthetic test routes.
- **Chain.** The idempotency step runs after the client limit, CSRF and origin, authentication, authorization and the bounded body read, and just before the operation. Startup refuses a `required` route without a durable store and key (`idempotency_required`).
- **Key and identity.** One `Idempotency-Key` holding a UUID version 4. A dedicated `IDEMPOTENCY_KEY` (never `RATE_LIMIT_KEY`) keys domain-separated HMACs: the record is bound to the client key and the principal, the request to its method, route, session boundary, reserved tenant and store slots, and body. No raw key, UID, token, cookie or body crosses the port.
- **Port.** `DurableIdempotencyStore` (`server/runtime/idempotency.ts`): `acquire` (acquired, in progress, replay, conflict, unavailable), a lease-checked `complete`, and a readiness `probe`. Every answer is strictly validated; an outage, an overrun or a malformed answer is a bounded 503. Recorded responses are sealed (AES-256-GCM, bound to their operation) and replayed byte for byte with the replaying request's own request ID.
- **Conformance.** `assertIdempotencyStoreContract` (`server/runtime/idempotencyStore.testkit.ts`) runs over two instances sharing synthetic state, and 22 positive controls prove it fails each broken adapter it exists to catch.
- **What remains.** No store is approved or composed. M6-OUTBOX-P3 (below) supplies the contract that commits the mutation, the completion, the audit record and the outbox events together; until an adapter implements it the crash window stands, and `perform` keeps it: one holder of an unexpired lease and the replay of a completed operation, never exactly-once execution.

**M6-OUTBOX-P3 (not live) — the atomic command transaction and the transactional outbox ([ADR-17](./10-architecture-decision-records.md)):**
- **Boundary.** PostgreSQL is the future authoritative transaction boundary: one transaction commits the mutation, the lease-checked idempotency completion, the durable audit record and the outbox events, or none of them. A cache may serve rate limits, never transaction-coupled idempotency or outbox state.
- **Commands.** A `required` route may declare a `command` — a contract validated at startup and a synchronous planner — committed through `CommandTransactionPort` (`server/runtime/commandTransaction.ts`). The lease is checked first inside the transaction, so a reclaimed attempt is fenced out; success is sent only after `committed`; a conflict is a 409 `write_conflict`; every other outcome is a 503 that assumes no rollback and releases no lease.
- **Outbox.** A closed, append-only event registry; an immutable, bounded envelope with delivery metadata outside it; `OutboxDeliveryStore` (claim, acknowledge, retry, dead-letter, probe) with fencing tokens, store-clock expiry, batches of at most 32, backoff from 1 s to 15 min and at most 20 attempts; one bounded delivery pass and no worker. Delivery is at least once until dead-lettered; consumers deduplicate by event ID; neither ordering nor exactly-once delivery is claimed.
- **Audit.** A transaction-local audit record built from trusted sources only, for the adapter to write through the existing append-only writer on the same transaction; the actor, like tenant and store, is null until M5.
- **Conformance and containment.** Two suites over two instances sharing synthetic state, 17 positive controls each; no production route, adapter, worker, database or network client; the approved-adapter table stays closed; no migration changed.
- **What remains — M6 is not complete.** A PostgreSQL adapter for the three ports over one database, passing all three suites against real PostgreSQL with fault injection; its schema migration and the managed apply of migrations, migration 005 included (unexecuted against any managed database); an approved rate-limit store and adapter and the deployment half of the proxy contract; a deployable worker and publishers with dead-letter observability, redrive and retention (M8); the composition and an owner-approved deployable build; full audit coverage (G-AUDIT) and actor attribution (M5); credential encryption and rotation; the DSAR audit, workflow and retention foundations. The four dev-only High advisories remain pre-launch maintenance (G-APPSEC).

**M6-PG-P4 (not live) — the PostgreSQL transactional store ([ADR-17](./10-architecture-decision-records.md)):**
- **Schema.** Migration 006 adds `idempotency_record` and `outbox_event` — digest, lease, token, state, attempt, time and size bounds enforced by the database, one row per scope and per event ID, delivery states the table keeps internally consistent, indexes for retention, due claims and expired claims — and `m6_store_clock()`, the one clock every decision reads. RLS is enabled with a policy for `tmpos_app` alone, updates are column-scoped so a committed envelope cannot be rewritten, and there is no delete, no role change and no second audit table; it refuses to finish while a direct grant on its objects names any role but its owner and `tmpos_app` (a platform's default grant included), or grants `tmpos_app` more than it is granted or any right to grant it on — direct object grants only, not effective privilege through membership. Its reverse refuses while it would destroy an undelivered event or a retained record. (M6-PG-P5 moved these objects into the internal schema `tmpos_internal`; see below.)
- **Adapter.** `server/persistence/postgresTransactionalStore.ts`: one shared transaction kernel and three separate ports over one database. Each call is one bounded transaction (lock and statement timeouts below its deadline, an idle-in-transaction timeout at twice it; an abort cancels the statement in flight); every decision reads the store clock after locking its row, except a claim, which never waits on a lock and reads it once; preconditions are conditional statements, so no error is read as a conflict; an error before COMMIT is `unavailable`, and a COMMIT whose fate is unknown rejects as indeterminate. A command commits in order: fence, mutation, audit record (the existing writer, same transaction), events, completion, COMMIT.
- **Proof, against disposable PostgreSQL only.** The three unchanged conformance suites over two independent instances on separate connections, as a non-owner LOGIN holding `tmpos_app` and `tmpos_audit_writer`; migration up/down/up; constraints; the real clock after a lock wait; a failure at every part; conflict versus a reused event ID; concurrency; a lost acknowledgement that replays once; aborts; lock and statement timeouts; injected SQLSTATEs; a connection cut or ended by the server under an open transaction; claim order, the limit of 32, a locked row passed over and the attempt bound; commands with no events and with eight; no driver text leaving the adapter.
- **Containment.** Composed nowhere, outside the emitted artifact, and it constructs no client; the production entry is unchanged. (Since M6-PG-P7-R1 the transaction root composes it for a route that requires idempotency; see below.) While 006 is pending, the managed 005 apply refuses at its unchanged exact-[005] plan gate and status reports 005 and 006 pending (the launcher suite is rebaselined to prove it); the S2 suite proves 005 over 001–005 only.

**M6-PG-P5 (not live) — PostgreSQL activation hardening ([ADR-17](./10-architecture-decision-records.md)):**
- **Internal schema.** Migration 006 — applied to no managed database, so corrected in place rather than by a 007 — creates `tmpos_internal`, owned by the principal that applies it, with USAGE to `tmpos_app` alone, and puts `idempotency_record`, `outbox_event`, `m6_store_clock()` and the transition guard there; `public` holds none of them and `audit_event` stays in `public`. Its reverse drops only those objects, then the schema without CASCADE (a stray object refuses it), and keeps its refusal to destroy work.
- **Direct grants against effective reach.** The migration checks the direct object grants on the schema, both tables, their columns and both functions (an ACL never set is read as its default); effective privilege through membership and the ownership or superuser bypass are outside it by design. The suite proves each distinction against disposable PostgreSQL — inherited and nested membership, `WITH INHERIT FALSE` (reachable only through `SET ROLE`), `SET FALSE`, membership in the owner, superuser status, schema USAGE against table and function privileges — and doc 08 records the live check G-DBROLE must run.
- **Delivery state machine.** An `ENABLE ALWAYS` trigger on `outbox_event` admits inserts only as pending at attempt 0 and updates only from pending to claimed once due and from claimed to claimed once expired (a reclaim), pending, delivered or dead, a claim counting exactly one attempt and no update rewriting the envelope; delivered and dead are frozen — for the runtime role's own SQL, a mutator's and the owner's, replica sessions included (DA-16 closed). Due and claim-expiry times must be finite.
- **Search path.** Every store transaction pins `pg_catalog, pg_temp`, and every relation it touches is schema-qualified — the audit writer now names `public.audit_event` — so no operator or function placed in a writable schema can be chosen over PostgreSQL's own. Migration 006's up and down files pin the same path for their own transaction, so an operator planted ahead of `pg_catalog` in an applier's path cannot hide a stray grant from section 6, bind a constraint or let the rollback miss an undelivered event (M6-PG-23).
- **Attempt cap.** The store claims an event at most 20 times (`OUTBOX_DELIVERY_POLICY.maxAttempts`, bound from source, never from a request): an expired claim at the cap is dead-lettered (`attempts_exhausted`, unpublished) by the next claim, a retry at the cap is refused, and 006's 1 000 is a storage-integrity ceiling only.
- **Driver containment.** No released postgres.js fixes either connection-loss defect (DA-15), so the dependency stays at 3.4.9 and the store contains them in its own code except in one window: once the store has seen a transaction's `begin` settle nothing more is handed to the driver, and a connection lost mid-statement is rejected at that statement, but a close processed in the microtask gap after a statement returned can still let the body's next statement, or the driver's own ROLLBACK or COMMIT, be written (DA-19). `createSupervisedPgClient` retires a pool after any failure its transaction body did not raise, so the next call opens on a fresh one. Nothing is retried; failures before COMMIT stay `unavailable`, an ambiguous COMMIT stays indeterminate, and a retired pool ends within a bounded grace. Child-process tests witness both defects in the pinned driver and prove the store survives each loss (M6-PG-24–26).
- **Notices.** Both principals' client options drop every server NOTICE (`discardNotice`), which the driver would otherwise print whole to stdout; proved through a real server (M6-PG-27, DA-17 closed).

**M6-PG-P6 (not live) — database authority ([ADR-17](./10-architecture-decision-records.md)):**
- **No table for the runtime role.** Migration 006, still applied to no managed database and so corrected in place, takes every table, column and clock privilege away from `tmpos_app` and gives it EXECUTE on nine fixed lifecycle routines instead — acquire, complete, the command's fence and event enqueue, claim, acknowledge, retry, dead-letter and probe. Each is `SECURITY DEFINER`, owned by the principal that applies 006, pinned to `pg_catalog, pg_temp`, free of dynamic SQL, strictly validated and revoked from PUBLIC; each locks its row, reads the store's clock and changes a record only under the presented lease, or an event only under the presented claim token, which the runtime role can no longer read. The port answers are unchanged, the 20-attempt cap is fixed inside the claim routine, a reclaim never keeps the expired claim's token, RLS stays enabled with no policy and the transition guard stays (DA-18 closed; M6-PG-02, -20, -28, -29 and the three unchanged conformance suites). The adapter names no store table and issues no write of its own.
- **Transaction kernel.** The store no longer uses the driver's `begin()`. `createSupervisedPgClient` runs every transaction on pools of one connection each — opened by a plain statement before any `reserve()` — and issues BEGIN, the transaction-local settings, every body statement, COMMIT and ROLLBACK through one dispatcher behind a per-transaction gate that the driver's close callback shuts synchronously and each statement's hand-off checks, so nothing is handed to a closed connection. ROLLBACK goes only to a connection still usable, otherwise the pool is retired; a loss before COMMIT is `unavailable`, a lost COMMIT answer indeterminate, and nothing is replayed; transactions beyond the pool count wait in the kernel under their deadline. A mutator receives only a frozen statement function with `json`, which runs only fixed text beginning with SELECT, INSERT, UPDATE, DELETE, WITH or VALUES: savepoints, transaction control, COPY, session commands, fragments and concurrent statements are refused before the driver is asked. DA-19 and DA-20 are closed; DA-15's third defect — an ended pool reconnecting for a refused `reserve()` — was found and contained (M6-PG-25, -26, -30–33 in child processes, and the kernel's unit suite).

**M6-PG-P7 (not live) — session hygiene:**
- **Reset before reuse.** A connection returns to its pool only once its transaction's outcome is known, nothing is in flight, the gate is open and the kernel's own `DISCARD ALL` has been acknowledged, so no setting, role, advisory lock, LISTEN, temporary table, held cursor, prepared statement or sequence state a transaction leaves reaches the next one, and a caller waiting for the pool gets it only after the reset. The kernel forces the driver's `prepare` off, so the reset invalidates nothing the driver keeps and the driver never re-sends a statement by itself. A reset that fails, a close around it or an abort during it retires the pool without changing the answer, and nothing is retried; a body's statement function stops working once the body settles; a COMMIT the server answers ROLLBACK is `unavailable`; and an abort outside COMMIT retires the pool at once, so nothing that never finishes holds one (DA-21 closed; M6-PG-34–37 and the kernel's unit suite).

**M6-PG-P7-R1 (not live) — route-ready composition and the endpoint mode:**
- **One transaction root.** `server/composition/productionTransactions.ts` is the one production authority for durable idempotency and the command-transaction port, and it is driven by its route inventory, validated by the runtime's own route table. With no route requiring idempotency — today's inventory is empty — it reads, builds and probes nothing (not `APP_DATABASE_URL`, not `IDEMPOTENCY_KEY`), and the runtime serves its probes and bounded fallback as before. With one, it requires both, refuses with bounded codes before any client exists, and otherwise builds the kernel and the store once each and returns the idempotency store and the transaction port together, with no in-memory, test, local or fail-open alternative; a command route without exactly one mutator of its contract's kind, mode and aggregate type refuses. `IDEMPOTENCY_KEY` moved out of the sessions root. Readiness probes the two ports — the store's read-only probe routine — only when they are composed, under the existing deadline and sharing, and the root's `close` ends the kernel within its grace as a shutdown hook.
- **Endpoint mode enforced.** `APP_DATABASE_URL`, the runtime role's future secret (never `SUPABASE_DATABASE_URL`), is classified before any DNS, socket, TLS or SQL (`server/platform-identity/databaseEndpoint.ts`): only the direct database host or the shared session pooler on port 5432; the shared and dedicated transaction poolers on 6543 and every unknown, ambiguous, encoded or malformed URL — judged as written, so a spelling a URL parser would normalise (a control character, `:05432`, an empty port) is refused too — are refused, and no refusal carries the URL or any part of it. The grammar is the frozen migration executor's, restated because runtime composition may not import migration authority and bound to it by a parity suite. The database-client boundary (`createRuntimeStoreClient` in `db.ts`) builds the kernel with the routing values and the credential as explicit options under the shared transport policy, so the driver parses no connection string. DA-21's direct-or-session-mode precondition is enforced here.
- **Containment.** Only the transaction root composes the store, and only `db.ts` builds the kernel over the driver; the deployable entry, the emitted artifact and migration authority reach none of it. Still no business route (G-IDEMPOT), runtime login or secret (G-DBROLE), managed apply (G-MIGRATE) or deployable entry composing either root.

**M6-RATE-P2 (not live) — the distributed rate-limit store ([ADR-26](./10-architecture-decision-records.md)):**
- **Store.** PostgreSQL is the initial `DistributedRateLimiter` store, and the adapter (`server/persistence/postgresRateLimiter.ts`) stays behind the unchanged port. **Migration 014** (`014_m6_distributed_rate_limit`) owns its own schema, `tmpos_rate_limit`: a bucket table keyed by namespace, dimension, pseudonymous limiter key, limit and window; a one-row table holding the fingerprint of `RATE_LIMIT_KEY`; and four routines (the consume, the probe and the reclaim, `SECURITY DEFINER`, and the key check the consume and the probe share, granted to nobody). `tmpos_app` holds USAGE and EXECUTE on the consume, the probe and the reclaim, and no table privilege; section 6 refuses when `tmpos_audit_writer`, `anon` or `authenticated` can execute any of them, by a grant or by membership in `tmpos_app`. No role is created. Nothing is stored but pseudonymous HMAC keys with their namespace, dimension, policy, count and window times, and the key's fingerprint — no address, account identifier, token, cookie or request.
- **Semantics.** A fixed window opens at the first successful consume and is never extended. A consume is atomic across instances through its bucket's row lock, except one the committed state already refuses, which is answered from an unlocked read with no row lock and, once the key fingerprint is registered, no transaction ID or WAL; a refused consume changes nothing, and the retry-after comes from the database's clock. Each call is one transaction on the runtime kernel under lock 200 ms, statement 300 ms and idle-in-transaction 400 ms, below the runtime's 500 ms cap; the adapter answers at that cap even with COMMIT in flight, so an allowance committed later is answered unavailable (cost spent, never an allowance unrecorded). Consumes of one bucket are serialized per instance in the adapter ("lanes"), so one client holds at most one kernel connection per bucket it reaches; a line holds at most 64 consumes of one bucket (`RATE_LIMIT_LANE_DEPTH`), and past that a consume of that bucket is a 503 at once.
- **Fail closed.** An outage, timeout, abort, malformed answer or mismatched key is a bounded 503 and a failing readiness probe; a read-only session or a standby also fails the probe (`store_read_only`). `/health` is untouched. There is no local fallback, retry, queue or cache.
- **Key skew.** The first consume or probe registers the key's fingerprint, HMAC-SHA256 keyed with the bytes `RATE_LIMIT_KEY` decodes to (not its text) over the ASCII string `tmpos-rate-limit-key-fingerprint:v1`, atomically. Any other key makes that instance's limiter unavailable and its readiness fail, so a wrongly keyed first caller — or, on purpose, a holder of the runtime database credential without the key — locks every correctly keyed instance out until an operator deletes the fingerprint row as the owner and a correct instance registers; right after 014 is applied, a correctly keyed instance must call first, or the owner must confirm the registered fingerprint. Nothing does that automatically, and rotation needs a coordinated procedure that does not exist (doc 08 DA-53).
- **Cleanup.** Never inside a consume. After an allowed consume that opened a window, the adapter calls `m6_rate_limit_reclaim()` in the background, in its own transaction under 50 ms bounds: at most four expired buckets, oldest first, through the expiry index, skipping locked rows. Each such consume the adapter answers owes one call (one whose window opened only after its caller was answered unavailable owes none); owed calls run one at a time per instance, the next only after one deleted a full four, and fewer or a failure clears what is owed. Its failure changes no consume. No timer or worker: during a burst of new clients windows can open faster than one reclaim at a time clears them, the backlog stays while there is no traffic, and a long-held database snapshot can make every reclaim fail at its 50 ms statement bound (SQLSTATE 57014) while storage grows (doc 08 DA-52).
- **Composition.** The transaction root builds the adapter over its one kernel, and the sessions root binds it with the `RATE_LIMIT_KEY` it parsed itself. Handed that bundle and a valid key, the sessions root no longer names `rate_limit_store_unavailable`. No production entry composes either root.

The match is the name only: a case-insensitive literal substring after the ICU root locale's full uppercase of both sides (`é` matches `É`, `ß` matches `SS`), with `%`, `_` and `\` literal and no normalization or accent folding. The response shape, the default of 50 and the range 1–100 are unchanged; an invalid `q`, a repeat, an unknown key or a query over 4,096 characters is 400, and no refusal or log line repeats the text. A search page continues with its own 44-character cursor, bound to the normalized text by a digest; it carries no text, name or tenant, and another text's cursor or the other kind is 400.
- **The database.** Migration 025: schema `tmpos_customer_search` with one `STABLE SECURITY DEFINER` routine that restates 022's authority steps and 017's rechecks, reads only the derived tenant's customers (the tenant predicate inside the statement) and answers in the list's `(name, id)` order. `tmpos_app` gets USAGE and EXECUTE, no table or column privilege. 025 refuses to apply without the ICU collation `und-x-icu`.

- **Measured limits.** On a local disposable cluster with 25,000 synthetic customers (a tenant of 20,000): no match 8.459 ms and a rare match 8.279 ms, each a sequential scan of all 25,000 rows with literal parameters, and about 13 ms over the tenant's 20,000 index entries under a generic plan; a common match 0.121 ms and a continuation 0.309 ms, both through the `(tenant_id, name, customer_id)` page index. That index keeps a search to the tenant's range in page order and serves the continuation's keyset position; no installed index evaluates the uppercase substring predicate, so a rare or absent text costs time linear in the tenant's customers, bounded by the read's 2.7 s statement limit and the per-client rate limit. No substring accelerator is installed: a trigram index would need the `pg_trgm` extension, which this work does not add. Modest local synthetic evidence, not a benchmark (doc 08 DA-168).
