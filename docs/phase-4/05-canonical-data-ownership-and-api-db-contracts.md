# 05 — Canonical Data Ownership & API / Database Contracts

**Scope:** per-domain canonical data ownership, the production API/error contract, and the database & multi-tenant contract. Design-only. Existing durable schema is identity/authz/audit, plus one minimal business table; business tables are introduced per-domain in M7 ([06](./06-module-migration-map-m7.md)), the first being the minimal customer identity (M7A-CUSTOMERS-P1, §2).

Those triggers are its only change to earlier objects. They make these writes wait for a command or login that holds the actor's account, in every mode including replica mode: an anchor change (its provider reference or key) or delete; an identity-link insert or re-point; and a grant insert or re-point, of any scope. In an ordinary session the anchor delete and the grant insert or re-point already waited through their foreign keys, so 015 adds their wait in replica mode only. Every other write to an administrator's standing was already serialized by 009's locks. DA-76 is the recorded exception ([08](./08-production-gate-and-risk-register.md)). 016 (M5-TENANT-SESSION-P1, [ADR-31](./10-architecture-decision-records.md)) adds one table in 011's schema, `tmpos_session.tenant_grant_version`, and one column, `public.store.access_version` (bigint, default 1, CHECK 1..2^53−1). Its other changes to earlier objects are five row triggers, each enabled `ALWAYS`. `trg_tenant_access_version` (BEFORE UPDATE on `tenant`) and `trg_store_access_version` (BEFORE INSERT OR UPDATE on `store`) fire `tmpos_session.m5_access_version_moved` (`SECURITY INVOKER`, granted to nobody), which moves the row's access version by exactly one whenever its status changes, and a store's also when it moves to another tenant (`tenant_id`), whoever writes it, refuses any other change to it, and sets a new store's to 1 whatever its INSERT names; 010's command still moves the tenant version exactly once. A key never changes: an UPDATE that would change a tenant's `tenant_id` or a store's `store_id` raises 23514, as a replica too, because a row inserted again under the old key would start its version again. `trg_user_membership_tenant_grant_version` (AFTER INSERT, UPDATE and DELETE on `user_membership`) fires `tmpos_session.m5_tenant_grant_moved` (`SECURITY DEFINER`, granted to nobody), which adds one to the grant version of each actor whose tenant- or store-scope grant a write creates, removes or changes, cascaded deletes included; a change to `updated_at` alone moves nothing. `trg_tenant_tenant_grant_version` and `trg_store_tenant_grant_version` (AFTER DELETE on `tenant` and `store`) fire the same function, which adds one, once per actor, for each actor holding a tenant- or store-scope grant of any status that names the deleted row, so a replica's delete, which cascades nothing, still moves them; in an ordinary delete the cascade has already removed those grants, and each grant's own delete moved its actor's version. It also adds two routines. `m5_admit_tenant_session_v2(p_auth_provider, p_auth_provider_uid)` (`STABLE SECURITY DEFINER`) answers one row, `outcome, actor_id, account_status, limitation, security_version, memberships, authority_version, grant_version`: 011's six columns, with each membership entry also carrying `storeAccessVersion` (decimal text, null exactly when the grant names no store), plus the actor's platform authority version (013) and tenant grant version (016) as decimal text (0 for an actor with no row; both null in the one refusal row). It raises when it cannot read a tenant's or a store's access version. `m5_hold_tenant_standing(p_auth_provider, p_auth_provider_uid)` (`VOLATILE SECURITY DEFINER`) answers `absent` or `held` and locks the actor's standing until the caller's transaction ends (ADR-31). `tmpos_app` holds EXECUTE on those two routines and nothing else from 016. 011's `m5_admit_tenant_session` stays and stays granted, but the adapter no longer calls it. 016's up and its rollback each refuse while any tenant session exists. 017 (M7A-CUSTOMERS-P1, [ADR-32](./10-architecture-decision-records.md)) creates its own schema `tmpos_customer` with one table, `customer`, its page index and one routine, and changes nothing an earlier migration created. `m7a_customer_page(p_internal_user_id, p_security_version, p_membership_id, p_role_id, p_tenant_id, p_after_customer_id, p_limit)` (`STABLE SECURITY DEFINER`, run with `row_security = off`, so a row security ever FORCED on the table makes it fail rather than answer empty pages) re-confirms, in the same snapshot as the page, that the named tenant authority still holds. The account's status must be on the allow-list `active`, `trialing`, `overdue` or `read_only`, and 007's security version must be equal. The actor must hold exactly one active tenant-scope grant, counting only grants on a tenant that is not `suspended` or `pending_activation`, as 007's resolver counts them, and that grant must be the named membership, role and tenant. The tenant's status must be on the same allow-list. It then answers up to `p_limit` (at most 101) `(tenant_id, customer_id, name)` rows of that tenant after the continuation, ordered by `(name, customer_id)` under "C", or a single `invalid`, `denied` or `cursor_unknown` row. It decides no permission. 017 refuses to apply unless the applier holds the owner's privileges on `tenant`, `app_user`, `user_membership` and `identity_link`, none under forced row security. Its rollback refuses unless it runs under READ COMMITTED, and it runs its no-rows guard with `row_security = off`, so a forced row security refuses it (42501) rather than hiding rows it would drop. It takes ACCESS EXCLUSIVE on `public.tenant` and then on the customer table, so it belongs in a maintenance window; a customer INSERT locks in the opposite order and can deadlock with it, and PostgreSQL then aborts one side. It refuses while any customer row exists. While one exists, the chain cannot roll back past 017 (005's and 002's rollbacks would fail). 018 (M7A-CUSTOMERS-P2, [ADR-33](./10-architecture-decision-records.md)) creates its own schema `tmpos_mint` with two tables, the issuer key `issuer_key` and the mint ledger `tenant_session`, the ledger's expiry index, two helpers granted to nobody (`hmac_sha256`, `mint_message`) and three routines. Its only change to earlier objects is two revocations: `tmpos_app` no longer executes 011's `m5_session_create` or 017's `m7a_customer_page`. `m7a_session_create` (`VOLATILE SECURITY DEFINER`) is now the runtime's only session create. It takes 011's eleven row values and a proof, and checks every argument against 011's CHECKs first (`invalid`, nothing written). An administrative record, with no proof, goes to 011's create unchanged. A tenant record needs an HMAC-SHA256 proof under the installed issuer key over all eleven values (`refused` otherwise), a lifetime of at most eight hours and a creation at most 60 s ahead of the database clock; the routine then writes a ledger row (the SHA-256 of 016's admission answer for the principal and of the key) and the session, and answers `conflict` for a taken key. `m7a_customer_page_v2(p_session_key, p_after_customer_id, p_limit)` (`STABLE SECURITY DEFINER`, run with `row_security = off`) answers 017's page, run as its owner, for the authority it derives from the session: a ledger-minted, live (database clock) tenant session, minted under the key installed now, whose principal's standing is unchanged and holds exactly one tenant grant. Otherwise it answers `denied`, or `invalid` for a malformed key. `m7a_issuer_key_check(p_fingerprint)` (`STABLE SECURITY DEFINER`) answers only `match`, `mismatch`, `absent` or `invalid`. 018's rollback refuses unless it runs under READ COMMITTED, and while the key or the ledger holds a row; it restores the two revoked grants. 019 (M7A-CUSTOMERS-P3, [ADR-34](./10-architecture-decision-records.md)) creates no table either. Its one authority argument is the presenting session's store key, from which it derives the tenant, actor and grant as 018's read does, admitting only an account and tenant status of `active` or `trialing` and the roles `store_owner`, `manager` and `sales_staff`. `tmpos_app` gets USAGE and EXECUTE on it and still holds no privilege on the customer table. It changes nothing earlier migrations created. 020 (M7A-CUSTOMERS-P3-R1, [ADR-35](./10-architecture-decision-records.md)) creates its own schema `tmpos_role` with one table, `tenant_role_level` (below), and four `SECURITY DEFINER` routines `tmpos_app` may execute: `m7a_role_levels` (the stored levels of one tenant's role, the read every customer decision in the runtime makes), `m7a_role_level_set` (the store owner's edit, whose one authority argument is the session key), `m7a_customer_create` (019's create with its fixed role set replaced by the effective Customers level at Create or above) and `m7a_customer_page_v3` (018's `m7a_customer_page_v2` plus the effective level at View or above). Once that lock is acquired, no 020 edit or create commits until 021 commits; a 020 edit whose EXECUTE was checked before the revoke and which waited on that lock completes after it and fires the trigger. Its rollback refuses unless it runs under READ COMMITTED and while any version row exists, removes only what 021 created, and does not give `tmpos_app` its EXECUTE on 020's edit back ([08](./08-production-gate-and-risk-register.md) DA-128). 022 (M7A-CUSTOMERS-P4 Part 2, [ADR-38](./10-architecture-decision-records.md)) creates no table and changes no earlier object: its own schema `tmpos_customer_detail`, with one read routine, `m7a_customer_get` (§2). - **`audit_event` is append-only**: `reject_audit_event_mutation()` + `trg_audit_event_reject_mutation` (BEFORE UPDATE OR DELETE) raise `restrict_violation` for **all roles including the table owner**. Metadata is guarded (`audit_metadata_is_flat`, forbidden-key list: access/refresh tokens, raw JWT/JWKS, service-role key, DB URL, connection string, password, PAN, card number, provider secret). **Forward-hardening (M6/M7b):** when payments land, extend this guard + log/error redaction to **CVV/CVC, track1/2, and PIN block** so the enforced key-list matches the documented no-CHD boundary (§5), and make the [07](./07-quality-and-test-strategy.md) "no PAN/CVV/track/PIN" assertion check that guard. `evidence_level` ∈ `dev_sidecar_log_advisory | durable_compliance_event`. The writer's metadata allow-list is action-scoped (M6-ADMIN-AUDIT-P1). `sessionRef`, `replacedSessionRef` and `authenticatedAt` are kept only for the six session actions, `platform.admin.session.login`, `.reauthenticate` and `.logout` and, since M5-TENANT-SESSION-P1, `tenant.session.login`, `.reauthenticate` and `.logout`, and those six keep nothing else (a logout row may carry `sessionRef` alone). For every other action they are stripped by `sanitizeAuditMetadata` and refused by `validateAuditEventInput`, as any unknown key is. The writer also owns each session event's entire fixed row (`ADMIN_SESSION_AUDIT_EVENTS` at scope `platform`, `TENANT_SESSION_AUDIT_EVENTS` at scope `none`, with no tenant or store in either), and `validateAuditEventInput` refuses any row under those six ids that differs from it in any column.
- **RLS enabled on all 20 tables.** At 001–004 there were zero policies and 7/8 `REVOKE ALL … FROM public/anon/authenticated` (001's was added by 005). Migration 005 then adds the runtime roles and **five** tenant/store-scoped policies (`tenant`, `store`, `user_membership`, `tenant_feature_entitlement` for `tmpos_app`; an append-only one for `tmpos_audit_writer`), and 006's two `tmpos_internal` tables, 011's `tmpos_session.session`, 013's `tmpos_admission.platform_authority_version`, 014's two `tmpos_rate_limit` tables, 016's `tmpos_session.tenant_grant_version`, 017's `tmpos_customer.customer`, 018's two `tmpos_mint` tables, 020's `tmpos_role.tenant_role_level` and 021's `tmpos_role_edit.role_level_version` are RLS-enabled with no policy — defence in depth, since the runtime role holds no privilege on them at all. Note two things the phrase "RLS enabled" does not mean here: `FORCE ROW LEVEL SECURITY` is set on NO table (deliberately — a `SECURITY DEFINER` routine must be able to read its owner's rows), and 15 of the 20 carry no policy at all, so for those RLS is a deny-all backstop rather than a filter. Migration 012's `tmpos_directory.m5_tenant_directory_page` is such a routine. It reads `public.tenant` as its owner, because 005's policy opens no row to a platform context and 012 leaves that policy exactly as it is. It returns a bounded page of (tenant id, display name, status, row version) only while the caller's named platform grant still holds, and `tmpos_app` holds EXECUTE on it and nothing else in that schema besides USAGE. 012 adds no table. Migration 013's `tmpos_admission.m5_admit_platform_session` is another such routine: it calls 007's resolution as its owner and reads the version table, and `tmpos_app` holds EXECUTE on it and USAGE on the schema, and nothing on the table or the trigger function. 013 adds the twelfth table. Migration 014's `m6_rate_limit_consume`, `m6_rate_limit_probe` and `m6_rate_limit_reclaim` are three more: `tmpos_app` holds EXECUTE on those three and USAGE on `tmpos_rate_limit`, and nothing on either table or the key check; no other runtime-facing role (`tmpos_audit_writer`, `anon`, `authenticated`) may execute any of them or be a member of `tmpos_app` — section 6 refuses the apply otherwise, a `NOINHERIT` membership included, which `has_function_privilege` does not report but which can still `SET ROLE tmpos_app`. 014 adds the thirteenth and fourteenth tables. 015 adds no table and grants nothing: its trigger function carries no grant beyond its owner's, and section 4 refuses the apply if `tmpos_app`, `tmpos_audit_writer`, `anon` or `authenticated` can execute it or is a member of its owner. 016 adds the fifteenth table and two grants: `tmpos_app` holds EXECUTE on `m5_admit_tenant_session_v2` and `m5_hold_tenant_standing`, two definers that read or lock as their owner, and nothing on the new table or either trigger function. Its postcondition refuses otherwise, and refuses any runtime role that may UPDATE the status or access version of a tenant or store or DELETE either, UPDATE a tenant's `tenant_id` or a store's `store_id` or `tenant_id`, INSERT a tenant, or TRUNCATE or place a TRIGGER on `tenant`, `store` or `user_membership`. 005's table-wide INSERT on `public.store` still reaches the new column, and 016's trigger sets it to 1 whatever the INSERT names ([08](./08-production-gate-and-risk-register.md) DA-80). The owner alone may write the grant version table or disable 016's triggers ([08](./08-production-gate-and-risk-register.md) DA-41). 017 adds the sixteenth table and two grants: `tmpos_app` holds USAGE on `tmpos_customer` and EXECUTE on `m7a_customer_page`, a definer that reads the customer, grant, account and tenant rows as its owner, and nothing on the table. It does not rely on 005's session variables, which the runtime sets itself. Its postcondition requires the table's row security enabled and not forced, and `tmpos_app`'s EXECUTE and USAGE actually held. It refuses any wider grant, any column grant, any policy on the table, any runtime role that is a member of an owner of its schema, table or routine, and any runtime role holding an effective privilege on the table by any path, `pg_read_all_data` included (011's check). The routine returns each row's tenant id, and the adapter refuses any row that does not name the admitted tenant. The re-check is not a boundary against the runtime credential ([08](./08-production-gate-and-risk-register.md) DA-83). 018 adds the seventeenth and eighteenth tables, revokes that EXECUTE and 011's `m5_session_create` from `tmpos_app`, and grants it USAGE on `tmpos_mint` and EXECUTE on the schema's three routines only. Its postcondition refuses any wider grant, any column grant, any policy on either table, any runtime role that is a member of an owner of its schema, a table or a routine (a `NOINHERIT` membership included), and any runtime role holding an effective privilege on either table by any path. The customer read is now bound in the database to a minted session, which contains DA-83 against the runtime credential alone without closing it ([08](./08-production-gate-and-risk-register.md) DA-83, DA-93–DA-104). 020 adds the nineteenth table, revokes 019's EXECUTE and USAGE and 018's `m7a_customer_page_v2` EXECUTE from `tmpos_app`, and grants it USAGE on `tmpos_role` and EXECUTE on the schema's four routines only; its postcondition refuses any wider grant, any column grant, any policy on the table, and any runtime role that holds an effective privilege on the table or can still reach the revoked routines by any path ([08](./08-production-gate-and-risk-register.md) DA-118–DA-121). 021 adds the twentieth table, revokes 020's `m7a_role_level_set` EXECUTE from `tmpos_app`, and grants it USAGE on `tmpos_role_edit` and EXECUTE on `m7a_role_level_states` and `m7a_role_level_set_v2` only; its postcondition refuses any wider grant, any grant on the trigger function, any column grant or policy on the version table, any foreign key on it, any runtime role that holds an effective privilege on the version table or 020's table, is a member of an owner of 021's objects or of a table the edit rests on, or can execute 020's edit or the trigger function by any path, and any trigger on 020's table other than 021's own ([08](./08-production-gate-and-risk-register.md) DA-119, DA-121, DA-129). 022 adds no table: one schema, `tmpos_customer_detail`, with one `STABLE SECURITY DEFINER` routine, `m7a_customer_get` (§2). It grants `tmpos_app` USAGE on the schema and EXECUTE on the routine only, and changes no earlier object or ACL. Its postcondition code (`022_m7a_customer_detail.up.sql`, section 4) refuses to finish when any of these checks fails:
  - (a), lines 371–379: the schema holds anything but the one routine, meaning a relation of kind r, p, v, m, f, S, c, i or I, a standalone type, or a trigger calling one of its functions;
  - (c), lines 401–412, and (d), lines 414–425: a grant on the routine or schema beyond its owner's and a non-grantable EXECUTE or USAGE to `tmpos_app`;
  - (e), lines 427–443: `tmpos_audit_writer`, `anon` or `authenticated` can execute the routine through any role it is a member of;
  - (f), lines 445–459: `tmpos_app`, or a role it is a member of, holds a privilege on `tmpos_customer.customer` or can execute 017's page;
  - (g), lines 461–475: one of `tmpos_app`, `tmpos_audit_writer`, `anon` and `authenticated` is a member of the owner of the schema or the routine.

  These are checks in the migration's code, run at apply time. Like 020's and 021's postconditions, they check those runtime ROLES through membership, not the runtime LOGIN. The login's own shape is enforced at every start by the startup preflight ([08](./08-production-gate-and-risk-register.md) DA-132). Effect: PostgREST/anon/authenticated get deny-all; the owner-role connection still bypasses RLS, and GAP-17 (an app role that does not bypass RLS) stays open until a runtime LOGIN role exists (G-DBROLE).

**Customers — the first slice (M7A-CUSTOMERS-P1, code only, not deployed; [ADR-32](./10-architecture-decision-records.md)).** The durable customer identity is `tmpos_customer.customer` (migration 017, §1): a stable id, the owning tenant and the display name, and nothing else. It is tenant-owned, as the table above says. None of the client model's contact, loyalty, money or lifecycle fields exists server-side, and `loyalty_account`, the `active/archived` lifecycle, PII classification, retention, DSAR behaviour, any write beyond the create below (M7A-CUSTOMERS-P3) *(and, since M7A-CUSTOMERS-P7, the edit below)* and the cutover from `StoreLocalState.customers` are not built: they arrive with the product decisions that govern them ([08](./08-production-gate-and-risk-register.md) G-PERSIST, G-PRIVACY). No row is written outside disposable test databases. The read API is one route:
- **`GET /api/v1/customers`**: a tenant-session route under the canonical tenant route permission `view_customers` (the Customers domain at View or above, decided at tenant scope only), with a required trusted context, no body, no `Idempotency-Key` and no recent sign-in. It is a read, so a read-only actor may use it. *Since M7A-CUSTOMERS-P3-R1 ([ADR-35](./10-architecture-decision-records.md)) the level is the role's effective one: the owner's stored Customers level for that tenant and role, else the catalog default. A role an owner set to None is refused 403, an already-issued session included, and the database read (020's `m7a_customer_page_v3`) answers `denied` for it as well (below).*
- **Scope.** The tenant is taken only from the actor's one active tenant grant, which the tenant authorizer selects; never from the path, the query, a header, the cursor or a body.
- **Bound to the presenting session (M7A-CUSTOMERS-P2, [ADR-33](./10-architecture-decision-records.md)).** The read is bound in the database to the presenting minted tenant session. The route declares `sessionBinding: 'required'`, so the chain hands its handler that session's store key, and the adapter reads through migration 020's `tmpos_role.m7a_customer_page_v3` with the key as its only authority argument (since M7A-CUSTOMERS-P3-R1: 018's `m7a_customer_page_v2` exactly, plus the role's effective Customers level at View or above; 020 revoked `tmpos_app`'s EXECUTE on page_v2). The database requires the session to be minted (a ledger row), of the tenant audience, live on the database clock, minted under the issuer key installed now and of an unchanged standing, derives the actor and its one tenant grant itself, and runs 017's page for them. The runtime login can no longer call 017's page. The query, cursor, response, order and refusals below are unchanged: a session the database refuses is the same 403 `forbidden`, and the adapter still refuses (503) any row not naming the authorizer's tenant.
- **Query.** `limit` 1–100 (default 50) and `cursor`, each at most once. The cursor is opaque: 23 canonical base64url characters encoding a tag byte (0x02) and the last customer's id. It carries no authority: its position is looked up only among the admitted tenant's customers, so a cursor naming another tenant's customer, a deleted one or an unknown id is the same 400. Any other key, a repeat, an empty pair, an encoding, a non-canonical spelling or a query over 128 characters is 400 `invalid_request`. *(Since M7A-CUSTOMERS-P8 a third key, `q`, searches by name, the whole query may be up to 4,096 characters, and a search page continues with a second, 44-character cursor kind (tag 0x03). Without `q`, or with a `q` blank after decoding and trimming, the list, its cursor and its refusals are unchanged; see the name search below.)*
- **Response.** `200 { customers: [{ id, name }], nextCursor }` (`nextCursor` null on the last page), ordered by name under the "C" collation, then by id ([08](./08-production-gate-and-risk-register.md) DA-86). No email, phone, group, tier, total spent or other money value.
- **Refusals** keep the runtime's generic `{ error, requestId }` bodies: 401 for session refusals, 403 `forbidden` for any denial (a grant lost between the authorizer and the read included; *since M7A-CUSTOMERS-P5-R1 also a missing, repeated, malformed or other session's `X-TMPOS-Session-CSRF`, below*), and 503 `service_unavailable` for an outage, a timeout or an answer out of shape, never cached or synthetic data. Out of shape includes:
  - a row naming a tenant other than the admitted one (the adapter's check, independent of the routine's filter);
  - rows not in strictly increasing (name bytes, id) order (checked by the adapter over every row it reads, the look-ahead included, and by the runtime over the page);
  - a name that is not 1–200 characters of well-formed UTF-16.
- **Audit.** None, by owner decision; whether personal-data list reads are audited is open ([08](./08-production-gate-and-risk-register.md) DA-88).
- **Availability.** Served in code by the compiled tenant entry (M7A-CUSTOMERS-P2, commit 2; [ADR-33](./10-architecture-decision-records.md) decision 8), on the tenant host alone, and not deployed; the administrative entry still composes the administrative boundary only. The tenant entry lists the route in the tenant authorizer's read classification, builds the customer port over the shared transaction kernel, and composes the session store with the tenant issuer key, which the database owner installs ([08](./08-production-gate-and-risk-register.md) DA-87, DA-101).

**Customers — the create (M7A-CUSTOMERS-P3, code only, not deployed; [ADR-34](./10-architecture-decision-records.md)).** The write API is one route:
- **`POST /api/v1/customers`** is a tenant-session route under the canonical tenant route permission `create_customers`: the Customers domain at Create or above, decided at tenant scope only. By default `store_owner`, `manager` and `sales_staff` hold it and `technician` does not, and a `read_only` or `overdue` account or tenant denies it. *Since M7A-CUSTOMERS-P3-R1 ([ADR-35](./10-architecture-decision-records.md)) these are the defaults until an owner edits a role: the permission is decided on the role's effective Customers level, by the authorizer, again in the committing transaction, and again in the database by 020's `tmpos_role.m7a_customer_create`, which replaces 019's fixed role set.* The route requires a trusted context and an `Idempotency-Key`, and no recent sign-in. It is not a read, so a read-only actor may not use it.
- **Request.** A JSON body of at most 4,096 bytes holding exactly `{ name }`. Any other field, or none, is 400 `invalid_request`. *(Since M7A-CUSTOMERS-P6 the body is at most 8,192 bytes, `name` is required and `phone` and `email` are optional, and any other field is still 400; see the contact records below.)* The tenant is taken only from the actor's one active tenant grant: nothing in the path, a header or the body names it.
- **Name.** Trimmed at both edges. It must then be 1–200 characters, with no C0 control, DEL, C1 control, U+2028, U+2029, lone surrogate or Bidi_Control character. It must also hold at least one visible character, so a name made only of whitespace, format, default-ignorable or combining characters, or U+2800, is refused. Everything else is kept exactly: no case folding or normalization. Names need not be unique, so two keys with one name create two customers. Stored names are never rewritten.
- **Response.** `201 { customer: { id, name } }`: the server-generated id and the name as stored. There was no `Location` header at P3, because no customer-detail route existed. *(Since M7A-CUSTOMERS-P4 Part 2 the 201 carries `Location: /api/v1/customers/<id>`; see the detail read below.)* An identical retry under the same key replays it (`Idempotent-Replayed: true`) within the record's 24 h retention, once the session and authorization checks pass again.
- **Refusals** keep the generic bodies:
  - 401 for session refusals, and 403 `forbidden` for any denial;
  - 400 for a missing or malformed `Idempotency-Key`;
  - 409 `request_in_progress`;
  - 422 `idempotency_key_reused` for another request under the key; for the same signed-in identity this includes the same body under another tenant or actor;
  - 503 `service_unavailable` for an outage and for any refusal inside the committing transaction (lost authority, a duplicate id), which commits nothing;
  - 503 also for a commit whose acknowledgement was lost. That outcome is unknown, not a rollback: a retry under the key replays the 201 if the commit landed.
- **Transaction.** One PostgreSQL transaction does all of the following, or commits none of it:
  - holds the presenting session and the actor's standing;
  - decides the permission again;
  - creates the row through migration 020's `tmpos_role.m7a_customer_create` (M7A-CUSTOMERS-P3-R1; it replaced 019's `tmpos_customer_write.m7a_customer_create`), whose only authority argument is the session key, so the tenant is derived in the database, and which also requires the effective Customers level at Create or above, decided on the role row it locks;
  - appends the audit record;
  - seals the idempotency completion.
- **Audit.** One `audit_event` row per create: action `tenant.customer.create`, scope `tenant` with the tenant, and the actor. It records neither the name nor the customer id ([08](./08-production-gate-and-risk-register.md) DA-111). No outbox event is written.
- **Availability.** Served in code by the compiled tenant entry beside the read, on the tenant host alone. It is not deployed. Until M7A-CUSTOMERS-P5 the shop app did not call it; since then its Customer directory page does (see "the shop's Customer directory" below).

**Customers — an owner's per-role level (M7A-CUSTOMERS-P3-R1, code only, not deployed; [ADR-35](./10-architecture-decision-records.md)).** Migration 020 stores, per tenant, the Customers level of each of the three built-in roles an owner may edit (`manager`, `technician`, `sales_staff`, in `tmpos_role.tenant_role_level`, §1). Until edited a role holds its catalog default (`manager` Full, `technician` View, `sales_staff` Create); `store_owner` is Full and is never stored or edited. Only the Customers domain is stored, because it is the only one the server decides. Custom roles, other domains, deletion and delegated editing are not supported, and the shop app's role editor is unchanged: it calls no route, so a narrowing made there does not reach the server ([08](./08-production-gate-and-risk-register.md) DA-85, DA-124). The write API is one route, and there is no read route: the level is read by every customer decision, and the edit answers the level it stored.
- **`PUT /api/v1/roles/levels`** is a tenant-session route under the canonical tenant route permission `edit_role_levels`: sensitive, and granted only when the selected tenant grant's role is `store_owner` and the limitation is `none` (an interpretation flagged for owner confirmation). The route requires a trusted context, an `Idempotency-Key` and a recent sign-in (at most 10 minutes old). The revalidator judges its deadline again on the database clock inside the committing transaction, and the mutator once more, on the database clock, after 020's set routine answers, which is after that routine's own lock waits. The audit record, the completion and COMMIT then follow with no further freshness check, so they may complete after the sign-in deadline (within the command's own transaction deadline).
- **Request.** A JSON body of at most 8,192 bytes holding exactly `{ roleId, domain, level, reason }` *(since M7A-CUSTOMERS-P4 exactly six fields, adding `expectedTenant` and `expectedVersion`; see "the save precondition" below)*:
  - `roleId`: `manager`, `technician` or `sales_staff` (never `store_owner`);
  - `domain`: `customers` *(since M5-INVOICES-AUTH-P1 also `invoices`; see "Invoices — the owner's per-role level" below)*;
  - `level`: `none`, `view`, `create`, `edit`, `manage`, `approve` or `full`;
  - `reason`: trimmed, then 10–500 characters, with no C0 control, DEL, C1 control, U+2028, U+2029, lone surrogate or Bidi_Control character.

  Anything else, an extra field included, is 400 `invalid_request`. The tenant is taken only from the owner's one active tenant grant: nothing in the path or body names it, and `roleId` names the role edited, never the caller's.
- **Response.** `200 { roleLevel: { roleId, domain, level } }`, the level as stored *(since M7A-CUSTOMERS-P4 `roleLevel` also carries `version`, exactly `expectedVersion + 1`)*. An identical retry under the same key replays it (`Idempotent-Replayed: true`) within the record's 24 h retention.
- **Refusals** are the create's (above), plus 403 `step_up_required` for a stale sign-in, answered only by the chain's outer check, which touches no key. A deadline that passes at the revalidator, or after the routine's lock wait, rolls the transaction back: 503 `service_unavailable`, the lease kept. The same key from the stale session is then 403 `step_up_required` (no key touched); from a fresh sign-in within the lease it is 409 `request_in_progress`; after the lease it is decided afresh (`tests/db/roleLevels.integration.test.mjs` M7RLH-09 witnesses the 503, the kept lease, the 403 and the 409; the after-lease case is witnessed for the create, M7RLH-04, not for the edit). A non-owner, a store-scope grant, an administrative session and another tenant's owner cannot change the level.
- **Transaction.** One PostgreSQL transaction holds the presenting session and the owner's standing, decides `edit_role_levels` and the recent sign-in again, stores the level through 020's `tmpos_role.m7a_role_level_set` (whose only authority argument is the session key; it inserts the role's lock row if absent, a NULL level deciding as the default, locks it FOR UPDATE, reads the clock again, then writes the level), judges the recent sign-in once more after the routine answers, appends the audit record and seals the completion, or commits none of it. *(Since M7A-CUSTOMERS-P4 the routine is 021's `tmpos_role_edit.m7a_role_level_set_v2`, and `tmpos_app` no longer executes 020's set; see below.)*
- **Audit.** One `audit_event` row per edit: action `tenant.role.level.update`, permission `edit_role_levels`, scope `tenant` with the tenant, the actor, reason code `role_<role>_customers_to_<level>` and the owner's reason. No outbox event is written.
- **Effect and ordering.** The next customer request of that role, an already-issued session included, is decided on the new level; no re-login is needed. An edit that commits before a create's deciding check refuses the create (403 at the authorizer, or 503 inside the committing transaction, which keeps the lease). A create that holds the role row first makes the edit wait until it commits.
- **Direct calls.** Edits and creates are audited only through their routes: a runtime-role holder with a live key can call 020's routines directly with no audit or idempotency record ([08](./08-production-gate-and-risk-register.md) DA-118, DA-119). *(Since M7A-CUSTOMERS-P4 these are two routines: 020's customer create `tmpos_role.m7a_customer_create` (DA-118) and 021's `tmpos_role_edit.m7a_role_level_set_v2` (DA-119), which must be given the session's tenant and the role's current version; 020's setter is revoked from every runtime role. DA-118 and DA-119 stay open.)*
- **Availability.** Served in code by the compiled tenant entry, on the tenant host alone. It is not deployed. *(Since M7A-CUSTOMERS-P3-R2 the shop app calls it, for the three editable built-in roles' Customers level only, from its role screen over a tenant session; see below.)*

**Customers — the owner's read-back of per-role levels (M7A-CUSTOMERS-P3-R2, code only, not deployed; [ADR-36](./10-architecture-decision-records.md)).** A read on the edit's path lets the one person who may change a level see what the server holds. There is one new route:
- **`GET /api/v1/roles/levels`** is a tenant-session route under the edit's permission, `edit_role_levels` (the owner rule above): a manager, a technician, a sales_staff, a store-scope grant and a read-only limitation are the chain's 403 before the handler runs. It declares `trustedContext: 'required'`, `recentAuth: 'none'` (no recent sign-in: a read, not the sensitive change), no body and `idempotency: 'none'`, and it writes nothing.
- **Scope.** The tenant is the trusted scope's: the one tenant grant the tenant authorizer selected from the session's admission, never a path, query, header or body value. The runtime passes it as a parameter to 020's definer read `tmpos_role.m7a_role_levels(uuid, text)`; unlike the customer read, the database does not bind this read to the presenting session key ([08](./08-production-gate-and-risk-register.md) DA-121). *(Since M7A-CUSTOMERS-P4 the read is 021's `tmpos_role_edit.m7a_role_level_states(uuid)`, which also answers each role's version, still keyed by the bare trusted tenant id and not bound to the session key.)*
- **Query.** None: any `?` in the request target is 400 `invalid_request`, decided before the database is asked.
- **Response.** `200 { tenant, domain: "customers", roles: [ { roleId, level, defaultLevel, source, editable } ] }` *(since M7A-CUSTOMERS-P4 each entry also carries `version`; see below)*, four roles in the fixed order `store_owner`, `manager`, `technician`, `sales_staff`. `store_owner` is `full`, `source` `'fixed'`. Each other role holds its stored level (`source` `'stored'`), or, with no row or only 020's NULL lock row, its catalog default (`source` `'default'`). `editable` is false for `store_owner` and true for `manager`, `technician` and `sales_staff`, whatever the source. The three stored levels come from one statement, so from one snapshot. The runtime handler (`roleLevelDirectoryOf`, `server/runtime/roleLevelDirectory.ts`), not the database, validates the answer's shape: exactly those four records in that order, the owner's exactly unstored at `full`, every level one of the seven; anything else is a bounded 503. No actor, grant, membership, session or database detail is returned.
- **Refusals** keep the chain's generic `{ error, requestId }` bodies: 401 without a live session, 403 `forbidden` for anyone the owner rule refuses, the bounded 404 for a wrong Host, and 503 `service_unavailable` for an outage, a timeout or an answer out of shape. Every response is `Cache-Control: no-store`.
- **Audit.** None, like the customer read: a configuration read writes no `audit_event`.
- **What it is not.** A person's effective permission: the authorizer still caps a read-only account at View at request time. Two edits racing from two tabs are last-writer-wins, since the edit has no tenant or version precondition ([08](./08-production-gate-and-risk-register.md) DA-125); this read shows whichever committed last. *(Superseded by M7A-CUSTOMERS-P4: of two edits asserting the same version the first to commit wins and the other writes nothing; see below.)*
- **Availability.** Served in code by the compiled tenant entry beside the edit, on the tenant host alone. It is not deployed.
- **The shop app's use.** The shop app's role screen calls the tenant session login and current-session routes and `GET`/`PUT /api/v1/roles/levels`, same-origin, for the built-in roles' Customers level only. The role screen does not call the customer routes. Until M7A-CUSTOMERS-P5 no part of the shop app did; since then a separate page, the Customer directory, calls all three over the same session (see "the shop's Customer directory" below). It signs in through the M5 tenant-session login (the user's Firebase ID token as `Authorization: Bearer`, with `X-TMPOS-CSRF: 1`); the session is the browser-managed HttpOnly `__Host-tmpos_tenant_session` cookie, and of credentials the client holds only the session CSRF token and the UID it belongs to, in memory, for the PUT and the logout (`X-TMPOS-Session-CSRF`). *(Since M7A-CUSTOMERS-P5 also for the customer create. The directory page keeps the token it was handed, in memory, to compare it with the next one and to re-send an unconfirmed create on the same session.)* *Amended (M7A-CUSTOMERS-P5-R1, [ADR-40](./10-architecture-decision-records.md)): the token is also sent on `GET /api/v1/customers` (its cursor pages included) and `GET /api/v1/customers/{id}`, which now require it; `GET /api/v1/roles/levels` still carries none ([08](./08-production-gate-and-risk-register.md) DA-147). Every session check first reads `GET /api/v1/session` and reuses a session whose `subject` is the signed-in user's, so a page load no longer signs in again (see "reads bound to the checked session" below).* *(Separately, the editor keeps non-credential state in memory: drafts, reasons, and since M7A-CUSTOMERS-P4 each draft's expected tenant and version, per-attempt idempotency keys, and any held unresolved change, below.)* The logout is sent by the shop's auth-state handling on a Firebase sign-out or user switch, not by the role screen. It holds no issuer key, mint proof or database session key. The shop build and `/api/v1/*` must be served on one origin, the tenant host ([08](./08-production-gate-and-risk-register.md) DA-107).

**Customers — the save precondition on per-role levels (M7A-CUSTOMERS-P4 Part 1, code only, not deployed; [ADR-37](./10-architecture-decision-records.md)).** An owner's level edit now writes only when the tenant and the version the owner reviewed still hold, so a draft made for one tenant cannot land on another and an older tab cannot overwrite a newer level ([08](./08-production-gate-and-risk-register.md) DA-125). No route is added: the tenant entry still serves its nine routes, and both role-level routes keep their paths, permission (`edit_role_levels`, the owner rule), recent-sign-in rule, bounds and refusals except as stated here.
- **The version.** Migration 021 keeps a per-row counter for each editable role's Customers level in each tenant (`tmpos_role_edit.role_level_version`, §1). A role with no counter row is at version 0, and every level stored before 021 reads 0. Every UPDATE of the level row, by any path, adds exactly one, through an `AFTER UPDATE` row trigger enabled `ALWAYS`. Restoring a role's catalog default is an UPDATE (020 stores the default word; it never deletes a row or writes NULL), so a level that goes A → B → A still moves the version twice and a draft read at the first A stays stale. A customer create's NULL lock row is an INSERT and moves nothing. Only the owner of 020's table, the owner of 021's version table (possibly a different role), members of those roles and superusers can change a level without an UPDATE (an INSERT of a non-NULL level, a DELETE, a TRUNCATE), disable the trigger, or write version rows directly; no runtime role can ([08](./08-production-gate-and-risk-register.md) DA-129).
- **`GET /api/v1/roles/levels`.** Each role entry gains `version`: a safe integer of at least 0 for `manager`, `technician` and `sales_staff`, and `null` for `store_owner`, which is never edited. The three levels and versions come from one statement, `tmpos_role_edit.m7a_role_level_states(tenant)`, on one snapshot. The runtime handler validates the shape as before, and any version out of shape is the bounded 503. The tenant is still the authorizer-selected trusted scope passed as a bare id; the read is not bound to the session key in the database ([08](./08-production-gate-and-risk-register.md) DA-121).
- **`PUT /api/v1/roles/levels` request.** Exactly six fields, `{ roleId, domain, level, reason, expectedTenant, expectedVersion }`. `expectedTenant` is the `tenant` and `expectedVersion` the role's `version` of the read the owner's draft came from: a canonical lowercase UUID of any version, and a safe integer of at least 0 whose successor is still safe. Anything else, a missing or extra field included, is 400 `invalid_request`. Both are **preconditions, never selectors and never authority**: the tenant written is still the one the presenting session's single tenant grant names, derived in the database from the session key.
- **Response.** `200 { roleLevel: { roleId, domain, level, version } }`, where `version` is exactly `expectedVersion + 1`, the version the edit committed. An identical retry under the same key replays that sealed 200 (`Idempotent-Replayed: true`), even after a later edit has moved the level on; a fresh read shows the later version.
- **The precondition refusal.** When the session's tenant is not `expectedTenant`, or the role's version is not `expectedVersion`, nothing is written in either tenant: no level, no version, no audit record, no event and no idempotency completion. The answer is 409 `write_conflict` in the runtime's own `{ error, requestId }` body. It is **unsealed**, unlike the sealed version conflict of the platform commands (§3): the store rolls the whole command transaction back, and the key's lease, taken in its own earlier transaction, is left to expire under the existing policy. Until then the same key answers 409 `request_in_progress`; after it, the same key and body are planned and decided again against the state then (`tests/db/roleLevels.integration.test.mjs` M7RLH-10). A retry that asserts another tenant or version is another body, so it needs a new key; under the old key it is 422 `idempotency_key_reused`.
- **Transaction.** The command transaction is unchanged around the edit: the idempotency fence, the presenting session and the owner's standing held and re-read, `edit_role_levels` and the recent sign-in decided again, then the edit, then the recent sign-in judged once more on the database clock (only after an applied edit; a refused precondition is answered as it is), the audit record and the completion. The edit is 021's `m7a_role_level_set_v2`, whose only authority argument is still the session key. In order it runs 020's steps unchanged (the unlocked pre-check, 016's hold, the session and mint-ledger rows FOR SHARE, the issuer key row FOR SHARE, the database clock, the standing digest, a write account status, exactly one tenant grant on a write-status tenant as `store_owner`), then:
  1. the **tenant precondition**, before any insert: another tenant answers `tenant_mismatch`, having inserted and locked no role row in either tenant;
  2. an **unlocked version pre-check**: a version already moved answers `version_conflict` before any lock row is inserted;
  3. 020's lock row inserted if absent, and the role row FOR UPDATE, which serializes every edit and every create of that role in that tenant;
  4. the database clock again, so a session that expired while it waited is 020's no-row refusal, not a conflict;
  5. the **authoritative version check** on the version row FOR UPDATE, on a snapshot taken after the role-row wait: moved answers `version_conflict`;
  6. the level update, whose trigger advances the version; the routine reads the version back and raises unless it is exactly `expectedVersion + 1`, then answers `applied` with the tenant, actor, membership, level and new version.

  The runtime accepts `applied` only when those identities are the ones the transaction revalidated, the level is the one requested and the version is exactly `expectedVersion + 1`; one `tenant_mismatch` or `version_conflict` row with every other column null is the precondition refusal above; no row is a refusal (503), and anything else is a fault (503).
- **Ordering.** Of two edits that asserted the same version, the first to commit wins and the other writes nothing (409), whether it was refused by the pre-check or waited on the role row and was refused under it (`tests/db/roleLevelVersionRoutine.integration.test.mjs` M7RV-10). An edit and a customer create keep 020's ordering through the role row (M7RV-11).
- **Direct calls.** `tmpos_app` no longer executes 020's unconditional `m7a_role_level_set`. A holder of `tmpos_app` plus a live store-owner key can still call 021's set routine directly with no audit, reason, step-up, idempotency or outbox record, now only by naming the session's tenant and the role's current version, which the states read discloses to the same role ([08](./08-production-gate-and-risk-register.md) DA-119).
- **The shop app's use.** The server-backed panel (`src/tenant/ServerCustomerLevels.tsx`, `src/tenant/roleLevelsClient.ts`) keeps each draft as `{ level, baseTenant, baseVersion }` from the read that produced it and sends exactly that tenant and version.
  - Each new attempt gets a new `Idempotency-Key`. One Save press sends at most one PUT, and nothing re-sends a PUT on its own: no timer, read, focus or visibility change, session renewal or Reconnect. A PUT that gets no response at all is held, as below, until the owner presses Save again (corrected in M5-INVOICES-AUTH-P1-R1; until then a lost response was re-sent once, automatically).
  - **Unresolved attempts are held explicitly.** An attempt whose outcome is unknown is held per role as its key plus the exact change it sent (tenant, base version, level, reason). The triggers are no response at all, a 409 `request_in_progress`, a 5xx, or a body the client cannot name. Once the key may already have committed (a lost first attempt, or a held attempt re-sent), a session failure before sending or a refusal that does not say what the key did also leaves it held. A held row keeps its draft and says the change is not confirmed yet, never that it was not saved. Save re-sends exactly the held key and change. Only a 200 or a `write_conflict` settles it; "settled" means nothing else here. Changing the reason or the level is an explicit local abandonment of the held attempt, not a settlement: the panel stops tracking it, and that earlier attempt's server outcome may stay unknown. After a changed reason the row becomes a conflict if the version moved, otherwise an ordinary unsaved draft. A changed level starts a new draft against the version last read. A read alone never proves the save.
  - A read or a 409 `write_conflict` showing another version than a draft's base turns the draft into a conflict. The panel shows the server's current level and the unsaved choice, with **Discard** and **Reapply**, and Save is off. Reapply rebases the draft onto the level this panel read for that conflict; the owner must press Save again, under a new key.
  - **Last-known rows.** Some rows have no level established by a successful read since: a failed read-back, a read-back inconsistent with the save, or a newer read deferred while that role's save was in flight. Such a row is labelled "Last known level" rather than "Server level" until a later read succeeds, and Reapply is refused there; Discard remains.
  - A read that arrived while a role's save was in flight leaves that role alone. When the save ends without its own read-back, a fresh read follows.
  - **Saved means an exact match.** A change is shown as saved only after a 200 whose `version` is `baseVersion + 1` and a same-tenant read-back showing the requested level at exactly that version. A read-back at a greater version reports the change as acknowledged, then changed elsewhere. A conflict, an unresolved answer, a 401, a 403 or a failed read-back is never shown as saved.
  - **Tenant change.** A read naming another tenant clears every draft, key, hold and status, aborts pending reads and cancels unsent saves. It leaves a persistent notice that unsent changes were cleared and that no change was sent to the newly connected tenant. A save already sent is harmless to the new tenant, because the server checks its asserted tenant. Its answer appears only as a detached notice that names no tenant and claims only what the server answered, never as the new tenant's save. The notice says acknowledged for a 200, and not saved for a `write_conflict` or a refusal of a fresh attempt. It says not confirmed for an undecided answer, or for any refusal of an attempt that was held or had lost its first answer: such a refusal is never reported as not saved.
  - **User switch.** Each signed-in user gets their own panel instance, keyed by UID. A user switch or sign-out mounts a fresh panel, dropping everything, including notices and answers to the previous user's saves.
  - The grid's banner for custom roles and other domains is unchanged: those stay local-only.

**Invoices — the owner's per-role level (M5-INVOICES-AUTH-P1, code only, not deployed; [ADR-46](./10-architecture-decision-records.md)).** The store owner can store the Invoices level of the three editable built-in roles, beside their Customers level. It is **configuration only**: no served route decides on it, and no invoice operation (draft, save, create, issue, numbering, payment) is authorized or enforced by the server; invoices are still kept in the browser ([08](./08-production-gate-and-risk-register.md) DA-183, DA-184). - **Storage.** Migration 026 widens the domain CHECKs of 020's `tmpos_role.tenant_role_level` and 021's `tmpos_role_edit.role_level_version` to `customers` and `invoices`, and adds schema `tmpos_role_invoice` with two definer routines whose domain is fixed to `invoices`: `m7a_invoice_role_level_states(uuid)` and `m7a_invoice_role_level_set(text, text, text, uuid, bigint)`. Defaults are the catalog's (`manager` Full, `technician` View, `sales_staff` Create); no row is the default; `store_owner` is Full, never stored or edited. Custom roles keep their browser-only value.
- **`PUT /api/v1/roles/levels` with `domain: "invoices"`.** The same route, body (`{ roleId, domain, level, reason, expectedTenant, expectedVersion }`), bounds, owner rule, recent sign-in, refusals and response as for Customers, written through 026's set routine instead of 021's. The audit record's reason code is `role_<role>_invoices_to_<level>`. Each domain has its own version per role, so a Customers version never satisfies an Invoices precondition.
- **`GET /api/v1/roles/levels/invoices`** is a tenant-session route beside it, with the Customers read-back's requirement (`edit_role_levels`, `trustedContext: 'required'`, no recent sign-in, no body, `idempotency: 'none'`) and validation. It answers `200 { tenant, domain: "invoices", roles: [ { roleId, level, defaultLevel, source, editable, version } ×4 ] }`, in the order `store_owner`, `manager`, `technician`, `sales_staff`, from 026's states read on one snapshot; `store_owner` is `full`, `source` `'fixed'`, `version` `null`. Any query (`?` in the target) is 400 `invalid_request`, decided before the database is asked; a persistence answer out of shape, a throw or an overrun is the bounded 503. It is `Cache-Control: no-store`, writes no audit record and, like the Customers read-back, is keyed in the database by the bare trusted tenant id, not the session key (DA-121). `GET /api/v1/roles/levels` is unchanged byte for byte. The tenant entry serves thirteen routes.
- **Concurrency.** A stale `expectedVersion` or another tenant is the unsealed 409 `write_conflict`, nothing written in either tenant, the lease kept. A reset to the default is an UPDATE and advances the version, so no A → B → A cycle revives a stale draft; storing the level a role already holds also advances it. An audit-record fault rolls the whole edit back (503, the lease kept). A COMMIT whose answer is lost is a 503 whose outcome is **unknown**, not a rollback: the same key and body then replay whatever committed.
- **Idempotency.** The same key and body replay the recorded 200 byte for byte. The fingerprint covers the body bytes, domain included, so one key reused for another body, a Customers and an Invoices edit included, is 422 `idempotency_key_reused`.
- **The shop app's use.** The role screen's second panel, "Server-saved Invoices level" (`ServerInvoiceLevels` in `src/tenant/ServerCustomerLevels.tsx`, reading through `src/tenant/roleLevelsClient.ts`), applies every Customers panel rule above to the Invoices level and says that invoices and their actions are not enforced by the server. *(M7B-INVOICES-P1, commit `15110e4`: its copy now reads "Saved on the store server: only the Invoices level of the built-in roles (store owner fixed). Not deployed, and not applied to any managed database.

**Invoices — store-owned drafts and store discovery (M7B-INVOICES-P1, code only, not deployed; [ADR-47](./10-architecture-decision-records.md)).** The owner's stage decisions: an invoice draft is owned by a real store within a tenant; the operations are save, list and reopen (read-only); amounts are USD in integer cents; the only status is `draft`. Customers stay tenant-owned (no store column; "Customers — scope terms" below): a draft names a customer of its store's tenant. Commit `aedbee2` (with the scanner fix `b27354c`) is the store authority, migration 027 and `GET /api/v1/stores`; commit `29f35a9` the drafts, migration 028 and the three draft routes; commit `15110e4` the shop's "Server drafts" section. Draft prices are user-entered draft information: they set no catalog price, amount due, payment obligation or ledger entry. *(M7B-INVOICES-P2: drafts can now also be edited, below; discarding and deleting a draft stay deferred.)* *(M7B-INVOICES-DISCARD-P1: drafts can now also be discarded, below; deleting a draft stays deferred.)*
- **Store authority.** A store route is authorized only through the actor's own active store-scope grant (`public.user_membership`, `scope_type = 'store'`) at exactly the store the path names; the path's `{storeId}` is a requested target that selects among the actor's own grants and proves nothing. Exactly one such grant must exist: none, a grant at another store, two roles at one store (ambiguous), a tenant-scope grant, and a missing, foreign or non-canonical store segment are the same 403 `forbidden` (`server/composition/tenantAuthorization.ts`). Nothing is inherited from a tenant grant: no accepted document establishes tenant-to-store inheritance, so a tenant-only owner reaches no store route and discovers no store. A store row's existence proves nothing (`tmpos_app` may insert store rows, [08](./08-production-gate-and-risk-register.md) DA-29, DA-97); authority reads `public.store` only for its tenant and status (discovery also serves its name). Statuses: a save needs the account, the grant's tenant and the store `active` or `trialing`; reads admit `active`, `trialing`, `overdue` and `read_only`, and a read-only account, tenant or store (`read_only` or `overdue`) reads but cannot save.
- **Permissions.** Two store route permissions, decidable at store scope only (`STORE_ROUTE_PERMISSIONS` in `server/platform-identity/m5CanonicalPermissions.ts`; at tenant scope they name nothing): `view_invoice_drafts`, Invoices at View or above (list and reopen), and `create_invoice_drafts`, Invoices at Create or above and, on the same role, Customers at View or above (save). The role is the store grant's; its levels are its tenant's owner-edited per-role levels (020's and 026's stored rows; no row is the catalog default: `manager` Full, `technician` View, `sales_staff` Create, for both domains); `store_owner` is Full and never stored, at a store where it holds a store grant only. A browser-only custom role has no server authority: a membership admits the four built-in roles only. All three operations are decided by the authorizer at the path's store and by migration 028's routines, which re-derive the caller, its one store grant at the trusted store and the role's levels from the session key on their own (`m7b_invoice_draft_create`, `_page`, `_get`). Only the save, the one write, is also re-decided inside its command transaction by the revalidator, which re-selects the grant with the trusted scope's own store; the list and the reopen are reads (`TENANT_INVENTORY.reads` in `server/composition/tenantTransactions.ts`) and run in no command transaction. No other invoice operation reads these levels. *(M7B-INVOICES-P1-R2, commit `6b5cef8`: `create_invoice_drafts` also authorizes the read-only eligibility route below, through the save's own requirement object; the authorizer alone decides it (no 028 routine runs), and it is appended to `TENANT_INVENTORY.reads`. It performs no invoice operation, and no other permission, default or level changes.)* *(M7B-INVOICES-P2, commit `573de6c`: a third store route permission, `edit_invoice_drafts` (Invoices at Edit or above, no Customers corequisite), authorizes the draft edit and its edit eligibility read below; the edit is the second write the revalidator re-decides in its transaction.)*
- **`GET /api/v1/stores`** (`server/runtime/storeDirectory.ts`). A tenant session route with the session binding (`X-TMPOS-Session-CSRF` on this GET), no authorizer, no trusted context and no idle-window slide: the handler gets only the session key, and migration 027's `tmpos_store_access.m7b_store_directory` derives everything. `200 { "stores": [ { "id", "tenantId", "name", "readOnly" } ] }`: every store where the session's actor holds exactly one usable store grant, whose store is in the grant's tenant and whose account, tenant and store statuses admit a read; at most 200 (007's resolver refuses more grants), ordered by name in byte order with unnamed stores last, then id; no continuation. `name` is the stored name when it is 1–256 characters, else `null`; `readOnly` is true when the account, tenant or store is `read_only` or `overdue`; `tenantId` is what a save sends as `expectedTenant`. A tenant-only actor reads `{ "stores": [] }`. Any query is 400 `invalid_request`; a session that ended, or whose standing moved, after the chain's session check is 403 `forbidden`; an outage or a malformed answer is the bounded 503. No audit record (the tenant reads' rule).
- **`POST /api/v1/stores/{storeId}/invoice-drafts`** (`create_invoice_drafts`; `server/runtime/invoiceDrafts.ts`). An unsafe tenant command: Origin, `X-TMPOS-CSRF` and `X-TMPOS-Session-CSRF`, `Idempotency-Key` (one UUID v4), JSON body at most 64 KiB (a larger one is 413 `content_too_large`). Body exactly `{ expectedTenant, customerId, currency: "USD", lines: [ { description, quantity, unitPriceCents } ] }`, no other key at either level. `expectedTenant` and `customerId` are canonical lowercase UUIDs; `expectedTenant` is a precondition, never authority. 1–50 lines, kept in order. `description` follows the customer name's pipeline at 256: trimmed, then 1–256 Unicode scalar values with at least one visible scalar and no C0 control (NUL included), DEL, C1 control, line or paragraph separator, lone surrogate or Bidi_Control character; migration 028's CHECK restates every rule PostgreSQL can represent, and the runtime-only ones are NUL, the lone surrogate and the visible-scalar rule. `quantity` is a safe integer of at least 1, `unitPriceCents` a safe integer of at least 0 (`-0` refused, as in every record); every `quantity × unitPriceCents` and their sum are computed in BigInt (never a float) and must stay at most 9007199254740991. Either one, on the list or on one customer, clears both the list and the customer shown and cancels reads in flight. 429: the page waits for `Retry-After` (whole seconds, held to 1–300; 60 without one); a later deadline wins, no read starts during the wait, and a first-page read the wait blocked runs once when it ends. 503 or no answer: "The customer directory is unavailable right now.", and rows already confirmed on this session stay only under a "last known" label, after a failed "Load more" as after a failed refresh. 400 to a cursor: one reload from the first page. The page shows its saved notice, `Saved on the server: "<name>".`, only on the validated 201, fresh or replayed (`Idempotent-Replayed: true`), whose name equals the name sent.

"Check again" re-sends exactly that pair: only by the user's action, only under the session CSRF token it was first sent with, and only within 23 hours, a client cutoff under the 24 h retention. A reload loses the attempt. - **Request.** `{ expectedVersion, name, phone?, email? }`, nothing else: an unknown key, or `id`, `createdAt`, a tenant or a version under any other name, is 400 `invalid_request`. `expectedVersion` is a safe integer from 1 to 2^53 − 2. `name` is required and judged by the create's rule. `phone` and `email` are optional: omitted leaves the stored value; JSON `null` or a string that is blank after `trim()` clears it (SQL NULL); any other string is normalized by the create's rule; any other type is refused. - **Answers.**

  - A withdrawn authority or session refuses with nothing written. An outage, a timeout, a malformed store answer or a COMMIT whose answer was lost is the established bounded 503: the outcome is unknown, and the runtime assumes no rollback (DA-163).
- **Idempotency.** The fingerprint is contract version 2's array with the canonical target appended after the body; a literal route's fingerprint is byte-identical to before, so the create's pinned vector, its sealed completions and `IDEMPOTENCY_CONTRACT_VERSION` (2) are unchanged. Under one key, a changed body, or the same body sent to another customer, is `422 idempotency_key_reused`. A completed edit's retry replays its sealed answer before anything is evaluated again, even after later edits moved the version, and a replay still needs the current session and authorization.

A changed edit commits the customer's new values and version, exactly one audit record and the sealed completion, or nothing. An audit or completion fault rolls the change and the version back.

Metadata stays `{}`: the changed field names are not recorded, because the writer's allow-list has no key for them (DA-158). No old or new name, phone or email reaches the record, a log line, an event, a refusal reason or an idempotency diagnostic. A no-op, a conflict and a refusal write none. The create's record is unchanged and still names no customer (DA-111).

The customer search (025) filters by that derived tenant. In the server code, "store key" means the session store's key (a digest of the session id), never a store id. The shop's UI copy says "store" for the tenant, the business, as in "No customer with this address is available in this store."; these documents say "tenant" for that scope, and earlier passages that said "store" for it (P4's role-level passages here and in docs 09 and 10, and P5 to P7 here) now say "tenant".

**Customers — searching by name (M7A-CUSTOMERS-P8, code only, not deployed; [ADR-43](./10-architecture-decision-records.md)).** The list takes an optional name search; no route, permission, table, index or extension is added. The server and database change is commit `8ed4e56`, the shop's search form commit `f326a4c`.
- **`GET /api/v1/customers?q=…`.** The list's route and policy, unchanged: `view_customers`, tenant audience, `trustedContext: 'required'`, `sessionBinding: 'required'` (the session CSRF header), no body, no `Idempotency-Key`, no recent sign-in. The tenant is the trusted scope's only, never the query's. The 401, 403, 429 and 503 answers are the list's.
- **The query.** `limit`, `cursor` and `q`, each at most once; any other key, a repeat or an empty pair is 400 `invalid_request`, as before. `limit` (1–100, default 50) and `cursor` keep their raw grammar. The whole raw query is bounded at 4,096 characters (it was 128); longer is 400. `q`'s raw value is printable ASCII, decoded as `application/x-www-form-urlencoded` (every `+` a space, then percent-decoding as UTF-8): a malformed escape, invalid UTF-8 or an encoded surrogate is 400. It is then trimmed. Blank after that (`q=`, `q=+`, `q=%20`) is the unfiltered list exactly as before, its cursor included. Otherwise it is the applied search text, refused (400) when it holds a C0 or C1 control, DEL, U+2028, U+2029 or a Bidi_Control character, or more than 200 code points. Every parse refusal is the same 400 with the one log reason `customer_directory_query_invalid`; no refusal body, reason or log line carries the text.
- **The match.** Name only. A customer matches when its name contains the text as a literal substring once both are uppercased by the ICU root locale's full mapping (`pg_catalog."und-x-icu"`): case-insensitive, so `é` matches `É` and `ß` matches `SS`. `%`, `_` and `\` are literal: the pattern escapes them explicitly, so nothing in the text is a wildcard. It is an uppercase mapping, not case folding, and it applies no Unicode normalization, accent folding or language rule: a name stored decomposed (NFD) does not match its composed (NFC) spelling, `e` does not match `é`, Turkish dotless `ı` matches `I` but `i` does not find a dotted `İ`, and Greek accents are kept ([08](./08-production-gate-and-risk-register.md) DA-169, DA-170).
- **Order and pages.** The list's order: name under "C", then id. A search page continues with its own cursor: 44 canonical base64url characters encoding a tag byte (0x03), the last customer's id and the first 16 bytes of the SHA-256 of the normalized search text's UTF-8. It carries no text, name, tenant or authority. It is accepted only with the same normalized text (another spelling of it, such as `+` for a space, included): a search carrying an unfiltered, malformed or other text's cursor, and a request without `q` carrying a search cursor, are each 400. Its position is looked up only among the admitted tenant's customers, at that customer's current name, and the anchor need not match the text; a deleted or foreign anchor is the list's 400 (`customer_directory_cursor_unknown`). As for the list, no snapshot spans pages: a create or an edit between two pages can make a later page repeat or skip a customer ([08](./08-production-gate-and-risk-register.md) DA-84, amended; DA-171 for the digest).
- **Response.** Unchanged: `200 { customers: [{ id, name }], nextCursor }`, `nextCursor` a search cursor when another page follows, else null. No count of matches is given.
- **The database (migration 025, `025_m7a_customer_search`).** Schema `tmpos_customer_search` holds one routine, `m7a_customer_search(p_session_key, p_expected_tenant, p_query, p_after_customer_id, p_limit)`: plpgsql, `STABLE`, `SECURITY DEFINER`, pinned to `search_path = pg_catalog, pg_temp` and run with `row_security = off`. It judges every argument first and answers one `invalid` row for a malformed key, a null tenant, an empty text, a text over 200 characters or holding a character 017's name rule refuses anywhere in a name, or a limit outside 1–101; the runtime never sends one, and its adapter reads `invalid` as a fault (503). It then decides the list's authority exactly as 022's detail read does, restating its steps statement for statement rather than calling it: a minted, live, tenant-audience session under the installed issuer key, the unchanged standing, exactly one tenant grant, the role's current Customers level at View or above (`store_owner` full; an editable role's stored level, else the catalog default), the expected tenant as a precondition, never a selector, and 017's rechecks. A read-only or overdue account or tenant still reads. Any refusal is one `denied` row. A continuation's anchor is read only in the derived tenant (one `cursor_unknown` row otherwise). The page is one statement with the tenant predicate inside it, ordered by `(name collate "C", customer_id)`, at most `p_limit` rows: the runtime asks one more than its page to know another follows. It writes nothing, takes no row, advisory or write lock (only the ordinary read locks every query takes) and raises no message of its own. The adapter calls it only when the query carries a search, and judges its rows with the list's own checks (every row the authorizer's tenant, distinct, storable, in page order).
- **Cost.** The predicate is `upper(name collate "und-x-icu") collate "C" LIKE` the escaped `'%text%'` pattern, filtered to the derived tenant. The customer table has two indexes: `customer_pkey` (`customer_id`) and 017's `customer_tenant_page_idx` (`tenant_id, name, customer_id`). The page index keeps a search to the tenant's range in page order and serves a continuation's keyset position; no installed index evaluates the uppercase substring predicate itself. The planner either walks the tenant's range of the page index in page order, stopping once its page is full, or scans the whole table and sorts the matches, so a rare or absent text uppercases every name in the tenant's range or, under the sequential plan, in the table. Either way the rows come back in `(name collate "C", customer_id)` order. Measured with EXPLAIN (ANALYZE, BUFFERS) on a local disposable PostgreSQL 16.10 cluster holding 25,000 synthetic customers (a tenant of 20,000 and one of 5,000), modest evidence and not a benchmark: with literal parameters a search with no match took 8.459 ms and a rare match (3 rows) 8.279 ms, each by a sequential scan of all 25,000 rows; under a generic plan, as a cached plan may run, the same two visited the tenant's 20,000 index entries in about 13 ms; a common match (the first 101 of 5,460) took 0.121 ms and its continuation page 0.309 ms, both through the page index. The cost grows linearly with the tenant's customers (with the whole table's when the planner chooses a sequential scan) and is bounded by the read's 2.7 s statement limit and, over HTTP, the per-client rate limit. No substring accelerator is installed: a trigram index would need the `pg_trgm` extension, which this work does not add. This is recorded, not a defect fixed here ([08](./08-production-gate-and-risk-register.md) DA-168).
- **Grants and readiness.** `tmpos_app` gets USAGE on the schema and EXECUTE on the routine, nothing else; no other runtime role, and not PUBLIC, holds either, and `tmpos_app` still holds no privilege on the customer table or its columns. The startup preflight requires exactly 001–025 and these two grants, and the P7 build refuses a 025 database. The tenant entry's reads readiness asks the search routine last, after the profile's: a random key no session holds must answer exactly one `denied` row (`probeCustomerSearch`).
- **ICU.** 025 refuses to apply where the ICU root collation `pg_catalog."und-x-icu"` is absent, so a server built without ICU never answers a different match. Which names match follows the ICU version PostgreSQL is built with ([08](./08-production-gate-and-risk-register.md) DA-169).
- **Rollback.** `025_m7a_customer_search.down.sql` refuses when 025 is not applied; otherwise it drops exactly the routine and the schema with their grants, and proves that `tmpos_app` still executes the 001–024 customer reads and edit (020's list, 022's detail read, 024's profile read and edit) and holds nothing on the customer table. 025 holds no data, so there is no data guard: whatever customers exist or were edited, the database is then exactly the 001–024 one. Migrations 001–024 are unchanged. The order is 025 first, then 024, 023, 022, 021, 020, and the database does not enforce it. Rolling 020 back while 025 is applied leaves the search routine raising for an editable role (it reads 020's role-level table; the runtime answers 503); rolling back 022, 023 or 024 first leaves it working, since it reads none of their objects. 025's rollback then refuses while `tmpos_app` cannot execute 020's `m7a_customer_page_v3`, 022's `m7a_customer_get` or 024's `m7a_customer_profile` and `m7a_customer_update`, until they are applied again; it does not check 021 or 023.
- **Privacy and logging.** The search text, names, contacts and the raw query never reach a log line, a refusal body or reason, or an error message of the runtime or the routine; the request log names the route's path only. The shop keeps the text out of the address, history, browser storage and analytics. A GET's query is part of its request target, so a proxy, load balancer or edge in front of a deployment may record `q`, and a search cursor's digest, in its access log: redacting them on this path is a pre-deployment requirement, not inspected or changed in this stage ([08](./08-production-gate-and-risk-register.md) DA-167, DA-171). A database log that captured bind parameters would expose search texts (DA-102, amended). No audit record is written (the list's owner decision, DA-88, amended).
- **The shop app's use (commit `f326a4c`).**
  - *The form.* The server-backed list has a form labelled "Search customers by name", with an input, a Search button (Enter submits too) and Clear. The input is a draft: nothing is sent while typing, and typing never relabels results already shown. Search applies the draft as the server would (trimmed; blank is the unfiltered list); a refused character or more than 200 characters is said inline, accessibly, and nothing is sent. Applying drops the collected pages and the cursor and reads page one; Clear empties the draft and reads the unfiltered page one. Refresh, Load more, Try again and the read after a rate-limit wait use the applied search. The client (`customersClient.list`) sends `q=<encodeURIComponent(text)>`, before any cursor, only for a non-empty normalized text, and each kind of request sends and accepts only its own kind of cursor.
  - *States.* Loading; "Customers matching “x”" over the results; "No customers match “x”." only after a successful search page with no rows; the existing empty text after a successful unfiltered page with no rows; and rate limited, temporarily unavailable, signed out and access denied exactly as the list shows them. A failed read is never shown as "no matches". The summary is announced in a polite live region, and no total count is shown. Selecting a result opens the existing profile.
  - *Async safety.* An older search's answer never replaces a newer one, and an answer for an earlier session, tenant or user, or one that arrives after the page has gone, is dropped. An ended session clears the rows, the cursor, the draft and the applied search; a new session generation starts with an empty draft and the unfiltered list; an access-denied answer clears the applied search with the rows. Search, Clear, Refresh and Load more follow the same plain rule: after a confirmed end only Reconnect signs in (DA-150, amended; wording corrected in M7A-CUSTOMERS-P10).
  - *Mutations.* A search never re-sends, changes or detaches a pending create or edit, its bytes, its key or its "Check again" window. After a confirmed create or a confirmed edit, the list reloads from its first page under the applied search, if any; a created customer appears in a search's results only when the server returns it. A confirmed edit first puts the confirmed name in the edited customer's row where it is shown, so a reload that fails keeps the rows with that name, never the one from before the edit.
- **Unchanged.** The list without `q`, its cursor and its refusals; the detail read, the profile read, the create and the edit; the browser-only Customers screen and its records (DA-144); and migrations 001–024.
- **Availability.** The compiled tenant entry still serves twelve routes, on the tenant host alone. Nothing is deployed, and no managed database was touched.

**Customers — customer references in drafts (M7A-CUSTOMERS-P9, shop code only, not deployed; [ADR-44](./10-architecture-decision-records.md)).** A new invoice draft can name a customer saved on the server. No route, permission, migration, grant, dependency or browser storage is added, and the server is unchanged. The typed reference and the picker are commit `a5f1416`, their use in the invoice draft commit `17a659b`. *Since M7A-CUSTOMERS-P10 ([ADR-45](./10-architecture-decision-records.md)), a new repair ticket draft can name one too, and the picker is a keyboard modal: the picker's keyboard contract is commit `c46d3eb`, the repair draft (with the move of `usableDraftCustomer`) commit `5eeda24`, and the server is still unchanged.*
- **The reference.** A draft names its customer by one tagged, frozen field (`src/tenant/customerReference.ts`): `none`, `local` (an id of the browser's own customer list) or `server`. Being one field, a draft never holds an active local and an active server customer at once, and every reader states which source it accepts: `localCustomerIdOf` answers `''` for none and for a server reference, never a server id.
- **Local ids keep their meaning.** A local id is the browser list's own: the seeds `c1` to `c5`, `c<timestamp>` (the Customers screen) and `c-<timestamp>` (the dashboard's and the POS's quick add). Every invoice, repair ticket, order, return and other record that already names a customer keeps its local id and its name and contact snapshot, untouched. Nothing is migrated, mapped, imported, merged or backfilled, and a name, phone or email never establishes identity: a server customer is never looked up in the local list or matched to a local one by any field ([08](./08-production-gate-and-risk-register.md) DA-176, with DA-144).
- **A server reference.** The server-issued customer id (a canonical lowercase UUID; a branded type that only `serverCustomerReference` makes, and only from a list row whose id is canonical and whose name is non-empty), the name that list answer gave (for display only, never identity), the UID of the signed-in shop user it was chosen by, and an opaque session context naming the checked tenant session it was chosen under (compared by identity; it holds no token and nothing of the tenant). It has no phone, email or other contact field: a list answer carries only `{ id, name }`, and only those two are copied.
- **Where it lives.** In the invoice page's React state only (since M7A-CUSTOMERS-P10 also the repair tickets page's), as every local draft is (the browser's customers and invoices are themselves plain React state, `src/context/StoreLocalState.tsx`): never in browser storage, a URL or a log. A reload, leaving the page, or closing the Create Invoice dialog or the new repair ticket form loses it.
- **Where it is consumed.** Only the Create Invoice draft (`src/components/Invoices.tsx`) and, since M7A-CUSTOMERS-P10, the new repair ticket draft (`src/components/RepairTickets.tsx`); both decide what a held reference counts as through `usableDraftCustomer` (`src/tenant/customerReference.ts`): a server customer is none unless the signed-in user chose it and the Customers View hint holds. Create and edit still build an invoice only from a `local` reference, through the same local lookup and snapshot as before, and the stored invoice's shape is unchanged; a server reference never reaches that lookup, `addInvoice`, `updateInvoice`, shipping or returns. With a server reference Save ("Generate Invoice") is disabled and the dialog says "This draft uses a customer saved on the server. Creating an invoice for a server customer isn't available yet, so this draft can't be created. To create the invoice here, choose a customer from this browser's list instead.", which also describes the disabled Save (`aria-describedby`). Choosing a local customer replaces a server one. The Edit Invoice dialog offers no server picker: it opens on the invoice's stored local id and saves a local customer as before. *In the repair draft* `none` also stands for a typed walk-in name, whose id (`walk-in-<timestamp>`) is minted at save only, as before, and is never a draft reference; a pick from the browser's list is a `local` reference with its name and contact snapshot; the server field sits below the customer box. Typing in the box or a local pick replaces a server customer, Remove clears only the binding, and every close of the form (Cancel, the backdrop, a created ticket) ends the draft and drops it. A server choice fills no contact, device or other field. With a server reference Create Ticket is disabled and described (`aria-describedby`) by "This ticket uses a customer saved on the server. Creating a repair ticket for a server customer isn't available yet, so this ticket can't be created. To create it here, type the customer's name or choose a customer from this browser's list instead.", and the create handler returns without a ticket, a reset or a close. A ticket's `customerId` is the local reference's id or the walk-in id, never a server id; editing a ticket and the ticket detail offer no picker. *(M7B-INVOICES-P2: the server drafts section also renders it, in its New server draft dialog since M7B-INVOICES-P1 and, since commit `4f3c700`, in its editor, seeded with the draft's own customer; without the local Customers View hint the customer is kept as it is.)*
- **The picker** (`src/tenant/ServerCustomerPicker.tsx`). A dialog over the existing `GET /api/v1/customers` (page one, Load more and P8's name search) through the existing session and customers clients; it reads customers only. Each row shows the name, "ID ending" and the id's last eight characters, so identical names stay distinguishable, and a Select button; nothing is selected automatically, not even a single match. The draft shows the choice as a "Server customer" card with Change and Remove. The entry point is offered while the tenant's plan includes the Customers feature (`canAccess('customers')`, as the directory route's own guard requires) and the local role state holds Customers at View or above, inside a Create Invoice dialog that needs Invoices at Create or, since M7A-CUSTOMERS-P10, a new repair ticket form that needs Repairs at Create. All are checks in the browser, presentation and enforcement in that tab only: the server's 403 decides the customer read alone ([08](./08-production-gate-and-risk-register.md) DA-140, amended), and no server route creates or authorizes an invoice or a repair ticket *(wording corrected in M7A-CUSTOMERS-P10: this sentence first read "all are hints, and the server's 403 decides")*. A selection binds only if all three still hold when it is reported.
- **Session behaviour.** One generation per checked session token: a session check runs before every read, the dialog fixes the first token it sees, and a different token starts a new generation (reads in flight cancelled; a running rate-limit wait cleared; rows, cursor and search cleared; page one read again). A window focus or a return to the tab runs one plain session check (it never signs in after a confirmed end): in the open dialog once a token is fixed and while it is not signed out, with Select disabled until it answers (a return while a read is out is checked when that read settles, so no row it brings is selectable unchecked); in the draft's field while the dialog is closed and a server customer is held. A server reference is dropped from the draft, with a notice, once the session it was chosen under is known to be over: an ended session, a refused sign-in or no signed-in identity (an open dialog then shows signed out with Reconnect, and the notice says to choose "Select a server customer", then Reconnect); a 403, unless the fresh session check it triggers finds a different token; or a different token (an open dialog starts a new generation). An undecided focus or tab-return check (an outage or a rate limit) keeps it, keeps the dialog's rows and starts no wait; after a 403 an undecided check leaves the refusal standing, and a rate-limited one also starts the wait. A rate-limited read disables Search, Clear and Try again for the `Retry-After` seconds (60 without one) and says "Too many requests. Wait N seconds, then try again." A user switch, or the local role state losing Customers View or the plan losing the Customers feature, makes it none in the same render and drops it. A late answer cannot bind: the field is keyed by the user and the draft, a report from an earlier draft's field is ignored, and a dialog applies only the latest read or check of its current generation while it is mounted. Opening the dialog connects as the directory page does on open; after a confirmed end only the dialog's Reconnect signs in, and its token is the dialog's first, so the user's own Reconnect shows no "connection changed" notice ([08](./08-production-gate-and-risk-register.md) DA-150, amended). The module's latest UID and token pair is forgotten when the draft's field unmounts. Focus returns to the search input when the focused control goes away. *Since M7A-CUSTOMERS-P10 the dialog is a keyboard modal* (DA-178, closed at code and browser level): its overlay is `z-[190]`, above every host dialog (the repair form is `z-[110]`) and below the `z-[200]` toasts; while it is open every other child that `<body>` had when it opened carries the `inert` attribute, and closing it removes exactly what it set; Tab and Shift+Tab wrap around its enabled buttons and inputs and, from anything else, land on the first or the last; Escape is default-prevented and stopped, so it closes the picker alone and a host dialog stays open; a press on the backdrop moves no focus; a press on its own text that is no control focuses the dialog itself (`tabIndex={-1}`: no Tab stop, no ring of its own), so Escape and Tab still reach it; on close focus returns to "Select a server customer", or to Change when a customer is held, and a check while the dialog is closed that drops the held customer with focus on Change or Remove moves focus to "Select a server customer"; every control shows a `focus-visible` outline. The invoice and repair dialogs around it are not keyboard modals of their own ([08](./08-production-gate-and-risk-register.md) DA-181).
- **Trust.** A reference held by the client is not authority. A future durable invoice command (M7b) must itself resolve the authenticated actor, the trusted tenant scope, the invoice permission, and the customer's ownership by that tenant and its eligibility; a UUID or any client-held field satisfies none of these ([08](./08-production-gate-and-risk-register.md) DA-175). The same holds for a future durable repair command (M7d), with the repair permission in place of the invoice permission ([08](./08-production-gate-and-risk-register.md) DA-180).
- **Unchanged.** Every server route, grant and migration (001–025); the browser's customer list and the Customers screen (DA-144); every existing invoice and its edit, shipping and return paths; every stored repair ticket, editing a ticket and its detail; the POS, returns, shipping and every other screen that names a customer (DA-177, closed for the repair draft only).

## 3. API & error contract (production standard)

| Aspect | Standard |
|---|---|
| Versioned paths | `/api/v1/...` (tenant), `/admin/v1/...` (Backend CP) |
| Request/response schemas | typed, validated at the boundary; reject unknown fields on writes |
| Pagination/filtering/sorting | cursor pagination; explicit allowlisted filter/sort fields. The first tenant read, `GET /api/v1/customers` (M7A-CUSTOMERS-P1, §2), pages by an opaque keyset cursor that carries no authority, allows no filter or sort parameter, and refuses any other query key with 400 `invalid_request` |
| Concurrency | `version`/`updated_at` optimistic concurrency; conflicting write → 409 `write_conflict`, sealed as the idempotency record's completion in the transaction that decided it (M5-GIAM-D1-P2-R1), so an identical retry replays it and the key cannot mutate while that record is retained. *Exception (M7A-CUSTOMERS-P4, [ADR-37](./10-architecture-decision-records.md)): the owner's role-level edit's tenant and version precondition refusal is an UNSEALED 409 `write_conflict`: its command transaction records no mutation, audit record, event or completion, while the key's separately committed lease remains until it expires under the existing policy and the same key is then decided afresh (§2)* *(M7B-INVOICES-P2, [ADR-48](./10-architecture-decision-records.md): the store invoice draft save's and edit's `expectedTenant` mismatch is the same UNSEALED 409 `write_conflict`; the edit's stale version, a stale no-op included, is the standard SEALED 409.)* |
| Idempotency | `Idempotency-Key` header for retryable/mutating requests; durable key store in PostgreSQL, completed in the mutation's own transaction ([ADR-17](./10-architecture-decision-records.md)). Since M7A-CUSTOMERS-P3 it is required by tenant session commands as well as platform commands; the first is `POST /api/v1/customers`, and the second `PUT /api/v1/roles/levels` (§2). The request is bound to the authorizer's trusted tenant and actor, never the request's, so a key never replays across tenants or actors ([ADR-34](./10-architecture-decision-records.md)) |
| Correlation | server-generated `request_id`/`trace_id`; **no sensitive identifier** in correlation values. *Administrative session audit (M6-ADMIN-AUDIT-P1, [03 §2b](./03-backend-control-plane-login-session-blueprint.md)):* a row's `request_id` is the operation id, a random UUID the server generates for that one login, reauthentication or logout. The request's log line carries the same value as `operationId`, except for a logout whose client disconnected first: that line (reason `aborted`) is written at the close, before the id exists, and one info-level `session_logout_after_close` line carries both `requestId` and `operationId`. `trace_id` is null. A client's `X-Request-Id` may be adopted as the request correlator in logs and refusal bodies, but it is never persisted in an audit row. A session is named only by `sessionRef` = base64url(SHA-256(`tmpos-audit-session-ref:v1\n` + store key)). The store key is not used because the definer session routines accept it and the runtime role may execute them, so the key would let a reader of the audit trail read, extend or end a live session |
| Error envelope | bounded `{ error: { code, message, correlationId } }`; **no stack traces, no raw DB/provider errors**. The shipped runtime's own refusals carry `{ error, requestId }`, and a RECORDED rejection (M5-GIAM-D1-P2-R1) carries the refusal word alone — a body replayed byte for byte may hold no correlation value, so the fresh one travels on `X-Request-Id` |
| Auth errors | 401 (unauthenticated), sanitized |
| Authz errors | 403 (authenticated but not permitted), sanitized reason code |
| Validation | 422 with field-level codes (no echoed secrets). *The shipped runtime answers a body its contract refuses with 400 `invalid_request` and no field-level code, and the tenant customer create and the owner's role-level edit do the same (M7A-CUSTOMERS-P3 and -P3-R1, §2). There, 422 means only a reused `Idempotency-Key`* |
| Conflicts | 409 (version conflict, or an idempotent request still in progress; since M7B-INVOICES-P2 also the sealed `invalid_state` when a draft's state admits no edit); 422 (an `Idempotency-Key` reused for a different request — [08](./08-production-gate-and-risk-register.md) G-IDEMPOT) |
| Rate limits | 429 + `Retry-After` (whole seconds: the time left in the window on the shared store's database clock, migration 014, [ADR-26](./10-architecture-decision-records.md)); a limiter that cannot answer is a bounded 503, never an allowance |
| Unavailable/degraded | 503 with retry guidance; provider failure surfaces as a bounded upstream-unavailable code, never the raw provider error |

## 5. Payment contract (G-PCI — DECIDED: integrated capability in scope)

TM POS2026 supports **cash**, **external-terminal/manual-reference**, **integrated card-present via a PCI-certified semi-integrated terminal/provider**, and **hosted/tokenized CNP** flows. Direction is **DECIDED**; the specific provider is selected in **M7b** by documented criteria (and must not become a hidden future milestone).

**Hard data boundary (never in TM POS2026 — not received, stored, persisted, logged, or exposed):** raw PAN, CVV/CVC, magnetic-stripe/track data, PIN/PIN block, unencrypted cardholder data, processor credentials in browser storage. Card data is collected only by **provider-hosted/provider-certified components**; TM POS2026 holds only **opaque payment-method tokens**.

| Aspect | Contract |
|---|---|
| Aggregate root | `payment` (per order/invoice), with `payment_event` (append-only state log), `payment_method_token` (opaque), `terminal_device`, `dispute` |
| Lifecycle | initiated → authorized → captured → settled; plus void, refund, dispute, failed — each an appended `payment_event` |
| Idempotency | `Idempotency-Key` on every payment mutation + **duplicate-charge prevention** (a retried authorize/capture never double-charges) |
| Webhooks | provider webhooks **signature-verified** at the egress boundary before processing; replay-safe |
| Reconciliation | periodic reconciliation of provider settlement vs local `payment` state; discrepancies flagged |
| Refunds / voids / disputes | modeled explicitly; refunds idempotent; disputes tracked to resolution |
| Credentials | processor credentials **encrypted at rest + rotated** (G-SECRETS); never in browser storage |
| Provider outage | defined degraded behavior (queue/deny with safe classification; never a silent success) |
| Terminal/device | `terminal_device` assignment scoped to **tenant/store**; a device cannot act outside its store |
| PCI validation | applicable PCI validation category (SAQ A / P2PE / other) **confirmed with the selected provider/acquirer or QSA before production** — **not claimed** until the final integration architecture establishes eligibility. As a multi-tenant orchestrator holding provider credentials, terminal assignments, and tokens, the platform's own **PCI service-provider scope (TPSP / Payment-Facilitator, responsibility matrix, per-tenant AoC)** is validated alongside the merchant category |
| Audit | every payment state transition writes a durable append-only `audit_event` |
| CHD containment (all surfaces) | **no raw PAN/CVV/track/PIN or processor secret in ANY operational, observability (logs/metrics/traces), evidence, export/BI, receipt, or support surface** — reconciliation, refunds, disputes, webhook payloads, receipts, and support tools handle only opaque tokens + masked/last-4; redaction enforced and tested (G-PCI evidence, [07](./07-quality-and-test-strategy.md)) |

### 5.1 Store-owned payment gateway connection model

**Ownership (OWNER CORRECTION):** payment-gateway connections are configured at the **STORE** level — by the **Store Owner**, or another active store user holding an **explicit canonical permission** to manage gateway connections ([04 §2.1](./04-canonical-iam-and-four-user-migration.md)). They are **not** supplied, configured, retrieved, or normally viewed by the System Owner. The store-facing location is **Store Settings → Payments / Payment Gateway** (not the System Owner Backend Control Plane). Cash and external-terminal methods remain available **independently** of any integrated gateway.

**Platform vs store split:** the **System Owner Backend CP governs the connector catalog and security policy** (which providers exist, availability by environment/region, minimum versions/security requirements, bounded connector health, global connector disablement during an incident, feature/plan eligibility, aggregate failure review, audited break-glass) — see the boundary in [03 §9](./03-backend-control-plane-login-session-blueprint.md). The **store owns its own merchant connection** (selection, authorization, activation, replacement, disconnection).

**Connection flow (store-initiated):**
```
platform connector catalog → store selects provider → canonical store-scoped permission check
  → recent-authentication / step-up → server-generated OAuth or provider-hosted onboarding
  → provider authorization → encrypted store-scoped connection reference
  → server-side connection validation → webhook registration + verification
  → terminal pairing (if applicable) → store makes connection active → durable audit
```
**OAuth / provider-hosted onboarding is preferred.** **No raw secret/API-key entry in the browser** when the provider offers a secure OAuth/onboarding flow.

**Credential handling (when a provider unavoidably requires a secret):** collect through a **dedicated protected server exchange**; never hold longer than necessary in React state; **never** in `localStorage`/`sessionStorage`; **never returned after acceptance**; **envelope-encrypted through the approved credential service** (§4 + M6); store **only a credential reference** in ordinary application tables; **redacted** from logs/traces/errors/audit/support/exports/backups; **rotation + revocation** supported. **OAuth access/refresh tokens are long-lived secrets and use this same envelope-encrypted / reference-only / rotation-revocation model.**

**OAuth callback binding (model invariant, not just a test):** the OAuth flow MUST use an unguessable **`state`** parameter (CSRF), **PKCE**, an **exact redirect-URI allowlist**, and a callback that **binds the returned provider account to the initiating store's authenticated session** — so authorization-code injection / connection-CSRF cannot link a victim store to an attacker's merchant account, and a returned account cannot be bound to any store other than the one that initiated the flow.

**Connector-catalog integrity (model invariant):** each connector's definition (OAuth URLs, API endpoints, **webhook hosts**) is **code-shipped, reviewed, and integrity-protected, subject to the provider egress allowlist ([ADR-07](./10-architecture-decision-records.md)) — NOT free-form admin-entered.** Any catalog mutation is a **step-up + reason + durable-audit** controlled action. (This closes the indirect path by which a compromised System Owner could repoint a connector at an attacker host and harvest every connecting store's credentials.)

### 5.2 Multi-store isolation & durable entities

Every connection is owned by exactly **(`tenant_id`, `store_id`, `provider_key`, `environment`)**. Conceptual durable entities (schemas NOT implemented in M1): `payment_provider_connection`, `payment_terminal`, `payment_webhook_registration`, `payment_provider_health`, `payment_provider_event`.

**Isolation invariants:** one store cannot query/use another store's connection; webhook events correlate to the correct provider account + tenant + store + environment; **sandbox credentials cannot process production payments**; production and test credentials are isolated; a terminal is assigned to one authorized store/environment (pairing relies on provider-attested device identity / P2PE-certified hardware; connection/credential-reference tables carry tenant/store RLS like other business tables — [03 §7](./03-backend-control-plane-login-session-blueprint.md), G-DBROLE); **credential references cannot be reassigned by client input**; **provider account identifiers are never accepted as authority**; the server derives tenant/store scope from the canonical session + authorization context; **a `provider_account_id` is uniquely and provider-verifiably bound to exactly one connection** (established via the OAuth callback binding above) so webhook correlation cannot be hijacked or made ambiguous by a second store claiming the same account id.

### 5.3 Active-provider & switching rules

**One active integrated provider per store/payment channel** for the initial design (multiple only if the architecture explicitly supports safe channel routing); cash/external-terminal remain independent. **Provider replacement must check** pending authorizations, unsettled transactions, refunds/disputes, active terminals, webhook backlog, and reconciliation status — **unsafe switching is blocked**. Old credentials are revoked or retained only for **bounded reconciliation/refund obligations**. Activation/disconnection is **idempotent and audited**; **no duplicate charge can result from failover or retries**. The replacement/disconnect safety checks read a **server-owned source of truth** for pending authorizations, unsettled funds, disputes, active terminals, webhook backlog, and reconciliation locks (never client-asserted). A **verified** webhook (dispute/chargeback/late refund) arriving **after** the bounded retention window is not silently dropped — it is captured and routed to the dispute/compliance path so no financial/compliance event is lost.

### 5.4 Initial connector catalog (M7b — Stripe / Square / Adyen)

The initial M7b connector catalog targets **three provider families** (initial supported options — not three simultaneously-required live integrations), subject to current official API/country/hardware verification during M7b:

| Provider | Connection model | Card-present | CNP |
|---|---|---|---|
| **Stripe** | Stripe Connect / platform connection | Stripe Terminal | hosted/tokenized where applicable |
| **Square** | OAuth merchant connection (Payments API) | Terminal/device APIs where supported | hosted where applicable |
| **Adyen** | platform/account-holder integration where applicable | in-person/terminal | enterprise/multi-region |

**M7b verification (each candidate):** supported merchant countries; supported transaction currencies; **Morocco/US and intended launch-market availability**; card-present hardware; OAuth/platform-account model; API maturity/versioning; webhook support; refunds/voids/disputes/reconciliation; sandbox/test capability; pricing/commercial onboarding; PCI scope; marketplace/platform restrictions; account portability; provider-outage behavior; support model. If a provider cannot support the launch market or the store-owned connection model, **M7b may replace it only via a documented ADR + owner approval — with no new milestone**.

## 6. Privacy & data-rights (DSAR) contract (G-PRIVACY — DECIDED: implement, not exclude)

A production privacy foundation is **in scope**, distributed across milestones (no new milestone). **No universal-compliance claim is made** — final policy and jurisdictional obligations require owner/legal review.

**Roles:** the **tenant is the data controller** for its store/customer/employee data; the **platform is the processor** (plus controller for platform-operator data). DSAR requests are authorized through tenant approval with platform escalation.

| Capability | Contract |
|---|---|
| Data inventory & classification | every domain table tags PII / sensitive-data class (customer/employee PII, tokens, etc.) — the classification is the discovery index |
| Request identity verification | a data-subject request verifies requester identity before any data is disclosed or erased |
| Authorization boundary | tenant approval + platform escalation ([04](./04-canonical-iam-and-four-user-migration.md)); a tenant cannot export/erase another tenant's data |
| Cross-domain discovery | a request fans out across all M7 domains holding the subject's data (customers, employees, orders, invoices, payments-tokens, repairs, returns, shipping, support) |
| Access / export | structured, machine-readable export of the subject's data (portability where applicable) |
| Correction | correct inaccurate PII with audit |
| Deletion / anonymization | delete or anonymize **where legally permitted**; where deletion is barred (legal hold, financial-record retention), record the restriction reason |
| Retention & legal hold | per-domain retention policy; legal hold suspends deletion; restriction where applicable |
| Lawful basis & consent | **per-purpose lawful-basis record** (GDPR Art 6) and, where consent is the basis, a **consent capture/withdrawal ledger** (Art 7 — withdrawal as easy as granting) backing the rights to object/restrict; notice linkage |
| Request intake & SLA | DSAR **intake channel**, statutory **SLA/deadline timers**, requester communications, and legal-hold **exemption** handling (workflow lands in M6) |
| Breach notification | **statutory breach-notification workflow** (GDPR Art 33/34 — 72-hour supervisory-authority + data-subject notice; US state breach laws): assessment record, regulator + subject notice, wired into G-INCIDENT; the G-HIST M8 investigation triggers this branch if actual PII/CHD exposure is found |
| Processor contracts & transfers | **Art 28 DPAs** with tenant-controllers, a **sub-processor register** (payment provider, shipping, integrations), and **cross-border transfer mechanisms** (SCCs / adequacy / transfer-impact assessment) — legal-sign-off evidence at M9 |
| Provider propagation | erasure/correction propagates to third parties/providers holding the data (payment tokens, shipping, integrations) |
| Deadline / status | each request tracks statutory deadline + status; overdue surfaced |
| Failure / partial completion | partial completion is explicit and audited — never reported as fully complete when a domain/provider failed |
| Backup limitations | backups and their deletion limitations are documented (erasure from live systems + a documented backup-expiry policy) |
| Immutable audit | every DSAR action writes a durable append-only `audit_event` |
| Jurisdiction boundary | documented jurisdiction/legal-review boundaries; owner/legal sign-off at M9 |

**Milestone distribution:** **M1** these contracts + processor-obligation framing; **M5** requester/tenant/platform authorization + identity verification; **M6** audit, request-intake/SLA-timer/consent-ledger **workflow**, event, and retention/legal-hold foundations; **M7a–M7h** domain-specific export/correction/deletion behavior; **M8** operational privacy workflow, monitoring, and **breach-notification/incident integration**; **M9** UAT, evidence, DPA/sub-processor-register/cross-border-transfer evidence, and policy/legal-owner sign-off. **No new milestone.**
