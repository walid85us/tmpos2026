# 05 — Canonical Data Ownership & API / Database Contracts

**Scope:** per-domain canonical data ownership, the production API/error contract, and the database & multi-tenant contract. Design-only. Existing durable schema is identity/authz/audit, plus one minimal business table; business tables are introduced per-domain in M7 ([06](./06-module-migration-map-m7.md)), the first being the minimal customer identity (M7A-CUSTOMERS-P1, §2).

Those triggers are its only change to earlier objects. They make these writes wait for a command or login that holds the actor's account, in every mode including replica mode: an anchor change (its provider reference or key) or delete; an identity-link insert or re-point; and a grant insert or re-point, of any scope. In an ordinary session the anchor delete and the grant insert or re-point already waited through their foreign keys, so 015 adds their wait in replica mode only. Every other write to an administrator's standing was already serialized by 009's locks. DA-76 is the recorded exception ([08](./08-production-gate-and-risk-register.md)). 016 (M5-TENANT-SESSION-P1, [ADR-31](./10-architecture-decision-records.md)) adds one table in 011's schema, `tmpos_session.tenant_grant_version`, and one column, `public.store.access_version` (bigint, default 1, CHECK 1..2^53−1). Its other changes to earlier objects are five row triggers, each enabled `ALWAYS`. `trg_tenant_access_version` (BEFORE UPDATE on `tenant`) and `trg_store_access_version` (BEFORE INSERT OR UPDATE on `store`) fire `tmpos_session.m5_access_version_moved` (`SECURITY INVOKER`, granted to nobody), which moves the row's access version by exactly one whenever its status changes, and a store's also when it moves to another tenant (`tenant_id`), whoever writes it, refuses any other change to it, and sets a new store's to 1 whatever its INSERT names; 010's command still moves the tenant version exactly once. A key never changes: an UPDATE that would change a tenant's `tenant_id` or a store's `store_id` raises 23514, as a replica too, because a row inserted again under the old key would start its version again. `trg_user_membership_tenant_grant_version` (AFTER INSERT, UPDATE and DELETE on `user_membership`) fires `tmpos_session.m5_tenant_grant_moved` (`SECURITY DEFINER`, granted to nobody), which adds one to the grant version of each actor whose tenant- or store-scope grant a write creates, removes or changes, cascaded deletes included; a change to `updated_at` alone moves nothing. `trg_tenant_tenant_grant_version` and `trg_store_tenant_grant_version` (AFTER DELETE on `tenant` and `store`) fire the same function, which adds one, once per actor, for each actor holding a tenant- or store-scope grant of any status that names the deleted row, so a replica's delete, which cascades nothing, still moves them; in an ordinary delete the cascade has already removed those grants, and each grant's own delete moved its actor's version. It also adds two routines. `m5_admit_tenant_session_v2(p_auth_provider, p_auth_provider_uid)` (`STABLE SECURITY DEFINER`) answers one row, `outcome, actor_id, account_status, limitation, security_version, memberships, authority_version, grant_version`: 011's six columns, with each membership entry also carrying `storeAccessVersion` (decimal text, null exactly when the grant names no store), plus the actor's platform authority version (013) and tenant grant version (016) as decimal text (0 for an actor with no row; both null in the one refusal row). It raises when it cannot read a tenant's or a store's access version. `m5_hold_tenant_standing(p_auth_provider, p_auth_provider_uid)` (`VOLATILE SECURITY DEFINER`) answers `absent` or `held` and locks the actor's standing until the caller's transaction ends (ADR-31). `tmpos_app` holds EXECUTE on those two routines and nothing else from 016. 011's `m5_admit_tenant_session` stays and stays granted, but the adapter no longer calls it. 016's up and its rollback each refuse while any tenant session exists. 017 (M7A-CUSTOMERS-P1, [ADR-32](./10-architecture-decision-records.md)) creates its own schema `tmpos_customer` with one table, `customer`, its page index and one routine, and changes nothing an earlier migration created. `m7a_customer_page(p_internal_user_id, p_security_version, p_membership_id, p_role_id, p_tenant_id, p_after_customer_id, p_limit)` (`STABLE SECURITY DEFINER`, run with `row_security = off`, so a row security ever FORCED on the table makes it fail rather than answer empty pages) re-confirms, in the same snapshot as the page, that the named tenant authority still holds. The account's status must be on the allow-list `active`, `trialing`, `overdue` or `read_only`, and 007's security version must be equal. The actor must hold exactly one active tenant-scope grant, counting only grants on a tenant that is not `suspended` or `pending_activation`, as 007's resolver counts them, and that grant must be the named membership, role and tenant. The tenant's status must be on the same allow-list. It then answers up to `p_limit` (at most 101) `(tenant_id, customer_id, name)` rows of that tenant after the continuation, ordered by `(name, customer_id)` under "C", or a single `invalid`, `denied` or `cursor_unknown` row. It decides no permission. 017 refuses to apply unless the applier holds the owner's privileges on `tenant`, `app_user`, `user_membership` and `identity_link`, none under forced row security. Its rollback refuses unless it runs under READ COMMITTED, and it runs its no-rows guard with `row_security = off`, so a forced row security refuses it (42501) rather than hiding rows it would drop. It takes ACCESS EXCLUSIVE on `public.tenant` and then on the customer table, so it belongs in a maintenance window; a customer INSERT locks in the opposite order and can deadlock with it, and PostgreSQL then aborts one side. It refuses while any customer row exists. While one exists, the chain cannot roll back past 017 (005's and 002's rollbacks would fail). 018 (M7A-CUSTOMERS-P2, [ADR-33](./10-architecture-decision-records.md)) creates its own schema `tmpos_mint` with two tables, the issuer key `issuer_key` and the mint ledger `tenant_session`, the ledger's expiry index, two helpers granted to nobody (`hmac_sha256`, `mint_message`) and three routines. Its only change to earlier objects is two revocations: `tmpos_app` no longer executes 011's `m5_session_create` or 017's `m7a_customer_page`. `m7a_session_create` (`VOLATILE SECURITY DEFINER`) is now the runtime's only session create. It takes 011's eleven row values and a proof, and checks every argument against 011's CHECKs first (`invalid`, nothing written). An administrative record, with no proof, goes to 011's create unchanged. A tenant record needs an HMAC-SHA256 proof under the installed issuer key over all eleven values (`refused` otherwise), a lifetime of at most eight hours and a creation at most 60 s ahead of the database clock; the routine then writes a ledger row (the SHA-256 of 016's admission answer for the principal and of the key) and the session, and answers `conflict` for a taken key. `m7a_customer_page_v2(p_session_key, p_after_customer_id, p_limit)` (`STABLE SECURITY DEFINER`, run with `row_security = off`) answers 017's page, run as its owner, for the authority it derives from the session: a ledger-minted, live (database clock) tenant session, minted under the key installed now, whose principal's standing is unchanged and holds exactly one tenant grant. Otherwise it answers `denied`, or `invalid` for a malformed key. `m7a_issuer_key_check(p_fingerprint)` (`STABLE SECURITY DEFINER`) answers only `match`, `mismatch`, `absent` or `invalid`. 018's rollback refuses unless it runs under READ COMMITTED, and while the key or the ledger holds a row; it restores the two revoked grants. 019 (M7A-CUSTOMERS-P3, [ADR-34](./10-architecture-decision-records.md)) creates no table either. It adds its own schema, `tmpos_customer_write`, with one `VOLATILE SECURITY DEFINER` routine, `m7a_customer_create(p_session_key, p_customer_id, p_name)`, the only way the runtime creates a customer. Its one authority argument is the presenting session's store key, from which it derives the tenant, actor and grant as 018's read does, admitting only an account and tenant status of `active` or `trialing` and the roles `store_owner`, `manager` and `sales_staff`. `tmpos_app` gets USAGE and EXECUTE on it and still holds no privilege on the customer table. It changes nothing earlier migrations created. The tables:

- **`audit_event` is append-only**: `reject_audit_event_mutation()` + `trg_audit_event_reject_mutation` (BEFORE UPDATE OR DELETE) raise `restrict_violation` for **all roles including the table owner**. Metadata is guarded (`audit_metadata_is_flat`, forbidden-key list: access/refresh tokens, raw JWT/JWKS, service-role key, DB URL, connection string, password, PAN, card number, provider secret). **Forward-hardening (M6/M7b):** when payments land, extend this guard + log/error redaction to **CVV/CVC, track1/2, and PIN block** so the enforced key-list matches the documented no-CHD boundary (§5), and make the [07](./07-quality-and-test-strategy.md) "no PAN/CVV/track/PIN" assertion check that guard. `evidence_level` ∈ `dev_sidecar_log_advisory | durable_compliance_event`. The writer's metadata allow-list is action-scoped (M6-ADMIN-AUDIT-P1). `sessionRef`, `replacedSessionRef` and `authenticatedAt` are kept only for the six session actions, `platform.admin.session.login`, `.reauthenticate` and `.logout` and, since M5-TENANT-SESSION-P1, `tenant.session.login`, `.reauthenticate` and `.logout`, and those six keep nothing else (a logout row may carry `sessionRef` alone). For every other action they are stripped by `sanitizeAuditMetadata` and refused by `validateAuditEventInput`, as any unknown key is. The writer also owns each session event's entire fixed row (`ADMIN_SESSION_AUDIT_EVENTS` at scope `platform`, `TENANT_SESSION_AUDIT_EVENTS` at scope `none`, with no tenant or store in either), and `validateAuditEventInput` refuses any row under those six ids that differs from it in any column.
- **RLS enabled on all 18 tables.** At 001–004 there were zero policies and 7/8 `REVOKE ALL … FROM public/anon/authenticated` (001's was added by 005). Migration 005 then adds the runtime roles and **five** tenant/store-scoped policies (`tenant`, `store`, `user_membership`, `tenant_feature_entitlement` for `tmpos_app`; an append-only one for `tmpos_audit_writer`), and 006's two `tmpos_internal` tables, 011's `tmpos_session.session`, 013's `tmpos_admission.platform_authority_version`, 014's two `tmpos_rate_limit` tables, 016's `tmpos_session.tenant_grant_version`, 017's `tmpos_customer.customer` and 018's two `tmpos_mint` tables are RLS-enabled with no policy — defence in depth, since the runtime role holds no privilege on them at all. Note two things the phrase "RLS enabled" does not mean here: `FORCE ROW LEVEL SECURITY` is set on NO table (deliberately — a `SECURITY DEFINER` routine must be able to read its owner's rows), and 13 of the 18 carry no policy at all, so for those RLS is a deny-all backstop rather than a filter. Migration 012's `tmpos_directory.m5_tenant_directory_page` is such a routine. It reads `public.tenant` as its owner, because 005's policy opens no row to a platform context and 012 leaves that policy exactly as it is. It returns a bounded page of (tenant id, display name, status, row version) only while the caller's named platform grant still holds, and `tmpos_app` holds EXECUTE on it and nothing else in that schema besides USAGE. 012 adds no table. Migration 013's `tmpos_admission.m5_admit_platform_session` is another such routine: it calls 007's resolution as its owner and reads the version table, and `tmpos_app` holds EXECUTE on it and USAGE on the schema, and nothing on the table or the trigger function. 013 adds the twelfth table. Migration 014's `m6_rate_limit_consume`, `m6_rate_limit_probe` and `m6_rate_limit_reclaim` are three more: `tmpos_app` holds EXECUTE on those three and USAGE on `tmpos_rate_limit`, and nothing on either table or the key check; no other runtime-facing role (`tmpos_audit_writer`, `anon`, `authenticated`) may execute any of them or be a member of `tmpos_app` — section 6 refuses the apply otherwise, a `NOINHERIT` membership included, which `has_function_privilege` does not report but which can still `SET ROLE tmpos_app`. 014 adds the thirteenth and fourteenth tables. 015 adds no table and grants nothing: its trigger function carries no grant beyond its owner's, and section 4 refuses the apply if `tmpos_app`, `tmpos_audit_writer`, `anon` or `authenticated` can execute it or is a member of its owner. 016 adds the fifteenth table and two grants: `tmpos_app` holds EXECUTE on `m5_admit_tenant_session_v2` and `m5_hold_tenant_standing`, two definers that read or lock as their owner, and nothing on the new table or either trigger function. Its postcondition refuses otherwise, and refuses any runtime role that may UPDATE the status or access version of a tenant or store or DELETE either, UPDATE a tenant's `tenant_id` or a store's `store_id` or `tenant_id`, INSERT a tenant, or TRUNCATE or place a TRIGGER on `tenant`, `store` or `user_membership`. 005's table-wide INSERT on `public.store` still reaches the new column, and 016's trigger sets it to 1 whatever the INSERT names ([08](./08-production-gate-and-risk-register.md) DA-80). The owner alone may write the grant version table or disable 016's triggers ([08](./08-production-gate-and-risk-register.md) DA-41). 017 adds the sixteenth table and two grants: `tmpos_app` holds USAGE on `tmpos_customer` and EXECUTE on `m7a_customer_page`, a definer that reads the customer, grant, account and tenant rows as its owner, and nothing on the table. It does not rely on 005's session variables, which the runtime sets itself. Its postcondition requires the table's row security enabled and not forced, and `tmpos_app`'s EXECUTE and USAGE actually held. It refuses any wider grant, any column grant, any policy on the table, any runtime role that is a member of an owner of its schema, table or routine, and any runtime role holding an effective privilege on the table by any path, `pg_read_all_data` included (011's check). The routine returns each row's tenant id, and the adapter refuses any row that does not name the admitted tenant. The re-check is not a boundary against the runtime credential ([08](./08-production-gate-and-risk-register.md) DA-83). 018 adds the seventeenth and eighteenth tables, revokes that EXECUTE and 011's `m5_session_create` from `tmpos_app`, and grants it USAGE on `tmpos_mint` and EXECUTE on the schema's three routines only. Its postcondition refuses any wider grant, any column grant, any policy on either table, any runtime role that is a member of an owner of its schema, a table or a routine (a `NOINHERIT` membership included), and any runtime role holding an effective privilege on either table by any path. The customer read is now bound in the database to a minted session, which contains DA-83 against the runtime credential alone without closing it ([08](./08-production-gate-and-risk-register.md) DA-83, DA-93–DA-104). Effect: PostgREST/anon/authenticated get deny-all; the owner-role connection still bypasses RLS, and GAP-17 (an app role that does not bypass RLS) stays open until a runtime LOGIN role exists (G-DBROLE).

**Per-domain contract (applies to each):** aggregate root + FK boundaries within the tenant/store subtree; explicit lifecycle/status model; separate read API and write API; a transaction boundary per mutation; optimistic-concurrency version field; idempotency requirement for externally-triggered/retryable writes; audit requirement (append-only `audit_event`); event/outbox where cross-domain or provider effects occur; retention/deletion rule (soft-delete + purge policy); sensitive-data classification (PII in customers/employees; payment data in payments; provider credentials in payments/integrations/shipping — encrypted, never in audit metadata); external-provider relationship (shipping/integrations only, via egress boundary).

**All current UI-only models lack a durable backend** — every domain above is a migration target; none has a table today except the minimal customer identity below, which the shop app does not use yet.

**Customers — the first slice (M7A-CUSTOMERS-P1, code only, not deployed; [ADR-32](./10-architecture-decision-records.md)).** The durable customer identity is `tmpos_customer.customer` (migration 017, §1): a stable id, the owning tenant and the display name, and nothing else. It is tenant-owned, as the table above says. None of the client model's contact, loyalty, money or lifecycle fields exists server-side, and `loyalty_account`, the `active/archived` lifecycle, PII classification, retention, DSAR behaviour, any write beyond the create below (M7A-CUSTOMERS-P3) and the cutover from `StoreLocalState.customers` are not built: they arrive with the product decisions that govern them ([08](./08-production-gate-and-risk-register.md) G-PERSIST, G-PRIVACY). No row is written outside disposable test databases. The read API is one route:
- **`GET /api/v1/customers`**: a tenant-session route under the canonical tenant route permission `view_customers` (the Customers domain at View or above, decided at tenant scope only), with a required trusted context, no body, no `Idempotency-Key` and no recent sign-in. It is a read, so a read-only actor may use it.
- **Scope.** The tenant is taken only from the actor's one active tenant grant, which the tenant authorizer selects; never from the path, the query, a header, the cursor or a body.
- **Bound to the presenting session (M7A-CUSTOMERS-P2, [ADR-33](./10-architecture-decision-records.md)).** The read is bound in the database to the presenting minted tenant session. The route declares `sessionBinding: 'required'`, so the chain hands its handler that session's store key, and the adapter reads through migration 018's `m7a_customer_page_v2` with the key as its only authority argument. The database requires the session to be minted (a ledger row), of the tenant audience, live on the database clock, minted under the issuer key installed now and of an unchanged standing, derives the actor and its one tenant grant itself, and runs 017's page for them. The runtime login can no longer call 017's page. The query, cursor, response, order and refusals below are unchanged: a session the database refuses is the same 403 `forbidden`, and the adapter still refuses (503) any row not naming the authorizer's tenant.
- **Query.** `limit` 1–100 (default 50) and `cursor`, each at most once. The cursor is opaque: 23 canonical base64url characters encoding a tag byte (0x02) and the last customer's id. It carries no authority: its position is looked up only among the admitted tenant's customers, so a cursor naming another tenant's customer, a deleted one or an unknown id is the same 400. Any other key, a repeat, an empty pair, an encoding, a non-canonical spelling or a query over 128 characters is 400 `invalid_request`.
- **Response.** `200 { customers: [{ id, name }], nextCursor }` (`nextCursor` null on the last page), ordered by name under the "C" collation, then by id ([08](./08-production-gate-and-risk-register.md) DA-86). No email, phone, group, tier, total spent or other money value.
- **Refusals** keep the runtime's generic `{ error, requestId }` bodies: 401 for session refusals, 403 `forbidden` for any denial (a grant lost between the authorizer and the read included), and 503 `service_unavailable` for an outage, a timeout or an answer out of shape, never cached or synthetic data. Out of shape includes:
  - a row naming a tenant other than the admitted one (the adapter's check, independent of the routine's filter);
  - rows not in strictly increasing (name bytes, id) order (checked by the adapter over every row it reads, the look-ahead included, and by the runtime over the page);
  - a name that is not 1–200 characters of well-formed UTF-16.
- **Audit.** None, by owner decision; whether personal-data list reads are audited is open ([08](./08-production-gate-and-risk-register.md) DA-88).
- **Availability.** Served in code by the compiled tenant entry (M7A-CUSTOMERS-P2, commit 2; [ADR-33](./10-architecture-decision-records.md) decision 8), on the tenant host alone, and not deployed; the administrative entry still composes the administrative boundary only. The tenant entry lists the route in the tenant authorizer's read classification, builds the customer port over the shared transaction kernel, and composes the session store with the tenant issuer key, which the database owner installs ([08](./08-production-gate-and-risk-register.md) DA-87, DA-101).

**Customers — the create (M7A-CUSTOMERS-P3, code only, not deployed; [ADR-34](./10-architecture-decision-records.md)).** The write API is one route:
- **`POST /api/v1/customers`** is a tenant-session route under the canonical tenant route permission `create_customers`: the Customers domain at Create or above, decided at tenant scope only. By default `store_owner`, `manager` and `sales_staff` hold it and `technician` does not, and a `read_only` or `overdue` account or tenant denies it. The route requires a trusted context and an `Idempotency-Key`, and no recent sign-in. It is not a read, so a read-only actor may not use it.
- **Request.** A JSON body of at most 4,096 bytes holding exactly `{ name }`. Any other field, or none, is 400 `invalid_request`. The tenant is taken only from the actor's one active tenant grant: nothing in the path, a header or the body names it.
- **Name.** Trimmed at both edges. It must then be 1–200 characters, with no C0 control, DEL, C1 control, U+2028, U+2029, lone surrogate or Bidi_Control character. It must also hold at least one visible character, so a name made only of whitespace, format, default-ignorable or combining characters, or U+2800, is refused. Everything else is kept exactly: no case folding or normalization. Names need not be unique, so two keys with one name create two customers. Stored names are never rewritten.
- **Response.** `201 { customer: { id, name } }`: the server-generated id and the name as stored. There is no `Location` header, because no customer-detail route exists. An identical retry under the same key replays it (`Idempotent-Replayed: true`) within the record's 24 h retention, once the session and authorization checks pass again.
- **Refusals** keep the generic bodies:
  - 401 for session refusals, and 403 `forbidden` for any denial;
  - 400 for a missing or malformed `Idempotency-Key`;
  - 409 `request_in_progress`;
  - 422 `idempotency_key_reused` for another request under the key; for the same signed-in identity this includes the same body under another tenant or actor;
  - 503 `service_unavailable` for an outage and for any refusal inside the committing transaction (lost authority, a duplicate id), which commits nothing;
  - 503 also for a commit whose acknowledgement was lost. That outcome is unknown, not a rollback: a retry under the key replays the 201 if the commit landed.
- **Transaction.** One PostgreSQL transaction does all of the following, or commits none of it:
  - holds the presenting session and the actor's standing;
  - decides the permission again;
  - creates the row through migration 019's `tmpos_customer_write.m7a_customer_create`, whose only authority argument is the session key, so the tenant is derived in the database;
  - appends the audit record;
  - seals the idempotency completion.
- **Audit.** One `audit_event` row per create: action `tenant.customer.create`, scope `tenant` with the tenant, and the actor. It records neither the name nor the customer id ([08](./08-production-gate-and-risk-register.md) DA-111). No outbox event is written.
- **Availability.** Served in code by the compiled tenant entry beside the read, on the tenant host alone. It is not deployed, and the shop app does not call it.

## 3. API & error contract (production standard)

| Aspect | Standard |
|---|---|
| Versioned paths | `/api/v1/...` (tenant), `/admin/v1/...` (Backend CP) |
| Request/response schemas | typed, validated at the boundary; reject unknown fields on writes |
| Pagination/filtering/sorting | cursor pagination; explicit allowlisted filter/sort fields. The first tenant read, `GET /api/v1/customers` (M7A-CUSTOMERS-P1, §2), pages by an opaque keyset cursor that carries no authority, allows no filter or sort parameter, and refuses any other query key with 400 `invalid_request` |
| Concurrency | `version`/`updated_at` optimistic concurrency; conflicting write → 409 `write_conflict`, sealed as the idempotency record's completion in the transaction that decided it (M5-GIAM-D1-P2-R1), so an identical retry replays it and the key cannot mutate while that record is retained |
| Idempotency | `Idempotency-Key` header for retryable/mutating requests; durable key store in PostgreSQL, completed in the mutation's own transaction ([ADR-17](./10-architecture-decision-records.md)). Since M7A-CUSTOMERS-P3 it is required by tenant session commands as well as platform commands; the first is `POST /api/v1/customers` (§2). The request is bound to the authorizer's trusted tenant and actor, never the request's, so a key never replays across tenants or actors ([ADR-34](./10-architecture-decision-records.md)) |
| Correlation | server-generated `request_id`/`trace_id`; **no sensitive identifier** in correlation values. *Administrative session audit (M6-ADMIN-AUDIT-P1, [03 §2b](./03-backend-control-plane-login-session-blueprint.md)):* a row's `request_id` is the operation id, a random UUID the server generates for that one login, reauthentication or logout. The request's log line carries the same value as `operationId`, except for a logout whose client disconnected first: that line (reason `aborted`) is written at the close, before the id exists, and one info-level `session_logout_after_close` line carries both `requestId` and `operationId`. `trace_id` is null. A client's `X-Request-Id` may be adopted as the request correlator in logs and refusal bodies, but it is never persisted in an audit row. A session is named only by `sessionRef` = base64url(SHA-256(`tmpos-audit-session-ref:v1\n` + store key)). The store key is not used because the definer session routines accept it and the runtime role may execute them, so the key would let a reader of the audit trail read, extend or end a live session |
| Error envelope | bounded `{ error: { code, message, correlationId } }`; **no stack traces, no raw DB/provider errors**. The shipped runtime's own refusals carry `{ error, requestId }`, and a RECORDED rejection (M5-GIAM-D1-P2-R1) carries the refusal word alone — a body replayed byte for byte may hold no correlation value, so the fresh one travels on `X-Request-Id` |
| Auth errors | 401 (unauthenticated), sanitized |
| Authz errors | 403 (authenticated but not permitted), sanitized reason code |
| Validation | 422 with field-level codes (no echoed secrets). *The shipped runtime answers a body its contract refuses with 400 `invalid_request` and no field-level code, and the tenant customer create does the same (M7A-CUSTOMERS-P3, §2). There, 422 means only a reused `Idempotency-Key`* |
| Conflicts | 409 (version conflict, or an idempotent request still in progress); 422 (an `Idempotency-Key` reused for a different request — [08](./08-production-gate-and-risk-register.md) G-IDEMPOT) |
| Rate limits | 429 + `Retry-After` (whole seconds: the time left in the window on the shared store's database clock, migration 014, [ADR-26](./10-architecture-decision-records.md)); a limiter that cannot answer is a bounded 503, never an allowance |
| Unavailable/degraded | 503 with retry guidance; provider failure surfaces as a bounded upstream-unavailable code, never the raw provider error |

## 5. Payment contract (G-PCI — DECIDED: integrated capability in scope)

TM POS2026 supports **cash**, **external-terminal/manual-reference**, **integrated card-present via a PCI-certified semi-integrated terminal/provider**, and **hosted/tokenized CNP** flows. Direction is **DECIDED**; the specific provider is selected in **M7b** by documented criteria (and must not become a hidden future milestone).

**Hard data boundary (never in TM POS2026 — not received, stored, persisted, logged, or exposed):** raw PAN, CVV/CVC, magnetic-stripe/track data, PIN/PIN block, unencrypted cardholder data, processor credentials in browser storage. Card data is collected only by **provider-hosted/provider-certified components**; TM POS2026 holds only **opaque payment-method tokens**.

| Aspect | Contract |
|---|---|
| Aggregate root | `payment` (per order/invoice), with `payment_event` (append-only state log), `payment_method_token` (opaque), `terminal_device`, `dispute` |
| Lifecycle | initiated → authorized → captured → settled; plus void, refund, dispute, failed — each an appended `payment_event` |
| Idempotency | `Idempotency-Key` on every payment mutation + **duplicate-charge prevention** (a retried authorize/capture never double-charges) |
| Webhooks | provider webhooks **signature-verified** at the egress boundary before processing; replay-safe |
| Reconciliation | periodic reconciliation of provider settlement vs local `payment` state; discrepancies flagged |
| Refunds / voids / disputes | modeled explicitly; refunds idempotent; disputes tracked to resolution |
| Credentials | processor credentials **encrypted at rest + rotated** (G-SECRETS); never in browser storage |
| Provider outage | defined degraded behavior (queue/deny with safe classification; never a silent success) |
| Terminal/device | `terminal_device` assignment scoped to **tenant/store**; a device cannot act outside its store |
| PCI validation | applicable PCI validation category (SAQ A / P2PE / other) **confirmed with the selected provider/acquirer or QSA before production** — **not claimed** until the final integration architecture establishes eligibility. As a multi-tenant orchestrator holding provider credentials, terminal assignments, and tokens, the platform's own **PCI service-provider scope (TPSP / Payment-Facilitator, responsibility matrix, per-tenant AoC)** is validated alongside the merchant category |
| Audit | every payment state transition writes a durable append-only `audit_event` |
| CHD containment (all surfaces) | **no raw PAN/CVV/track/PIN or processor secret in ANY operational, observability (logs/metrics/traces), evidence, export/BI, receipt, or support surface** — reconciliation, refunds, disputes, webhook payloads, receipts, and support tools handle only opaque tokens + masked/last-4; redaction enforced and tested (G-PCI evidence, [07](./07-quality-and-test-strategy.md)) |

### 5.1 Store-owned payment gateway connection model

**Ownership (OWNER CORRECTION):** payment-gateway connections are configured at the **STORE** level — by the **Store Owner**, or another active store user holding an **explicit canonical permission** to manage gateway connections ([04 §2.1](./04-canonical-iam-and-four-user-migration.md)). They are **not** supplied, configured, retrieved, or normally viewed by the System Owner. The store-facing location is **Store Settings → Payments / Payment Gateway** (not the System Owner Backend Control Plane). Cash and external-terminal methods remain available **independently** of any integrated gateway.

**Platform vs store split:** the **System Owner Backend CP governs the connector catalog and security policy** (which providers exist, availability by environment/region, minimum versions/security requirements, bounded connector health, global connector disablement during an incident, feature/plan eligibility, aggregate failure review, audited break-glass) — see the boundary in [03 §9](./03-backend-control-plane-login-session-blueprint.md). The **store owns its own merchant connection** (selection, authorization, activation, replacement, disconnection).

**Connection flow (store-initiated):**
```
platform connector catalog → store selects provider → canonical store-scoped permission check
  → recent-authentication / step-up → server-generated OAuth or provider-hosted onboarding
  → provider authorization → encrypted store-scoped connection reference
  → server-side connection validation → webhook registration + verification
  → terminal pairing (if applicable) → store makes connection active → durable audit
```
**OAuth / provider-hosted onboarding is preferred.** **No raw secret/API-key entry in the browser** when the provider offers a secure OAuth/onboarding flow.

**Credential handling (when a provider unavoidably requires a secret):** collect through a **dedicated protected server exchange**; never hold longer than necessary in React state; **never** in `localStorage`/`sessionStorage`; **never returned after acceptance**; **envelope-encrypted through the approved credential service** (§4 + M6); store **only a credential reference** in ordinary application tables; **redacted** from logs/traces/errors/audit/support/exports/backups; **rotation + revocation** supported. **OAuth access/refresh tokens are long-lived secrets and use this same envelope-encrypted / reference-only / rotation-revocation model.**

**OAuth callback binding (model invariant, not just a test):** the OAuth flow MUST use an unguessable **`state`** parameter (CSRF), **PKCE**, an **exact redirect-URI allowlist**, and a callback that **binds the returned provider account to the initiating store's authenticated session** — so authorization-code injection / connection-CSRF cannot link a victim store to an attacker's merchant account, and a returned account cannot be bound to any store other than the one that initiated the flow.

**Connector-catalog integrity (model invariant):** each connector's definition (OAuth URLs, API endpoints, **webhook hosts**) is **code-shipped, reviewed, and integrity-protected, subject to the provider egress allowlist ([ADR-07](./10-architecture-decision-records.md)) — NOT free-form admin-entered.** Any catalog mutation is a **step-up + reason + durable-audit** controlled action. (This closes the indirect path by which a compromised System Owner could repoint a connector at an attacker host and harvest every connecting store's credentials.)

### 5.2 Multi-store isolation & durable entities

Every connection is owned by exactly **(`tenant_id`, `store_id`, `provider_key`, `environment`)**. Conceptual durable entities (schemas NOT implemented in M1): `payment_provider_connection`, `payment_terminal`, `payment_webhook_registration`, `payment_provider_health`, `payment_provider_event`.

**Isolation invariants:** one store cannot query/use another store's connection; webhook events correlate to the correct provider account + tenant + store + environment; **sandbox credentials cannot process production payments**; production and test credentials are isolated; a terminal is assigned to one authorized store/environment (pairing relies on provider-attested device identity / P2PE-certified hardware; connection/credential-reference tables carry tenant/store RLS like other business tables — [03 §7](./03-backend-control-plane-login-session-blueprint.md), G-DBROLE); **credential references cannot be reassigned by client input**; **provider account identifiers are never accepted as authority**; the server derives tenant/store scope from the canonical session + authorization context; **a `provider_account_id` is uniquely and provider-verifiably bound to exactly one connection** (established via the OAuth callback binding above) so webhook correlation cannot be hijacked or made ambiguous by a second store claiming the same account id.

### 5.3 Active-provider & switching rules

**One active integrated provider per store/payment channel** for the initial design (multiple only if the architecture explicitly supports safe channel routing); cash/external-terminal remain independent. **Provider replacement must check** pending authorizations, unsettled transactions, refunds/disputes, active terminals, webhook backlog, and reconciliation status — **unsafe switching is blocked**. Old credentials are revoked or retained only for **bounded reconciliation/refund obligations**. Activation/disconnection is **idempotent and audited**; **no duplicate charge can result from failover or retries**. The replacement/disconnect safety checks read a **server-owned source of truth** for pending authorizations, unsettled funds, disputes, active terminals, webhook backlog, and reconciliation locks (never client-asserted). A **verified** webhook (dispute/chargeback/late refund) arriving **after** the bounded retention window is not silently dropped — it is captured and routed to the dispute/compliance path so no financial/compliance event is lost.

### 5.4 Initial connector catalog (M7b — Stripe / Square / Adyen)

The initial M7b connector catalog targets **three provider families** (initial supported options — not three simultaneously-required live integrations), subject to current official API/country/hardware verification during M7b:

| Provider | Connection model | Card-present | CNP |
|---|---|---|---|
| **Stripe** | Stripe Connect / platform connection | Stripe Terminal | hosted/tokenized where applicable |
| **Square** | OAuth merchant connection (Payments API) | Terminal/device APIs where supported | hosted where applicable |
| **Adyen** | platform/account-holder integration where applicable | in-person/terminal | enterprise/multi-region |

**M7b verification (each candidate):** supported merchant countries; supported transaction currencies; **Morocco/US and intended launch-market availability**; card-present hardware; OAuth/platform-account model; API maturity/versioning; webhook support; refunds/voids/disputes/reconciliation; sandbox/test capability; pricing/commercial onboarding; PCI scope; marketplace/platform restrictions; account portability; provider-outage behavior; support model. If a provider cannot support the launch market or the store-owned connection model, **M7b may replace it only via a documented ADR + owner approval — with no new milestone**.

## 6. Privacy & data-rights (DSAR) contract (G-PRIVACY — DECIDED: implement, not exclude)

A production privacy foundation is **in scope**, distributed across milestones (no new milestone). **No universal-compliance claim is made** — final policy and jurisdictional obligations require owner/legal review.

**Roles:** the **tenant is the data controller** for its store/customer/employee data; the **platform is the processor** (plus controller for platform-operator data). DSAR requests are authorized through tenant approval with platform escalation.

| Capability | Contract |
|---|---|
| Data inventory & classification | every domain table tags PII / sensitive-data class (customer/employee PII, tokens, etc.) — the classification is the discovery index |
| Request identity verification | a data-subject request verifies requester identity before any data is disclosed or erased |
| Authorization boundary | tenant approval + platform escalation ([04](./04-canonical-iam-and-four-user-migration.md)); a tenant cannot export/erase another tenant's data |
| Cross-domain discovery | a request fans out across all M7 domains holding the subject's data (customers, employees, orders, invoices, payments-tokens, repairs, returns, shipping, support) |
| Access / export | structured, machine-readable export of the subject's data (portability where applicable) |
| Correction | correct inaccurate PII with audit |
| Deletion / anonymization | delete or anonymize **where legally permitted**; where deletion is barred (legal hold, financial-record retention), record the restriction reason |
| Retention & legal hold | per-domain retention policy; legal hold suspends deletion; restriction where applicable |
| Lawful basis & consent | **per-purpose lawful-basis record** (GDPR Art 6) and, where consent is the basis, a **consent capture/withdrawal ledger** (Art 7 — withdrawal as easy as granting) backing the rights to object/restrict; notice linkage |
| Request intake & SLA | DSAR **intake channel**, statutory **SLA/deadline timers**, requester communications, and legal-hold **exemption** handling (workflow lands in M6) |
| Breach notification | **statutory breach-notification workflow** (GDPR Art 33/34 — 72-hour supervisory-authority + data-subject notice; US state breach laws): assessment record, regulator + subject notice, wired into G-INCIDENT; the G-HIST M8 investigation triggers this branch if actual PII/CHD exposure is found |
| Processor contracts & transfers | **Art 28 DPAs** with tenant-controllers, a **sub-processor register** (payment provider, shipping, integrations), and **cross-border transfer mechanisms** (SCCs / adequacy / transfer-impact assessment) — legal-sign-off evidence at M9 |
| Provider propagation | erasure/correction propagates to third parties/providers holding the data (payment tokens, shipping, integrations) |
| Deadline / status | each request tracks statutory deadline + status; overdue surfaced |
| Failure / partial completion | partial completion is explicit and audited — never reported as fully complete when a domain/provider failed |
| Backup limitations | backups and their deletion limitations are documented (erasure from live systems + a documented backup-expiry policy) |
| Immutable audit | every DSAR action writes a durable append-only `audit_event` |
| Jurisdiction boundary | documented jurisdiction/legal-review boundaries; owner/legal sign-off at M9 |

**Milestone distribution:** **M1** these contracts + processor-obligation framing; **M5** requester/tenant/platform authorization + identity verification; **M6** audit, request-intake/SLA-timer/consent-ledger **workflow**, event, and retention/legal-hold foundations; **M7a–M7h** domain-specific export/correction/deletion behavior; **M8** operational privacy workflow, monitoring, and **breach-notification/incident integration**; **M9** UAT, evidence, DPA/sub-processor-register/cross-border-transfer evidence, and policy/legal-owner sign-off. **No new milestone.**
