# 03 — Backend Control Plane Login & Session Blueprint

**Scope:** the **separate** administrative login and session boundary for the Backend Control Plane (Backend CP), and the Backend CP's platform-governance responsibilities and controlled-action contract. Conceptual/design-only — endpoints are described, **not implemented** (implementation is M4). Delivered by **M4**; canonical authorization it relies on is **M5**.

## 1. Why separate

Today there is **no server session at all**: the live app uses the client Firebase session + a client-held role, and the DEV Backend CP shell's entry gate is a single local boolean with no auth ([01](./01-current-state-inventory-and-gap-matrix.md) §D, GAP-02). The Backend CP governs the entire platform (tenants, plans, entitlements, IAM, support, audit). It **must not** reuse the tenant/store browser session or share its trust boundary. A compromised or ordinary tenant session must never reach platform administration.

### 1a. Two server sessions, both required (not only the admin one)

The Backend CP is the *higher-privilege* boundary, but the **tenant/store application also needs a server session and per-request server-side identity verification** — otherwise canonical IAM ([04](./04-canonical-iam-and-four-user-migration.md)) has no verified tenant request identity to authorize, and the browser role/`sessionStorage` remains authoritative. **M4 delivers both session boundaries as separate, independent trust boundaries:** a tenant session cookie (for `/api/v1/*`) and a distinct admin session cookie (for `/admin/v1/*`). They share **one canonical IAM catalog and one status/suspension model** ([04](./04-canonical-iam-and-four-user-migration.md)) to avoid split-brain authorization, but never share a cookie, origin, or trust boundary. Each session is established by its own login exchange with the same server-side verification below.

## 2. Login & session requirements

| # | Requirement | Detail |
|---|---|---|
| 1 | **Dedicated entry** | A dedicated Backend CP entry route on a **dedicated admin hostname/subdomain (mandatory, a distinct origin)** — a separate cookie on a shared registrable domain is a weaker boundary and does not fully realize [ADR-02](./10-architecture-decision-records.md). |
| 2 | **No session reuse** | No automatic reuse of the tenant/store browser session. Admin auth is established independently. |
| 3 | **Firebase verification at the server** | The ID token is verified **only** at the server login exchange via `verifyIdToken(token, checkRevoked=true)` (adapter already exists, fails closed — [01](./01-current-state-inventory-and-gap-matrix.md) §E). The browser never uses the raw token as the app session. |
| 4 | **Server-issued admin session cookie** | `HttpOnly`, `Secure`, `SameSite=Strict` (unless an evidenced flow requires `Lax`), scoped to the exact admin origin, short-lived. |
| 5 | **CSRF protection** | Double-submit or synchronized-token CSRF for all state-changing admin requests, plus `Origin`/`Sec-Fetch-Site` checks (the BCP action guard already models exact-Origin + `Sec-Fetch-Site` + custom-intent-header defense). |
| 6 | **Trusted Origin** | Exact-match trusted Origin allowlist for the admin surface (no suffix/substring matching). |
| 7 | **Session rotation** | Rotate the session identifier on login and on privilege change; bounded absolute lifetime + inactivity timeout. |
| 8 | **Logout & revocation** | Explicit logout invalidates server-side; server-side revocation list; `checkRevoked=true` honored so disabled/revoked Firebase users cannot re-establish. |
| 9 | **MFA** | MFA required for Backend CP login. **M4 (M4-ADMIN-UI-P2, committed in `dd89ff9`):** an authenticator app (TOTP) only — the SMS/phone factor needs reCAPTCHA hosts that the admin CSP refuses (§2a). |
| 10 | **Step-up / recent-login** | Sensitive actions (status change, entitlement grant, role change, provisioning, break-glass) require recent-login/step-up re-authentication. **Progress (M5-ADMIN-STEPUP-P1; not deployed):** the tenant status command requires it, and the administrator can complete it in the console without leaving the page — a same-principal reauthentication mode of the existing login route (§2a, §3; [ADR-28](./10-architecture-decision-records.md)). |
| 11 | **Sanitized errors** | Login failures return a generic sanitized error; no user-enumeration, no provider detail. |
| 12 | **No token in browser storage** | No token in `localStorage`/`sessionStorage`; no UID/email/claim/token in URLs or browser logs (the DEV client comment already asserts the token is not placed in React state/logs — the M4 target must preserve this). |
| 13 | **Canonical authorization after auth** | Authentication ≠ authorization. After login, the effective admin authorization is resolved from **canonical Postgres** ([04](./04-canonical-iam-and-four-user-migration.md)), deny-by-default. |
| 14 | **Fail-closed status** | Suspended/inactive/parity/cap enforced server-side; missing mapping ⇒ deny (no synthetic/client-asserted administrator). |
| 15 | **Break-glass governance** | A governed, audited, time-boxed break-glass path with reason capture; never a silent bypass. |
| 16 | **Production hard-block for DEV paths** | The DEV-only action/diagnostic paths and DEV feature flags must be hard-blocked in production (`NODE_ENV==='production'` denies), not merely default-OFF. |
| 17 | **Login anti-automation** | Rate-limiting + brute-force lockout on the login exchange (MFA mitigates but is not anti-automation). |
| 18 | **Durable session store** | Server sessions backed by a durable store (e.g. Redis/DB) with a revocation list; sessions and revocation survive restart and work across instances. |
| 19 | **Cookie hardening** | Use the `__Host-` cookie prefix (host-locked, path `/`, Secure, no Domain) for both session cookies, in addition to HttpOnly/Secure/SameSite. |
| 20 | **Web/transport hardening** | Content-Security-Policy, `frame-ancestors`/X-Frame-Options (clickjacking — the admin CP especially), HSTS, and output-encoding/DOM-XSS controls on **both** SPAs. HttpOnly does **not** stop same-origin XSS from riding the cookie, and CSRF double-submit does not defend against same-origin XSS — so XSS controls are a first-class session-integrity requirement (gate G-WEBHARDEN). **Progress (M4-ADMIN-UI-P2, committed in `dd89ff9`; not deployed):** the admin half exists in code — the admin document CSP and header policy, a production-intended admin web listener, the API/SPA routing boundary and uncontrolled credential inputs (§2a); no admin-host deployment exists, and the tenant SPA remains M8. |

### 2a. Production composition and origin topology (M4, committed in `dd89ff9`)

- **Origin topology — distinct hosts, as #1 requires.** Each boundary accepts login and unsafe session requests only from its own exact configured origins (`SESSION_TENANT_ORIGINS`, `SESSION_ADMIN_ORIGINS`: comma-separated exact `https` origins). The two may never share a host: cookies are host-scoped, so another port on the same host is not a separate boundary. A dedicated subdomain of the same site qualifies — SameSite=Strict does not separate same-site hosts, but the exact Origin check, the session-bound CSRF token and the host-only `__Host-` cookies do — and a separate registrable domain is stronger still. A same-origin deployment is not supported, and missing, malformed or ambiguous configuration refuses composition. Audiences, cookies, stores, admission, CSRF labels and route prefixes stay separate in every case.
- **Production composition.** The provider-independent runtime (`server/runtime`) defines the ports. One provider-aware composition root (`server/composition/productionSessions.ts`) binds the identity verifier (the Firebase adapter) and each boundary's own durable session store, admission and authorizer — all or nothing, from configuration only, naming every missing dependency when it refuses. Without the transaction root's adapters it refuses. The durable session store and both boundaries' admissions and authorizers exist in code: PostgreSQL adapters over migrations 011 and 013, which the transaction root builds over its one kernel and hands over, bound by `durableSessionAdapters`, with the administrative admission and its authorizer always bound together (M5-GIAM-D1-P4). Since M6-RATE-P2 the distributed rate limiter is bound the same way: the PostgreSQL store over migration 014, built by the transaction root and bound with the sessions root's own parsed `RATE_LIMIT_KEY` ([ADR-26](./10-architecture-decision-records.md)), so a composition handed that bundle and a valid key no longer names `rate_limit_store_unavailable`, and the login limits are counted in one store every instance shares. No production entry composes either root, so production sessions are not active; that entry is the next composition task *(until M6-ENTRY-P1, below)*. **M6-ENTRY-P1:** the deployable entry (`server/entry/productionEntry.ts`) composes the administrative boundary only (SESSION_TENANT_ORIGINS neither read nor required); every route but the two probes answers only on the admin host, and the probes answer on any host; no entry composes the tenant boundary ([02 §2.1](./02-target-production-architecture.md)). The entry is code-only and not deployed, so production sessions are still not active.
- **Lifecycle.** Admin sessions last 1 h absolute / 15 min idle, tenant sessions 8 h / 30 min. Admission is re-checked on every protected request of both boundaries, the current-session read included, against a witness of the principal's standing (the tenant boundary since M5-GIAM-D1-P2; the administrative boundary since M5-GIAM-D1-P4, which replaced its 1-minute interval with a `p1:` witness that includes migration 013's platform authority version, [ADR-25](./10-architecture-decision-records.md)); logout never asks. A denial, at revalidation or at login, refuses and then ends every session of the principal in that boundary (a revocation that fails is logged `session_admission_denied_unrevoked` or `login_admission_denied_unrevoked`, and those sessions stay until a later check refuses them); a changed witness revokes the session presented; an unavailable admission is a 503 that revokes nothing. *(Since M5-TENANT-SESSION-P1 a denial is exactly `false` — what both composed admissions answer — or `{ admitted: false }`. Any other malformed answer (another non-object, an `admitted` that is not a boolean, an admission without a valid version) is `admission_unavailable`, a 503 that revokes nothing; before, it was a denial that ended every session.)* Only a successful authorized request slides the idle window. Every port call is bounded (3 s by default) and handed a cancellation signal — an in-flight provider verification is abandoned at the deadline rather than cancelled; an outage is a 503, never a credential verdict.
- **Admin login evidence (#9, and the recent-login precondition of #10).** A provider-verified authenticator-app (`totp`) second factor and an authentication at most 5 minutes old; the tenant login requires neither. Step-up for sensitive actions remains: a route declaring `recentAuth: 'required'` refuses with 403 `step_up_required` unless the session's bound authentication is at most 10 minutes old (`RECENT_AUTH_MAX_AGE_MS`), judged again inside the committing transaction; since M5-ADMIN-STEPUP-P1 the administrator renews that authentication through the login route's reauthentication mode (below). **TOTP only (M4-ADMIN-UI-P2):** the SMS/phone factor needs reCAPTCHA script and frame hosts (`www.google.com`, `www.gstatic.com`, known CSP-bypass hosts) that the admin CSP refuses, so neither the console nor the server login policy accepts it. This is a product limitation: admin accounts must enrol an authenticator app, and a phone-only admin gets the same generic refusal as any failed sign-in.
- **Admin console (M4-ADMIN-UI-P1, committed in `dd89ff9`; production login not active).**
  - **What it is.** The console (`src/backend-control-plane/console/`) is the production successor of the DEV mock shell. `src/main.tsx` chooses the surface from the address before anything loads.
  - **Where it runs.** In a production build it runs only on a configured administration origin: `VITE_ADMIN_CONSOLE_ORIGINS`, an exact `https` list fixed at build time. A missing or malformed list refuses on every host. The console owns that origin entirely. On any other address, `/admin` renders a refusal and makes no administrative request. A Vite dev server serves the console under `/admin` on the development host; production builds compile that branch out, which the build check and the browser suite prove.
  - **Sign-in.** It uses the existing Firebase client SDK on its own in-memory instance, so nothing reaches IndexedDB or Web Storage. It completes the provider's second-factor challenge and sends the one ID token once, as the Bearer of the bodiless `POST /admin/v1/session/login`. The provider session is signed out as soon as that token is read.
  - **Session handling.**
    - The session CSRF token lives only in the client's memory and is sent with logout alongside the intent header. Script never reads or constructs the HttpOnly cookie.
    - The shell renders only after `GET /admin/v1/session` confirms the session. The console re-reads the session on every in-console navigation and when the tab becomes visible; a read never extends the session.
    - Every refusal reads as one generic denial, while 429 and 503 are reported distinctly. A logout is reported only when the server confirms it.
  - **Workspaces.** The 11 workspaces are navigation placeholders marked "Coming later", with no action and no permission data. *(M5-GIAM-D1-P3: Tenant Management is now open, as described below. `navigation.ts` defines ten workspace modules beside the Command Center home, and the other nine stay placeholders.)*
- **Admin console hardening and read-only Command Center (M4-ADMIN-UI-P2, committed in `dd89ff9`; nothing deployed, production login not active).**
  - **API/SPA routing boundary.** `/admin/v1/*` and `/api/v1/*` are never a console page on any origin and are never redirected. One canonical rule decides it: decode once (a malformed escape counts as API), then every backslash — literal or decoded from `%5C` — is a slash, lowercase, drop empty and `.` segments and resolve `..` (never above the root). The rule lives in three places: `server/runtime/adminWeb.ts` `isApiPath`; the Vite dev/preview guard, which answers with the runtime's bounded JSON 404 and API header policy, never the SPA document; and the console surface (`src/backend-control-plane/console/adminSurface.ts`), where a page load renders a bounded "Not found" page that loads neither application chunk, sends no request and keeps the address. Inside the running console, an address under the same rule (`/admin/v1/*` or `/api/v1/*`, in any spelling) renders the same page, where P1 redirected it to `/admin`; any other unknown address still goes to `/admin`.
  - **Web policy and listener.** The admin document CSP is exactly `default-src 'none'; script-src 'self' https://apis.google.com; style-src 'self'; img-src 'self'; connect-src 'self' https://identitytoolkit.googleapis.com; frame-src https://<authDomain>; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. `apis.google.com` and `frame-src` exist only for the Google popup resolver; `form-action 'none'` also stops a native form submit from putting credentials in a URL; there is no `unsafe-inline`, `unsafe-eval` or wildcard. The other headers are `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, a deny-list Permissions-Policy, CORP `same-origin`, `no-store` on the document and immutable caching on hashed assets. HSTS (`max-age=31536000; includeSubDomains`) is sent only at the HTTPS boundary; the runtime adds it under the production classification (`server/runtime/server.ts`) *(until M6-ENTRY-P1; since then `server/runtime/server.ts` is deleted and the deployable entry sends it on every response, `hsts: true` in `server/entry/productionEntry.ts` — see the HSTS deployment invariant under [08](./08-production-gate-and-risk-register.md) G-CPLOGIN)*. The production-intended listener (`createAdminWebListener`, `server/runtime/adminWebServer.ts`) serves a build preloaded at startup by `loadAdminBuild`, so no request touches the filesystem, and it delegates an API path to the runtime or refuses it. Nothing deploys it: the Replit static deployment (`.replit`) serves the tenant surface, and no admin-host deployment exists (deployment invariants: [08](./08-production-gate-and-risk-register.md) G-CPLOGIN). *Since M6-ENTRY-P1, `createAdminWebListener` is still composed by nothing, the M6-ENTRY-P1 entry included (it serves only the 8 API routes of [02 §2.1](./02-target-production-architecture.md)), and that entry is not deployed. `adminWeb.ts`, `adminWebServer.ts` and `commandCenter.ts` are also outside the server build since M6-ENTRY-P1 (`tsconfig.server.json` builds only the closure of `server/entry/main.ts`; the root typecheck still covers them), so the admin-host deployment stage must give them a build path.* The dev server deliberately sends no framing header, because the Replit Preview embeds it in an iframe.
  - **Fonts.** The admin origin fetches no web font: Manrope and Material Symbols moved to the tenant-only `src/tenantFonts.css` (imported by `src/App.tsx`), and the console uses the platform UI stack. The tenant SPA still loads Google Fonts; that belongs to M8 / G-WEBHARDEN for both SPAs.
  - **Credentials.** Phone MFA is gone (TOTP only — see the admin login evidence above). The email, password and verification-code inputs are uncontrolled, so no typed credential reaches the markup; autocomplete stays `username` / `current-password` / `one-time-code`.
  - **Read-only Command Center (`server/runtime/commandCenter.ts`).** `GET /admin/v1/command-center`, body none, policy session/admin plus `{ scope: 'platform', permission: 'view_command_center' }` (the existing catalog view capability); there is no other method, so no state-changing operation. It maps an injected reader port into a bounded view: posture counts, per-area attention counts, governance signals and service health, each section `available` / `unavailable` / `not_configured` with `asOf` and `stale`. No reader string ever reaches the output, and a reader failure or overrun is a bounded 503. It is registered nowhere — the composition root and the deployable entry do not import it, and a test pins that the deployable app composes no such route — and no authoritative source exists (real data is M7h). The console dashboard (`/admin`) replaces the placeholder overview and leaves the workspace pages unchanged; it refreshes manually only, and an unavailable or not-configured section never shows a number. A reading that ages past 24 hours while the page is open becomes unavailable too, as the server would then say. Ages count from the server's generation instant plus the time elapsed on the page. A fixed page-clock offset therefore changes nothing, and a page clock stepped forward can only make a reading age early. The admission-revalidation race ([08](./08-production-gate-and-risk-register.md) G-CPLOGIN) still blocks production session activation, operational data access and every sensitive admin action; nothing in this stage bypasses it.
- **Tenant Management workspace (M5-GIAM-D1-P3; nothing deployed, production login not active; [10](./10-architecture-decision-records.md) ADR-24).**
  - **Open workspaces.** Tenant Management is the one open workspace: its navigation entry carries `open: true` (`navigation.ts`), so the shell shows no "Soon" badge and the page shows no "Coming later" notice. The other nine workspace modules stay placeholders.
  - **What it reads.** `GET /admin/v1/tenants`, under `view_tenants` with a required trusted context. It returns a server-paginated list of `{ tenantId, displayName | null, status, version }`, an opaque `nextCursor` and `actions` hints. The hints are presentation only: the page shows a control only when the server says it would allow it, and each command is still authorized by its own chain.
  - **What it changes.** A tenant's display name and its `active <-> suspended` status, through the two existing commands only. The console's `command` method (`adminSessionClient.ts`) sends PATCH to exactly those two paths with the session CSRF token and an `Idempotency-Key`. Every change names the server's version and holds one key per intent: the same key on a retry after an uncertain answer, a new key after a definitive one. Nothing is shown as done before the server confirms it; a conflict shows the current details, and the directory is read again after every definitive answer. Suspend and reactivate sit behind a confirmation dialog.
  - **What it does not do.** There is no step-up UI: a `step_up_required` refusal asks the person to sign in again *(until M5-ADMIN-STEPUP-P1, below)*. There are no store lifecycle controls ([08](./08-production-gate-and-risk-register.md) DA-41), and nothing reaches the legacy `/owner` tree.
- **Recent sign-in for a sensitive action (M5-ADMIN-STEPUP-P1; nothing deployed, production login not active; [10](./10-architecture-decision-records.md) ADR-28).**
  - **The reauthentication mode.** `POST /admin/v1/session/login` sent with the request header `X-TMPOS-Reauthenticate: 1` (beside the usual Bearer ID token and intent header) is a reauthentication. It runs every step of an ordinary login first and in the same order — host, Origin and intent, the client and account limits, provider verification, the TOTP second factor, the 5-minute authentication age and admission (a denial still ends every session of that principal, as at any login). It then requires the presented cookie to authenticate as a valid (unexpired, unrevoked) administrative session under the same rules as any session request, that session's principal to EQUAL the one just verified, and its security version to equal the version this login's admission just reported (a session issued before the principal's standing changed is not renewed).
  - **Refusals.** An absent, malformed, unknown, expired or revoked presented session (`login_reauth_no_session`) a different principal (`login_reauth_mismatch`) and a presented session whose security version differs from this login's admission version (`login_reauth_stale_version`; the next ordinary session request revokes it through the existing version-mismatch path) all get the generic 401 of any failed login. These checks run after the ordinary login steps and create and revoke nothing, so another administrator signing in leaves the prior session exactly as it was — still too old for step-up; an admission denial at the ordinary step still ends every session of that principal, unchanged. A header with any value other than exactly `1`, or on more than one line, is the same 401 (`login_reauth_header_invalid`) and is never served as an ordinary login. A store outage while reading the presented session is the bounded 503. The reasons are server-side only; the answers do not distinguish them.
  - **Rotation.** On a match the login rotates as it always does: the presented session is revoked, a new identifier is issued with the NEW provider-verified authentication time bound once, the new `__Host-` cookie is set, and the answer is `{ status: 'active', csrfToken }`. The old record is revoked, never updated, so the old cookie answers 401 and cannot borrow the new evidence. Nothing a request carries sets or extends the authentication time. Without the header a login is exactly as before. The tenant boundary shares the code, but no client or entry uses it there. *Amended (M7A-CUSTOMERS-P5-R1, [10](./10-architecture-decision-records.md) ADR-40): on the tenant boundary the login's 200, in either mode, and the 200 of `GET /api/v1/session` are `{ status: 'active', csrfToken, subject }`, where `subject` is a labelled digest of the session's own verified principal that names no tenant and grants nothing ([05](./05-canonical-data-ownership-and-api-db-contracts.md) §2; [08](./08-production-gate-and-risk-register.md) DA-148). The administrative answer above is unchanged.*
  - **The console flow.** On a definitive `step_up_required` for Suspend or Reactivate, the page closes the confirmation, discards its reason and idempotency key, and opens a recent-sign-in dialog that names the tenant and the action and says the tenant was not changed. "Sign in again" runs the same in-page provider sign-in as the console's sign-in screen (password or Google popup, then the TOTP code; in-memory, signed out after one token is read), then `reauthenticate` in `adminSessionClient.ts`, which sends the mode above, supersedes the old session's in-flight requests (their late answers are ignored), suppresses duplicates and keeps the shell mounted. No redirect is used, and nothing is written to storage, the address or history.
  - **Outcomes.** Renewed: the client confirms the new session with `GET /admin/v1/session` and adopts its CSRF token; the page says "Sign-in completed" and that the tenant has not been changed — text distinct from any action-completed message — reads the directory again, and returns to the same tenant, the resume state living at page level so it survives the re-read. If the tenant still allows that transition and the server still offers the action, focus moves to its trigger and the page asks for a new confirmation: a newly typed reason, the re-read version and a new key. Otherwise it shows the current state and why the action no longer applies, with no control for it. Refused (a failed sign-in, a different administrator, an admission refusal that left the prior session standing): the dialog says sign-in was not accepted for the administrator who started the action and the tenant was not changed, and offers Try again and Cancel. A provider cancellation, rejection, rate limit or outage is reported in the dialog with the tenant unchanged. If the prior session has ended, the console follows its existing expiry path to the sign-in screen and nothing resumes ([08](./08-production-gate-and-risk-register.md) DA-61). Cancel closes the dialog, returns focus to the action's trigger (or the tenant heading) and announces that the tenant was not changed.
  - **Accessibility.** The dialog is a labelled modal (`role="dialog"`, `aria-modal`) that focuses its heading on open, contains focus, treats Escape as Cancel and returns focus when it closes; results and errors are announced. The browser suite (`tests/browser/admin-console.browser.test.mjs`, production build) completes the journey keyboard-only and shows the dialog reflowing at 320 CSS px / 400 % zoom.
  - **What it does not change.** No route (`SHIPPING_ROUTES` is unchanged), no migration (005–014 are byte-identical to the stage's entry commit, and none follows 014), and no change to `RECENT_AUTH_MAX_AGE_MS`, the 5-minute login age, the transaction-time check, the cookie, Origin, CSRF, host, trusted-proxy or rate-limit rules. Recency rests on the provider's `auth_time` ([08](./08-production-gate-and-risk-register.md) DA-62). A store failure mid-rotation and concurrent reauthentications behave as at an ordinary login (DA-61). *Since M5-ADMIN-REVOKE-P1 ([10](./10-architecture-decision-records.md) ADR-30), `establish` repeats the live, administrative and same-principal checks where it writes, in the same transaction (§2b). A presented session that a logout, a revocation or another reauthentication ended first refuses the reauthentication with the same generic 401 (`login_reauth_no_session`), and nothing is created, ended or recorded. The version check is not repeated as such: a standing that moved since this login's admission is caught by `establish`'s standing check and answers 401 `login_standing_changed`. On the administrative boundary at most one of several concurrent reauthentications presenting one cookie succeeds (DA-61(b)).*
- **Tenant login, recent sign-in and logout (M5-TENANT-SESSION-P1; code only — no entry composes the tenant boundary and it has no business route; [10](./10-architecture-decision-records.md) ADR-31).** *(Since M7A-CUSTOMERS-P2 commit 2, the compiled tenant entry composes the tenant boundary, in code only, not deployed; [10](./10-architecture-decision-records.md) ADR-33 decision 8.)*
  - **The establish order.** After the ordinary login steps of `POST /api/v1/session/login`, admission included, the session is written by ONE store transaction, `establish`:
    1. 016's hold (`tmpos_session.m5_hold_tenant_standing`) locks until COMMIT the actor's account FOR UPDATE, then FOR SHARE its identity links (`link_id` order), every grant of any scope and status (`membership_id` order), every tenant any grant names (`tenant_id` order) and every store any grant names (`store_id` order).
    2. The next statement re-reads `m5_admit_tenant_session_v2`. The recomputed `t2:` witness must equal the new record's, which this login's own admission read produced.
    3. The presented session, if any, is ended; the new session is created; its `tenant.session.*` row is inserted (§2b).
  - **Who waits.** A change committed before step 2 refuses the login. A change not yet committed waits for this COMMIT, and the next protected request judges it: an account write; a link or grant of the actor changed, removed, inserted or re-pointed; an anchor change; and an update or delete of a tenant or store that a grant names, 010's command included.
  - **Recent sign-in.** With `X-TMPOS-Reauthenticate: 1`, the handler's checks run as on the administrative boundary (a valid presented tenant session, the same principal, the security version this login's admission reported). `establish` then requires the presented session to be, in this order, live, of the tenant audience, the same principal's, and ended by this transaction. So a logout, a revocation or another recent sign-in that committed first refuses it, and at most one of several concurrent recent sign-ins presenting one cookie succeeds.
  - **Refusals.**
    - A standing that moved, or no longer admits, since this login's admission read: 401 `login_standing_changed`.
    - A recent sign-in whose presented session is not ended by this transaction: 401 `login_reauth_no_session`.
    - In both cases nothing is ended, created or recorded.
    - An outage, a timeout or a malformed answer (the hold, the re-read, the session routines or the audit insert): the bounded 503, and nothing is revoked or written. An admission that admits but names no actor is a 503 `admission_unavailable` before anything is read or written.
    - A COMMIT whose answer was lost: 503, outcome unknown. The session and its row may exist, but its id was never delivered.
  - **Logout.** The cookie is always cleared. `end` ends the live tenant session with its `tenant.session.logout` row. When nothing is live it answers `absent`, and the logout is 204 (`logout_session_absent`) with no row. When `end` fails, a warn-level `session_logout_audit_unconfirmed` event is written and the plain revocation runs: 204 `logout_audit_unconfirmed` (DA-64). When that fails too, the answer is 503, and the row may stay live until its idle expiry (30 minutes) or absolute expiry (8 hours).
  - **What it does not change.** No route (`SHIPPING_ROUTES` is unchanged, and none is under `/api/v1`), no tenant host in the deployable entry (`audiences: ['admin']`), and no change to the tenant login policy (no second factor, no authentication age), cookie, Origin, CSRF or rate-limit rules.

### 2b. Administrative session audit (M6-ADMIN-AUDIT-P1; nothing deployed, production login not active; [10](./10-architecture-decision-records.md) ADR-29)

The administrative boundary writes one durable `audit_event` row for each session it issues and each logout that ends one, in the same PostgreSQL transaction as the session change. No route, migration, grant or definer routine is added: the runtime login already holds INSERT on `public.audit_event` through `tmpos_audit_writer` (migration 005), and the row goes through the existing writer, as a command's row does. The tenant boundary is not audited (stated open, [08](./08-production-gate-and-risk-register.md) DA-65). *(Since M5-TENANT-SESSION-P1 it is, with its own family of three events; see "Tenant session events" below.)*

**Events (frozen).** The server picks the action from the path it took. A header alone never produces a reauthentication row, and no refusal produces any row.

| Event | When | `action_id` | `decision` | `reason_code` | `actor_internal_user_id` |
|---|---|---|---|---|---|
| Login | An ordinary admin login that passed every step, admission included, and created a session | `platform.admin.session.login` | `allow` | `admin_session_created` | the actor this login's own admission selected |
| Reauthentication | The same, with `X-TMPOS-Reauthenticate: 1`, after every same-principal check (§2a) passed | `platform.admin.session.reauthenticate` | `allow` | `admin_session_reauthenticated` | the actor this login's own admission selected |
| Logout | An intentional logout that ended the live session presented | `platform.admin.session.logout` | `not_applicable` | `admin_session_ended` | null |

**Row fields (every event).**
- `request_id` is the operation id, a random UUID the server generates for each audited operation (`sessions.ts` login and logout). The store refuses anything else before a statement is sent. It is never the client's `X-Request-Id`. The request's log line carries the same value as `operationId`, so the row and the HTTP result join on an id no client chose. The exception is a client that disconnected before the audited step. Its request log line (reason `aborted`) is written at the close, before the id exists. An admin login then creates no session and writes no row. A logout still runs: a session still live is ended with its row, and one info-level `session_logout_after_close` line carries `requestId` and `operationId` to join them. `trace_id` is null. `event_id` is the writer's own random UUID.
- The actor for login and reauthentication is `context.actor` of the admission decision that login just obtained: a UUID, which the writer validates. On this boundary, an admission that admits without naming a scope is a faulty adapter. It answers 503 `admission_unavailable` before anything is read, created or revoked. A logout re-asks no admission and so establishes no actor. Its row carries a null actor: the runtime's entry type is a discriminated union (`SessionEstablishAudit | SessionEndAudit`), and the store and the writer each refuse a logout entry that names an actor. The row names the session by `sessionRef`, which equals the `sessionRef` of the login or reauthentication row that created that session. That row holds the actor.
- `actor_auth_provider` and `on_behalf_of_internal_user_id` are null. `scope_type` is `platform`, and `tenant_id`, `store_id` and `subject_tenant_id` are null. `required_permission` is `n_a`: admission is a standing check, not a catalog permission. `result_status` is `succeeded` and `evidence_level` is `durable_compliance_event`, which is what the `tmpos_audit_writer_append` policy requires. `source_of_truth` is `session_transaction` and `evaluated_by` is `m6_postgres_session_store@v1`.
- `human_readable_reason` is one fixed sentence per event. It takes no caller text ([08](./08-production-gate-and-risk-register.md) DA-35).
- The writer owns each event's entire fixed row (`ADMIN_SESSION_AUDIT_EVENTS`, built by `buildAdminSessionAuditEvent` in `auditEventWriter.ts`). The store supplies only the operation id, the actor and the metadata values. `validateAuditEventInput` refuses any row under one of the three action ids that differs from that shape in any column, including a `request_id` that is not a UUID. That stops drift, not forgery: any writer caller can still build a well-formed row, and the runtime role can insert into the table directly.
- `metadata` holds flat scalars. These three action ids keep only the three keys below, and none of the general allow-list. A logout row may carry `sessionRef` alone. For every other action the writer strips or refuses the three keys, as it does any unknown key:
  - `sessionRef` names the session created or ended: base64url(SHA-256(`tmpos-audit-session-ref:v1\n` + store key)), a 43-character, one-way, domain-separated digest. The store key is itself the SHA-256 of the session id. The key is not used because the session routines accept it and the runtime role may execute them, so a reader of the audit trail holding that role could otherwise read, extend or end a live session.
  - `replacedSessionRef` (login and reauthentication only) is present only when this transaction read the presented session live, took its row lock and ended it, and that session was administrative *(since M5-TENANT-SESSION-P1: of the new record's own audience)*.
  - `authenticatedAt` (login and reauthentication only) is the provider-verified `auth_time`, in epoch ms, bound into the new session, when it is not null.
  - The store refuses any metadata the writer would not persist exactly as given, and the transaction rolls back.
- The row never holds the session id, cookie, store key, CSRF token, ID token, TOTP code, password, provider uid, email, request body or a database error.

**Persistence and ordering.** Each audited operation is one kernel transaction, with the audit INSERT as its last statement. The INSERT must return command `INSERT` with exactly one row affected. Any other result rolls back the transaction, because a trigger could otherwise drop the row silently.
- **Login and reauthentication (`establish`).** *(Ordered against revocation since M5-ADMIN-REVOKE-P1, [10](./10-architecture-decision-records.md) ADR-30.)*
  - **The standing, first.** The transaction root's standing check re-reads 013's admission for the new record's provider reference. It then takes 009's locks for the scope that read selected (the account FOR UPDATE, links and grants FOR SHARE, held until COMMIT) and reads 013 again. The witness must equal the record's. Otherwise `establish` answers `standing_changed` having written nothing, and the login is 401 `login_standing_changed`. A fault throws, and the login is a 503. A store built without the check throws `standing_check_missing`.
  - **The presented session.** If a cookie was presented, `m5_session_get` reads the presented key. Ending it means `m5_session_touch` writes back the stamp as read and must answer `updated`: it takes the row lock and waits out a concurrent deleter, after whose commit it answers `absent`. Then `m5_session_revoke` must answer `revoked`.
    - A reauthentication requires the presented session to be, in this order, live, administrative *(since M5-TENANT-SESSION-P1: of the new record's own audience)*, the same principal's, and ended here. Anything else answers `session_ended` with nothing written (401 `login_reauth_no_session`). The checks come before the end, so a refusal deletes nothing.
    - For an ordinary login, a presented session that is not live, or that another transaction ended first, is not ended here and is not named. The login still creates its session and row.
  - **The new session, then its record.** `tmpos_mint.m7a_session_create` must answer `created` *(since M7A-CUSTOMERS-P2 every create goes through migration 018's mint, which for the administrative audience takes no proof and calls 011's `m5_session_create` unchanged)*, and then the audit row is inserted. A taken new key fails the whole transaction, so the presented session stays as it was.
- **Logout (`end`).** The same read, touch and revoke run on the presented key, then the audit row is inserted. If nothing is live to end, `end` answers `absent` and nothing is recorded. That covers a session another transaction already ended, and one past its absolute expiry at this instance's clock. When the read finds nothing live, the same transaction still runs `m5_session_revoke` on the key, deleting any expired row left under it, so an instance whose clock runs behind cannot keep accepting it. The runtime runs no plain revoke for `absent` and answers 204 (log reason `logout_session_absent`).
- **Revocation takes priority over the record at logout.** When `end` fails for any reason (a throw, a timeout, a refused record, or an answer that is neither `ended` nor `absent`), a warn-level `session_logout_audit_unconfirmed` event is written, and then the plain `revoke` runs. If it succeeds, the answer is 204 with log reason `logout_audit_unconfirmed`. The row is then absent, or present if the first commit's answer was lost (DA-64). If the fallback fails too, the cookie is cleared and the answer is the bounded 503; the warning, written first, still records why the audited end failed.

**Failure classes.**
1. **Refusal before a trusted actor exists.** This covers a bad token, a missing or bad TOTP, a stale `auth_time`, a rate limit, an admission denial, and any reauthentication refusal. No row is written, and the session effects are as before: an admission denial still ends every session of the principal, unaudited (DA-65).
2. **Failure before commit.** A routine or the audit insert throws, times out, answers malformed, or affects no row. Everything rolls back. Login answers the bounded 503 (`session_unavailable` or `session_timeout`) with no `Set-Cookie`, and the presented session is kept.
3. **Outcome unknown.** A deadline or lost connection during COMMIT gives the same 503 with no cookie, but the session change and its row may both be committed. The row then truthfully records a session that was never delivered, because nobody holds its id. For a login that presented a session, that session may have been ended, and the administrator signs in again. At logout the fallback revoke is idempotent.
4. **The audit insert is refused.** For login this is class 2. Logout takes the fallback: the revocation is confirmed and the row is absent.
5. **Session-store outage.** Login answers 503 with nothing committed and no row. At logout both attempts fail: the answer is 503, the cookie is cleared, and the warning is still written. The session is still live, unless a lost commit answer ended it.

**Audience split.** `audited = audience === 'admin'` is fixed once when the boundary is built. The administrative store must offer `establish` and `end`, or startup refuses with `session_store_audit_required`. The tenant boundary keeps `create` and `revoke`, never calls the audited pair, and is not audited. In the PostgreSQL adapter, `establish` and `end` refuse any record that is not administrative, and `create` refuses an administrative one, so `establish` is the only application path to an administrative session. The database does not enforce that (DA-66). *Superseded by M5-TENANT-SESSION-P1: `audited` is gone. Both boundaries require `establish` and `end` (startup refuses a store without them, for either), and both use them alone. `establish` and `end` accept both audiences and record each in its own family. The standing check `establish` runs first dispatches on the record's audience (ADR-31). The adapter's `create` still refuses only an administrative record; it still writes a tenant record with no row, and no boundary calls it (DA-66).*

**Tenant session events (M5-TENANT-SESSION-P1; code only, no entry composes the tenant boundary; [10](./10-architecture-decision-records.md) ADR-31).** *(Since M7A-CUSTOMERS-P2 commit 2, the compiled tenant entry composes the tenant boundary, in code only, not deployed; [10](./10-architecture-decision-records.md) ADR-33 decision 8.)* The tenant boundary records its sessions through the same store operations and writer, one row per operation, in the same transaction:

| Event | When | `action_id` | `decision` | `reason_code` | `actor_internal_user_id` |
|---|---|---|---|---|---|
| Login | A tenant login that passed every step and whose `establish` committed | `tenant.session.login` | `allow` | `tenant_session_created` | the internal user this login's tenant admission resolved |
| Reauthentication | The same, with `X-TMPOS-Reauthenticate: 1`, after every same-principal check (§2a) passed | `tenant.session.reauthenticate` | `allow` | `tenant_session_reauthenticated` | the internal user this login's tenant admission resolved |
| Logout | An intentional logout that ended the live tenant session presented | `tenant.session.logout` | `not_applicable` | `tenant_session_ended` | null |

Every other column is fixed as in the administrative rows, with two differences: `scope_type` is `none`, and `tenant_id` and `store_id` are null, because a tenant session selects no tenant or store at login (each route selects one per request from the actor's own grants), and each event has its own fixed sentence. The metadata keys are the same three. The writer owns the rows (`TENANT_SESSION_AUDIT_EVENTS`, built by `buildSessionAuditEvent('tenant', …)`), and `validateAuditEventInput` refuses a row under one of these ids at any other scope. The store takes the family from the new record's audience at `establish`, and from the ended session's audience at `end`, building both candidate rows before the transaction so that a refused entry aborts nothing. The tenant admission names the actor (`{ admitted, securityVersion, actor }`). No refusal writes a row, and the unaudited classes of DA-65 apply unchanged.

## 3. Administrative session endpoints (conceptual contracts — not implemented in M1)

| Endpoint | Purpose | Auth in | Result |
|---|---|---|---|
| `POST /admin/v1/session/login` | Login exchange: Firebase ID token → verify → issue admin cookie | Firebase Bearer (once) | Set-Cookie (HttpOnly admin session) + sanitized whoami |
| `GET /admin/v1/session/whoami` | Current admin session (the whoami contract; delivered as `GET /admin/v1/session`) | admin cookie | `{ status, csrfToken }` only until the M5 capability summary exists — no identity, token or email |
| `POST /admin/v1/session/logout` | Invalidate server-side session | admin cookie | cleared cookie |

| `POST /admin/v1/session/refresh-eligibility` | Re-resolve permissions/entitlements after a governance change | admin cookie | refreshed capability summary |

These endpoints are described to fix the **contract**; wiring is M4.

**M4 delivered contract (runtime, committed in `dd89ff9`):** each boundary exposes exactly `POST <prefix>/session/login`, `GET <prefix>/session` (the current session) and `POST <prefix>/session/logout`, where `<prefix>` is `/admin/v1` for the administrative boundary and `/api/v1` for the tenant/store boundary. Login and the current-session read return the session-bound CSRF token, so no separate CSRF bootstrap endpoint exists. Step-up, admin-initiated revocation and eligibility refresh remain conceptual under `/admin/v1/session/*` until their milestone. *(M5-ADMIN-STEPUP-P1: step-up is delivered as the reauthentication mode of `POST /admin/v1/session/login` (§2a), not as a `…/session/step-up` route or a separate grant: the renewed session itself carries the new authentication time.)*

## 4. Backend CP responsibilities (governs the whole platform)

Platform operators, tenants, stores, users & memberships, roles & permissions, provisioning, plans & entitlements, subscriptions & billing governance, feature flags, module availability, domains & integrations, support operations, approvals, audit/security, operational health, data-quality findings, migration state, background jobs, provider status, incident/recovery controls.

## 5. Controlled-action contract (every admin mutation)

The DEV controlled-action pilot already demonstrates the target shape ([01](./01-current-state-inventory-and-gap-matrix.md) §E: method/dev/flag → request-security guard → global rate → verify Bearer → read-only identity → per-principal rate → authz guard → handler). Generalized, every Backend CP mutation MUST use:

1. a **typed service/API contract** (no ad-hoc row mutation);
2. **canonical authorization** (server-resolved, deny-by-default);
3. **explicit scope** (platform vs specific tenant/store);
4. **validation** of the request body;
5. a **transaction boundary**;
6. **idempotency** where applicable (durable key store — [05](./05-canonical-data-ownership-and-api-db-contracts.md));
7. **durable audit** (append-only `audit_event`, not advisory-only — closes GAP-07);
8. **reason capture** for sensitive operations;
9. **safe result classification** (bounded envelope, no stack/DB/provider leakage);
10. **least privilege**;
11. **production-safe error handling**.

**Read-only inspection is separated from controlled mutations.** Read lenses (the C01–C07 pattern) never mutate and never construct authority from request input; controlled mutations pass the full chain above. **The Backend CP must not bypass domain services or mutate database rows arbitrarily** — all administrative writes route through typed services with canonical authorization.

## 6. M4→M5 interim authorization posture

M4 delivers the session boundaries and the admin shell wired to server endpoints, but the **canonical authorization** those endpoints resolve against is **M5**. In the interval between M4 and M5, admin endpoints MUST enforce only the **existing narrow pilot guard** (visibility `system_owner` by exact equality, permission floor `manage`, fail-closed) — the same guard the DEV controlled-action pilot already uses — and MUST NOT expose generalized admin capability until M5 generalizes the canonical authorization service. No admin surface authenticates-without-authorization: unmapped/insufficient principals are denied.

> **INVARIANT (M4 mutation gate):** **No generalized Backend CP mutation endpoint may become available during M4 before the M5 canonical permission for that action exists.** The narrow pilot action (DEV-only, isolated, `system_owner` exact-eq) may remain under **hard environment gating** (`NODE_ENV==='production'` denies), a **typed-service allowlist**, **durable audit on every pilot action**, and **explicit removal-or-promotion criteria** (the pilot is either removed or promoted to a canonical M5-governed action — it does not linger unmanaged). Every *new* administrative mutation requires its canonical M5 permission to be defined and enforced before the endpoint is exposed. This prevents an authenticated-but-unauthorized admin capability window between M4 and M5.

## 7. Residual: admin mutation prohibition is application-enforced

The "no arbitrary row mutation" rule (§5) is an **application-layer convention**: the privileged admin/migration DB role bypasses RLS by design ([05 §4](./05-canonical-data-ownership-and-api-db-contracts.md)), so the database does not itself enforce it. This residual is compensated by making **typed-service + canonical-authorization + durable-audit mandatory** on every path that uses the privileged role, and by keeping the privileged role out of the tenant request path (which runs under the scoped, RLS-bound app role). Tracked under gate G-DBROLE.

## 8. System Owner boundary — store payment gateways (payment gateways are STORE-owned)

Payment-gateway connections are **store-owned** ([05 §5.1](./05-canonical-data-ownership-and-api-db-contracts.md)); the System Owner governs the **connector catalog and security policy only**.

**The System Owner Backend CP MAY:** define the supported connector catalog; control connector availability by environment/region; establish minimum versions and security requirements; view **bounded** connector health; view **sanitized** connection status; **disable a connector globally during a security incident**; manage feature/plan eligibility; review aggregate operational failures; support **audited break-glass** workflows.

**The System Owner MUST NOT normally:** supply a store's merchant credentials; retrieve or reveal a store credential; impersonate a store connection; activate a gateway for a store without store authorization; process a store payment outside a governed support workflow; **see raw provider tokens/secrets**; silently move a connection between stores.

**Any exceptional delegated-support workflow requires:** explicit **store consent** + **time-bounded elevation** + **step-up authentication** + **least privilege** + **reason capture** + **durable audit** + **automatic expiry** + **no credential reveal**. This is the only path by which a platform operator touches a store connection, and it never reveals a credential. **Allowed break-glass action set is bounded to diagnostics** (view sanitized status/health, assist a store-initiated reconnection); it **explicitly EXCLUDES** silent production activation, connection replacement, and any fund movement (payment/refund/void) — any state-changing break-glass action additionally requires **store-side positive confirmation + dual approval**.

**Global connector disablement** (a platform-wide payment-availability lever) is itself a **step-up + reason + durable-audit** action with **affected-store notification** — it disables catalog availability/routing, and does **not** touch, own, or reveal any store credential or perform a store-authorized lifecycle action.
